# fixtures

시드 데이터와 테스트 계정. **다섯 저장소가 모두 쓴다.**

`00 §11.3`이 "같은 API 명세 준수 테스트와 핵심 E2E 시나리오를 네 구현이 공유한다"를, `05 §4.2`가 "같은 테스트는 동일 시드의 별도 테넌트에서 실행한다"를 요구한다. `CORE-AC-28`은 여기서 한 걸음 더 나간다 — **같은 시드와 같은 요청이면 네 구현이 같은 금액·상태·오류를 받아야 한다.**

## 파일

- [`accounts.json`](accounts.json) — 고객 4명, `02 §3.1`의 일곱 역할 직원, `READ_ONLY_AUDITOR` 한시 부여 2건(유효·만료)
- [`catalog.json`](catalog.json) — 파트너·장소·상품·회차
- [`bookings.json`](bookings.json) — 예약·결제·환불·출석·체크인 이벤트·쿠폰

**이 JSON이 유일한 원본이다.** 프론트 4벌과 E2E는 npm 패키지로 그대로 읽고, Core API는 기동 시 이걸 읽어 DB에 넣는 로더를 둔다. 값을 SQL에도 적으면 두 벌이 되고, 그 순간 `CORE-AC-28`이 무너진다.

## 시각 규약 — 절대 시각을 쓰지 않는다

모든 시각은 **앵커 기준 상대 오프셋(분)**이다. `startOffsetMinutes: 4380`은 "적재 시점 + 73시간"이다.

절대 시각으로 박으면 하루만 지나도 취소 정책 경계 시드가 썩는다. `00 §6.4`의 STANDARD 72시간 경계를 시험하려면 회차가 "지금부터 71시간 뒤"에 있어야 하는데, 어제 날짜를 박아두면 그 회차는 이미 지난 것이 된다.

로더는 적재 시각을 앵커로 잡고 `앵커 + offset`으로 실제 시각을 만든다. 앵커를 고정하고 싶으면 환경변수로 넘긴다.

## 테넌트 격리 — Postgres 스키마 분리

`05 §4.2`가 요구하는 구현별 격리는 **스키마**로 구현한다.

```
daylink DB
 ├ t_next    ─ 같은 테이블 정의, 같은 시드
 ├ t_nuxt
 ├ t_react
 └ t_vue
```

연결 시 `search_path`만 바꾸면 되고 테이블 정의는 한 벌이다. 초기화는 `DROP SCHEMA t_next CASCADE` 한 줄이다.

`tenant_id` 컬럼 방식을 쓰지 않은 이유는 **거르는 걸 한 번이라도 빠뜨리면 비교가 오염되기 때문**이다. `05 §10`의 위험 6번이 정확히 그것이고, 동시성 테스트에서는 더 위험하다. 스키마 분리는 빠뜨릴 자리가 없다.

## 규칙

- **금액을 손으로 적지 않는다.** `00 §6.3` 공식으로 계산한다 — `G = 단가 × 인원`, `C = G - D`, `F = floor(G × 0.12)`, 정산 기준액 `= G - F`.
- **`confirmedSeats`는 파생값이다.** 예약 행의 합이 권위다. 숫자만 올려두면 좌석은 찼는데 참가자 명단이 비는 상태가 된다.
- 실제 개인정보를 넣지 않는다. 이메일은 전부 `.test` 도메인이다.
- 쓰기 흐름 비교는 각 구현 전용 스키마에서 하고 종료 후 초기화한다(`05 §4.2`).
