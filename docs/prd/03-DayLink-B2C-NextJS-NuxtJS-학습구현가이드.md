# DayLink B2C Next.js·Nuxt 비교 학습 구현 가이드

| 항목 | 내용 |
|---|---|
| 기준 PRD | `01-DayLink-B2C-PRD.md` v2.1 |
| 개정 | 2026-08-24 — IA 확인필요 결정 1·7 반영 (체험 식별자 `{id}` 통일). 2026-08-24 재확정 — 서비스 소개는 `/about` 신설이 아니라 `/policies/about`으로 흡수 |
| 구현 A | Next.js + React |

| 목표 | 공개 B2C를 양쪽 메타 프레임워크의 권장 방식으로 구현하고 차이를 비교 |

## 1. 이 배치가 학습에 적합한 이유

B2C에는 검색 엔진에 노출할 홈·지역·카테고리·상품 상세와 사용자별 예약·결제 화면이 함께 존재한다. 따라서 정적 생성, 서버 렌더링, 클라이언트 상호작용, 경로별 캐시, 메타데이터, 인증 경계를 한 제품 안에서 자연스럽게 다룰 수 있다.

Next.js와 Nuxt는 이 문제를 각 생태계의 전체 애플리케이션 프레임워크로 해결한다. 같은 B2C PRD를 양쪽에서 구현하면 React와 Vue의 문법 차이만이 아니라 데이터 로딩, 서버·클라이언트 경계, 캐시 무효화, 오류 처리, 배포 구조의 차이를 비교할 수 있다.

## 2. 비교의 원칙

1. 두 구현은 같은 Core API와 OpenAPI 스키마를 사용한다.
2. 화면 ID, URL, 필드, 문구, 권한, 상태, 분석 이벤트, 인수조건을 동일하게 유지한다.
3. 한쪽 기능이 끝나기 전에 다른 쪽에 추가 기능을 넣지 않는다.
4. 소스 파일 수나 줄 수를 같게 만들지 않는다.
5. 한 프레임워크의 기능을 다른 프레임워크에서 억지로 흉내 내지 않는다.
6. 비교 결과에는 구현 완성도 차이와 프레임워크 특성 차이를 구분해 기록한다.

## 3. 공통 구현 기준선

### 3.1 공유할 것

- API 스키마와 생성 타입
- 디자인 토큰, 아이콘 원본, 이미지 비율
- 테스트 계정과 시드 데이터
- 화면별 인수조건과 E2E 시나리오
- 분석 이벤트 이름·속성
- 접근성 검사 기준
- 성능 측정 조건과 기기·네트워크 프로필

### 3.2 공유하지 않을 것

- React·Vue 컴포넌트 코드
- 상태 관리 구현
- 라우터 래퍼와 데이터 요청 훅·컴포저블
- 프레임워크 내부 캐시 래퍼
- 생태계 전용 UI 패키지

공유 범위가 너무 크면 두 구현이 각각의 생태계를 배우는 목적이 약해진다. 제품 규칙과 자산은 공유하되 UI 구현은 독립시킨다.

## 4. 경로별 렌더링·캐시 요구

아래 표의 “제품 의도”는 동일해야 하지만 구체적인 API와 파일 구조는 각 프레임워크에 맞춘다.

| 경로군 | 제품 의도 | 초기 응답 | 캐시·갱신 | 개인화 |
|---|---|---|---|---|
| 홈 `/` | 공개 탐색·검색 유입 | 서버에서 핵심 콘텐츠 제공 | 운영 콘텐츠 단위 갱신 | 로그인 여부만 제한적으로 반영 |
| 지역·카테고리 | 색인 가능한 목록 | 서버 제공 | 조건별 재사용·주기 갱신 | 없음 |
| 검색 `/search` | URL 기반 동적 결과 | 서버 결과 제공 후 상호작용 | 검색 조건별 제한적 캐시 | 없음 |
| 상품 상세 `/experiences/{id}` | 설명은 공개, 재고는 변동 | 핵심 설명 서버 제공 | 상품 정보와 재고 갱신 주기 분리 | 찜 상태만 개인화 |
| 로그인·가입 | 인증 입력 | 공용 캐시 금지 | 캐시 금지 | 사용자별 |
| 예약·결제 | 민감·실시간 | 사용자별 응답 | 공용 캐시 금지 | 필수 |
| 내 예약·계정 | 개인정보 | 사용자별 응답 | 공용 캐시 금지 | 필수 |
| 도움말·정책·소개 `/help` `/policies/{slug}` | 정적 콘텐츠 | 사전 생성 가능 | 배포 또는 게시 시 갱신 | 없음 |

체험 경로는 `{slug}`가 아니라 `{id}`를 사용한다(01 §4.2 식별자 규약). 분류 체계인 `/categories/{slug}`·`/regions/{slug}`와 정적 문서 `/policies/{slug}`만 `{slug}`를 유지하므로 **두 종류의 경로 파라미터가 한 제품 안에 공존한다.** 정적 생성 대상 경로를 사전에 열거할 때 이 차이가 드러난다 — 분류·정책은 목록이 유한하고 체험은 그렇지 않다. 서비스 소개는 별도 경로가 아니라 `/policies/about`이므로(01 §4.2 정적 문서 규약) 사전 생성 대상 slug는 `about`·`terms`·`privacy`·`cancellation` 넷으로 고정된다.

### 4.1 상품 상세 분리 기준

- 설명, 이미지, 위치, 정책은 상대적으로 오래 재사용할 수 있다.
- 회차 재고, 가격 견적, 찜 여부는 별도 요청 또는 사용자 상호작용 시 다시 확인한다.
- 캐시된 “잔여 1석” 표시만 믿고 결제하지 않으며 임시 확보 생성이 최종 검증이다.

## 5. 개념 대응표

완전한 일대일 대응표가 아니다. 같은 제품 문제를 각 프레임워크에서 어디서 해결할지 정하는 출발점이다.

| 제품 문제 | Next.js 구현 학습 | Nuxt 구현 학습 |
|---|---|---|
| 파일 기반 화면 | App Router의 page·layout·중첩 경로 | pages·layouts·중첩 경로 |
| 서버·클라이언트 경계 | Server Component와 Client Component 경계 | 범용 렌더링과 클라이언트 전용 컴포넌트 경계 |
| 서버 데이터 조회 | 서버 컴포넌트 데이터 로딩, 요청 메모화·캐시 판단 | `useFetch`·`useAsyncData`와 서버 렌더링 데이터 전달 |
| 경로별 렌더링 | 정적·동적 렌더링, 재검증 | universal rendering, route rules, hybrid rendering |
| 페이지 메타 | Metadata API와 동적 메타데이터 | `useHead`, `useSeoMeta` |
| 서버 엔드포인트 | Route Handler | Nitro server route |
| 요청 선처리 | Middleware 또는 프록시 역할의 경로 정책 | route middleware와 server middleware 구분 |
| 오류·로딩 | route loading·error·not-found 경계 | error page, error handling, pending UI |
| 코드 분할 | 동적 가져오기, 클라이언트 경계 최소화 | 비동기 컴포넌트, 지연 로딩 |
| 이미지·폰트 | 프레임워크 제공 최적화 기능 | Nuxt 모듈 또는 표준 최적화 구성 |
| 배포 | 서버·정적·플랫폼별 출력 확인 | Nitro preset·서버·정적 출력 확인 |

Next.js의 Server Component와 Nuxt의 서버 렌더링 Vue 컴포넌트는 내부 모델이 같지 않다. 결과가 비슷하다는 이유로 같은 개념이라고 단정하지 않고 네트워크·번들·수명주기를 각각 확인한다.

## 6. 기능별 학습 과제

### 6.1 라우팅·레이아웃

공통 과제:

- 공개 레이아웃, 인증 레이아웃, 결제 레이아웃을 분리한다.
- 동적 상품 경로, 정책 문서 경로, 찾을 수 없음 화면을 구현한다.
- 검색 조건을 URL과 양방향 동기화한다.
- 로그인 후 원래 목적지로 안전하게 복귀한다.

비교 질문:

- 중첩 레이아웃의 데이터와 UI 상태는 언제 유지되는가?
- 경로 변경과 서버 데이터 재요청 범위가 어떻게 다른가?
- 인증 검사를 서버, 미들웨어, 화면 중 어디에 배치했는가?

### 6.2 데이터 로딩·캐시

공통 과제:

- 공개 상품 정보와 사용자별 정보를 분리한다.
- 홈 콘텐츠 게시, 상품 수정, 판매 중단 때 관련 캐시만 갱신한다.
- 예약·결제·재고 응답은 공용 캐시에 들어가지 않게 한다.
- 서버에서 가져온 초기 데이터가 클라이언트에서 불필요하게 중복 요청되지 않게 한다.

비교 질문:

- 기본 캐시 동작을 명시적으로 설명할 수 있는가?
- 데이터 갱신 후 어느 화면이 언제 새 값을 보게 되는가?
- 캐시 키와 무효화 단위가 제품의 데이터 경계와 맞는가?

### 6.3 서버·클라이언트 컴포넌트 경계

공통 과제:

- 공개 설명은 서버 결과에 포함하고 필터·달력·결제 폼만 필요한 만큼 상호작용시킨다.
- 브라우저 API가 필요한 부분을 좁은 경계로 분리한다.
- 큰 라이브러리가 모든 공개 페이지의 초기 번들에 포함되지 않게 한다.

비교 질문:

- 클라이언트 자바스크립트가 필요한 이유를 컴포넌트별로 설명할 수 있는가?
- 서버 전용 비밀값이 클라이언트 번들로 노출되지 않는가?
- 하이드레이션 불일치가 발생할 수 있는 시간·난수·브라우저 의존 값을 어떻게 처리했는가?

### 6.4 폼·쓰기·낙관적 UI

공통 과제:

- 로그인, 검색 필터, 예약 인원, 쿠폰, 결제, 취소, 후기 폼을 구현한다.
- 클라이언트와 서버 유효성 오류를 같은 항목에 연결한다.
- 찜처럼 되돌릴 수 있는 작업과 결제·취소처럼 위험한 작업의 낙관적 처리 기준을 다르게 한다.
- 멱등 키와 중복 선택 방지를 적용한다.

비교 질문:

- 서버 쓰기를 프레임워크 기능으로 감쌀지 직접 API 호출할지 어떤 기준으로 정했는가?
- 진행 상태와 서버 최종 상태가 어긋날 때 어떻게 복구하는가?

### 6.5 메타데이터·검색 노출

공통 과제:

- 홈, 지역, 카테고리, 상품 상세, 서비스 소개에 고유 제목·설명·대표 이미지·표준 URL을 제공한다.
- 체험 경로에 `{slug}`를 쓰지 않으므로 URL에서 얻던 키워드 신호가 없다. 제목·설명·구조화 데이터가 그 몫을 대신하는지 두 구현에서 같은 기준으로 확인한다.
- 예약·결제·계정 경로는 색인 대상에서 제외한다.
- 판매 중단·삭제 상품의 상태 코드와 대체 경로를 정한다.
- 구조화 데이터는 화면 내용과 일치하는 최소 범위로 제공한다.

### 6.6 오류·스트리밍·대기 UI

공통 과제:

- 전체 서비스 오류, 경로 단위 오류, 빈 결과, 찾을 수 없음을 구분한다.
- 느린 후기·추천 영역이 핵심 상품 정보와 예약 버튼을 막지 않게 한다.
- 결제 결과 불명 상태에서는 재결제 버튼보다 상태 확인을 우선한다.

### 6.7 이미지·성능

공통 과제:

- 반응형 이미지 크기, 비율, 지연 로딩, 대표 이미지 우선순위를 정의한다.
- 실제 상품 카드·상세 이미지로 LCP·CLS·INP를 측정한다.
- 개발 모드가 아닌 제품 빌드로 비교한다.

## 7. 공통 테스트 체계

### 7.1 테스트 계층

| 계층 | 공유 범위 | 예시 |
|---|---|---|
| API 명세 | 완전 공유 | 가격·재고·권한·오류 스키마 |
| 도메인 예제 | 입력·기대값 공유 | 취소 환불액, 상태 전이 |
| 컴포넌트 | 시나리오 공유, 코드 독립 | 필터, 달력, 오류 요약 |
| E2E | 시나리오·선택 기준 공유 | 검색부터 모의 결제 완료 |
| 접근성 | 규칙·대상 화면 공유 | 키보드, 이름, 초점, 대비 |
| 성능 | 조건·측정 경로 공유 | 홈, 검색, 상품 상세 |

### 7.2 구현 동등성 검사

- 같은 API 스냅숏으로 두 화면의 핵심 텍스트·금액·상태를 비교한다.
- 화면 픽셀을 완전히 같게 만들기보다 정보 계층, 조작, 결과, 접근성의 동등성을 본다.
- 테스트 선택자는 화면 ID와 의미 기반 속성을 사용하고 프레임워크 DOM 구조에 의존하지 않는다.
- 공통 E2E를 한쪽에서만 건너뛰는 경우 사유와 해소 일정을 기록한다.

## 8. 권장 구현 순서

1. 공통 API 스키마, 시드 데이터, 디자인 토큰 확정
2. 홈·검색·상품 상세의 공개 읽기 흐름
3. 인증과 목적지 복귀
4. 회차 선택·임시 확보·주문 확인
5. 모의 결제와 결과 복구
6. 내 예약·취소·환불 상태
7. 찜·후기·계정
8. 메타데이터·오류·접근성·성능 개선
9. 같은 E2E와 측정 조건으로 비교

한 기술로 B2C 전체를 완성한 뒤 다른 기술을 시작하면 기억과 요구사항이 달라질 수 있다. 기능 묶음별로 두 구현을 번갈아 완료하는 편이 비교에 유리하다.

| 사용자 결과 | 결과가 같은지, 차이가 있다면 이유 |
| 성능 | 서버 응답, 클라이언트 JS, LCP·INP·CLS |
| 복잡도 | 상태 위치, 캐시 무효화, 오류 복구 난이도 |
| 재작업 | 잘못 이해한 기본 동작과 수정 내용 |
| 결론 | 다음 기능에도 적용할 원칙 |

## 10. 자연스럽게 학습되는 범위

- 파일 기반 라우팅과 중첩 레이아웃
- 정적·서버·클라이언트·혼합 렌더링 판단
- 서버 데이터 로딩과 클라이언트 상호작용
- 캐시와 무효화
- 인증·리디렉션·미들웨어
- 동적 메타데이터와 검색 노출
- 오류·로딩·찾을 수 없음 처리
- 폼·서버 쓰기·멱등성
- 이미지·번들·성능 최적화
- 테스트, 접근성, 배포 출력

## 11. 의도적으로 제외하는 학습 범위

- 제품 요구가 없는 실시간 다중 사용자 편집
- 프레임워크 내부 렌더러 수정
- 실험 단계 기능을 쓰기 위한 기능 추가
- 동일 UI 안에 React와 Vue를 섞는 구성
- 학습 목적만을 위한 과도한 미들웨어·서버 엔드포인트
- 의미 없는 모든 페이지의 강제 스트리밍
