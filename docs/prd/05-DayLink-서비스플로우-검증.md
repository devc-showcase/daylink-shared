| 항목 | 내용 |
|---|---|
| 검증 기준일 | 2026-08-21 (최초) · **2026-08-24 (개정)** |
| 검증 대상 | 제품 개요, B2C PRD, Admin PRD, 두 학습 구현 가이드, **Core API PRD** |

## 1. 검증 목적

이번 검증은 화면 수가 충분한지를 보는 검토가 아니다. 실제 서비스처럼 구현할 때 다음 문제가 생기지 않는지를 확인한다.

- 제품과 사용자 역할의 경계가 맞는가
- 같은 제품의 두 구현이 기능적으로 갈라지지 않는가
- 상태 전이가 끊기거나 서로 모순되지 않는가
- 가격·재고·결제·환불의 최종 판단 주체가 명확한가
- 메뉴 권한과 실제 데이터 권한이 일치하는가
- 네트워크 실패·중복 요청·동시 처리 후 복구할 수 있는가
- B2C와 Admin 사이에 필요한 업무 연결이 빠지지 않았는가

## 2. 검증 결론

수정된 구조는 학습 목적에 맞는다.

- B2C 요구사항 하나를 Next.js와 Nuxt에서 각각 구현한다.
- Admin 요구사항 하나를 React와 Vue에서 각각 구현한다.
- 파트너센터와 현장 데스크는 별도 제품이 아니라 Admin의 권한 모듈이다.
- 기능 비교 기준은 소스 구조가 아니라 같은 API 입력이 만드는 사용자 결과와 인수조건이다.

문서상 구현을 시작할 수 없는 P0 결함은 없다. 다만 완전 오프라인 긴급 취소, 실제 PG, 법률·개인정보, 두 공개 구현의 중복 색인은 구현·출시 환경에서 별도 통제가 필요하다.

## 4. 배포·비교 환경 검증

두 구현을 동시에 공개하면 같은 콘텐츠가 서로 다른 주소에서 색인되는 문제가 생길 수 있다. 또한 두 Admin 구현이 같은 테스트 데이터를 동시에 변경하면 비교 결과가 오염될 수 있다.

### 4.1 환경 정책

| 환경 | B2C 정책 | Admin 정책 |
|---|---|---|
| 로컬 | 서로 다른 포트, 같은 모의 API 스키마 | 서로 다른 포트, 격리된 테스트 테넌트 |
| CI | 구현별 새 시드 데이터 | 구현별 새 시드 데이터 |
| 비교 스테이징 | Next·Nuxt 별도 호스트, 모두 `noindex` | React·Vue 별도 호스트, 외부 비공개 |
| 공개 포트폴리오 | 한 구현만 색인 또는 둘 다 `noindex` | 인증된 데모 계정만 허용 |

### 4.2 동등성 비교 정책

- 같은 테스트는 동일 시드의 별도 테넌트에서 실행한다.
- 읽기 성능 비교는 같은 API 응답 스냅숏을 사용한다.
- 쓰기 흐름 비교는 각 구현 전용 데이터 세트를 사용하고 종료 후 초기화한다.
- 제품 요구 변경은 PRD를 먼저 바꾸고 두 구현 작업을 같은 변경 묶음으로 만든다.
- 한쪽만 통과한 기능은 “구현 완료”로 처리하지 않는다.

## 5. 주요 서비스 플로우 검증

### 5.1 상품 입점·심사·공개

```text
파트너(Admin)
입점 작성 → 입점 제출 → 운영자 심사 → 승인
                                   └→ 반려 → 보완 → 재제출

파트너(Admin)
상품 임시 저장 → 심사 제출 → 운영자(Admin) 승인 → 공개 → B2C 노출
                              └→ 반려 → 수정 → 재제출
```

검증 결과:

- 작성·제출·승인·공개 상태가 분리되어 있다.
- 제출본은 스냅숏으로 남는다. 심사 중에 원본을 바꿔도 제출본은 그대로다.
- 승인 직후 자동 공개인지 파트너 공개 선택인지 모호할 수 있어 `APPROVED`와 `PUBLISHED`를 분리했다.
- 반려는 새 심사 차수로 이어지고 이전 의견을 보존한다.
- B2C는 `PUBLISHED`이면서 유효 회차가 있는 상품만 신규 예약 대상으로 노출한다.

### 5.2 회차 생성·재고·임시 확보

```text
파트너(Admin) 회차 생성
  → B2C 회차 조회
  → 고객 인원 선택
  → Core API 재고 확인·10분 임시 확보
  → 결제 성공: 확보 소비·예약 확정
  → 실패·이탈·만료: 확보 해제
```

검증 결과:

- 화면 재고와 서버 최종 재고의 차이를 허용하되 결제 전에 다시 검증한다.
- 마지막 좌석 경쟁은 원자적 임시 확보로 한 사용자만 성공하게 한다.
- 브라우저 타이머가 아니라 서버 만료 시각이 기준이다.
- 확정 예약 인원과 활성 임시 확보 인원의 합보다 정원을 줄일 수 없다(`06 §8.3`).
- 같은 사용자의 중복 임시 확보는 복구하거나 기존 것을 해제한 후 생성한다.

### 5.3 인증 후 예약 복귀

```text
비회원 상품 상세 → 회차·인원 선택 → 로그인
  → 인증 성공 → 원래 상품·선택 복구
  → 서버 재고 재검증 → 임시 확보 → 주문 확인
```

검증 결과:

- 인증 전 선택값은 편의를 위해 보존하지만 좌석을 선점하지 않는다.
- 외부 URL을 복귀 주소로 사용하지 않도록 허용 경로를 제한한다.
- 로그인 지연 중 매진될 수 있으므로 재고 실패 화면을 별도로 둔다.

### 5.4 결제·예약 확정

```text
임시 확보 ACTIVE
  → 주문 견적 재확인
  → PAYMENT_PENDING
  → 모의 결제 성공 확인
  → 예약 CONFIRMED + 확보 CONSUMED

예외: 사용자 취소 / 실패 / 시간 초과 / 결과 불명
```

검증 결과:

- 클라이언트 성공 화면만으로 예약을 확정하지 않는다.
- 결제 요청과 예약 확정에 멱등 식별자를 사용한다.
- 결과 불명 상태에서 재결제를 유도하지 않고 서버 상태를 조회한다.
- 예약 생성과 재고 소비가 부분 성공하지 않도록 트랜잭션 경계를 Core API에 둔다.
- 실제 PG 웹훅 순서 뒤바뀜은 모의 테스트 항목으로만 다루며 실제 연동 시 재검증한다.

### 5.5 고객 취소·환불

```text
B2C 예약 상세
  → 서버 기준 취소 가능 여부·예상 환불액 조회
  → 고객 확인
  → 예약 CANCEL_PENDING
  → 예약 CANCELLED
  → 환불 PROCESSING
  → SUCCEEDED / PARTIALLY_SUCCEEDED / FAILED
  → Admin CS·정산 대기열 반영
```

검증 결과:

- 예약 취소와 환불 성공을 다른 상태로 관리한다.
- 정책은 예약 시점 스냅숏과 서버 시각을 사용한다.
- 취소 중복 요청은 같은 업무 결과를 반환한다.
- 환불 실패 후 재시도 전 기존 외부 처리 상태를 확인한다.
- 원거래와 정산 원장을 수정하지 않고 환불·조정 항목을 추가한다.

### 5.6 파트너·플랫폼 귀책 회차 취소

```text
파트너(Admin) 회차 취소 요청
  → 영향 예약·금액 확인
  → 회차 판매 중단
  → 예약별 전액 취소·환불 업무 생성
  → B2C 고객 상태·알림 반영
  → 정산 조정
```

검증 결과:

- 파트너가 예약이 있는 회차를 즉시 삭제하지 못한다.
- 일부 예약만 업무 생성에 실패하면 재실행 가능한 작업 목록을 남긴다.
- 고객 귀책 정책이 아니라 실제 결제액 전액 환불을 적용한다.
- 이미 이용 완료·환불된 예외 예약은 별도 검토 대기열로 보낸다.

### 5.7 현장 체크인·오프라인 동기화

```text
현장 담당자(Admin /desk)
  → 장소·회차 선택
  → 최신 명단 동기화
  → QR 또는 수동 체크인
  → 온라인: 즉시 서버 확정
  → 오프라인: 임시 이벤트 저장
  → 연결 복구: clientEventId로 전송
  → 자동 반영 또는 충돌 대기열

사고 발생 시
현장 담당자(Admin /desk)
  → 사고 보고 작성 `/desk/incidents/new`
  → 제출
  → 사고 상세 `/desk/incidents/{id}`
  → 추가 메모만 등록 (원문 수정·삭제 불가)
  → 사내 운영 `/ops/incidents/{id}`에서 조치·타임라인 처리
```

검증 결과:

- 현장 기능은 Vue 전용이 아니라 React·Vue Admin 모두 구현한다.
- 오프라인 스냅숏은 최소 개인정보와 토큰 해시만 저장한다.
- 마지막 동기화 후 2시간이 지나면 오프라인 정상 승인을 막는다.
- 같은 이벤트 재전송은 중복 출석을 만들지 않는다.
- 여러 기기 충돌은 원본을 삭제하지 않고 보정 이벤트로 해결한다.
- 사고 제출 이후의 추가 메모는 현장용 사고 상세(`/desk/incidents/{id}`)에서 남긴다. 02 §7 ADM-DSK-05가 요구하는 행동에 대응하는 화면이 이제 존재한다.
- 사고 상세로 들어가는 진입점은 제출 직후 이동, 통합 알림, 그리고 사고 목록(`/desk/incidents`) 세 가지다. 목록이 없으면 교대가 바뀌거나 알림을 읽음 처리한 뒤 추가 메모 경로가 사라지므로, 목록을 진입점 요구사항으로 둔다.
- 현장 담당자는 사내 운영용 사고 상세(`/ops/incidents/{id}`)에 접근하지 않는다. ADM-AC-07의 최소 노출 원칙과 모듈 경계를 함께 지킨다.

잔여 위험:

- 완전히 오프라인인 동안 다른 채널에서 긴급 취소된 예약은 현장 기기가 알 수 없다. 오프라인 처리를 “임시”로 표시하고 긴급 연락 절차를 둬도 기술적으로 완전히 제거할 수 없다.

### 5.8 정산 대사

```text
확정 예약·환불·쿠폰·수수료 원장
  → 정산 기간 집계        → 정산 목록 `/ops/settlements`
  → 자동 대사              → 정산 대사 `/ops/reconciliation`
  → 일치: 확정 승인        → 정산 상세 `/ops/settlements/{id}`
  → 불일치: 유형 분류 → 조정 항목 → 재대사 → 승인
  → 파트너 Admin 정산 상세 `/partner/settlements/{id}` 반영
```

검증 결과:

- 플랫폼 쿠폰과 파트너 부담액을 구분한다.
- 정산 원장을 직접 덮어쓰지 않는다.
- 정산 확정과 재개방 권한을 분리한다.
- 파트너 화면의 합계와 운영자 원장 합계가 같은 계산식으로 검증된다.
- 목록·대사·상세의 책임이 분리된다. 목록은 기간별 정산 상태, 대사는 차이 분석, 상세는 결재다. 02 §8 ADM-OPS-05의 '확정과 재개방은 서로 다른 권한과 승인 절차'는 상세 화면에 남는다.
- 플랫폼 정산 목록(`/ops/settlements`)과 파트너 정산 목록(`/partner/settlements`)이 대칭 구조를 갖는다. 이전에는 파트너 쪽에만 목록이 있었다.

### 5.9 예약 문의

```text
고객(B2C) 예약 상세 `/bookings/{id}`
  → 예약 문의 `/bookings/{id}/inquiry`
  → 운영자 문의 대기열 `/ops/inquiries` (미답변 조회)
  → 접수 (멱등 식별자 사용)
  → 문의 RECEIVED
  → CS(Admin) 예약 상세 `/ops/bookings/{id}` 문의 스레드 인라인
  → 답변 등록 (InquiryMessage 추가)
  → ANSWERED → CLOSED
  → B2C 스레드에 반영
```

검증 결과:

- 문의는 항상 하나의 예약에 종속된다. 예약과 무관한 일반 문의 창구를 두지 않으므로 문의 조회 권한이 예약 소유권과 업무 범위에서 그대로 파생된다.
- Admin에 별도 문의 화면을 두지 않고 예약 상세에 인라인한다. CS가 예약 맥락을 보지 않고 답변하는 상황을 구조적으로 막는다.
- 답변은 메시지 추가이고 기존 메시지를 수정·삭제하지 않는다. 06 §4의 `InquiryMessage`가 '추가만'인 이유다.
- 문의 상태와 예약·환불 상태를 한 값으로 합치지 않는다. 취소·환불 처리 중인 예약에도 문의할 수 있다.
- 문의 접수 재전송은 중복 접수를 만들지 않는다. 06 §8.2의 멱등 처리가 그대로 적용된다.

잔여 위험:

- 문의 응답 시간 약속(SLA)을 정의하지 않았다. 학습 범위에서는 상태 전이만 다루고 기한 관리와 알림 에스컬레이션은 제외한다.

## 6. 상태 간 정합성 규칙

| 상황 | 허용 여부 | 처리 |
|---|---|---|
| `CONFIRMED` 예약 + 결제 실패 | 불가 | 결제 상태 재조회·운영 경보 |
| `CANCELLED` 예약 + 환불 처리 중 | 허용 | B2C에 두 상태를 분리 표시 |
| `CANCELLED` 예약 + 체크인 완료 | 원칙상 불가 | 충돌 대기열·운영자 보정 |
| `COMPLETED` 예약 + 후기 없음 | 허용 | 후기 작성 가능 상태 |
| `PUBLISHED` 상품 + 유효 회차 없음 | 허용 | 상세 노출 가능, 예약 불가 표시 |
| 판매 중단 상품 + 기존 예약 | 허용 | 신규 예약 차단, 기존 예약 조회 유지 |
| 확정 인원 > 회차 정원 | 불가 | 정원 축소 요청 거부 |
| 환불 합계 > 실제 결제액 | 불가 | 서버 검증 거부·운영 경보 |
| 체크인 합계 > 예약 인원 | 불가 | 중복·충돌 처리 |

## 7. 권한 흐름 검증

### 7.1 인증 영역

- B2C와 Admin은 세션·쿠키·토큰 대상을 분리한다.
- Admin은 한 제품이지만 파트너 계정과 사내 운영 계정의 역할 체계를 구분한다.
- 일반 계정에 파트너 역할과 사내 운영 역할을 동시에 부여하지 않는다.
- 긴급 운영 권한은 기간, 사유, 승인자를 갖고 만료된다.

### 7.2 객체 단위 권한

다음 검사는 화면 진입뿐 아니라 모든 API 요청에서 수행한다.

- 파트너 사용자의 `partnerId` 소속
- 상품 담당자의 상품·장소 범위
- 현장 담당자의 장소·회차·날짜 범위
- 고객의 예약·후기 소유권
- CS·정산 담당자의 업무 권한
- 내보내기 파일의 생성자·역할·만료
- 한시 역할(`READ_ONLY_AUDITOR`)의 승인 범위와 **유효 기간**. 별도 철회가 없어도 종료일이 지나면 거부한다
- 문의의 예약 소유권. 고객은 본인 예약의 문의만, CS는 업무 범위 안의 예약 문의만 조회한다

### 7.3 권한 변경

- 역할이 철회되면 활성 Admin 세션과 캐시를 갱신한다.
- 역할 전환 시 이전 역할 데이터가 화면에 남지 않게 한다.
- 권한 없는 링크 알림은 내용을 노출하지 않고 접근 거부 처리한다.

- 같은 API 오류에 서로 다른 다음 행동을 제공함

- 한쪽에서만 인수 테스트를 건너뜀
- 한쪽 구현의 캐시 때문에 오래된 가격·권한·재고가 확정값처럼 보임

## 12. 최종 판정

### 구현 착수: 가능

조건은 다음과 같다.

1. B2C와 Admin PRD를 기능 정의의 단일 기준으로 사용한다.
2. 기술별 구현 가이드는 기능을 추가·삭제하는 문서로 사용하지 않는다.
3. 같은 Core API와 공통 인수 테스트를 먼저 준비한다. 여기서 "먼저 준비"는 **OpenAPI 명세·오류 코드·멱등 규약과 인수 테스트 코드의 선작성**을 뜻하며 구현 깊이까지 먼저 완성하라는 뜻은 아니다(06 §15).
4. 비교 환경의 데이터와 검색 색인을 격리한다.
5. 잔여 위험 여섯 건은 실제 연동·운영 단계의 검증 항목으로 유지한다.

위 조건을 지키면 서비스 흐름과 비교 학습 목적 사이에 현재 확인된 기획상 차단 결함은 없다.
