## 1. 제품 개요

Core API는 DayLink의 업무 규칙을 판정하는 단일 권위자다. 네 개의 프론트 구현은 화면과 상호작용만 다르고 가격·재고·권한·상태 전이·정산은 전부 이 서버가 결정한다.

### 1.1 이 문서가 존재하는 이유

00 v2.0까지 Core API는 §8의 "책임 목록" 여덟 줄로만 존재했다. 실제로 구현하기로 결정하면서 다음이 필요해졌다.

- 여덟 가지 책임을 구현 가능한 수준의 규칙으로 펼치는 것
- 네 프론트 구현이 갈라지지 않도록 명세를 고정하는 것
- 동시성·멱등성처럼 화면에서는 보이지 않는 요구사항에 인수조건을 붙이는 것

### 1.2 왜 mock으로 대체하지 않는가

00 §8의 여덟 책임 중 다섯 — 원자적 재고 확보, 중복 예약 방지, 상태 전이, 정산 원장, 멱등 처리 — 은 트랜잭션 경계와 동시성 제어 없이 성립하지 않는다. 응답만 흉내 내는 mock은 이 규칙을 강제하지 못하므로 프론트가 규칙을 어겨도 테스트가 통과한다. 그러면 00 §9의 동등성 검증이 무의미해진다.

### 1.3 왜 1벌만 만드는가

Core API를 두 벌로 만들면 프론트 구현 간 차이가 프레임워크 차이인지 백엔드 차이인지 판정할 수 없다. 00 §5가 "구현마다 별도 백엔드를 만들어 결과가 달라지는 방식은 허용하지 않는다"고 못박은 것이 이 이유다.

이 결정의 대가는 §12에 있다. 프론트는 같은 요구를 두 번 구현해 서로 채점하지만 Core API에는 그 장치가 없다.

### 2.1 스택 선택 근거

00 §2가 Spring 계열로 고정한 이유는 SI 실무 적용 목적이다. 국내 SI 현장에서 가장 널리 쓰이는 스택이므로 여기서 익힌 트랜잭션·계층 분리·감사 로그 패턴이 상주 현장에 그대로 옮겨진다.

국내 백엔드 채용과 SI 현장에서 Kotlin 선호도가 낮다고 판단해 언어를 Java로 확정했다 (2026-08-24). 학습 자체는 Kotlin이 가볍지만(TypeScript에서 널 안전·타입 추론·데이터 클래스가 그대로 전이된다) 이 프로젝트의 2순위 목적이 SI 실무 적용이므로 현장 코드와의 거리를 우선한다. 참고 자료 밀도에서도 Java가 앞선다.

**Java 21을 택한 이유.** Spring Boot 4의 최소 요구는 Java 17이고 21·25를 권장한다. 25가 최신 LTS지만 Spring 실전 자료는 21 기준이 압도적이며 이 프로젝트에서 백엔드는 기준선이 없는 신규 학습 영역이므로 자료 밀도가 결정 변수다.

**Java를 택하면서 새로 생기는 위험.** Kotlin에는 체크 예외가 없다. Java에는 있고 Spring의 `@Transactional`은 기본적으로 unchecked exception에서만 롤백한다. 즉 체크 예외를 선언하고 던지면 트랜잭션이 커밋된다. §8의 동시성·원자성 요구사항이 이 한 가지로 조용히 무너질 수 있으므로 롤백 규칙을 ADR에 명시하고 §14.2의 경합 테스트로 검증한다.

현장 레거시는 Java 8·11 + Spring Boot 2.x가 많다. Boot 2 → 3에서 `javax.*` → `jakarta.*` 네임스페이스가 바뀌었다. 이것이 현장 코드를 읽을 때 가장 먼저 마주치는 차이다. 최신으로 배우되 이 간극은 별도로 인지한다.

### 2.2 프론트와의 언어 분리가 만드는 부담

네 프론트 구현은 TypeScript다. Core API를 JVM으로 두면 다음이 추가된다.

- 언어·빌드 도구(Gradle 또는 Maven)·테스트 도구(JUnit 5)가 하나 더 늘어난다
- 타입을 공유할 수 없고 OpenAPI 생성기를 경유해야 한다
- 도메인 규칙이 두 언어로 표현되므로 정의가 어긋날 여지가 생긴다
- TypeScript의 `strictNullChecks`에 익숙한 상태에서 Java는 `null` 가능성이 타입에 나타나지 않는다. `Optional`은 반환값에만 쓰는 관례이고 필드·파라미터에는 쓰지 않으므로 타입이 보장해 준다는 기대가 통하지 않는다

세 번째가 실질적 위험이다. 완화책은 §9.1의 명세 우선 규칙이다.

## 3. 범위

### 3.1 범위 안

- 인증·인가와 역할·조직·장소 범위 판정
- 상품·회차·재고와 원자적 임시 확보
- 예약·모의 결제·취소·환불 상태 전이
- 쿠폰 적용과 금액 계산
- 정산 원장과 조정 항목
- 출석·체크인과 오프라인 이벤트 충돌 판정
- 예약 종속 문의 접수와 답변 스레드
- 감사 로그
- 비동기 작업(내보내기·집계)과 파일 만료
- 멱등 요청 처리와 추적 ID

### 3.2 범위 밖

00 §12를 따르되 Core API에 한해 다음을 명시한다.

- 다중 리전·다중 인스턴스 운영과 분산 트랜잭션
- 메시지 브로커 전제의 이벤트 소싱·CQRS
- 쿠버네티스 운영 인프라와 무중단 배포
- 실제 PG·은행 연동, 웹훅 서명 검증
- 샤딩·읽기 복제·분산 캐시

학습 목표는 규모가 아니라 정확성이다. 단일 인스턴스·단일 데이터베이스에서 동시성·멱등성·불변 원장을 정확히 만드는 것이 목표다.

### 4.1 불변 원칙

"추가만"과 "불변"으로 표시한 엔터티는 `UPDATE`·`DELETE` 하지 않는다. 정정이 필요하면 반대 방향 항목을 추가한다. 00 §6.3의 "환불과 정산 조정은 원거래를 수정하지 않고 별도 원장 항목으로 남긴다"와 02 §8 ADM-OPS-05의 원칙을 데이터 계층에서 강제한다.

### 4.2 스냅숏 원칙

`Booking`은 예약 시점의 상품명·회차·단가·취소 정책·게시 버전을 자기 안에 복사해 보관한다. 상품이 나중에 수정되어도 과거 예약의 조건은 바뀌지 않는다. 05 §5.5와 01 §5.5 B2C-BOOK-02가 이 동작을 요구한다.

### 4.3 문의 종속 원칙

`Inquiry`는 항상 하나의 `Booking`에 종속된다. 예약과 무관한 일반 문의는 만들지 않는다(01 §5.5 B2C-INQ-01). 따라서 문의 조회 권한은 예약 소유권과 담당 업무 범위에서 파생되며 별도 권한 체계를 두지 않는다. 답변은 `InquiryMessage` 추가이고 기존 메시지를 수정·삭제하지 않는다.

## 5. 상태 전이

00 §7을 그대로 따른다. Core API는 아래 전이만 허용하고 정의되지 않은 전이 요청은 거부한다.

| 대상 | 전이 |
|---|---|
| 상품 | `DRAFT → SUBMITTED → APPROVED → PUBLISHED → PAUSED → ARCHIVED`, `SUBMITTED → REJECTED → DRAFT` |
| 임시 확보 | `ACTIVE → PAYMENT_PENDING → CONSUMED`, `ACTIVE → EXPIRED`, `ACTIVE → RELEASED` |
| 예약 | `PAYMENT_PENDING → CONFIRMED → COMPLETED`, `PAYMENT_PENDING → PAYMENT_FAILED`, `CONFIRMED → CANCEL_PENDING → CANCELLED`, `CONFIRMED → NO_SHOW` |
| 환불 | `REQUESTED → APPROVAL_PENDING → PROCESSING → SUCCEEDED \| PARTIALLY_SUCCEEDED \| FAILED` |
| 출석 | `NOT_CHECKED_IN → PARTIAL → COMPLETE`, `→ NO_SHOW`, `→ CORRECTED` |
| 문의 | `RECEIVED → IN_PROGRESS → ANSWERED → CLOSED`, `RECEIVED → CLOSED`(중복·오접수) |

문의를 네 단계로 나눈 것은 **CS 대기열이 그 구분을 요구하기 때문이다.** `/ops/inquiries`(ADM-OPS-022)가 미답변을 가려내야 하는데, 접수·착수·답변·종결이 각각 다른 행동을 부른다 — `RECEIVED`는 아무도 안 잡은 것이고, `IN_PROGRESS`는 담당자가 있으니 중복으로 잡지 않아야 하며, `ANSWERED`는 고객 회신을 기다리는 것이고, `CLOSED`만 대기열에서 빠진다. 셋으로 줄이면 대기열이 "안 잡힌 것"과 "잡혀 있는 것"을 구분하지 못한다.

### 5.1 상태를 합치지 않는다

예약 취소와 환불 성공은 다른 상태다. 예약이 `CANCELLED`인데 환불이 `FAILED`일 수 있다. 클라이언트가 두 상태를 하나로 합쳐 보여주지 않도록 API도 두 필드를 분리해 응답한다(B2C-AC-08과 ADM-AC-11의 근거).

## 6. 금액·정책 계산

### 6.1 금액 공식

00 §6.3을 그대로 구현한다.

```text
상품 총액 G = 예약 시점 단가 × 인원
플랫폼 할인 D = 적용 쿠폰 할인액
고객 결제액 C = G - D
플랫폼 수수료 F = floor(G × 0.12)
파트너 정산 기준액 = G - F
```

플랫폼 쿠폰 비용은 파트너 정산액에서 차감하지 않는다. 즉 `D`는 `G`에서 빠지지만 `G - F`에서는 빠지지 않는다.

### 6.2 취소 환불액

00 §6.4의 템플릿을 사용하되 판정 기준은 두 가지다.

- **시각**: 클라이언트 시각이 아니라 **서버 시각**
- **정책**: 현재 상품의 정책이 아니라 **예약에 저장된 정책 스냅숏**

01 §5.5 B2C-CAN-01이 "계산 기준 시각"을 화면에 표시하라고 요구하므로 응답에 기준 시각을 포함한다.

계산과 부담 배분은 ADR-0019가 정한다.

```text
환불액 R = floor(C × 환불률)          C = 고객 결제액 = G - D
플랫폼 반납액 P = min(R, F)
파트너 부담액 S = R - P
```

**환불률은 상품 총액 `G`가 아니라 고객 결제액 `C`에 곱한다.** 받지 않은 돈을 돌려줄 수 없다. 쿠폰은 **환불률이 100%일 때만** `CouponIssue`를 미사용으로 되돌린다. 수수료를 먼저 전액 반납하고 모자라는 만큼을 파트너가 부담한다.

### 6.3 반올림

금액은 원 단위 정수다. 수수료는 `floor`다 — **나머지를 플랫폼에 불리한 쪽으로 버린다.** 원 단위에서 소수점은 반드시 어디론가 가야 하는데, 반올림하면 플랫폼이 파트너 몫에서 1원을 더 가져가는 경우가 생긴다. 정산 대사에서 그 1원을 설명하는 비용이 얻는 것보다 크다. 수수료율 12%는 학습용 가정이고 실측 근거가 없다. 환불액도 `floor`다(ADR-0019). 두 자리의 방향이 같으므로 문서 안에 반올림 기준은 하나뿐이고, 버려진 끝수는 플랫폼에 남는다. 반올림 차이는 정산 대사에서 "차이 사유 분류"의 한 항목이 된다(02 §8 ADM-OPS-05).

## 8. 동시성·멱등성 요구사항

이 절이 Core API PRD의 핵심이다. 화면에서는 보이지 않지만 인수조건 다수가 여기에 걸려 있다.

### 8.1 원자적 재고 확보

회차 잔여 좌석 검사와 임시 확보 생성은 하나의 원자적 연산이어야 한다.

- `SELECT`로 잔여를 읽고 애플리케이션에서 비교한 뒤 `UPDATE` 하는 방식은 금지한다. 두 문장 사이에 다른 트랜잭션이 끼어들 수 있다.
- 조건부 갱신, 행 잠금, 또는 제약 조건 중 하나로 데이터베이스가 판정하게 한다.
- 선택한 방식과 그 방식이 어떤 격리 수준에서 안전한지를 ADR에 기록한다.

**검증 방법**: 마지막 1좌석에 동시 요청 N건을 보내 정확히 1건만 성공하는지 확인한다. 락을 제거했을 때 이 테스트가 실패하는 것을 먼저 확인한 뒤 락을 넣는다. 실패를 만들지 못하는 테스트는 무효로 간주한다.

**N은 고정값이 아니라 파라미터로 둔다.** 기본 50으로 돌리되 값을 올려가며 여러 번 확인한다. 50이라는 숫자 자체에는 근거가 없다 — 중요한 것은 락을 뺐을 때 실패가 나오는 값이다. **커넥션 풀 크기가 결과를 좌우하므로**(풀이 동시성 상한이다) 실행마다 N과 풀 크기를 함께 기록한다.

> **N을 올릴 때는 DB의 `max_connections`를 같이 본다.** 2026-09-04에 N=200으로 돌렸더니 두 테스트가 `FATAL: sorry, too many clients already`로 깨졌다. `postgres:18` 기본값이 100이라 스레드가 먼저 서버 한계에 부딪힌 것이다. **락 결함이 아니라 환경 포화다.** 이 둘을 구분하지 못하면 테스트가 거짓 신호를 준다 — 실패했으니 락이 동작한다고 읽거나, 반대로 락 문제로 오인한다. 그래서 검사기는 예상 밖 SQL 오류를 통과로 삼지 않고 실패로 올린다.

### 8.2 멱등 처리

| 항목 | 규칙 |
|---|---|
| 적용 범위 | 예약 생성, 결제, 취소, 환불, 체크인, 정산 조정 등 모든 쓰기 |
| 키 범위 | 클라이언트가 생성. 체크인은 `clientEventId`를 그대로 사용 |
| 저장 | 키 + 요청 지문 + 응답 본문 + 상태 |
| 재전송 | 같은 키·같은 요청 → 저장된 응답을 그대로 반환. 새 부작용 없음 |
| 진행 중 충돌 | 같은 키가 처리 중이면 새로 실행하지 않고 "처리 중" 응답 |
| 키 재사용 위반 | 같은 키에 다른 요청 본문 → 거부 |
| 유효 기간 | **24시간**(서버 기록 시각 기준, 판정도 서버 시각). 만료된 키는 **거부**한다 — `IDEMPOTENCY_KEY_EXPIRED`(410). 근거는 ADR-0018 |
| 만료 행 | **7일 보관 후 삭제.** 유효 기간이 지나도 행은 남아 410을 돌려준다 — 지우면 같은 키가 새 요청으로 흘러 거부가 무력해진다 |

"같은 요청을 두 번 보내면 같은 응답"만으로는 부족하다. 진행 중 중복, 부분 실패, 키 유효 기간, 응답 재현 저장까지 설계해야 한다.

### 8.3 정원 축소 제한

회차 정원은 확정 예약 인원 + 활성 임시 확보 인원보다 작게 줄일 수 없다. 축소 요청 시점의 값을 잠그고 판정한다(ADM-AC-05의 근거).

### 8.4 체크인 인원 상한

한 예약의 누적 체크인 인원은 예약 인원을 초과할 수 없다. 여러 기기가 동시에 보내는 경우에도 서버가 상한을 강제한다.

### 8.5 환불 총액 상한

한 예약의 누적 환불액은 고객 실결제액을 초과할 수 없다. 승인 직전에 기존 환불 총액을 다시 조회해 판정한다(ADM-AC-12와 05 §11.1의 항목).

### 8.6 한시 역할 만료

`READ_ONLY_AUDITOR`처럼 종료일을 갖는 권한은 별도 철회 행위가 없어도 종료일이 지나면 거부한다(02 §3.2). 만료 판정은 토큰 발급 시각이 아니라 **요청 처리 시점의 서버 시각**으로 한다. 이미 발급된 세션이 만료 이후에도 통과하면 안 된다.

이는 `CORE-AC-24`(권한 철회)와 다른 경로다. 철회는 누군가의 행위로 발생하고 만료는 시간 경과로 발생하므로 철회 시 세션을 정리하는 구현만으로는 만료가 덮이지 않는다.

### 8.7 낙관적 동시성

상품 편집처럼 여러 사용자가 같은 리소스를 수정하는 경우, 버전 필드로 충돌을 감지하고 조용한 덮어쓰기를 금지한다. 충돌 시 최신 서버본과 요청본을 함께 반환해 클라이언트가 비교 화면을 그릴 수 있게 한다. 02 §9.3이 이를 요구한다.

## 9. 프론트 4벌과의 명세 규칙

### 9.1 명세 우선

OpenAPI 스키마와 오류 코드를 코드보다 먼저 확정한다. 네 프론트 구현이 서로 다른 시점에 개발되므로 명세가 흔들리면 구현마다 다른 가정이 굳는다. 05 §12 조건 3의 "같은 Core API와 공통 인수 테스트를 먼저 준비한다"를 이 규칙으로 해석한다.

### 9.2 한쪽에만 유리한 엔드포인트 금지

엔드포인트를 특정 프론트 프레임워크의 편의를 위해 추가하지 않는다. 네 구현이 모두 쓰는 형태로 설계하거나 프론트에서 해결한다. 00 §9의 동등성 원칙이 깨지기 때문이다.

### 9.3 도메인 규칙의 이중 정의 방지

Core API가 JVM, 프론트가 TypeScript이므로 같은 규칙이 두 언어로 표현될 수 있다. 다음을 금지한다.

- 프론트가 금액·환불액·잔여 좌석·권한을 자체 계산해 표시하는 것
- 프론트가 상태 전이 가능 여부를 자체 판단하는 것

프론트는 서버가 계산한 값을 표시만 한다. 표시용 파생값(예: 남은 시간 카운트다운)은 허용하되 최종 판정 근거로 쓰지 않는다.

## 11. 오프라인 체크인 판정

02 §7 ADM-DSK-03·04와 05 §5.7을 서버 관점에서 정의한다.

### 11.1 스냅숏

- 현장 담당자가 명시적으로 내려받는다. 자동 동기화가 아니다.
- 포함 데이터: 예약 식별자, 표시용 최소 이름, 인원, 토큰 해시, 마지막 동기화 시각
- 마지막 동기화 후 2시간을 넘긴 스냅숏으로는 정상 승인하지 않는다. 서버가 스냅숏 시각을 검증한다. **2시간은 현장 교대 주기를 기준으로 잡았다** — 교대자가 바뀌면 장치도 바뀌고, 그전에 받아 둔 스냅숏은 이미 낡았다고 본다. 더 길게 잡으면 앞 교대의 스냅숏으로 체크인이 넘어간다.

### 11.2 이벤트 판정

오프라인 이벤트가 도착하면 서버가 현재 사실과 대조해 분기한다.

| 상황 | 서버 판정 |
|---|---|
| 같은 `clientEventId` 재전송 | 저장된 결과 반환. 중복 출석 없음 |
| 다른 기기가 같은 인원을 이미 처리 | 먼저 반영된 것까지만 인정. 후속 이벤트는 현재 공식 인원으로 교정 |
| 누적 인원 초과 | 거부하고 공식 인원 반환 |
| 취소된 예약의 늦은 이벤트 | **자동 반영 금지.** 충돌 대기열로 |
| 다른 회차의 토큰 | 자동 반영 금지 |
| 권한이 회수된 행위자의 이벤트 | 격리 대기열로 |
| 2시간 초과 스냅숏 기반 | 정상 승인하지 않음 |

### 11.3 원본 보존

충돌 해결은 원본 이벤트를 삭제하지 않고 보정 이벤트를 추가하는 방식이다. ADM-AC-10의 근거다.

## 12. 이 구현의 구조적 취약점과 보완책

Core API에는 비교 대상이 없다. 프론트는 같은 요구를 두 기술로 만들어 서로를 채점하지만(00 §9) 백엔드는 한 벌뿐이다. 그 결과 **잘못된 설계가 모든 테스트를 통과하면서 살아남을 수 있다.**

대표적인 예가 §8.1이다. `SELECT` 후 `UPDATE` 방식은 순차 요청 테스트를 전부 통과한다. 동시 요청을 보내지 않으면 결함이 드러나지 않는다.

보완책 네 가지를 둔다.

| 보완책 | 내용 |
|---|---|
| **실패 우선 테스트** | 동시성·멱등 테스트는 안전장치를 제거했을 때 **먼저 실패하는 것을 확인**한 뒤 장치를 넣는다. 실패를 만들지 못하는 테스트는 폐기한다 |
| **프론트를 검증 장치로 사용** | 프론트 구현이 먼저 돌아가는 상태에서 서버 규칙을 조인다. 서버를 조였을 때 프론트에서 무엇이 깨지는지가 규칙의 실재를 증명한다 |
| **책임별 반례 작성** | 00 §8의 여덟 책임마다 "클라이언트가 판단하면 깨지는 시나리오"를 문장으로 쓴다. 쓰지 못하면 그 책임을 이해하지 못한 것이다 |
| **격리 수준 명시** | 동시성 방어마다 어떤 격리 수준에서 안전한지를 ADR에 적는다. "락을 걸었으니 안전하다"는 설명으로 인정하지 않는다 |

## 14. 필수 테스트

05 §11.1을 확장한다.

### 14.1 도메인

- 금액 공식 표본: 쿠폰 있음·없음, 인원 1~6, 반올림 경계
- 취소 환불액 표본: 정책별 경계 시각 앞뒤 1초
- 상태 전이 허용·거부 행렬 전수

### 14.2 동시성

- 마지막 1좌석 동시 요청 N=50
- 안전장치 제거 시 실패 확인(CORE-AC-02)
- 정원 축소와 신규 임시 확보 경합
- 환불 승인과 다른 환불 처리 경합
- 임시 확보 만료 작업과 결제 요청 경합

### 14.3 멱등

- 같은 키 순차 재전송
- 같은 키 동시 전송
- 같은 키·다른 본문
- 만료 후 재사용

### 14.4 권한

- 역할·조직·장소 조합별 접근 행렬
- 권한 철회 후 기존 세션 요청
- 한시 역할 종료일 경계 앞뒤 1초 요청 (철회 행위 없이)
- 종료일이 지난 한시 역할로 발급된 기존 세션의 후속 요청
- 다른 고객·다른 파트너 리소스 직접 접근

### 14.5 오프라인

- 재전송 중복 방지
- 2기기 동일 인원 처리
- 2시간 초과 스냅숏
- 취소된 예약의 늦은 이벤트
- 권한 회수된 행위자의 이벤트

## 15. 학습 관점

Core API는 이 프로젝트에서 유일하게 기준선이 없는 신규 학습 영역이다. 00 §2.1이 정의한 대로, 프론트는 숙련 기술로 먼저 풀고 새 기술로 다시 푸는 구조지만 백엔드에는 "먼저 푼 답"이 없다.

따라서 진행 방식을 다르게 둔다.

- 명세와 스키마를 먼저 확정하고 구현 깊이는 나중에 올린다. 명세가 흔들리면 네 프론트가 전부 흔들린다.
- 동시성 심화는 프론트가 돌아간 뒤에 한다. 서버를 조였을 때 화면에서 무엇이 깨지는지를 관찰하는 것이 학습 경로다.
- §12의 보완책 네 가지를 형식이 아니라 게이트로 쓴다. 특히 "실패 우선 테스트"를 지키지 않으면 이 문서의 동시성 요구사항 전체가 통과한 것처럼 보이면서 실제로는 구현되지 않은 상태가 될 수 있다.

## 16. 출시 판단 기준

- CORE-AC-01 ~ 29가 실제 데이터베이스와 동시 요청 조건에서 통과한다.
- 순차 요청만으로 통과한 항목은 통과로 보지 않는다.
- 00 §8의 여덟 책임마다 "클라이언트가 판단하면 깨지는 시나리오"가 문서로 존재한다.
- 각 동시성 방어의 안전 근거가 격리 수준·락 종류와 함께 ADR에 기록되어 있다.
- `@Transactional`의 롤백 규칙이 ADR에 명시되어 있고 체크 예외 경로에서 롤백이 일어나는지 테스트로 확인했다.
- 네 프론트 구현이 같은 시드에서 같은 결과를 받는다.
- 모의 결제·학습용 정책·법률 미검증 범위가 문서에 표시되어 있다.
