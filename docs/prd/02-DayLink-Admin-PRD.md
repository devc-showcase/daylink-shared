# DayLink Admin PRD

| 항목 | 내용 |
|---|---|
| 문서 버전 | 2.2 |
| 기준일 | 2026-08-24 |
| 개정 사유 | (v2.1) IA 확인필요 7건 확정 반영 (결정 2·3·4·5·6) / **(v2.2) 회차 경로를 `slots`로 개명(ADR-0014), ADM-PTN-03·ADM-AC-05의 정원 축소 하한을 `06 §8.3`에 맞춰 정정** |
| 제품 | DayLink Admin |
| 대상 | 파트너, 현장 담당자, 사내 운영자 |
| 제품 경계 | B2C가 아닌 모든 업무 기능을 하나의 Admin에 통합 |
| 구현 전제 | 동일 PRD를 두 개의 기술 구현에 적용 |
| 기술 표기 | 없음. 구현 차이는 별도 학습 구현 가이드에서 관리 |

## 1. 제품 개요

DayLink Admin은 DayLink의 비고객 업무를 처리하는 하나의 웹 애플리케이션이다. 입점부터 상품 판매, 현장 운영, 고객지원, 환불, 정산, 감사까지 다룬다.

한 Admin 안에서 사용자의 조직·역할·장소 권한에 따라 필요한 메뉴만 제공한다. 파트너센터, 운영자센터, 현장 데스크를 서로 다른 제품으로 만들지 않는다.

### 1.1 해결할 문제

- 파트너가 상품 심사 상태, 예약 현황, 정산 근거를 한 흐름에서 확인하기 어렵다.
- 현장 담당자는 네트워크 불안정 상황에서도 빠르게 참가자를 확인해야 한다.
- 사내 운영자는 예약·결제·환불·정산 상태가 엇갈릴 때 근거를 추적해야 한다.
- 역할마다 보는 개인정보 범위와 실행 가능한 조치가 달라 권한 오류 위험이 크다.

### 1.2 제품 목표

1. 상품 등록부터 판매·현장·정산까지 하나의 업무 흐름으로 연결한다.
2. 사용자에게 필요한 모듈만 노출하고 API에서도 동일한 권한을 강제한다.
3. 대량 표, 복합 폼, 상태 전이, 파일 작업, 오프라인 동기화를 실무 수준으로 다룬다.
4. 위험한 조작은 근거·사유·변경 전후 값을 남긴다.
5. 두 구현이 같은 업무 결과를 내도록 한다.

### 1.3 범위 밖

- 고객용 검색·예약 화면
- 실제 사업자 진위 조회·계약 전자서명
- 실제 계좌 송금과 세금계산서 발행
- 콜센터 전화 시스템, 실시간 상담 채팅
- 물리 출입 장치·전용 QR 리더 연동
- 마이크로 프론트엔드와 조직별 별도 배포

## 2. 하나의 Admin과 모듈 경계

| 모듈 | 사용자 | 핵심 업무 |
|---|---|---|
| 공통 | 모든 Admin 사용자 | 로그인, 조직·장소 선택, 알림, 내 계정 |
| 파트너 운영 | 파트너 관리자·실무자 | 입점, 상품, 회차, 예약, 참가자, 정산 |
| 현장 운영 | 현장 담당자·파트너 관리자 | 당일 회차, 명단, QR·수동 체크인, 사고 |
| 플랫폼 운영 | CS·심사·정산·시스템 관리자 | 심사, 고객지원, 환불, 대사, 정책, 감사 |

모듈은 메뉴와 권한의 구분이지 별도 사이트가 아니다. 로그인, 디자인 체계, API 규칙, 알림, 감사, 오류 처리는 공유한다.

## 3. 역할과 권한

### 3.1 역할 정의

| 역할 코드 | 역할 | 데이터 범위 |
|---|---|---|
| `PARTNER_OWNER` | 파트너 관리자 | 소속 파트너 전체 |
| `PARTNER_EDITOR` | 파트너 상품 담당 | 허용된 상품·장소 |
| `VENUE_STAFF` | 현장 담당자 | 배정된 장소·당일 회차 |
| `OPS_REVIEWER` | 입점·상품 심사자 | 심사 대상과 관련 이력 |
| `OPS_CS` | 고객지원 담당 | 고객·예약·환불 업무 범위 |
| `OPS_FINANCE` | 정산 담당 | 거래·정산·대사 데이터 |
| `OPS_ADMIN` | 시스템 관리자 | 계정·역할·감사·운영 설정 |
| `READ_ONLY_AUDITOR` | 감사 열람자 | 승인된 읽기 전용 범위. **기간·사유·승인자를 갖고 만료된다** |

### 3.2 권한 원칙

- 사용자는 로그인 후 사용할 조직과 역할을 선택한다. 하나뿐이면 자동 선택한다.
- 일반 계정에 파트너 역할과 사내 운영 역할을 동시에 부여하지 않는다.
- 현장 담당자는 예약자의 체크인에 필요한 최소 정보만 조회한다.
- 권한은 메뉴, 화면, 버튼, API, 내보내기에서 모두 확인한다.
- 권한 변경과 강제 로그아웃은 지연 없이 반영한다.
- 고위험 권한 부여는 실행자와 승인자를 분리한다.
- `READ_ONLY_AUDITOR`는 상시 역할이 아니라 한시 역할이다. 부여 시 범위·시작일·종료일·사유·승인자를 함께 기록한다. 별도 철회가 없어도 종료일이 지나면 요청을 거부한다.

### 3.3 주요 행위 권한표

| 행위 | 파트너 관리자 | 상품 담당 | 현장 담당 | 심사자 | CS | 정산 | 시스템 관리자 | 감사 열람자 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| 상품 작성 | O | 범위 내 | - | - | - | - | - | - |
| 상품 심사 제출 | O | 범위 내 | - | - | - | - | - | - |
| 상품 승인·반려 | - | - | - | O | - | - | - | - |
| 회차·재고 관리 | O | 범위 내 | 열람 | - | 열람 | - | - | 승인 범위 열람 |
| 참가자 열람 | O | 범위 내 | 최소 정보 | - | 업무상 열람 | - | - | 승인 범위 열람 |
| 체크인 | O | 범위 내 | O | - | 정정 요청 | - | - | 승인 범위 열람 |
| 고객 취소·환불 | 요청·열람 | 열람 | - | - | O | 열람 | 긴급 권한 | 승인 범위 열람 |
| 정산 대사·확정 | 열람 | 제한 열람 | - | - | 열람 | O | - | 승인 범위 열람 |
| 쿠폰 관리 | - | - | - | - | - | 열람 | O | 승인 범위 열람 |
| 콘텐츠 관리 | - | - | - | - | - | - | O | 승인 범위 열람 |
| 계정·역할 관리 | 소속 조직 | - | - | - | - | - | O | - |
| 감사 로그 | 소속 제한 | - | - | 제한 | 제한 | 재무 범위 | O | 승인 범위 |

`감사 열람자`(`READ_ONLY_AUDITOR`)는 어떤 행위에서도 쓰기를 수행하지 않는다. '승인 범위 열람'은 부여 시 지정한 조직·장소·기간 안에서만 읽을 수 있다. 범위 밖 데이터는 존재 여부도 노출하지 않는다.

`00 §6.3`은 플랫폼 쿠폰 비용을 파트너 정산액에서 차감하지 않는다고 정했다. '쿠폰 관리'에서 정산 담당에게 열람을 주는 이유다. 할인액 전체가 플랫폼 부담이므로 정산 담당이 그 금액을 대사해야 한다. 생성·수정은 `§3.2`의 실행자·승인자 분리 원칙에 따라 정산 담당에게 주지 않는다.

## 5. 공통 기능 요구사항

### ADM-COM-01 인증·세션

- Admin 전용 인증을 사용하고 B2C 세션으로 자동 진입시키지 않는다.
- 사내 고위험 역할은 추가 인증을 요구한다.
- 세션 만료 시 입력 내용을 안전하게 임시 보존하고 로그인 후 복구 여부를 묻는다.
- 권한 철회·계정 정지 시 활성 세션을 종료한다.

### ADM-COM-02 역할·업무 문맥

- 현재 조직, 역할, 장소를 상단에 명확히 표시한다.
- 문맥 전환 시 저장하지 않은 변경 사항과 진행 중 작업을 확인한다.
- URL 직접 접근에서도 현재 문맥과 대상 리소스 권한을 다시 검사한다.

### ADM-COM-03 알림

- 심사 결과, 회차 임박, 취소·환불, 동기화 충돌, 정산 차이를 역할에 맞게 제공한다.
- 읽음 처리는 알림 원인의 업무 상태를 바꾸지 않는다.
- 알림에서 이동한 상세 화면이 권한 밖이면 내용을 노출하지 않는다.

### ADM-COM-04 비동기 작업

- 대량 내보내기·파일 생성·대사 작업은 백그라운드 작업으로 처리한다.
- 작업 상태는 대기, 진행, 완료, 일부 실패, 실패, 만료로 구분한다.
- 완료 파일은 권한과 만료 시간을 적용하고 다운로드를 기록한다.

## 6. 파트너 운영 요구사항

### ADM-PTN-01 입점

- 사업자 기본 정보, 담당자, 정산 정보, 장소, 필수 서류를 단계별로 입력한다.
- 단계 저장과 이어쓰기를 지원한다.
- 제출 이후 심사 중에는 심사 대상 필드를 잠그고 반려 시 사유별로 수정할 수 있게 한다.
- 민감한 계좌 정보는 마스킹하고 권한 있는 사용자만 수정한다.

### ADM-PTN-02 상품 작성·심사

- 기본 정보, 설명, 이미지, 장소, 소요 시간, 가격, 인원, 준비물, 취소 정책을 작성한다.
- 임시 저장, 유효성 검사, 고객 화면과 유사한 미리보기를 제공한다.
- 신규 작성은 `/partner/experiences/new`로 진입한다. 첫 저장 시 식별자를 발급해 `/partner/experiences/{id}`로 교체한다. 진입만으로 상품 행을 생성하지 않는다.
- 제출 시 변경본 스냅숏을 만들고 심사 결과와 의견을 이력으로 남긴다.
- 반려된 필드는 사유와 함께 강조하되 다른 입력을 잃지 않는다.
- 승인 이후 공개 정보 변경이 재심사 대상인지 필드별 정책으로 결정한다.

### ADM-PTN-03 회차·재고

- 단일 회차와 반복 회차를 생성할 수 있다.
- 정원은 확정 예약 인원과 활성 임시 확보 인원의 합보다 작게 줄일 수 없다. 판정 기준은 `06 §8.3`이다.
- 이미 예약된 회차의 시간·장소 변경은 영향받는 예약 수와 알림 필요성을 확인한다.
- 회차 취소는 사유를 입력하고 고객 전액 환불 업무를 생성한다.

### ADM-PTN-04 예약·참가자

- 예약 상태, 결제 상태, 환불 상태, 출석 상태를 별도 열로 표시한다.
- 파트너는 고객의 결제 수단 상세와 불필요한 개인정보를 볼 수 없다.
- 참가자 내보내기는 목적, 범위, 보관 주의 문구를 확인한 뒤 백그라운드로 생성한다.

### ADM-PTN-05 정산

- 상품 총액, 플랫폼 할인, 수수료, 취소·환불 조정, 파트너 정산액을 구분한다.
- 정산 상세의 합계는 거래 원장 합계와 일치해야 한다.
- 파트너는 이의를 제출할 수 있지만 원장을 직접 수정할 수 없다.

### ADM-PTN-06 팀 관리

- 파트너 관리자는 사용자를 초대하고 상품·장소 범위를 지정한다.
- 마지막 파트너 관리자 권한은 제거할 수 없다.
- 초대 만료, 재발송, 회수 상태를 제공한다.

## 7. 현장 운영 요구사항

### ADM-DSK-01 오늘의 회차

- 현재 장소의 오늘 회차를 시작 시간순으로 표시한다.
- 회차별 예약 인원, 체크인 인원, 미체크인 인원, 취소 변동을 요약한다.
- 모바일 화면과 터치 조작을 우선한다.

### ADM-DSK-02 체크인

- QR 토큰 또는 예약 번호·이름 뒤 일부로 참가자를 찾는다.
- 체크인 전 상품, 회차, 예약 상태, 인원, 이미 처리된 수를 확인한다.
- 전체 또는 일부 인원을 체크인할 수 있다.
- 동일 인원의 중복 체크인은 같은 결과를 반환하고 중복 출석을 만들지 않는다.
- 수동 처리와 정정은 사유를 남긴다.

### ADM-DSK-03 오프라인 모드

- 현장 담당자가 명시적으로 회차를 내려받아 최소 명단 스냅숏을 저장한다.
- 저장 데이터는 예약 식별자, 표시용 최소 이름, 인원, 토큰 해시, 마지막 동기화 시각으로 제한한다.
- 회차 시작 30분 전에 동기화를 시도한다. 입장 준비를 시작하는 시점이라, 이때 받아 두면 회차가 끝날 때까지 `06 §11.1`의 2시간 안에 들어온다.
- 마지막 동기화 후 2시간을 넘긴 스냅숏은 오프라인 체크인을 승인하지 않고 관리자 연락 절차를 안내한다.
- 오프라인 이벤트는 `clientEventId`를 사용하고 네트워크 복구 시 순서대로 전송한다.
- 오프라인 처리 결과는 서버 확인 전까지 “임시 처리”로 표시한다.

### ADM-DSK-04 충돌 해결

- 같은 예약을 여러 기기에서 처리한 경우 서버 기록, 로컬 이벤트, 처리 시각, 담당자를 비교한다.
- 자동 병합할 수 없는 인원·취소 충돌은 권한 있는 사용자에게 보낸다.
- 해결 결과는 원본 이벤트를 삭제하지 않고 보정 이벤트로 남긴다.

### ADM-DSK-05 사고 보고

- 회차, 예약, 유형, 심각도, 설명, 발생 시각, 선택 이미지를 입력한다.
- 심각 사고는 제출과 동시에 사내 운영 알림을 생성한다.
- 현장 담당자는 제출 후 원문을 임의로 삭제하지 못하고 추가 메모만 남긴다.
- 추가 메모는 사고 상세 화면(`/desk/incidents/{id}`)에서 남기며 원문과 메모는 각각 별도 항목으로 보존한다.
- 제출한 사고를 나중에 다시 찾을 수 있도록 사고 목록(`/desk/incidents`)을 제공한다. 범위는 배정 장소이며 상태·기간·회차로 필터링한다. 목록이 없으면 제출 직후와 알림으로만 접근할 수 있어 교대가 바뀌거나 알림을 읽음 처리한 뒤에는 추가 메모를 남길 경로가 사라진다.
- 현장 담당자는 배정 장소에서 발생한 사고만 조회한다. 사내 운영용 사고 상세(`/ops/incidents/{id}`)에는 접근하지 않는다.

## 8. 플랫폼 운영 요구사항

### ADM-OPS-01 심사

- 파트너·상품 심사 대기열은 상태, 경과 시간, 위험 표지, 담당자로 필터링한다.
- 승인·반려 전 체크리스트와 사유를 입력한다.
- 심사자는 자신이 작성한 파트너 계정이나 이해 충돌 대상의 승인 권한을 갖지 않는다.
- 반려 후 재제출은 새 심사 차수로 남긴다.

### ADM-OPS-02 고객·예약 지원

- 고객 검색은 정확한 이메일·전화·예약 번호를 우선하고 과도한 전체 검색을 제한한다.
- 고객 상세 진입과 개인정보 조회는 사유와 함께 기록한다.
- 예약 상세는 상태별 타임라인, 가격·정책 스냅숏, 결제·환불·체크인을 함께 보여주되 상태를 합치지 않는다.

### ADM-OPS-03 취소·환불

- 시스템이 계산한 정책 환불액과 운영자가 변경한 예외 금액을 구분한다.
- 예외 환불은 사유, 증빙, 허용 한도, 필요 승인자를 확인한다.
- 환불 요청과 실제 처리 결과를 분리한다.
- 실패한 환불은 재시도 전에 외부 처리 여부를 조회해 중복 환불을 막는다.

### ADM-OPS-04 사고

- 현장 사고, 고객 문의, 관련 예약·회차, 담당자, 조치 내역을 타임라인으로 관리한다.
- 심각도 변경과 종결에는 사유가 필요하다.
- 종결 후 수정은 추가 이력으로 남긴다.

### ADM-OPS-05 정산 대사

- 예약·결제·환불·수수료·파트너 정산 원장을 기준별로 대조한다.
- 차이는 누락, 중복, 금액 불일치, 상태 불일치로 분류한다.
- 원장 항목은 직접 덮어쓰지 않고 조정 항목을 추가한다.
- 정산 확정과 재개방은 서로 다른 권한과 승인 절차를 사용한다.
- 정산 목록(`/ops/settlements`)은 기간별 정산 상태를 담당한다. 대사(`/ops/reconciliation`)는 차이 분석을, 상세(`/ops/settlements/{id}`)는 결재를 담당한다.

### ADM-OPS-06 콘텐츠·쿠폰

- 공개 기간, 대상, 우선순위, 상태를 관리한다.
- 쿠폰은 총 예산, 1인 한도, 유효 기간, 대상 상품, 중복 규칙을 가진다.
- 이미 사용된 쿠폰의 핵심 조건을 소급 변경하지 않는다.

### ADM-OPS-07 접근 제어·감사

- 역할 부여는 대상, 범위, 시작·종료일, 사유, 승인자를 기록한다.
- 감사 로그는 일반 화면에서 수정·삭제할 수 없다.
- 조회는 행위자, 대상, 이벤트, 기간, 추적 ID로 필터링한다.
- 민감 데이터 내보내기와 권한 변경은 높은 우선순위로 표시한다.

## 9. 공통 화면설계 기준

### 9.1 레이아웃·내비게이션

- 데스크톱은 좌측 메뉴, 상단 업무 문맥, 본문 구조를 기본으로 한다.
- 현장 모듈은 같은 애플리케이션 안에서 모바일 우선 레이아웃을 사용한다.
- 현재 역할·조직·장소와 운영 환경을 항상 식별할 수 있게 한다.
- 권한이 없는 메뉴는 숨기되 URL 접근 시 접근 거부 화면을 제공한다.

### 9.2 표·검색·필터

- 표는 정렬, 필터, 페이지, 열 표시 설정을 URL 또는 저장된 보기로 복구한다.
- 일괄 처리는 선택 항목 대상과 전체 검색 결과 대상을 구분한다.
- 대량 데이터는 클라이언트 전체 적재를 전제로 하지 않는다.
- 개인정보 열은 기본 마스킹하며 열람 권한과 목적 확인 후 표시한다.
- 행 선택과 상세 이동 조작이 충돌하지 않게 한다.

### 9.3 폼·임시 저장

- 필수 항목과 제출 조건을 화면 진입 시 알 수 있게 한다.
- 복합 폼은 단계 이동 전에 저장 상태와 오류 수를 표시한다.
- 화면 이탈·역할 전환 전에 저장하지 않은 변경을 경고한다.
- 동시 수정 충돌 시 최신 서버본과 사용자 변경을 비교하고 덮어쓰기를 강요하지 않는다.

### 9.4 저장·승인·삭제

- 저장, 제출, 승인, 공개는 서로 다른 상태 전이와 버튼으로 구분한다.
- 승인·환불·정산 확정·권한 변경은 대상과 영향을 재확인한다.
- 업무 이력이 있는 데이터는 물리 삭제 대신 비활성·보관 처리한다.
- 고위험 조작은 사유를 필수로 하고 결과의 감사 로그 ID를 제공한다.

### 9.5 로딩·빈 결과·오류

| 상태 | 표시 원칙 |
|---|---|
| 목록 최초 로딩 | 열 구조가 유지되는 자리 표시 또는 진행 표시 |
| 필터 갱신 | 기존 목록과 갱신 중 상태를 구분 |
| 빈 결과 | 권한 없음·데이터 없음·검색 결과 없음을 구분 |
| 저장 오류 | 항목 오류와 시스템 오류를 구분하고 안전한 입력 보존 |
| 세션 만료 | 로그인 복귀와 초안 복원 가능 여부 안내 |
| 동시 수정 | 최신 값, 내 변경, 충돌 필드를 비교 |
| 작업 결과 불명 | 재실행 전에 서버 작업 상태 조회 |

### 9.6 팝업·드로어

- 빠른 확인은 드로어, 복잡한 업무는 별도 상세 화면을 사용한다.
- 긴 폼이나 다단계 결재를 작은 팝업에 넣지 않는다.
- 팝업을 닫으면 원래 초점으로 돌아간다.
- 위험한 조치의 확인창에는 대상, 금액·인원 영향, 되돌림 가능 여부를 적는다.

### 9.7 메시지·유효성

- 내부 API 오류 코드만 노출하지 않는다.
- 권한 오류는 권한 요청 경로가 있을 때만 안내한다.
- 금액·상태 변경 메시지는 처리 기준 시각과 업무 식별자를 포함한다.
- 성공 알림만 띄우고 실제 목록 상태가 갱신되지 않는 상황을 허용하지 않는다.

## 10. 데이터·보안 요구사항

- 모든 변경 API는 멱등 식별자와 행위자 문맥을 사용한다.
- 서버가 조직·역할·리소스 범위를 다시 확인한다.
- 한시 역할은 유효 기간을 함께 확인한다. 별도 철회가 없어도 종료일이 지난 권한으로는 요청을 처리하지 않는다.
- 고객 예약 문의는 예약 상세(`/ops/bookings/{id}`)의 인라인 스레드에서 조회·답변한다. 별도 문의 **상세** 화면은 두지 않는다.
- 미답변 문의를 찾는 대기열(`/ops/inquiries`)을 제공한다. 상태(`RECEIVED`·`IN_PROGRESS`·`ANSWERED`·`CLOSED`)·경과 시간·담당자로 필터링한다. 행을 열면 해당 예약 상세의 문의 스레드로 이동한다. 환불 대기열(`/ops/refunds`)과 같은 패턴이다.
- 대기열 없이 알림에만 의존하면 알림을 읽음 처리한 뒤 미답변 문의를 다시 찾을 수 없다. 읽음 처리는 §5 ADM-COM-03에 따라 업무 상태를 바꾸지 않으므로 업무 상태 기준의 진입점이 따로 필요하다.
- 개인정보 열람과 CSV 내보내기는 목적, 사용자, 시각, 대상 범위를 기록한다.
- 파일 업로드는 형식·크기·악성 파일 검사를 거친다.
- 현장 오프라인 데이터는 만료 후 제거하고 장기 저장하지 않는다.
- 비밀번호, 전체 인증 토큰, 결제 인증값은 로그에 남기지 않는다.
- 운영 환경의 위험 조작은 테스트 환경과 시각적으로 구분한다.

## 11. 분석·운영 지표

| 지표 | 정의 |
|---|---|
| 심사 처리 시간 | 제출부터 승인·반려까지 |
| 상품 재작업률 | 반려 후 재제출 비율 |
| 체크인 처리 시간 | 스캔부터 결과 확정까지 |
| 오프라인 충돌률 | 동기화 이벤트 중 수동 해결 비율 |
| 환불 처리 시간 | 요청부터 성공·실패 확정까지 |
| 정산 차이율 | 대사 대상 중 불일치 항목 비율 |
| 권한 거부율 | 화면·API 접근 거부 건수 |
| 구현 동등성 | 공통 Admin E2E 통과율 |

이벤트 이름과 속성은 두 구현에서 같고 구현 식별자만 다르게 기록한다.

| ID | 조건 |

| ADM-AC-02 | 숨겨진 메뉴 URL에 직접 접근해도 API가 권한을 거부한다. |

| ADM-AC-05 | 확정 예약 인원과 활성 임시 확보 인원의 합보다 작게 회차 정원을 줄일 수 없다. |
| ADM-AC-06 | 파트너의 회차 취소가 고객 전액 환불 업무와 연결된다. |

| ADM-AC-08 | 오프라인 체크인을 반복 전송해도 출석이 중복되지 않는다. |

| ADM-AC-10 | 다중 기기 체크인 충돌은 원본 이벤트를 보존한 채 해결된다. |
| ADM-AC-11 | 예약·결제·환불·출석 상태가 별도로 조회된다. |

| ADM-AC-16 | 같은 시드 데이터와 요청에서 두 구현의 결과가 일치한다. |

## 13. 대표 E2E 시나리오

1. 파트너 입점 작성 → 제출 → 운영자 반려 → 보완 → 승인
2. 상품 임시 저장 → 미리보기 → 심사 제출 → 승인 → 공개
3. 반복 회차 생성 → 예약 발생 → 정원 축소 제한 → 회차 취소와 환불 업무 생성
4. 파트너 예약 조회 → 참가자 파일 비동기 생성 → 권한·만료 적용 다운로드
5. 현장 명단 동기화 → 오프라인 QR 체크인 → 네트워크 복구 → 중복 없는 서버 반영
6. 두 기기의 같은 예약 체크인 → 충돌 대기열 → 보정 이벤트로 해결
7. CS 예약 조회 → 정책 환불액 확인 → 예외 승인 → 환불 실패 후 안전한 재처리
8. 정산 대사 → 금액 차이 발견 → 조정 항목 → 승인 → 파트너 정산 상세 반영
9. 시스템 관리자의 역할 부여 → 대상 사용자 세션 갱신 → 감사 로그 조회
10. 권한 없는 사용자의 직접 URL·API 접근 → 데이터 미노출

## 14. 출시 판단 기준

- 모든 역할의 업무가 두 구현에서 동일하게 완료되어야 한다. 판정은 인수조건 16개(ADM-AC-01~16)로 한다.
- 공통 화면 목록·요구사항 ID·API 명세·테스트 시나리오를 사용해야 한다.
- 파트너·현장·사내 운영 모듈을 구현 편의 때문에 별도 제품으로 분리하지 않는다.
- 권한, 금액, 상태 전이를 클라이언트만으로 판단하지 않는다.
- 오프라인 체크인의 잔여 위험과 실제 결제·법률 미검증 범위를 운영 문서에 표시한다.
