## 0. 시작 전 — PRD와의 충돌 3건

규칙 1에 따라 본 커리큘럼이 PRD와 충돌하는 지점을 먼저 명시한다. 충돌하는 곳에서는 PRD를 따르되, 아래 형태로 PRD에 **범위 단계(Phase) 열을 추가**하는 방식으로 해소한다. PRD의 요구 자체를 삭제하지 않는다.

| # | 충돌 지점 | PRD 문언 | 본 커리큘럼 | 해소 방식 |
|---|---|---|---|---|
| C1 | 화면 목록 축소 | 01 §4.2 "화면 경로는 제품 요구사항이다" / 02 §14 "공통 화면 목록·요구사항 ID를 사용해야 한다" | 49개 화면만 구현하고 30개는 보류 | 화면을 **삭제하지 않고** IA v2.0에 `범위=Phase1 / Phase2` 열을 추가한다. Phase2는 미구현이며 "PRD에 없는 화면"이 되는 것이 아니다. 두 구현이 **동일하게** Phase1만 만들므로 00 §9 동등성은 유지된다. |
| C2 | Core API 구현 시점 | 05 §12 조건 3 "같은 Core API와 공통 인수 테스트를 **먼저 준비**한다" | M1에서 얇은 Core API, M3에서 동시성·멱등·원장 심화 | "먼저 준비"를 **계약(OpenAPI)과 인수 테스트 코드의 선작성**으로 해석한다. M1에서 스키마·오류 코드·멱등 헤더 규약·인수 테스트를 모두 확정하고, 구현 깊이만 미룬다. "먼저 준비"를 "먼저 완성"으로 읽으면 이는 충돌이며, 그 경우 PRD가 우선한다 — 다만 그 해석을 택하면 M1이 390시간이 되고 프론트 첫 화면이 5개월 뒤로 밀린다. |
| C3 | Admin 구현 순서 | 04 §9 권장 순서에서 현장(7)·오프라인(8)이 예약·환불·정산(5)·내보내기(6)보다 뒤 | 7·8을 5·6보다 앞으로 이동 | 04 §9는 "**권장** 구현 순서"이며 준수 의무 문언이 없다. 반면 05 §11.3은 오프라인 스냅숏 만료·재전송·다중기기 충돌을 "구현 전 필수 테스트"로 지정한다. 필수 항목을 예산 소진 시 잘리는 마지막 자리에 두지 않는다. |

## 2. 현재 수준 진단

(a) 이미 가진 것 / (b) 없는 것 / (c) **잘못 알고 있을 가능성이 높은 것**.
(c)는 근거 없는 추측이 아니라, 각 기술의 2→3, 2→4 사이에서 **의미가 바뀐 API**만 지목했다.

### 2.1 React SPA — 심화 구간

| 구분 | 내용 |
|---|---|
| (a) 가진 것 | 컴포넌트·props·훅·라우팅, 기존 코드 유지보수 판단, JSX 안에서의 조건부·리스트 렌더링 |
| (b) 없는 것 | 서버 상태 캐시 도구의 **무효화 설계**(캐시 키 경계 = 업무 데이터 경계), 대용량 표 가상화와 접근성 병행, Error Boundary × Suspense × lazy 3자 조합, `useSyncExternalStore`, IndexedDB 구독을 UI에 연결하는 계층 |
| (c) 오해 가능 | ① `useEffect`를 파생 상태 계산에 사용 — 04 §5 마지막 문단이 명시적으로 금지(외부 시스템 동기화 전용) ② `useMemo`/`useCallback`을 측정 없이 관성으로 적용 — 04 §6.2 비교 질문이 "적용 전후 실제 측정값이 개선됐는가"를 요구 ③ Context를 서버 상태 저장소로 사용해 원본을 이중화 — 04 §4가 "서버 응답을 전역 저장소에 다시 복사해 두 개의 원본을 만들지 않는다"로 금지 |

### 2.2 Next.js — 심화 구간 (App·Pages 둘 다 경험)

둘 다 써봤다는 사실은 학습 부담을 낮추지만, **두 라우터의 데이터 모델이 다르다는 점 때문에 특정 오해를 오히려 강화**한다.

| 구분 | 내용 |
|---|---|
| (a) 가진 것 | 파일 기반 라우팅, 두 라우터의 데이터 로딩 진입점, 배포 출력 형태, 마이그레이션 상황 경험 |
| (b) 없는 것 | 데이터 캐시와 라우터 캐시의 **계층 분리**를 근거로 설명하기, `revalidateTag`의 실제 무효화 도달 범위, 03 §4.1이 요구하는 "상품 정보와 재고 갱신 주기 분리"를 캐시 태그로 표현하기 |
| (c) 오해 가능 | ① **"SSR이니까 매 요청 새 데이터"** — Pages Router의 `getServerSideProps` 직관. App Router에서는 서버 컴포넌트의 `fetch`가 요청 메모화와 데이터 캐시라는 **별개 계층**을 지나므로 이 직관이 틀린다 ② **`"use client"`가 "이 컴포넌트만 클라이언트"** — 실제로는 그 지점부터 import 그래프 아래 전체가 클라이언트 번들 진입점이 된다. 03 §6.3이 "큰 라이브러리가 초기 번들에 포함되지 않게 한다"를 과제로 둔 이유 ③ **fetch 기본 캐시 동작의 버전 의존성** — Next는 버전에 따라 기본값이 바뀌어 왔다. 03 §12 마지막 문장이 "버전 표기와 기능 상태는 구현 시작 시 다시 확인하고 잠금 파일로 고정"을 요구하는 것이 이 지점이다. 기억에 남은 기본값을 그대로 쓰면 안 된다 ④ Route Handler와 Server Action의 책임 구분 |

### 2.3 Vue 3 — **새 기술 구간 + negative transfer 최대 위험**

Vue 2 경험은 여기서 자산이 아니라 **부채**로 작동할 수 있다. 아래 (c) 12항목이 이 프로젝트의 최대 오답 후보다.

| 구분 | 내용 |
|---|---|
| (a) 가진 것 | 템플릿 문법의 큰 틀(`v-if`/`v-for`/`v-bind`/`v-on`), SFC 파일 구조, props·이벤트로 내려주고 올리는 설계 감각, 반응성이라는 개념 자체 |
| (b) 없는 것 | Composition API 전체(`ref`/`reactive`/`computed`/`watch`/composable), `provide`·`inject`, Pinia, Teleport·Suspense·비동기 컴포넌트, 반응성 추적 범위를 개발 도구로 확인하는 방법, TypeScript와 결합된 `defineProps`/`defineEmits` |
| (c) **잘못 알 가능성 (12항목)** | ① `reactive()` 객체를 구조분해하면 반응성이 끊긴다 — Vue 2 `data`에는 이 함정 자체가 없었다 ② `ref`의 `.value`는 템플릿에서 자동 언랩되지만 스크립트에서는 아니다 — `this.x`의 일관성이 사라졌다 ③ `Vue.set`/`this.$set` 습관 — Vue 3는 Proxy라 불필요하지만, **반대로 Proxy 감지 범위를 과신**하는 역방향 오류가 새로 생긴다 ④ `watch`를 "값 바뀌면 뭐든 처리"로 사용 — 04 §5가 명시적으로 금지하고 `computed`를 우선하라고 요구한다. Vue 2 시절 습관이 그대로 넘어오는 1순위 항목 ⑤ 이벤트 버스(`new Vue()` 인스턴스의 `$on`/`$emit`)가 제거됐다 ⑥ `filters` 제거 ⑦ `v-model` 계약 변경: `value`/`input` → `modelValue`/`update:modelValue`, 다중 `v-model` 가능 ⑧ `.sync` 제거 → `v-model:arg` ⑨ 다중 루트(프래그먼트) 허용 → 루트 속성 자동 상속(`inheritAttrs`) 동작이 달라진다 ⑩ 생명주기 이름 변경(`beforeDestroy`→`beforeUnmount`, `destroyed`→`unmounted`) ⑪ Vuex의 `mutations` 개념이 Pinia에는 없다 ⑫ 스코프 슬롯 문법 통합(`slot-scope` → `v-slot`) |

### 2.4 Nuxt 4 — 새 기술 구간

| 구분 | 내용 |
|---|---|
| (a) 가진 것 | Nuxt 2의 파일 기반 라우팅·레이아웃 개념, universal rendering이라는 개념, 배포해본 경험 |
| (b) 없는 것 | `useFetch`/`useAsyncData`의 키·중복 요청·서버→클라 페이로드 전달, `routeRules`와 hybrid rendering, Nitro server routes, `useSeoMeta`, `useNuxtApp`, Nitro preset별 배포 출력 |
| (c) 오해 가능 | ① **디렉터리 구조** — Nuxt 4는 `app/` 하위가 기본 소스 루트다. Nuxt 2의 루트 `pages/`·`layouts/` 배치를 그대로 가정하면 시작부터 막힌다 ② `asyncData`/`fetch`(Options) → 컴포저블 전환. 단순 이름 변경이 아니라 **키 관리와 중복 요청 제어라는 새 책임**이 생겼다 ③ 내장 Vuex `store/` 디렉터리가 사라졌다 ④ `mode: 'universal' \| 'spa'` 전역 스위치 → **경로별** `routeRules`. 03 §4 표가 요구하는 "경로군마다 다른 렌더링"이 Nuxt 2 방식으로는 표현되지 않는다 ⑤ Connect 기반 serverMiddleware → Nitro `defineEventHandler` ⑥ `@nuxtjs/axios` → `$fetch` ⑦ `head()` 옵션 → `useHead`/`useSeoMeta` ⑧ 플러그인 시그니처 `(context, inject)` → `defineNuxtPlugin`, `this.$nuxt`/`context` → `useNuxtApp()` ⑨ `nuxt build && nuxt start` → Nitro preset 선택 |

### 2.5 백엔드 — **제로 베이스 구간** (확정 답: 프론트에서 API 호출만)

| 구분 | 내용 |
|---|---|
| (a) 가진 것 | TypeScript, HTTP 의미론, JSON 계약을 소비해본 경험(계약 설계에 실제로 유효한 자산), 비동기 처리, 오류를 사용자 행동으로 번역해본 경험. 00 §8의 "클라이언트가 계산한 값을 신뢰하지 않는다"를 **당한 쪽 관점에서** 이해하고 있다 |
| (b) 없는 것 | 관계형 스키마 설계, 인덱스, SQL, 트랜잭션 경계, 격리 수준(READ COMMITTED / REPEATABLE READ / SERIALIZABLE)과 각각에서 발생하는 이상 현상, 비관적·낙관적 락, 데드락, 마이그레이션 운영, 커넥션 풀, 백그라운드 작업·큐, 서버 로깅·추적 ID, 부하·동시성 테스트 하네스 |
| (c) 오해 가능 | ① **"ORM을 쓰면 트랜잭션은 알아서 된다"** — ORM은 경계를 대신 정해주지 않는다 ② **"재고 확인 후 감소"를 `SELECT` → 검사 → `UPDATE` 두 문장으로 쓰면 원자적이라고 착각** — 00 §8의 "원자적 임시 확보"와 05 §5.2의 "마지막 좌석 경쟁"이 정확히 이 지점이다. 이 오해는 **테스트를 통과하면서 존재할 수 있다**(동시 요청을 안 보내면 안 드러난다) ③ **"멱등성 = 같은 요청 두 번 보내면 같은 응답"** 수준까지만 이해 — 진행 중 중복 요청, 부분 실패, 키 유효 기간, 응답 재현 저장이 빠진다 ④ **"취소 = 환불"** — 05 §5.5와 00 §7.4가 예약 상태와 환불 상태를 분리한 이유를 상태 기계로 설명하지 못한다 ⑤ **"원장 금액이 틀리면 고치면 된다"** — 00 §6.3과 05 §5.8의 불변 원장·조정 항목 원칙과 정면 충돌 ⑥ **낙관적 UI의 서버 투영** — 프론트 습관에서 오는 오류. 04 §6.4는 승인·환불·정산·권한 변경을 서버 확정 전 성공으로 표시하지 말라고 요구한다 |

### 3.3 Core API를 어디에 넣는가

**두 번에 나눠 넣는다.** 한 번에 넣지 않는 이유는 아래 표에 있다.

| 시점 | 넣는 것 | 넣지 않는 것 | 근거 |
|---|---|---|---|
| **M1 (앞)** | OpenAPI 계약 전체, 오류 코드, 멱등 헤더 규약, DB 스키마, 시드 데이터, 인수 테스트 코드(전부 실패 상태로), 단일 요청 기준 CRUD | 동시성 제어, 락, 원장, 감사 로그 | 05 §12 조건 3이 "같은 Core API와 공통 인수 테스트를 먼저 준비"를 요구한다. 계약은 반드시 앞이어야 두 구현이 갈라지지 않는다 |
| **M3 (중간)** | 원자적 재고 임시확보, 멱등 처리, 예약·결제·환불·정산 상태 전이, 불변 원장·조정 항목, 감사 로그, 체크인 충돌 판정 | | 00 §8 전 항목. B2C 2벌이 이미 돌아가는 상태에서 서버를 조이면, **프론트에서 무엇이 깨지는지를 직접 관찰**하게 된다. 이것이 D3의 학습 경로다 |

**Core API 전체를 M1에 몰아넣는 안을 기각한 이유:** 백엔드 제로 베이스에서 00 §8 전 항목은 약 280시간이다. 주 20시간이면 14주 동안 화면이 한 개도 나오지 않는다. 그리고 그 14주 동안 만든 설계를 검증할 프론트가 없어, 잘못된 설계를 **검증 없이 확정**하게 된다. 이는 05 §11.1의 "구현 전 필수 테스트"를 형식적으로만 통과시키는 결과가 된다.

## 6. 가장 비현실적인 가정 하나

> **"Core API는 내가 직접 실무 레벨로 만든다."**

지목 근거는 난이도가 아니라 **구조**다.

**1. 이 프로젝트에서 유일하게 절단 손잡이가 없는 항목이, 유일하게 경험이 0인 항목이다.**
§4에서 확인했듯이 화면은 158 → 98로 자를 수 있고 그것으로 340시간을 회수했다. 그런데 Core API는 자를 수 없다. 00 §5가 "구현마다 별도 백엔드를 만들어 결과가 달라지는 방식은 허용하지 않는다"고 못박았고, 00 §8이 요구하는 7개 책임 중 어느 하나를 빼도 인수조건이 무너진다 — 원자적 재고를 빼면 B2C-AC-04, 멱등을 빼면 AC-05·AC-10·ADM-AC-08, 불변 원장을 빼면 ADM-AC-13, 충돌 판정을 빼면 ADM-AC-10이 사라진다. 즉 **범위 조절이 불가능한 220~280시간짜리 블록이, 당신이 서버 코드를 한 번도 운영해본 적 없는 영역에 놓여 있다.**

**2. 단일 실패점이다.**
네 개의 프론트 구현이 전부 같은 Core API에 의존한다(00 §5 다이어그램). Core API가 멈추면 158화면이든 98화면이든 전부 멈춘다. 프론트 구현 4벌은 서로 독립적이라 한 벌이 늦어도 나머지가 진행되지만, Core API는 그렇지 않다.

**3. "실무 레벨"이라는 표현 자체가 검증 불가능하다.**
당신이 정한 성공 기준은 "왜 그렇게 설계했는지 설명할 수 있다"이다. 그런데 백엔드 설계는 **비교 대상이 없으면 자기 채점이 되지 않는다.** 프론트는 같은 요구를 두 기술로 만들어 서로를 채점하는 구조를 이미 갖췄다(00 §9, 05 §8). Core API에는 그 장치가 없다. 그래서 §2.5 (c)②의 오해 — `SELECT` 후 `UPDATE`를 원자적이라 믿는 것 — 는 **순차 테스트를 전부 통과하면서 1년 내내 살아남을 수 있다.** M3의 대비책(락을 빼면 테스트가 깨지는 것을 먼저 확인)을 넣은 이유가 이것이지만, 그 장치 하나로 백엔드 전 영역을 덮지는 못한다.

**무엇을 바꾸라는 것이 아니다.** Core API를 포기하면 이 프로젝트는 00 §8이 요구하는 학습의 절반을 잃는다. 다만 계획에서 **"부가적으로 백엔드도 만든다"로 취급되고 있다면 그 위치가 틀렸다.** 시간으로 보면 1,190시간 중 390시간(33%)이 백엔드이고, 위험으로 보면 100%가 백엔드에 걸려 있다. 이 프로젝트는 "프론트 4벌 비교 + 백엔드"가 아니라 **"백엔드 신규 학습 + 프론트 4벌 비교"** 순서로 불려야 하며, 마일스톤 명칭과 시간 배분도 그렇게 되어 있어야 한다.
