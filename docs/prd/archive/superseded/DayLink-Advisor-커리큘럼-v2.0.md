| # | 충돌 | PRD 문언 | 본 커리큘럼 | 해소 |
|---|---|---|---|---|

### 0.5 새로 발견한 긴장 1건 — 충돌은 아니나 규칙이 필요하다

00 §2.1은 "기준선으로 요구사항을 확정한 뒤 학습 대상으로 다시 푼다"를 규정하고, 03 §8 마지막 문단과 04 §9 마지막 문단은 "기능 묶음별로 두 구현을 번갈아 완료하라"고 한다. 제품 전체 단위로 읽으면 충돌하고, **기능 묶음 단위로 읽으면 양립한다.**

**판정: 기능 묶음 단위 교차를 채택한다.** 00 §2.1이 금지한 것은 "기준선 코드를 옆에 두고 옮기는 것"이지 묶음 단위 교차가 아니다. 03 §8이 경고하는 위험(한 기술을 전부 끝내면 기억과 요구사항이 달라짐)은 실재한다.

**대신 절차를 강제한다.** 묶음 하나를 기준선으로 완성 → 커밋 → **에디터에서 기준선 소스를 닫고** PRD와 화면 목록만 열어둔 상태로 학습 대상 구현 착수. 이 절차가 없으면 00 §2.1 규칙 1은 선언으로만 남는다.

## 2. 현재 수준 진단

(a) 가진 것 / (b) 없는 것 / (c) **잘못 알고 있을 가능성이 높은 것**. (c)는 추측이 아니라 **의미가 바뀐 API**와 **다른 실행 모델에서 오는 직관 오류**만 지목했다.

백엔드를 v1.0의 1개 항목에서 **3개(언어·프레임워크·영속성)로 분해**한다. 스택이 고정되면서 학습 대상이 셋으로 늘었기 때문이다.

| 구분 | 내용 |
|---|---|
| (a) | TypeScript 숙련. 정적 타입, 제네릭, 인터페이스, 널 안전(`strictNullChecks`), 함수형 컬렉션 조작, 빌드 도구 사용 경험이 **그대로 전이된다** |
| (b) | JVM 실행 모델, 빌드 도구(Gradle/Maven), 표준 라이브러리 관용구, 예외 체계, 컬렉션 프레임워크, 패키지·모듈 구조, JAR·클래스패스 |
| (c) | ① **`null` 처리** — TS의 `strictNullChecks`와 Kotlin의 널 안전은 비슷해 보이지만, Java 라이브러리 경계(플랫폼 타입)에서 무력화된다 ② **`equals`/`hashCode`** — TS에는 대응 개념이 없다. ### 2.6 Spring Boot — 신규 프레임워크 (기준선 없음). **최대 오답 구간**

| 구분 | 내용 |
|---|---|
| (a) | 의존성 주입이라는 개념 자체(Angular·NestJS 계열을 본 적 있다면), HTTP 라우팅·미들웨어 개념, 설정 파일 기반 구성 |
| (b) | 빈 생명주기와 스코프, 계층 분리(Controller·Service·Repository), `@Transactional` 전파·격리 속성, 전역 예외 처리, 검증(Bean Validation), Spring Security 인증·인가, 프로파일과 설정 외부화, Actuator |
| (c) **JS 개발자가 틀리는 지점** | ① **`@Transactional`은 프록시 기반이라 같은 클래스 내부 호출(self-invocation)에서는 동작하지 않는다.** 트랜잭션이 걸린 줄 알았는데 안 걸린 상태로 06 §8의 요구사항이 통과한 것처럼 보인다 ② **전파 속성**(`REQUIRED`/`REQUIRES_NEW`)을 모르면 중첩 서비스 호출에서 롤백 범위를 오판한다 ③ **롤백은 기본적으로 unchecked exception에서만 일어난다.** 예외를 잡아 로깅하고 삼키면 트랜잭션이 커밋된다 ④ **`readOnly = true`는 최적화 힌트이지 쓰기 차단 보장이 아니다**(DB·드라이버에 따라 다르다) ⑤ **"JS는 싱글 스레드라 경쟁 조건이 없다"는 직관이 통째로 무효다.** JVM 웹 서버는 요청마다 스레드를 쓴다. 싱글턴 빈에 가변 필드를 두면 요청 간 상태가 오염된다. **이것이 이 프로젝트 전체에서 가장 위험한 negative transfer다** ⑥ **커넥션 풀 크기가 실질적 동시성 상한**이다. Node에서 신경 쓰지 않던 값이 06 §14.2의 N=50 부하 테스트 결과를 좌우한다 ⑦ **`@Transactional(isolation = ...)`이 DB·드라이버에 따라 무시될 수 있다.** 06 §12 보완책 4가 "락을 걸었으니 안전하다"를 인정하지 않는 이유 |

| 구분 | 내용 |
|---|---|
| (a) | JSON 데이터 구조 조작, 비동기 처리, API 응답을 소비해본 경험 |
| (b) | 관계형 스키마 설계, 정규화, 인덱스, 실행 계획, 조인, 집계, 마이그레이션 운영(Flyway 등), 트랜잭션 경계, 격리 수준별 이상 현상(dirty read·non-repeatable read·phantom), 비관적·낙관적 락, 데드락, 커넥션 풀 |
| (c) | ① **"ORM을 쓰면 트랜잭션은 알아서 된다"** — ORM은 경계를 대신 정해주지 않는다 ② **`SELECT` → 애플리케이션 비교 → `UPDATE`가 원자적이라고 착각** — **06 §8.1이 이 패턴을 명시적으로 금지했다.** 순차 테스트를 전부 통과하면서 존재할 수 있다 ③ **JPA의 영속성 컨텍스트와 dirty checking** — "저장 호출을 안 했는데 `UPDATE`가 나간다". TS에 대응 개념이 없어 추적이 어렵다 ④ **flush 타이밍** — 언제 SQL이 나가는지 모르면 락 획득 순서를 통제할 수 없다 ⑤ **낙관적 락은 충돌을 막지 않고 감지만 한다** — 06 §8.6이 요구하는 것은 감지 후 **조용한 덮어쓰기 금지**이지 차단이 아니다 ⑥ **"원장 금액이 틀리면 고치면 된다"** — 06 §4.1이 `UPDATE`·`DELETE`를 데이터 계층에서 금지 |

### 3.5 영속성 계층 — **명시적 SQL 우선, JPA는 M3 후반** (PRD 미규정 항목)

06 §2는 "관계형 데이터베이스"만 정하고 접근 방식을 열어두었다. Advisor 판단을 제시한다.

| 단계 | 선택 | 근거 |
|---|---|---|
| M1~M3 전반 | **Spring JDBC 또는 MyBatis (명시적 SQL)** | 06 §8.1이 "조건부 갱신·행 잠금·제약 조건 중 하나로 **데이터베이스가 판정하게 하라**"를 요구한다. 명시적 SQL에서는 락과 조건이 코드에 그대로 보이므로 D9("어떤 격리 수준에서 안전한지 말할 수 있다")에 직접 도달한다 |
| M3 후반 | **JPA 도입, 낙관적 락(`@Version`)에 한정** | 06 §8.6이 요구하는 버전 기반 충돌 감지는 JPA의 정석 사용처다. 이 시점이면 §2.7 (c)③④(dirty checking·flush 타이밍)를 추적할 기반이 생긴다 |

**JPA를 처음부터 쓰지 않는 이유:** dirty checking과 flush 타이밍이 "언제 어떤 SQL이 나가는지"를 가린다. §2.7 (c)②의 오해 — `SELECT` 후 `UPDATE`가 원자적이라는 착각 — 를 가진 상태에서 JPA를 쓰면, 그 오해를 **관찰할 수 없는 형태로** 코드에 심게 된다. 06 §12가 지적한 "잘못된 설계가 테스트를 통과하며 살아남는" 구조가 여기서 가장 잘 작동한다.

**SI 실무 관점의 부수 효과:** 국내 SI 현장에서 MyBatis 비중이 낮지 않다. 명시적 SQL로 시작하는 것이 2순위 목적에도 어긋나지 않는다.

### 4.3 UI 완성도 하향 — 회수 120h

**03 §7.2가 근거를 직접 제공한다:**
> "화면 픽셀을 완전히 같게 만들기보다 정보 계층, 조작, 결과, 접근성의 동등성을 본다."

00 §9의 "반드시 동일" 목록에도 시각 완성도는 없다. 따라서 다음을 **네 구현 모두에서 동일하게** 낮춘다 — 한쪽만 낮추면 동등성이 깨진다.

| 낮추는 것 | 유지하는 것 | 근거 |
|---|---|---|
| 커스텀 디자인 시스템, 브랜드 비주얼, 일러스트 | 03 §3.1의 디자인 토큰 공유 | 04 §7.2 "거대 표·폼 생성기를 먼저 만들지 않는다" |
| 애니메이션·트랜지션·마이크로 인터랙션 | Teleport·Transition의 **개념 비교용 최소 1개소** | 04 §11 Vue 학습 범위 |
| 반응형 브레이크포인트 다단계 | 데스크톱 1종 + `/desk` 모바일 1종 | 02 §4.3이 현장 화면만 모바일로 지정 |
| 빈 상태·로딩 스켈레톤의 시각 정교화 | 03 §6.6의 오류·빈 결과·찾을 수 없음 **구분** | 인수조건이 구분을 요구하지 시각을 요구하지 않는다 |

**포트폴리오 공개와의 충돌:** 공개는 3순위 목적이다. UI 완성도가 필요하면 M5 이후 **B2C Next.js 1벌에만** 별도 시간을 배정한다. 그 시점에는 요구사항이 확정되어 있으므로 순수 시각 작업이 되고, 04 §10의 측정 결과를 오염시키지 않는다.

### 4.4 Core API 비동기 작업 축소 — 회수 40h

06 §3.1은 "비동기 작업(내보내기·집계)과 파일 만료"를 범위에 두고 CORE-AC-22가 이를 요구한다. 그러나 00 §12와 06 §3.2가 **메시지 브로커 전제의 이벤트 소싱·CQRS를 범위 밖**으로 두었다.

| 구현할 것 | 보류할 것 |
|---|---|
| `Job` 엔터티 상태 전이, 파일 생성, 만료 시각, 권한·목적·시각·범위 기록 (CORE-AC-22 전부) | 전용 워커 프로세스, 재시도 정책, 우선순위 큐, 분산 잠금 |
| Spring의 비동기 실행 + DB 상태로 충분 | |

**(a) 학습 목표가 유지되는 이유:** CORE-AC-22가 요구하는 것은 큐 인프라가 아니라 **권한·목적·만료·감사**다. **(b) 잃는 것:** 작업 실패 재시도와 중복 실행 방지. 후자는 §8.2의 멱등 처리가 이미 커버한다.

## 6. 가장 비현실적인 가정 하나

v1.0에서 지목한 "Core API를 직접 실무 레벨로 만든다"는 PRD v2.1이 정면으로 받아들였다. 06 §12가 품질 취약점을 다뤘고 §13이 인수조건을 붙였다. 그 지적은 해소됐으므로 다시 하지 않는다.

**지금 가장 비현실적인 가정은 이것이다.**

> **"Core API는 1벌이므로 프론트 4벌보다 작은 작업"이라는, 문서 구조가 만들어내는 착시.**

PRD는 이 가정을 명시적으로 쓰지 않았다. 그러나 문서 전체가 그렇게 배치되어 있다.

**1. 문서 구조가 시간 구조를 반대로 보여준다.**
00 §2 표에서 Core API는 한 행, 프론트는 두 행 × 2벌이다. 00 §5 다이어그램에서 Core API는 가운데 한 상자이고 프론트는 네 갈래다. 06 §1.3은 "1벌만 만드는 이유"를 설명하는 데 지면을 쓰지, 그것이 얼마나 큰 작업인지는 말하지 않는다. 실제 배분은 **Core API 635h(46%) 대 프론트 4벌 512h(37%)** 다. **Core API 하나가 프론트 네 벌보다 크다.**

**2. 인수조건 수가 이 착시를 강화한다.**
CORE-AC 28개, 프론트 AC 30개로 비슷해 보인다. 그런데 프론트 30개는 **2벌씩 판정하므로 실제 판정 60회**, CORE-AC는 28회다. 판정 횟수는 프론트가 2배인데 시간은 Core API가 더 든다. 이유는 06 §1.3이 이미 적었다 — **프론트는 두 번째 구현이 첫 번째를 참조할 수 있지만 Core API에는 "먼저 푼 답"이 없다.** 문서는 이 사실을 §12에서 *품질* 문제로만 다루고 *일정* 문제로는 다루지 않았다.

**3. 위험이 비대칭인데 문서는 대칭으로 읽힌다.**
Core API가 지연되면 프론트 네 벌이 전부 멈춘다(00 §5, 06 §1.1). 반대는 성립하지 않는다 — Nuxt 구현이 늦어도 Next·React·Vue는 진행된다. **일정 위험의 100%가 46%짜리 단일 블록에 몰려 있다.** 06 §12는 "잘못된 설계가 테스트를 통과하며 살아남는" 품질 위험만 다루고, "이 블록이 늦으면 나머지가 전부 멈춘다"는 일정 위험은 어느 문서에도 없다.

**무엇을 바꾸라는 것이 아니다.** Spring 선택도, 직접 구현도, 1벌 결정도 각각 근거가 있고 나는 반대하지 않는다. 문제는 **인식과 배치**다. 구체적으로 두 가지를 권한다.

- **00 §2의 제품 배치 표에 시간 비중 열을 추가한다.** Core API 46% / B2C 2벌 22% / Admin 2벌 25% / 학습·검증 7%. 표를 볼 때마다 실제 무게가 보여야 한다.
- **M3(335h·16.8주)를 4개 서브 게이트로 쪼개고 각각에 CORE-AC ID를 붙인다.** 이 프로젝트에서 가장 긴 단일 구간이자 실패해도 실패한 줄 모를 수 있는 유일한 구간이 하나의 덩어리로 남아 있으면, 그 안에서 무슨 일이 일어나는지 외부에서 볼 수 없다.

이 프로젝트는 "프론트 4벌 비교 학습 + Core API"가 아니라 **"Spring 기반 Core API 신규 학습 + 프론트 4벌 비교 학습"** 이며, 마일스톤 명칭·문서 배치·시간 인식이 전부 그 순서를 따라야 한다.
