# PRD 03 — DayLink 운영자센터

- 제품명: DayLink Ops
- 기술: React + TypeScript + Vite 기반 SPA
- 문서 버전: 1.0
- 우선순위 표기: P0 필수, P1 후속, P2 학습 확장
- 공통 정책: `00-DayLink-PRD-개요.md`를 따른다.

## 1. 제품 요약

본사 담당자가 파트너 입점·상품을 심사하고, 예약·환불 민원을 처리하고, 정산 원장을 대사하고, 민감한 운영 행위를 감사하는 내부 업무 시스템이다. 공개 검색 노출이 필요 없는 SPA로 만들어 React 자체의 상태·렌더링·동시성·컴포넌트 설계를 집중 학습한다.

## 2. 목표와 제외 범위

### 2.1 목표

- 담당자가 많은 건을 표, 필터, 단축키로 빠르고 정확하게 처리한다.
- 심사·환불·권한 변경에서 담당자 충돌과 자기 승인을 막는다.
- 고객·파트너가 보는 상태와 내부 처리 이력을 한 타임라인에서 추적한다.
- 대량 목록과 실시간 큐가 입력 반응성을 해치지 않는다.
- 모든 민감정보 열람과 상태 변경에 사유와 감사 기록을 남긴다.
- React의 hooks, context/reducer, Suspense/lazy, transition, optimistic UI, portal, Error Boundary를 실제 업무 요구와 연결한다.

### 2.2 제외 범위

- 실제 은행 송금·PG 관리자 기능
- 데이터베이스 직접 편집과 감사 로그 삭제
- 고객을 대신한 상품 구매
- 범용 BI·데이터 웨어하우스
- 공개 CMS 전체 기능

## 3. 사용자와 권한

| 역할 | 주요 업무 | 고위험 제한 |
|---|---|---|
| 심사 담당 | 입점·상품 승인/반려 | 환불·정산·역할 변경 불가 |
| CS 담당 | 고객·예약 조회, 정책 내 취소·환불 | 예외 환불 자기 승인 불가 |
| CS 승인자 | 예외·고액 환불 승인 | 자신이 요청한 건 승인 불가 |
| 정산 담당 | 정산 대사, 조정 요청 | 원장 행 삭제·기존 금액 수정 불가 |
| 콘텐츠 담당 | 홈 노출 순서, 공지·쿠폰 설정 | 예약·민감정보 접근 불가 |
| 보안 감사자 | 감사 로그·권한 변경 이력 조회 | 업무 상태 변경 불가 |
| 슈퍼관리자 | 계정·역할·긴급 차단 | 감사 로그 삭제 불가, 일상 CS 처리 금지 |

운영 권한은 기본적으로 최소 권한이며, 메뉴 노출과 무관하게 API가 매 요청을 검사한다.

## 4. 성공 지표

| 지표 | 정의 |
|---|---|
| 심사 처리시간 | 큐 등록부터 최종 결정까지 걸린 시간 |
| 반려 후 재반려율 | 같은 사유로 다시 반려된 비율 |
| 1차 CS 해결률 | 다른 담당자 이관 없이 해결된 사건 비율 |
| 환불 오승인 건수 | 정책·권한·금액이 잘못된 승인 건수, 목표 0 |
| 동시 편집 충돌 발견률 | 조용한 덮어쓰기 대신 충돌로 차단된 비율 |
| 정산 미대사 잔액 | 기준 기간 내 원인을 찾지 못한 차액 |
| 감사 추적 완결률 | 고위험 행위에 actor·reason·before/after·traceId가 모두 있는 비율 |

## 6. 공통 업무 UI 요구사항

### OPS-UI-001 [P0] 데이터 그리드

- 서버 필터·정렬·cursor pagination을 사용한다.
- 열 표시, 너비, 고정, 밀도를 사용자별로 저장한다.
- 필터 상태는 URL에 직렬화해 공유·복원 가능해야 한다.
- 모든 행 기능은 키보드로 접근 가능해야 하며 가로 스크롤에서 주요 식별 열을 고정한다.
- 1만 건을 브라우저에 내려받아 필터링하지 않는다.

### OPS-UI-002 [P0] 작업 상세 패널

- 목록에서 행을 열면 split pane 또는 drawer로 상세를 표시한다.
- 상세 URL을 직접 열 수 있고 새로고침해도 선택 대상이 유지된다.
- 패널 너비는 드래그·키보드 조절을 모두 지원한다.

### OPS-UI-003 [P0] 변경 확인

- 상태 변경 모달은 대상, 현재 상태, 예상 후속 효과, 필수 사유를 표시한다.
- 위험도에 따라 재인증 또는 2차 승인 요구를 표시한다.
- 단순히 `확인하시겠습니까?`만 제공하지 않는다.

### OPS-UI-004 [P0] 실시간 큐

- SSE로 새 사건, 담당자 지정, 상태 변경을 수신한다.
- 연결 끊김을 표시하고 재연결 뒤 누락 구간을 다시 조회한다.
- 새 항목이 들어와도 사용자가 읽는 행과 스크롤을 강제로 밀지 않는다.

### OPS-UI-005 [P0] 민감정보 열람

- 연락처는 기본 마스킹한다.
- 권한자가 업무 사유를 입력하고 제한 시간 동안만 원문을 본다.
- 열람 행위 자체를 감사 기록에 남긴다.
- 화면 복사 방지는 보안 통제가 아니므로 권한·감사·보유기간을 핵심 통제로 삼는다.

## 7. 기능 요구사항

### 7.1 로그인·세션

#### OPS-AUTH-001 [P0] 내부 인증

- 외부 고객·파트너 계정과 분리된 내부 IdP를 사용한다.
- MFA를 필수로 한다.
- 로그인 성공 후 역할에 맞는 첫 화면으로 이동한다.

#### OPS-AUTH-002 [P0] 세션 만료

- 유휴·절대 만료를 구분한다.
- 읽기 중 만료되면 작업 내용을 보존하고 재인증 후 안전하게 복귀한다.
- 승인·환불 명령은 재인증 후에도 자동 재전송하지 않고 사용자가 다시 확인한다.

### 7.2 대시보드

#### OPS-DASH-001 [P0] 역할별 업무 큐

- 내 미처리, SLA 임박, 반려 후 재제출, 환불 승인 대기, 정산 차이를 역할별로 표시한다.
- 카드 클릭 시 동일 조건이 적용된 목록으로 이동한다.
- 실시간 값과 집계 기준 시각을 함께 보여준다.

#### OPS-DASH-002 [P1] 운영 지표

- 예약 확정, 취소, 결제 오류, 체크인 충돌, 심사 처리 추세를 제공한다.
- 차트는 표 형식 원자료와 동일한 필터를 사용한다.

### 7.3 입점·상품 심사

#### OPS-REV-001 [P0] 큐 배정

- 상태, 제출 시각, 재제출, 위험 신호로 필터링한다.
- 담당자는 건을 가져오거나 관리자에게 재배정할 수 있다.
- 두 명이 동시에 가져오면 먼저 성공한 담당자만 배정되고 다른 화면은 즉시 갱신한다.

#### OPS-REV-002 [P0] 버전 비교

- 현재 공개본, 제출본, 직전 반려본을 필드 단위로 비교한다.
- 변경, 삭제, 새 항목을 색뿐 아니라 기호·텍스트로 구분한다.
- 이미지, 취소 정책, 장소, 접근성 제한을 독립 검토 항목으로 표시한다.

#### OPS-REV-003 [P0] 승인

- 필수 검토 항목을 모두 확인한 뒤 승인할 수 있다.
- 승인 명령은 심사 스냅샷 version을 포함한다.
- 제출본이 바뀌었으면 409로 차단하고 새 비교를 요구한다.
- 승인 후 즉시 게시하지 않고 파트너에게 `APPROVED` 상태를 제공한다.

#### OPS-REV-004 [P0] 반려

- 필드별 사유 코드와 구체적인 수정 의견을 입력한다.
- 같은 사유의 중복 문구를 템플릿으로 제안하되 담당자가 검토한다.
- 모호한 `보완 필요`만으로 반려할 수 없다.

### 7.4 고객·파트너 관리

#### OPS-CUST-001 [P0] 고객 검색

- 정확 예약번호, 이메일 해시, 전화번호 뒷자리 등 제한된 조건으로 검색한다.
- 과도한 부분 일치 대량 검색을 제한하고 조회 사유를 기록한다.
- 탈퇴·정지·정상 상태와 예약 이력을 구분한다.

#### OPS-PTN-001 [P0] 파트너 조회·제재

- 입점, 상품, 회차, 예약, 민원, 정산 요약을 보여준다.
- 신규 판매 중지, 로그인 정지, 사업장 현장 운영 중지를 서로 다른 조치로 제공한다.
- 제재 범위, 시작·종료, 사유, 영향 예약을 확인한다.

#### OPS-PTN-002 [P1] 긴급 판매 중지

- 심각한 안전 문제 시 신규 검색·hold만 즉시 막는다.
- 기존 예약은 자동 취소하지 않고 별도 사고 대응 계획을 요구한다.
- 후속 담당자와 처리 기한을 지정한다.

### 7.5 예약·환불

#### OPS-BKG-001 [P0] 통합 타임라인

- hold, 결제 시도, 웹훅, 확정, 알림, 체크인, 취소, 환불, 정산 항목을 시간순으로 보여준다.
- 고객 화면 상태와 내부 원시 상태를 구분한다.
- 각 이벤트에서 traceId와 연관 사건으로 이동할 수 있다.

#### OPS-BKG-002 [P0] 정책 내 환불

- 서버가 계산한 환불액과 정책 버전을 보여준다.
- 권한 있는 CS는 계산 결과를 변경하지 않고 실행할 수 있다.
- 중복 제출은 같은 환불 결과를 반환한다.

#### OPS-RFD-001 [P0] 예외 환불 요청

- 정책보다 유리한 환불, 100,000원 초과 환불, 체크인 후 환불은 사유와 증빙을 첨부해 승인 요청한다.
- 요청자는 금액을 수정할 수 있지만 수정 시 기존 승인은 무효가 된다.
- 요청 생성 자체는 돈을 움직이지 않는다.

#### OPS-RFD-002 [P0] 2차 승인

- 승인자는 요청자와 달라야 한다.
- 현재 예약·결제·기환불 금액을 다시 조회해 과다 환불을 차단한다.
- 승인 시 Core API가 환불 실행과 원장 조정 항목을 생성한다.
- 반려 시 사유를 요청자 타임라인에 남긴다.

#### OPS-RFD-003 [P0] 결제 불일치

- `결제 승인·예약 미확정`, `환불 성공·내부 미반영`, `중복 웹훅`을 별도 큐로 제공한다.
- 운영자는 원시 상태를 직접 덮어쓰지 않고 `재처리`, `보상 환불`, `무시 사유 기록` 명령만 사용할 수 있다.

### 7.6 사고 관리

#### OPS-INC-001 [P0] 사고 사건

- 회차, 사업장, 관련 예약, 현장 보고, 고객 문의를 하나의 사건으로 묶는다.
- 심각도, 담당자, 다음 조치, 기한, 상태를 관리한다.
- 사고 종결 전 필수 후속 조치 누락을 검사한다.

#### OPS-INC-002 [P1] 일괄 고객 조치

- 영향 예약을 서버에서 다시 계산하고 대상 스냅샷을 만든다.
- 알림, 일정 변경 제안, 전액 취소 중 조치를 선택한다.
- 실행 전 대상 수·총 환불 예상액·제외 대상을 검토한다.

### 7.7 정산

#### OPS-SET-001 [P0] 정산 대사

- 예약별 매출, 수수료, 환불, 조정 항목과 합계를 제공한다.
- 결제 합계와 정산 원장 합계 차이를 자동 표시한다.
- 반올림·취소 시점·기간 귀속 등 차이 사유를 분류한다.

#### OPS-SET-002 [P0] 조정 항목

- 기존 원장 행을 수정하지 않고 양수·음수 조정 항목을 추가한다.
- 금액, 귀속 기간, 사유, 증빙, 승인자를 요구한다.
- 고액 조정은 환불과 같은 2차 승인 원칙을 적용한다.

#### OPS-SET-003 [P1] 파트너 이의 제기

- 파트너가 선택한 원장 항목과 증빙을 확인한다.
- 답변, 추가 자료 요청, 조정 승인, 기각 상태를 관리한다.

### 7.8 콘텐츠·쿠폰

#### OPS-CMS-001 [P0] 공지·노출 관리

- 공개 기간, 대상, 우선순위, 링크를 설정한다.
- 예약·결제 화면을 가리는 전역 공지는 긴급 상황에서만 허용한다.
- 미리보기와 예약 게시를 분리한다.

#### OPS-CPN-001 [P1] 쿠폰 캠페인

- 유효 기간, 대상 상품·지역, 최소 금액, 할인 방식, 총 혜택 한도를 설정한다.
- 겹치는 조건과 과도한 할인 예시를 사전 계산한다.
- 발급 후 핵심 조건을 소급 변경할 수 없고 중지와 새 캠페인만 허용한다.

### 7.9 감사·접근 제어

#### OPS-AUD-001 [P0] 감사 로그

- actor, 역할, action, target, before/after, reason, IP/device 식별, traceId, 시간을 검색한다.
- 원문 개인정보를 무제한 덤프하지 않고 필요한 필드만 마스킹한다.
- 감사 로그 내보내기도 감사 대상이다.

#### OPS-ACC-001 [P0] 운영자 권한

- 계정 생성, 역할 부여, 일시 정지, 회수를 지원한다.
- 역할 변경은 다른 슈퍼관리자의 승인을 요구한다.
- 마지막 활성 슈퍼관리자를 제거할 수 없다.
- 긴급 권한은 만료 시각과 사건번호가 필수다.

### 7.10 시스템 상태

#### OPS-SYS-001 [P1] 비동기 작업

- CSV 생성, 알림 발송, 웹훅 처리, 정산 집계 작업의 상태와 재시도 횟수를 표시한다.
- 운영자가 무제한 재시도 폭주를 만들지 않게 횟수·간격 제한을 둔다.

#### OPS-SYS-002 [P1] 기능 플래그

- 플래그 대상, 환경, 기본값, 만료일, 소유자를 표시한다.
- 결제·환불 핵심 규칙을 클라이언트 플래그만으로 우회할 수 없다.

## 8. React 학습 요구사항 연결

| React 기능 | 적용 요구사항 | 구현 의도 |
|---|---|---|
| JSX, props, composition | 표 셀, 패널, 승인 폼 | 상속 대신 작은 컴포넌트 조합 |
| controlled/uncontrolled input | 필터, 대형 폼 | 값 제어 비용과 ref 기반 입력 비교 |
| `useState` | 로컬 토글·입력 | 가장 가까운 소유자에 단순 상태 배치 |
| `useReducer` | 심사·환불 다단계 폼 | 명시적 이벤트와 상태 전이 |
| Context | 세션, 권한, locale, feature context | 전역 접근이 필요한 안정 값만 제공 |
| `useEffect` | SSE·외부 SDK 동기화 | 외부 시스템 동기화에만 사용, 파생 상태 계산 금지 |
| `useLayoutEffect` | split pane 측정·초점 복구 | 화면 표시 전 DOM 측정이 필요한 곳으로 제한 |
| `useRef` | focus, 이전 값, 명령 중복 방지 | 렌더링과 무관한 가변 값 관리 |
| `useId` | 폼·오류·도움말 연결 | SSR이 없어도 안정적인 접근성 ID 구성 |
| `useMemo`·`useCallback` | 프로파일링된 대형 표 경계 | 관성적 사용 금지, 측정 후 적용 |
| `useDeferredValue` | 대형 표의 즉시 검색 미리보기 | 입력과 무거운 결과 렌더 분리 |
| `useTransition` | 필터·탭·상세 전환 | 비긴급 UI 갱신과 pending 표시 |
| `useOptimistic` | 담당자 가져오기, 내부 메모 | 빠른 반영과 409/실패 원복 |
| `useActionState` | 승인·반려 폼의 async 결과 | 제출 상태와 서버 오류 모델링 |
| custom hooks | 권한, pagination, SSE, mutation lock | 상태 있는 로직 재사용 |
| lazy + Suspense | 정산, 감사, 차트 라우트 | 코드 분할과 영역별 fallback |
| Error Boundary | 라우트·위젯 오류 | 한 기능 오류가 전체 앱을 중단하지 않음 |
| portal | 모달, 토스트, command palette | stacking·focus 경계 관리 |
| `useSyncExternalStore` | 세션 만료·네트워크·SSE 연결 상태 | 외부 store의 일관된 구독 |
| StrictMode | 개발 전체 | 부수효과 정리와 반복 실행 문제 발견 |
| Profiler | 그리드·타임라인 | 최적화 전 병목 측정 |
| `memo` | 실제 병목이 확인된 행·셀 | 불필요한 렌더 최적화를 근거 있게 적용 |

클래스형 컴포넌트는 제품 코드에서 Error Boundary 한 곳에만 허용한다. 나머지 Options-like 비교 학습은 `labs/`에 둔다.

## 9. 권장 프런트 구조

- 라우팅: 데이터 라우터를 지원하는 React Router
- 서버 상태: query cache 라이브러리. API 응답을 Context에 복제하지 않음
- 폼: 접근성 오류 연결과 schema validation을 지원하는 폼 도구
- 표: headless table + 필요 구간 가상화
- 스타일: 앱 전용 디자인 토큰과 접근 가능한 headless primitive
- API: OpenAPI 생성 타입 + 공통 fetch client
- 테스트: Vitest, React Testing Library, MSW, Playwright

라이브러리는 React 학습을 가리지 않도록 역할을 문서화한다. 서버 상태를 무조건 전역 store에 복제하지 않고 URL, query cache, 폼 상태, UI 상태를 분리한다.

## 10. 상태 소유권 원칙

| 상태 | 소유 위치 |
|---|---|
| 필터·정렬·선택 ID | URL |
| API 목록·상세·mutation 결과 | query cache |
| 승인·환불 입력 | form/reducer |
| 모달·패널 열림 | route 또는 가까운 UI state |
| 로그인·역할 요약 | session external store/context |
| 서버 권한·업무 상태 | Core API |

서버 응답에서 계산 가능한 값을 별도 state와 effect로 동기화하지 않는다. 낙관적 상태는 서버 응답이 오면 폐기할 수 있는 임시 표현으로 취급한다.

## 11. 인수 조건

### 11.1 핵심 E2E

1. 심사 담당자가 상품 제출본과 공개본을 비교해 승인하고 파트너센터에 결과가 반영된다.
2. 심사 중 파트너가 새 버전을 제출하면 기존 version 승인이 409로 차단된다.
3. 두 운영자가 같은 건을 가져오면 한 명만 성공하고 다른 화면은 실시간으로 갱신된다.
4. CS 담당자가 정책 내 환불을 두 번 제출해도 한 건만 실행된다.
5. 예외 환불 요청자는 자신의 요청을 승인할 수 없다.
6. 승인 직전 다른 환불이 처리되어 환불 가능액이 줄면 과다 환불이 차단된다.
7. 역할 회수 뒤 열린 탭에서 다음 API 요청이 거부되고 민감정보가 지워진다.
8. 정산 조정은 기존 원장을 바꾸지 않고 새 조정 행으로 남는다.
9. SSE가 끊겼다 복구되면 cursor 이후 누락 사건을 재조회하고 중복 표시하지 않는다.
10. 민감정보 원문 열람과 감사 로그 export가 모두 감사 기록에 남는다.

### 11.2 React 품질 기준

- 주요 라우트는 lazy chunk로 분리되고 로딩·오류 fallback이 있다.
- 필터 입력 중 대형 표가 느려져도 입력이 멈추지 않는다.
- effect는 외부 동기화 용도로 검토되며 파생값 복사 effect가 없다.
- Context 값 변경으로 무관한 전체 그리드가 다시 렌더되지 않는다.
- 모달 열기·닫기 후 초점이 올바르게 이동한다.
- Error Boundary 뒤 재시도로 해당 영역만 복구된다.
- 권한 없는 라우트의 번들 지연 로딩 여부와 무관하게 API는 접근을 거부한다.
