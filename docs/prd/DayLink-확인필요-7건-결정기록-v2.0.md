## 1. B2C 체험 식별자 — 전부 `id`

**문제.** `01 §4.2`에서 상세는 `/experiences/{slug}`, 예약 진입은 `/experiences/{id}/book`으로 갈렸다. 같은 절 하단이 "두 구현이 기술적 이유 없이 서로 다른 공개 URL을 사용하지 않는다"고 규정하므로 명세보다 먼저 확정돼야 한다.

**결정.** `/experiences/{id}`, `/experiences/{id}/book`.

**적용 범위 한정.** 체험 식별자에만 적용한다. `/categories/{slug}`, `/regions/{slug}`, `/policies/{slug}`는 **그대로 둔다** — 고정된 분류 체계라 변경 위험이 없고, 이쪽이 남으므로 `03 §6.5`의 검색 노출 학습에서 slug를 다루는 소재가 유지된다.

**잃는 것.** 상품 상세 URL의 가독성과 키워드. `03 §4`가 상세를 "색인 가능"으로 규정했으므로 SEO 손실이 0은 아니다. 완화책은 `03 §6.5`가 이미 요구하는 **표준 URL(canonical)과 구조화 데이터**이며, 이는 slug 유무와 무관하게 구현한다.

## 2. 상품 신규 작성 — `/partner/experiences/new`

**문제.** `02 §4.2`는 `ADM-PTN-004 = /partner/experiences/{id}` 한 경로만 정의하는데, `§6 ADM-PTN-02`가 임시 저장을 요구한다. **아직 저장하지 않은 신규 상품의 `{id}`가 정의되지 않았다.**

**결정.** `/partner/experiences/new`로 진입하고 **첫 저장 시** `id`를 발급해 `/partner/experiences/{id}`로 교체한다. 화면은 `ADM-PTN-004` 하나로 유지하고 URL 열에 두 진입 경로를 적는다(화면 수 증가 없음).

**근거.** `04 §6.3`의 '임시 저장'은 명시적 사용자 행동이다. 진입만으로 서버 행이 생기는 것은 임시 저장이 아니다. 그리고 `00 §7.1`이 물리 삭제를 금지하므로, 저장 의사 없는 빈 `Experience`가 쌓이면 학습 범위 밖의 정리 정책이 필요해진다.

**기각한 안.** 클라이언트 임시 ID 후 교체 — `06 §8.2`의 멱등 키 설계와 개념이 겹쳐 혼동을 만든다. 신규 생성의 중복 방지는 `Idempotency-Key`로 푸는 것이 PRD 방향이다.

## 3. 현장 사고 '추가 메모' — `/desk/incidents/{id}` 신설

**문제.** `02 §7 ADM-DSK-05`가 "현장 담당자는 제출 후 원문을 임의로 삭제하지 못하고 **추가 메모만 남긴다**"고 규정하는데, `§4.3` 현장 화면에는 `/desk/incidents/new`(작성)만 있다. **PRD 본문이 요구한 행동을 할 화면이 없다.** IA 누락이 아니라 PRD 내부 불일치다.

**결정 (v2.0).** `ADM-DSK-009 사고 상세·추가 메모 = /desk/incidents/{id}` **와** `ADM-DSK-010 사고 목록 = /desk/incidents` 를 함께 신설한다. 접근 권한은 둘 다 `VENUE_STAFF`(배정 장소) · `PARTNER_OWNER`. v1.0은 상세만 신설했으나 진입점이 없어 목록을 추가했다.

**근거.**
- `00 §1.2`가 `/partner`·`/desk`·`/ops`를 권한 모듈로 분리했다. 현장 담당자를 `/ops` 경로로 보내면 이 구조가 깨진다.
- `ADM-AC-07`이 현장 담당자를 "배정 장소·회차의 최소 개인정보만"으로 제한한다. `ADM-OPS-013`(사고 상세, 타임라인·조치)을 그대로 열면 이 완료 조건과 충돌한다.
- `06 §4`의 `CheckInEvent`처럼 사고 메모도 **추가만** 성격이다. 원문 보존 + 메모 추가 구조이므로 조회 화면이 필요하다.

**대가.** 화면 2행. 둘 다 완료 조건이 없어 M6 배치이므로 M1~M5 판정에는 영향이 없다.

## 4. 역할 권한 — `READ_ONLY_AUDITOR` 존치 + 6개 화면 확정

### 4-a. `READ_ONLY_AUDITOR`

**문제.** `02 §3.1`에 정의만 있고 **`§3.3` 권한표에 열이 없으며** 화면 목록 어디에도 등장하지 않는다.

**결정.** 존치하되 **기간·사유·승인자를 갖는 한시 역할**로 정의한다. 범위는 승인 시 지정하며 만료된다.

**근거 (결정적).** `06 §4`의 `RoleGrant`가 **"역할·조직·장소 범위, 시작·종료일, 사유, 승인자 / 추가만"** 으로 정의돼 있다. 그런데 나머지 7개 역할은 전부 상시 부여라 **시작·종료일과 승인자 필드를 쓸 일이 없다.** `READ_ONLY_AUDITOR`가 이 구조를 실제로 쓰는 유일한 역할이 되고, `CORE-AC-11`(범위 밖 미응답)·`CORE-AC-24`(권한 철회 시 세션 종료)의 **유일한 동적 검증 대상**이 된다. `05 §7.1`의 "긴급 운영 권한은 기간, 사유, 승인자를 갖고 만료된다"와도 같은 구조다.

### 4-b. 6개 화면 접근 권한

| 화면 | 이전 표기 | 확정 | 근거 |
|---|---|---|---|
| `ADM-OPS-019` 감사 로그 | 허용 역할 | `OPS_ADMIN`(전체) · `OPS_REVIEWER`·`OPS_CS`(제한) · `OPS_FINANCE`(재무 범위) · `PARTNER_OWNER`(소속 제한) · `READ_ONLY_AUDITOR`(승인 범위) | **`§3.3` '감사 로그' 행에 이미 있다.** 화면 목록에 전사하지 않았을 뿐 |

## 5. 정산 목록 — `/ops/settlements` 신설

**문제.** `§4.4`에 `ADM-OPS-014 /ops/reconciliation`(대사)와 `ADM-OPS-015 /ops/settlements/{id}`(상세)만 있고 목록이 없다. 파트너 쪽(`PTN-012 /partner/settlements`)에는 있는데 플랫폼 쪽에만 없는 비대칭이다. `05 §5.8`의 '정산 기간 집계'에 해당하는 화면이 목록인지 대사인지 정의되지 않았다.

**결정.** `ADM-OPS-021 정산 목록 = /ops/settlements` 신설. 대사(`OPS-014`)와 분리한다. 접근 권한 `OPS_FINANCE` · `OPS_ADMIN` · `READ_ONLY_AUDITOR`(읽기).

**책임 분리.** 목록은 기간별 정산 상태, 대사는 차이 분석, 상세는 결재다. `§8 ADM-OPS-05`의 "정산 확정과 재개방은 서로 다른 권한과 승인 절차"가 상세 화면에 남는다.

**대가.** 화면 1행. M6 배치 — `ADM-AC-13`은 `OPS-014`·`015`가 담당하므로 목록에는 완료 조건이 걸리지 않는다. M4에서는 대사 화면에서 상세로 진입한다.

## 6. B2C 문의 — 예약 종속 `/bookings/{id}/inquiry`

**문제.** `01 §4.2`가 `B2C-BOOK-002`의 주요 연결 화면을 "취소 예상액, 후기, **문의**"로 명시했는데 문의 화면이 없다. 3번과 같은 성격의 PRD 내부 불일치다.

**결정 (v2.0).** `B2C-INQ-001 예약 문의 = /bookings/{id}/inquiry` 신설. Admin은 문의 **상세** 화면을 두지 않고 `ADM-OPS-009` 예약 상세에 스레드를 인라인하되, 미답변 문의를 찾기 위한 **`ADM-OPS-022 문의 대기열 = /ops/inquiries`** 를 신설한다. `/ops/refunds` 대기열과 같은 패턴이다. v1.0은 대기열 없이 인라인만 두었다.

**근거.** `BOOK-002`가 가리키는 '문의'는 예약 맥락의 문의다. 일반 문의 창구가 아니다. `/bookings/{id}/cancel`, `/bookings/{id}/review`가 이미 같은 패턴이다.

**도메인 파급.** `06 §4`에 **`Inquiry` 엔터티가 없다** — PRD v2.1이 문의를 도메인으로 보지 않았다. 추가가 필요하다(§9 참조).

**기각한 안.** 독립 문의 도메인 신설 — B2C 접수 + Admin 목록·상세로 화면 3행이 늘고 담당자 배정·상태 기계까지 필요해진다. 예약과 무관한 문의를 받는 이점보다 분량이 크다.

## 7. B2C '서비스 소개' — `/about` 신설

**문제.** `01 §4.1` 하단 내비게이션은 '서비스 소개, 이용약관, 개인정보 처리방침, 취소 정책, 고객지원'인데 `§4.2` 목록에는 정책 문서(`/policies/{slug}`)만 있다. 나머지 셋은 `{slug}`로 흡수되는데 '서비스 소개'만 갈 곳이 없다.

**결정 (v2.0).** 별도 경로를 신설하지 않고 **`/policies/about`** 으로 흡수한다. `B2C-HELP-002`의 화면명을 '정책·소개 문서'로 바꾸고 slug 목록을 `about`·`terms`·`privacy`·`cancellation` 넷으로 고정한다. v1.0은 `/about`을 신설했으나 철회했다.

**대가.** 화면 증가 0. 어차피 `HELP-002`와 렌더링 전략·색인 정책이 같으므로 경로만 늘어나는 구조였다. 대신 `03 §4`의 정적 생성 대상 slug가 넷으로 고정돼 사전 열거가 명확해진다.

## 10. `CORE-AC-29` — 신설 확정

`READ_ONLY_AUDITOR`를 한시 역할로 정의한 결과 **"유효 기간 만료 시 자동 거부"**라는 서버 규칙이 새로 생겼다. `CORE-AC-24`는 "권한 **철회** 시 세션 종료"만 다루므로 **아무도 철회하지 않았는데 만료된 경우**를 덮지 못한다. `00 §11.6`이 완료 조건의 동시 요청 통과를 학습 완료 기준으로 삼으므로 검증되지 않는 규칙을 남기면 그 기준이 약해진다.

**신설 확정 (2026-08-24).** `06 §13`에 다음을 추가했다.

> `CORE-AC-29` — 한시 역할의 유효 기간이 지나면 별도 철회 없이도 요청이 거부되며, 만료 판정은 요청 처리 시점의 서버 시각을 사용한다. (근거: 02 §3.2, 06 §8.6)

동반 개정 4건도 함께 적용했다.

| 위치 | 내용 |
|---|---|
| `06 §8.6` **신설** | '한시 역할 만료' 절. 만료 판정을 **토큰 발급 시각이 아니라 요청 처리 시점의 서버 시각**으로 못박았다. 기존 §8.6(낙관적 동시성)은 **§8.7로 이동**했다 |
| `06 §13 CORE-AC-11` | "선택한 역할·조직·장소 범위" → "**승인 범위와 유효 기간을 포함한** 역할·조직·장소 범위" |
| `06 §13 CORE-AC-24` | "권한 철회 시" → "권한 철회 **또는 한시 권한 만료** 시" |
| `06 §14.4` | 권한 테스트에 "종료일 경계 앞뒤 1초 요청(철회 행위 없이)"와 "만료된 한시 역할로 발급된 기존 세션의 후속 요청" 추가 |

**커리큘럼 영향.** 완료 조건 58 → **59개**. M3 서브 게이트 G3(권한)이 `CORE-AC-10·11·12·24·29`가 되어 **55h → 69h**. `06 §8.7`로 이동한 낙관적 동시성 참조도 커리큘럼에서 정정했다.
