# DayLink 제품 기획 개요

| 항목 | 내용 |
|---|---|
| 문서 버전 | 2.2 |
| 기준일 | 2026-08-24 |
| 개정 사유 | Core API 언어를 **Java 21**로 확정 (§8.1). 상세 근거는 `06 §2.1` |
| 서비스 | 로컬 클래스·체험 예약 플랫폼 DayLink |
| 제품 구성 | B2C 1개, Admin 1개, **Core API 1개** |
| 구현 구성 | B2C를 Next.js와 Nuxt로 각각 구현, Admin을 React와 Vue로 각각 구현, **Core API는 단일 구현** |
| 학습 성격 | 프론트엔드는 숙련 기술을 기준선으로 삼는 **비대칭 비교 학습**, Core API는 **신규 학습** |
| 문서 원칙 | PRD는 기술 중립, 기술별 차이는 별도 학습 구현 가이드에서 정의. 단 Core API는 단일 구현이므로 스택을 PRD에 명시한다 |

## 1. 문서 개정 목적

기존 문서는 고객 웹, 파트너센터, 운영자센터, 현장 데스크를 서로 다른 네 개의 제품으로 정의했다. 이 구분은 같은 애플리케이션을 양쪽 생태계에서 구현하고 비교하려는 학습 목적과 맞지 않는다.

이번 개정에서는 제품 경계를 다음처럼 바로잡는다.

1. 고객이 사용하는 모든 기능은 하나의 **B2C 애플리케이션**으로 통합한다.
2. 파트너, 사내 운영자, 현장 담당자가 사용하는 모든 기능은 하나의 **Admin 애플리케이션** 안에서 권한별 모듈로 제공한다.
3. 동일 제품의 기능, 화면, API, 업무 규칙, 인수조건은 구현 기술과 무관하게 동일하다.
4. 프레임워크마다 소스 구조를 억지로 같게 만들지 않고 같은 사용자 결과를 각 생태계의 권장 방식으로 구현한다.

### 1.1 v2.1 개정 (2026-08-23)

v2.0은 네 프론트 구현을 대칭 비교로만 기술했고 Core API는 "책임"만 정의한 채 누가 어떻게 만드는지를 비워 두었다. 실제 학습 목적이 확인되면서 다음 두 가지를 명시한다.

1. **학습 목적의 비대칭.** 이 프로젝트의 출발점은 "네 기술을 균등하게 배운다"가 아니라 **"이미 숙련된 React·Next.js를 기준선으로 삼아 Vue 3·Nuxt 4를 학습한다"**이다. 산출물의 동등성은 그대로 유지하되, 학습 부담과 시간 배분이 대칭이 아님을 문서에 반영한다(§2.1).
2. **Core API를 직접 구현한다.** 명세 기반 mock으로 대체하지 않고 실제 데이터베이스와 트랜잭션을 갖춘 서버를 만든다. 이는 부가 작업이 아니라 **이 프로젝트에서 가장 큰 단일 신규 학습 영역**이며, 별도 문서 `06-DayLink-CoreAPI-PRD.md`로 분리한다(§8, §3).

이 두 가지는 v2.0의 요구사항을 삭제하지 않는다. 화면 목록, 인수조건, 동등성 원칙은 그대로 유효하다.

## 2. 최종 제품·기술 배치

| 제품 | 구현 A | 구현 B | 선택 이유 |
|---|---|---|---|
| B2C | Next.js + React | Nuxt + Vue | 공개 콘텐츠, 검색 유입, 메타데이터, 서버 렌더링, 정적 생성, 경로별 캐시를 양쪽 메타 프레임워크에서 비교하기 적합 |
| Admin | React SPA | Vue SPA | 검색 노출이 불필요하고 표·폼·상태·권한·오프라인 동기화가 중심이므로 라이브러리 자체의 구성 방식을 직접 비교하기 적합 |
| Core API | Spring Boot 4 + Java 21 (JVM) | 없음 — 단일 구현 | 네 프론트 구현이 공유하는 단일 권위자다. 두 벌로 만들면 비교의 기준선 자체가 흔들리므로 한 벌만 만든다. 스택은 SI 실무 적용 목적에 맞춰 국내 현장에서 가장 널리 쓰이는 Spring 계열로 고정한다 |

이 배치는 “React와 Next.js를 동시에 쓰지 않는다”는 뜻이 아니다. 핵심은 학습 단위를 구분하는 데 있다. Next.js 구현은 React 기반이지만 B2C에서는 Next.js가 제공하는 전체 애플리케이션 구조를 학습한다. Admin에서는 별도 메타 프레임워크 없이 React SPA를 구성해 React 중심의 설계 판단을 학습한다. Nuxt와 Vue도 같은 관계다.

### 2.1 학습 목적과 학습 비대칭

**산출물은 대칭이지만 학습은 대칭이 아니다.** 네 프론트 구현은 같은 화면·API·인수조건을 만족해야 하지만(§9), 각 구현이 학습에서 맡는 역할은 다르다.

| 구현 | 학습에서의 역할 | 성격 |
|---|---|---|
| B2C Next.js | **기준선** — 익숙한 기술로 요구사항을 먼저 푼다 | 심화·비교 |
| Admin React SPA | **기준선** | 심화·비교 |
| B2C Nuxt | **학습 대상** — 같은 요구사항을 새 생태계로 다시 푼다 | 신규 학습 |
| Admin Vue SPA | **학습 대상** | 신규 학습 |
| Core API | **신규 학습** — 비교 대상이 없는 단일 구현 | 제로 베이스 |

기준선 구현의 목적은 "무엇을 만들지"를 요구사항 모호함 없이 확정하는 데 있다. 학습 대상 구현에서 막혔을 때, 그 원인이 **새 프레임워크를 몰라서인지 요구사항이 모호해서인지 구분**할 수 있어야 하기 때문이다. 이 판단은 §11.5의 완료 기준과 직결된다.

이 비대칭에서 파생되는 규칙 두 가지를 둔다.

- **학습 대상 구현은 기준선 구현의 소스를 보고 시작하지 않는다.** PRD와 화면 목록만 보고 다시 만든다. 기준선 코드를 옆에 두고 옮기면 번역 작업이 되어 학습이 성립하지 않는다.
- **기준선에서 쉬웠던 구간이 학습 대상에서 어려우면, 그것을 프레임워크 우열의 근거로 삼지 않는다.** 숙련도 차이와 프레임워크 특성 차이를 분리해 기록한다(§9, §11.5).

Core API는 기준선이 없다. 같은 요구를 두 번 구현해 서로 채점하는 장치가 프론트에만 있고 백엔드에는 없으므로, **잘못된 설계가 테스트를 통과하면서 남아 있을 수 있다.** 이 구조적 취약점의 보완책은 `06-DayLink-CoreAPI-PRD.md` §12에 둔다.

## 4. 서비스 정의

DayLink는 사용자가 지역 기반 클래스와 체험을 검색하고 예약하는 가상 서비스다. 파트너는 상품과 일정을 관리하고 사내 운영자는 심사·고객지원·환불·정산을 처리하며 현장 담당자는 참가자를 확인하고 체크인한다.

### 4.1 핵심 사용자

| 사용자 | 목적 | 사용하는 제품 |
|---|---|---|
| 비회원·고객 | 체험 탐색, 예약, 결제, 취소, 후기 | B2C |
| 파트너 관리자 | 입점, 상품·일정·예약·정산 관리 | Admin |
| 파트너 실무자 | 담당 상품·회차·참가자 관리 | Admin |
| 현장 담당자 | 당일 명단 확인, QR·수동 체크인, 사고 보고 | Admin |
| CS 운영자 | 예약·고객 조회, 취소·환불 처리 | Admin |
| 상품 심사자 | 파트너·상품 검토와 승인 | Admin |
| 정산 담당자 | 거래·환불·정산 원장 대사 | Admin |
| 시스템 관리자 | 계정·역할·감사 로그 관리 | Admin |

## 5. 전체 구조

```text
                  ┌─ B2C 구현 A: Next.js ─┐
고객 ─────────────┤                       ├────┐
                  └─ B2C 구현 B: Nuxt ────┘    │
                                                │
                                                ▼
                                        DayLink Core API
                                                ▲
                                                │
파트너·운영자·현장 ┌─ Admin 구현 A: React SPA ──┤
──────────────────┤                            │
                  └─ Admin 구현 B: Vue SPA ────┘
```

네 구현은 같은 Core API, 데이터 정의, 테스트 계정, 시드 데이터, 업무 규칙을 사용한다. 구현마다 별도 백엔드를 만들어 결과가 달라지는 방식은 허용하지 않는다.

DayLink Core API는 **직접 구현한다.** 명세 기반 mock 서버로 대체하지 않는다. 이유는 §8.1에 있다.

### 5.1 이름이 겹치는 자리

같은 낱말이 두 가지를 가리키는 자리가 둘 있다. 구현에서 헷갈리므로 규약을 둔다.

- **회차는 `Slot`이다.** `Session`을 쓰지 않는다. `06 §8.6`이 같은 절에서 인증 세션을 "세션"이라 부르고, JVM에서 `Session`과 `HttpSession`이 한 파일에 들어오면 구분이 어렵다. 근거는 ADR-0014.
- **`.vue` 파일 안에서 도메인 값을 담는 이름으로 `slot`을 쓰지 않는다.** Vue의 컴포넌트 슬롯과 부딪힌다. `timeSlot`처럼 구분되는 이름을 쓴다. 타입명 `Slot` 자체는 그대로 둔다.

`Slot`이 뜻하지 않는 것도 적어 둔다. **한 `Slot`은 좌석 하나가 아니다.** 정원 1~N명을 담는 그릇이며, 남은 좌석은 `Slot`의 속성이지 `Slot`의 개수가 아니다. 영어 slot이 "자리 하나"로도 읽히므로 구현에서 오해하기 쉽다.

한국어로는 계속 **회차**라고 부른다. 개명 대상은 영어 식별자뿐이다.

## 6. 공통 업무 규칙

### 6.1 지역·시간·금액

- 서비스 국가는 대한민국, 통화는 KRW다.
- 사용 화면의 기본 시간대는 `Asia/Seoul`이다.
- 서버 저장·이벤트 시간은 UTC를 사용하고 화면에서 한국 시간으로 변환한다.
- 결제는 학습용 모의 결제만 사용한다. 실결제인 것처럼 표현하지 않는다.
- 플랫폼 수수료율은 학습용 12%로 고정한다.

### 6.2 예약 단위

- 주문 한 건에는 하나의 상품 회차만 포함한다.
- 예약 인원은 1명 이상 6명 이하다. 상한 6은 **소규모 체험의 동반 단위**를 기준으로 삼았다 — 가족·친구 단위 예약의 상식적 상한이고, 그보다 큰 인원은 단체 문의로 받는다.
- 고객 취소는 MVP에서 예약 전체 취소만 허용한다.
- 좌석은 결제 진입 시 10분간 임시 확보한다. 10분은 **결제 왕복 시간**을 기준으로 잡았다 — 카드 정보 입력, PG 리다이렉트 왕복, 간편결제 앱 전환과 재인증까지 들어간다. 더 짧으면 정상 결제 도중에 만료되고, 더 길면 이탈한 사용자가 재고를 오래 묶는다.
- 가격, 상품 핵심 정보, 회차, 취소 정책은 예약 시점 스냅숏으로 저장한다.

### 6.3 금액 계산

```text
상품 총액 G = 예약 시점 단가 × 인원
플랫폼 할인 D = 적용 쿠폰 할인액
고객 결제액 C = G - D
플랫폼 수수료 F = floor(G × 0.12)
파트너 정산 기준액 = G - F
```

플랫폼 쿠폰 비용은 파트너 정산액에서 차감하지 않는다. 환불과 정산 조정은 원거래를 수정하지 않고 별도 원장 항목으로 남긴다.

### 6.4 취소 정책 템플릿

| 정책 | 체험 시작 기준 | 고객 환불률 |
|---|---|---:|
| FLEXIBLE | 24시간 이상 전 | 100% |
| FLEXIBLE | 24시간 미만, 시작 전 | 50% |
| FLEXIBLE | 시작 후 | 0% |
| STANDARD | 72시간 이상 전 | 100% |
| STANDARD | 24시간 이상 72시간 미만 | 50% |
| STANDARD | 24시간 미만 또는 시작 후 | 0% |
| 공통 | 파트너·플랫폼 귀책 취소 | 실제 결제액 100% |

**구간을 나눈 기준은 파트너의 준비 비용이다.** 체험은 재료와 인력을 미리 잡는다. 72시간 전이면 재판매할 시간이 남아 파트너가 잃는 것이 없으므로 전액 환불한다. 24시간 안이면 준비가 이미 끝났으므로 환불하지 않는다. 그 사이 구간은 재판매 가능성이 반반이라 절반으로 나눈다. `FLEXIBLE`은 준비 비용이 작은 체험용이라 경계를 24시간 하나로 줄였다.

환불률 100/50/0은 그 구간 구분을 그대로 옮긴 값이고 실측 근거는 없다. 위 정책은 학습용 가정이다. 실제 출시 전 전자상거래·소비자보호·개인정보 정책 검토가 필요하다.

## 7. 상태 모델

### 7.1 상품

```text
DRAFT → SUBMITTED → APPROVED → PUBLISHED → PAUSED → ARCHIVED
            └────→ REJECTED → DRAFT
```

- 심사 전 상태와 판매 노출 상태를 분리한다.
- 승인된 상품이라도 파트너 또는 운영자가 일시 중지할 수 있다.
- 판매 이력이 있는 상품은 물리 삭제하지 않고 보관 처리한다.

### 7.2 재고 임시 확보

```text
ACTIVE → PAYMENT_PENDING → CONSUMED
   ├──→ EXPIRED
   └──→ RELEASED
```

- 10분 만료는 서버 시간을 기준으로 판단한다.
- 고객 화면의 타이머는 안내 수단이며 최종 권위가 아니다.

### 7.3 예약

```text
PAYMENT_PENDING → CONFIRMED → COMPLETED
       └───────→ PAYMENT_FAILED
CONFIRMED → CANCEL_PENDING → CANCELLED
CONFIRMED → NO_SHOW
```

### 7.4 환불

```text
REQUESTED → APPROVAL_PENDING → PROCESSING → SUCCEEDED
                                      ├──→ PARTIALLY_SUCCEEDED
                                      └──→ FAILED
```

예약 취소와 환불 성공은 같은 상태가 아니다. 예약이 취소되어도 환불 처리가 실패하거나 일부만 성공할 수 있다.

### 7.5 출석

```text
NOT_CHECKED_IN → PARTIAL → COMPLETE
              ├────────→ NO_SHOW
              └────────→ CORRECTED
```

출석은 예약 상태와 별도 기록한다. 관리 권한이 있는 사용자의 정정은 사유와 변경 전후 값을 감사 로그에 남긴다.

## 8. Core API 책임

Core API가 다음 항목의 최종 판단 주체다.

- 인증된 사용자와 역할·조직·장소 권한
- 상품 공개 가능 여부와 상태 전이
- 회차 재고, 임시 확보, 만료, 중복 예약 방지
- 서버 기준 가격, 쿠폰 적용, 결제액, 환불액
- 예약·결제·환불·정산 상태 전이
- 체크인 중복·충돌 판정
- 멱등 요청 처리와 감사 로그

클라이언트가 계산한 가격이나 권한 판정을 그대로 신뢰하지 않는다. 모든 쓰기 API는 `Idempotency-Key` 또는 동등한 멱등 식별자를 사용한다.

### 8.1 구현 주체와 스택

| 항목 | 결정 |
|---|---|
| 구현 방식 | **직접 구현.** 명세 기반 mock 서버로 대체하지 않는다 |
| 구현 벌 수 | 1벌. 프론트처럼 두 기술로 나누어 만들지 않는다 |
| 스택 | Spring Boot 기반 JVM 애플리케이션 |
| 언어 | **Java 21 (LTS)**. 확정 2026-08-24. 근거는 06 §2.1 |
| 프레임워크 버전 | **Spring Boot 4** |
| 데이터 저장소 | 관계형 데이터베이스. 트랜잭션과 격리 수준을 실제로 사용한다 |
| 버전 | 착수 시점의 안정판으로 고정하고 잠금 파일과 ADR에 기록한다 |

**mock으로 대체하지 않는 이유.** §8이 Core API에 부여한 여덟 가지 책임 중 다섯 가지 — 원자적 재고 확보, 중복 예약 방지, 상태 전이, 정산 원장, 멱등 처리 — 는 트랜잭션 경계와 동시성 제어 없이는 성립하지 않는다. 응답만 흉내 내는 mock은 이 규칙들을 강제하지 못하므로, 프론트 네 구현이 규칙을 어겨도 통과한다. 그러면 §9의 동등성 검증이 무의미해진다.

**단일 구현으로 두는 이유.** Core API는 네 프론트 구현이 공유하는 단일 권위자다. 두 벌로 만들면 비교의 기준선 자체가 흔들리고 프론트 구현 간 차이가 백엔드 차이에서 온 것인지 프레임워크 차이에서 온 것인지 판정할 수 없다.

상세 요구사항은 `06-DayLink-CoreAPI-PRD.md`에 둔다.

## 9. 두 구현의 동등성 원칙

| 항목 | 반드시 동일 | 달라도 되는 것 |
|---|---|---|
| 사용자 기능 | 화면 목적, 입력, 결과, 예외 | 컴포넌트 분리 방식 |
| 업무 규칙 | 상태 전이, 가격, 권한, 제한 | 상태 관리 도구 |
| API | 스키마, 오류 코드, 멱등 규칙 | 호출 래퍼 구현 |
| URL | 주요 공개·업무 경로 | 내부 파일 경로 |
| 품질 | 접근성, 테스트 시나리오, 목표 성능 | 렌더링·캐시 구현 세부 |
| 분석 | 이벤트 이름과 속성 | 이벤트 호출 위치의 코드 형태 |

한쪽 구현에만 편의 기능을 추가하면 비교 결과가 왜곡된다. 실험 기능은 양쪽에 동시에 반영하거나 본선과 분리한다.

**Core API는 동등성 비교의 대상이 아니라 전제다.** 단일 구현이므로 비교할 짝이 없고 대신 네 프론트 구현이 모두 같은 서버 규칙 위에서 평가되도록 보장한다. 따라서 프론트 구현 편의를 위해 Core API에 한쪽에만 유리한 엔드포인트를 추가하지 않는다. 그런 요청이 생기면 네 구현 모두가 쓰는 형태로 설계하거나, 프론트에서 해결한다.

## 10. 공통 비기능 요구사항

### 10.1 접근성

- 키보드만으로 핵심 흐름을 완료할 수 있어야 한다.
- 입력 항목에는 프로그램이 인식할 수 있는 이름과 오류 연결이 있어야 한다.
- 모달은 초점 진입·순환·복귀를 지원한다.
- 색상만으로 상태를 구분하지 않는다.
- 동적 변경과 오류는 보조기기에 전달한다.

### 10.2 보안·개인정보

- B2C와 Admin의 인증 영역, 세션 정책, 쿠키 범위를 분리한다.
- Admin 메뉴를 숨기는 것만으로 권한을 제어하지 않고 API에서 다시 검사한다.
- 개인정보는 역할별 최소 범위만 노출하고 조회·내보내기를 기록한다.
- 로그에는 비밀번호, 결제 인증값, 전체 토큰, 불필요한 개인정보를 남기지 않는다.

### 10.3 신뢰성

- 네트워크 재시도 때문에 중복 예약·환불·체크인이 생기지 않아야 한다.
- 상태 변경 실패 시 성공처럼 보이는 낙관적 화면을 유지하지 않는다.
- 오류는 사용자가 할 수 있는 다음 행동을 함께 안내한다.

### 10.4 관측성

- 모든 요청에 추적 ID를 부여한다.
- 핵심 상태 변경은 행위자, 시각, 대상, 변경 전후, 사유를 기록한다.
- B2C 전환 퍼널과 Admin 처리 시간을 구현별로 같은 이벤트 정의로 수집한다.

## 11. 학습 완료 기준

다음 조건을 모두 충족해야 비교 학습이 완료된 것으로 본다.

1. B2C PRD의 동일 인수조건이 Next.js와 Nuxt 구현에서 모두 통과한다.
2. Admin PRD의 동일 인수조건이 React와 Vue 구현에서 모두 통과한다.
3. 같은 API 명세 준수 테스트와 핵심 E2E 시나리오를 네 구현이 공유한다.
4. 기술별 구현 판단을 ADR에 기록하고, 단순 코드량이 아니라 사용자 성능·복잡도·유지보수성을 비교한다.
5. 한 구현의 미완성 기능을 프레임워크 한계로 오판하지 않는다.
6. **Core API PRD의 인수조건이 실제 데이터베이스와 동시 요청 조건에서 통과한다.** 순차 요청만으로 통과한 것은 통과로 보지 않는다.
7. **§8의 여덟 가지 책임마다, 클라이언트가 판단하면 어떤 시나리오에서 깨지는지 설명할 수 있다.**

6번과 7번은 v2.1에서 추가됐다. Core API가 신규 학습 영역이고 비교할 짝이 없으므로, 완료 판정을 "동작한다"가 아니라 "동시성 조건에서 통과한다"와 "왜 서버가 판단해야 하는지 설명할 수 있다"로 둔다.

## 12. 범위 밖

- 실제 PG 계약·정산 송금·세금계산서 발행
- 실명 인증, 해외 결제, 다국어·다통화
- 여러 회차를 한 번에 구매하는 장바구니
- 고객의 부분 취소·부분 인원 변경
- 실시간 채팅, 추천 AI, 소셜 피드
- 마이크로 프론트엔드, 자체 렌더러, 프레임워크 내부 구현 실험

Core API에서도 다음은 범위 밖이다.

- 다중 리전·다중 인스턴스 운영과 분산 트랜잭션
- 메시지 브로커를 전제로 한 이벤트 소싱·CQRS
- 쿠버네티스 기반 운영 인프라와 무중단 배포 파이프라인
- 실제 PG·은행 연동과 웹훅 서명 검증
- 대규모 트래픽을 전제로 한 샤딩·캐시 계층 설계

Core API의 학습 목표는 규모가 아니라 **정확성**이다. 단일 인스턴스와 단일 데이터베이스에서 동시성·멱등성·불변 원장을 정확히 만드는 것이 목표이며 확장성 주제는 그것이 끝난 뒤의 별도 과제다.

실무에서 자주 쓰이지 않거나 제품 흐름에 억지로 끼워 넣어야 하는 기능은 학습 범위에 포함하지 않는다.
