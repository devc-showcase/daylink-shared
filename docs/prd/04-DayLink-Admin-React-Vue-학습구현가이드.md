# DayLink Admin React·Vue 비교 학습 구현 가이드

| 항목 | 내용 |
|---|---|
| 기준 PRD | `02-DayLink-Admin-PRD.md` |
| 구현 A | React SPA |
| 구현 B | Vue SPA |
| 제품 범위 | 완전히 동일 |
| 목표 | 메타 프레임워크 없이 복잡한 업무 SPA를 구성하며 두 라이브러리의 실무 차이를 비교 |

## 1. 이 배치가 학습에 적합한 이유

Admin은 검색 노출보다 로그인 이후의 표, 필터, 복합 폼, 역할 권한, 대량 작업, 실시간 상태 갱신, 오프라인 동기화가 중요하다. 서버에서 공개 HTML을 만드는 능력보다 브라우저 안의 상태 소유권과 상호작용 설계가 학습의 중심이다.

따라서 React와 Vue를 각각 SPA로 구성하면 메타 프레임워크가 대신 결정해 주는 라우팅·데이터 요청·상태·오류 처리 구조를 직접 선택하고 비교할 수 있다.

다만 이는 모든 실무 React 프로젝트에 SPA가 우선이라는 뜻이 아니다. React 공식 문서는 새 앱에 프레임워크 사용을 우선 권장한다. 이 프로젝트는 이미 별도 Core API가 있고 검색 노출이 필요 없는 내부 업무 앱이다. 두 라이브러리 자체를 비교하려는 목적도 있어 SPA 구성을 의도적으로 선택한다.

## 2. 비교의 원칙

1. Admin은 제품 하나이며 파트너·현장·플랫폼 운영은 권한 모듈이다.
2. React와 Vue 구현은 같은 URL, 화면 ID, API, 권한, 필드, 상태, 인수조건을 사용한다.
3. 두 구현 모두 같은 SPA 제약에서 시작한다. 한쪽만 SSR이나 메타 프레임워크를 사용하지 않는다.
4. 생태계 도구를 무조건 배제하지 않는다. 실무에서 일반적인 라우터·서버 상태·폼·테스트 도구는 사용할 수 있다.
5. 라이브러리의 모든 API를 한 번씩 쓰기 위한 코드를 만들지 않는다. 제품 문제에 필요한 기능만 사용한다.
6. Composition API와 React 함수 컴포넌트를 기본으로 비교한다.

## 3. 권장 기준선

| 영역 | React SPA | Vue SPA | 공통 원칙 |
|---|---|---|---|
| 빌드 | Vite 기반 TypeScript | create-vue의 Vite·TypeScript | 제품 빌드·환경 변수 규칙 통일 |
| 라우팅 | React Router 계열 | Vue Router | 같은 경로·권한 결과 |
| 서버 상태 | 검증된 쿼리 캐시 도구 | 같은 개념의 Vue 어댑터 | API 캐시와 UI 상태 분리 |
| 전역 UI 상태 | Context·reducer 또는 경량 저장소 | Pinia | 필요한 상태만 전역화 |
| 폼 | React 생태계 폼 도구 또는 명시적 상태 | Vue 생태계 폼 도구 또는 명시적 상태 | 같은 스키마·오류 매핑 |
| 테스트 | Vitest, Testing Library 계열 | Vitest, Vue Test Utils | 공통 E2E 별도 실행 |
| E2E | 같은 브라우저 테스트 프로젝트 | 같은 브라우저 테스트 프로젝트 | 시나리오와 선택자 공유 |
| PWA | 동일 서비스 워커 정책 | 동일 서비스 워커 정책 | 오프라인 데이터·동기화 규칙 공유 |

도구 선정은 구현 시작 전 ADR로 고정한다. 도구 수를 같게 맞출 필요는 없지만 한쪽에서만 어려운 문제를 외부 패키지로 완전히 숨기면 비교 근거가 약해지므로 이유를 기록한다.

## 4. 상태 분류

상태를 먼저 분류한 뒤 React·Vue 도구를 선택한다.

| 상태 종류 | 예시 | 소유 위치 |
|---|---|---|
| URL 상태 | 검색어, 필터, 정렬, 페이지, 탭 | 라우터 |
| 서버 상태 | 상품, 예약, 환불, 정산, 권한 | 쿼리 캐시와 Core API |
| 폼 초안 | 상품 편집, 입점, 사고 보고 | 화면·폼 단위, 필요 시 임시 저장소 |
| 세션 문맥 | 사용자, 역할, 조직, 장소 | 인증·문맥 저장소 |
| 일시 UI 상태 | 팝업, 드로어, 선택 행 | 가까운 컴포넌트 |
| 장기 사용자 설정 | 표 열, 저장한 보기 | 사용자 설정 API 또는 제한된 로컬 저장 |
| 오프라인 상태 | 명단 스냅숏, 전송 대기 이벤트 | IndexedDB 계층과 동기화 관리자 |

서버 응답을 전역 저장소에 다시 복사해 두 개의 원본을 만들지 않는다. 계산 가능한 값은 파생 상태로 만든다. effect·watch로 동기화하는 코드는 최소화한다.

## 5. 개념 대응표

다음은 문법의 일대일 치환표가 아니라 같은 제품 문제를 학습하기 위한 비교 지점이다.

| 제품 문제 | React에서 학습 | Vue에서 학습 |
|---|---|---|
| 지역 상태 | `useState`, `useReducer` | `ref`, `reactive` |
| 파생 상태 | 렌더 중 계산, `useMemo`의 선택적 사용 | `computed` |
| 외부 동기화 | `useEffect` | `watch`, `watchEffect` |
| 재사용 로직 | custom Hook | composable |
| 하위 의존성 제공 | Context | `provide`·`inject` |
| 전역 업무 문맥 | Context·reducer 또는 저장소 | Pinia store |
| 느린 목록 입력 | transition·deferred value 검토 | 반응성 분리·스케줄링·디바운스 검토 |
| 비동기 컴포넌트 | lazy·Suspense 경계 | async component·Suspense 경계 |
| DOM 외부 UI | portal | Teleport |
| 화면 유지 | 라우터·상태 소유권으로 설계 | KeepAlive의 선택적 적용 |
| 오류 격리 | Error Boundary | error capture·앱 오류 처리 |
| 외부 저장소 구독 | `useSyncExternalStore` 검토 | 반응형 저장소·구독 어댑터 |
| 참조·DOM | `useRef` | template ref |

React의 effect와 Vue의 watch는 “값이 바뀌면 무엇이든 처리하는 곳”으로 쓰지 않는다. 외부 시스템 동기화가 아닌 파생 계산은 각각 렌더 계산과 `computed`를 우선한다.

## 6. 기능별 학습 과제

### 6.1 애플리케이션 셸·라우팅

공통 과제:

- 로그인, 추가 인증, 역할·조직 선택, 모듈별 중첩 경로를 구성한다.
- 역할에 따른 메뉴와 경로 접근을 제어한다.
- 표 필터·페이지·정렬·탭을 URL에 반영한다.
- 저장하지 않은 폼의 화면 이탈을 확인한다.
- 권한 변경 후 현재 화면이 더 이상 허용되지 않으면 안전한 경로로 이동한다.

비교 질문:

- 레이아웃과 경로 데이터의 경계가 어떻게 다른가?
- 라우터 가드와 화면 내부 권한 확인의 책임을 어디까지 두었는가?
- 브라우저 뒤로가기 시 표와 드로어 상태가 기대대로 복원되는가?

### 6.2 표·필터·대량 데이터

공통 과제:

- 서버 페이지 이동, 다중 필터, 정렬, 열 표시, 저장한 보기를 구현한다.
- 행 선택과 검색 결과 전체 선택을 구분한다.
- 긴 목록은 필요한 경우 가상화를 사용하되 접근성을 확인한다.
- 개인정보 열람과 마스킹, 내보내기 권한을 구현한다.
- 필터 입력 중 불필요한 요청을 줄이고 오래된 응답이 최신 결과를 덮지 않게 한다.

비교 질문:

- 각 행의 불필요한 다시 렌더링을 어떤 증거로 판단했는가?
- 최적화 API를 적용하기 전후 실제 측정값이 개선됐는가?
- 반응형 의존성과 컴포넌트 경계를 개발 도구로 설명할 수 있는가?

### 6.3 복합 폼·초안·동시 수정

공통 과제:

- 입점과 상품 편집의 단계형 폼을 만든다.
- 항목별 오류, 상단 오류 요약, 임시 저장, 제출, 반려 후 재작성을 지원한다.
- 서버 버전과 편집 버전을 비교해 동시 수정 충돌을 처리한다.
- 이미지 업로드의 진행·실패·재시도를 처리한다.
- 역할 전환과 화면 이탈 시 저장되지 않은 변경을 보호한다.

비교 질문:

- 필드 상태를 제어형·비제어형으로 선택한 이유는 무엇인가?
- 폼 전체가 매 입력마다 갱신되는가, 필요한 필드만 갱신되는가?
- 서버 오류를 동일한 필드 스키마로 어떻게 매핑했는가?

### 6.4 서버 상태·변경·낙관적 UI

공통 과제:

- 목록과 상세의 캐시 키, 새로 고침, 무효화 규칙을 정한다.
- 알림 읽음이나 행 표시 설정처럼 되돌릴 수 있는 작업만 제한적으로 낙관 처리한다.
- 승인, 환불, 정산, 권한 변경은 서버 확정 전 성공처럼 표시하지 않는다.
- 중복 전송 방지와 멱등 키를 적용한다.
- 요청 경쟁과 취소, 네트워크 복구를 처리한다.

### 6.5 역할·권한

공통 과제:

- 로그인 사용자의 역할·조직·장소 범위를 세션 문맥으로 관리한다.
- 메뉴, 버튼, 경로, API 오류에서 일관된 권한 결과를 제공한다.
- 권한이 바뀌면 관련 서버 캐시를 지우고 현재 문맥을 다시 검증한다.
- 권한 밖 데이터를 잠깐이라도 이전 화면에 남기지 않는다.

권한 컴포넌트는 사용성을 위한 것이며 보안의 최종 경계가 아니다. API 검사는 항상 남아 있어야 한다.

### 6.6 모달·드로어·포커스

공통 과제:

- 상세 드로어, 확인 모달, 전역 알림 영역을 문서 구조 밖 오버레이에 렌더링한다.
- 열기 전 초점 저장, 내부 초점 순환, 닫기 후 복귀를 구현한다.
- 중첩 모달을 피하고 긴 업무는 별도 경로로 전환한다.
- 브라우저 뒤로가기로 열린 상세를 닫을 수 있게 할지 URL 정책으로 결정한다.

이 기능에서 React의 portal과 Vue의 Teleport를 자연스럽게 비교할 수 있다.

### 6.7 코드 분할·대기·오류

공통 과제:

- 파트너, 현장, 플랫폼 운영 모듈을 경로 단위로 지연 로딩한다.
- 큰 편집기·차트·QR 스캐너는 필요한 화면에서만 불러온다.
- 전체 오류와 화면 일부 오류를 구분한다.
- 지연 로딩 실패, API 실패, 권한 오류, 데이터 없음의 복구 행동을 다르게 제공한다.

### 6.8 현장 PWA·오프라인 동기화

공통 과제:

- 같은 Admin의 `/desk` 경로에서 설치 가능한 현장 모드를 제공한다.
- 회차 명단을 사용자가 명시적으로 내려받고 만료 시각을 표시한다.
- IndexedDB에 최소 데이터와 전송 대기 이벤트를 저장한다.
- 네트워크 상태만 믿지 않고 요청 성공 여부로 온라인 상태를 판단한다.
- `clientEventId` 기반으로 체크인 재전송을 멱등 처리한다.
- 여러 탭·기기가 같은 대기열을 처리할 때 중복 전송을 막는다.
- 서비스 워커 갱신 중 데이터 형식 변화와 이전 대기열 마이그레이션을 검증한다.

비교 질문:

- UI 반응성과 오프라인 저장소 구독을 어떻게 연결했는가?
- 컴포넌트 수명주기와 무관한 동기화 관리자를 어디에 두었는가?
- 같은 충돌 입력이 두 구현에서 같은 해결 결과를 내는가?

### 6.9 실시간성

공통 과제:

- 체크인 수, 환불 상태, 비동기 작업 상태를 주기 조회 또는 서버 이벤트로 갱신한다.
- 화면이 보이지 않을 때 갱신 빈도를 줄인다.
- 연결 재개 시 누락 이벤트를 전체 상태 조회로 보정한다.
- 실시간 이벤트가 로컬 편집 폼을 무조건 덮어쓰지 않게 한다.

실시간 통신 자체를 학습하기 위해 모든 화면에 소켓을 넣지 않는다. 체크인과 긴 작업처럼 실제 효용이 있는 곳에만 적용한다.

## 7. 컴포넌트 설계 비교

### 7.1 공통 설계 단위

- 디자인 기본 요소: 버튼, 입력, 선택, 배지, 팝업
- 업무 패턴: 필터 바, 서버 표, 상태 타임라인, 승인 패널, 금액 내역
- 화면 기능: 상품 편집, 체크인, 환불 상세, 정산 대사

### 7.2 비교 시 주의점

- React 컴포넌트와 Vue SFC의 파일 구성을 억지로 같게 하지 않는다.
- props·이벤트 인터페이스는 같은 업무 의미를 갖되 문법까지 맞추지 않는다.
- 지나치게 범용적인 거대 표·폼 생성기를 먼저 만들지 않는다.
- 세 화면 이상에서 실제로 반복되는 패턴부터 공통화한다.
- 슬롯과 children의 사용 경험, 이벤트 전달, 양방향 입력 모델의 차이를 기록한다.

## 8. 공통 테스트 체계

| 계층 | 공통 기준 | 구현별 실행 |
|---|---|---|
| 순수 도메인 | 취소·수수료·권한 예제 | 같은 입력·기대값 |
| API 명세 | OpenAPI와 오류 코드 | 생성 클라이언트 검증 |
| 컴포넌트 | 사용자 행동·접근성 | 각 테스트 도구로 독립 구현 |
| 라우팅 | URL·권한·뒤로가기 | 같은 경로 표 사용 |
| E2E | 대표 10개 업무 흐름 | 같은 브라우저 시나리오 |
| 오프라인 | 스냅숏 만료·중복·충돌 | 네트워크 차단 조건 공유 |
| 성능 | 대용량 표·복합 폼·체크인 | 같은 데이터 크기·기기 |

테스트는 컴포넌트 내부 인스턴스나 프레임워크 전용 DOM 구조보다 사용자가 보는 역할·이름·상태를 기준으로 작성한다.

## 9. 권장 구현 순서

1. Vite·TypeScript·라우터·테스트 기준선
2. 공통 셸, 로그인, 역할·조직 문맥, 권한
3. 서버 표·필터·상세 드로어
4. 상품 복합 폼과 심사 상태
5. 예약·환불·정산의 상태 타임라인과 고위험 작업
6. 비동기 내보내기와 알림
7. 모바일 현장 화면과 체크인
8. 오프라인 저장·대기열·충돌 해결
9. 접근성·성능·번들 분석
10. 동일 E2E와 측정값 비교

기능 묶음마다 React와 Vue를 번갈아 구현한다. 한쪽 전체를 먼저 끝내면 뒤쪽 구현이 단순 번역이나 기억 의존 작업이 될 수 있다.

## 10. 비교 측정 항목

| 항목 | 측정 방법 |
|---|---|
| 초기 적재 | 로그인·대시보드의 JS 전송량과 표시 시점 |
| 경로 분할 | 미방문 모듈 코드가 초기 번들에 포함되는지 |

| 개발 경험 | 타입 오류, 개발 도구 추적, 테스트 작성 난이도 |

코드 줄 수, 취향, 예제의 짧음만으로 우열을 결론내리지 않는다.

## 11. 자연스럽게 학습되는 범위

### React

- 컴포넌트·props·이벤트·조건부 렌더링
- `useState`, `useReducer`, Context, custom Hook
- effect의 올바른 외부 동기화 용도
- 참조, portal, error boundary, lazy·Suspense
- 라우터·서버 상태·폼 도구의 조합
- 렌더링 측정과 필요한 경우의 메모화·transition

### Vue

- SFC, 템플릿, props·emits·slots
- `ref`, `reactive`, `computed`, `watch`
- composable, provide·inject, Pinia
- Teleport, Transition, KeepAlive, 비동기 컴포넌트·Suspense
- Vue Router와 폼·서버 상태 도구의 조합
- 반응성 추적과 갱신 범위 측정

### 공통 실무 범위

- TypeScript, 접근성, 테스트, 오류 복구
- 인증·권한, API 명세, 대량 데이터, 파일 작업
- PWA, IndexedDB, 서비스 워커, 동기화 충돌
- 성능 측정, 코드 분할, 운영 로그

## 12. 의도적으로 제외하는 학습 범위

- 같은 화면에 React와 Vue를 동시에 탑재
- 제품 이유 없는 클래스 컴포넌트·Options API 강제 사용
- 모든 상태의 전역 저장소화
- 모든 성능 API를 쓰기 위한 임의의 느린 화면
- 직접 만든 라우터·폼 엔진·쿼리 캐시
- 마이크로 프론트엔드와 런타임 모듈 연합
- 실험 기능만을 위한 업무 기능 추가

기존 방식의 읽기 능력이 필요하면 작은 별도 예제로 충분하다. 본 제품 코드에는 현재 실무 흐름에 맞는 기본 방식을 사용한다.
