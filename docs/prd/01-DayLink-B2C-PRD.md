## 1. 제품 개요

DayLink B2C는 사용자가 지역별 클래스와 체험을 발견하고 일정과 인원을 선택해 예약한 뒤, 취소·환불·후기까지 처리하는 공개 웹 서비스다.

### 1.1 해결할 문제

- 사용자는 지역, 날짜, 관심 분야에 맞는 체험을 한곳에서 비교하기 어렵다.
- 상세 페이지의 가격·잔여 좌석·취소 조건이 불명확하면 예약을 중단한다.
- 결제 후 예약 상태와 환불 진행 상황을 각각 확인하기 어렵다.
- 체험 전후에 필요한 장소 안내와 후기 작성 경로가 흩어져 있다.

### 1.2 제품 목표

1. 비회원도 검색 결과와 상품 상세를 충분히 확인할 수 있게 한다.
2. 상품 상세에서 예약 확정까지 불필요한 이탈을 줄인다.
3. 가격·재고·취소 조건을 예약 전에 명확히 보여준다.
4. 예약, 취소, 환불, 후기의 상태를 사용자가 스스로 확인할 수 있게 한다.
5. 같은 요구사항으로 만든 두 구현을 사용자 결과와 품질 기준으로 비교할 수 있게 한다.

### 1.3 범위 밖

- 다중 회차 장바구니
- 고객의 부분 취소·부분 인원 변경
- 실시간 채팅과 커뮤니티 피드
- 실제 결제·실명 인증
- 해외 지역·다국어·다통화
- 파트너 또는 운영자용 기능

## 2. 사용자와 권한

| 구분 | 권한 |
|---|---|
| 비회원 | 홈·검색·상세·후기·도움말 열람, 로그인·가입 |
| 고객 | 비회원 권한, 결제·예약·취소, 찜, 후기, 프로필 관리 |
| 이용 정지 고객 | 공개 화면 열람, 본인 예약 조회. 신규 예약·후기 작성 제한 |

비회원이 인증이 필요한 기능을 선택하면 현재 목적지를 보존한 채 로그인으로 이동한다. 로그인 성공 후 원래 흐름으로 복귀한다.

## 3. 핵심 성과 지표

학습 프로젝트이므로 절대 매출 목표 대신 흐름의 완성도와 기술 구현의 동등성을 측정한다.

| 지표 | 정의 | 목표 |
|---|---|---:|
| 검색 성공률 | 검색 후 상세 페이지를 연 세션 비율 | 45% 이상 |
| 예약 진입률 | 상세 조회 후 일정 선택을 시작한 비율 | 12% 이상 |
| 결제 완료율 | 유효한 임시 확보 생성 후 예약 확정 비율 | 70% 이상 |
| 고객 자가 해결률 | 취소·환불 문의 없이 화면에서 완료한 비율 | 80% 이상 |
| 구현 동등성 | 공통 핵심 E2E 통과율 | 양쪽 100% |
| 접근성 | 핵심 흐름의 중대 자동 검사 오류 | 0건 |

화면 경로는 제품 요구사항이다. 두 구현이 기술적 이유 없이 서로 다른 공개 URL을 사용하지 않는다.

**식별자 규약.** 체험은 상세와 예약 진입 모두 `{id}`를 사용한다. 분류 체계인 카테고리·지역과 정적 문서인 정책은 `{slug}`를 유지한다. 체험에 `{slug}`를 쓰지 않는 이유는 상품명 수정으로 공개 URL이 깨지는 것을 막기 위해서다. 검색 노출은 §9의 표준 URL과 구조화 데이터로 확보한다.

**정적 문서 규약.** 서비스 소개는 별도 경로를 두지 않고 `/policies/about`으로 제공한다. `/policies/{slug}`가 다루는 slug는 `about`, `terms`, `privacy`, `cancellation`이며 목록은 유한하고 사전에 열거된다. 별도 `/about` 경로를 두지 않는 이유는 렌더링 전략과 색인 정책이 정책 문서와 동일해 경로만 늘어나기 때문이다.

## 5. 상세 기능 요구사항

### 5.1 홈·탐색

#### B2C-HOME-01 홈 구성

- 지역, 날짜, 인원, 키워드를 입력하는 검색 진입부를 제공한다.
- 운영자가 지정한 기획전, 인기 카테고리, 가까운 체험을 노출한다.
- 위치 권한이 없거나 거부된 경우 서울 중심의 기본 지역을 사용하고 변경할 수 있게 한다.
- 상품 카드는 대표 이미지, 제목, 지역, 평점·후기 수, 1인 기준가, 가장 빠른 예약 가능일을 표시한다.

#### B2C-SRCH-01 검색 조건

- 키워드, 지역, 카테고리, 날짜 범위, 인원, 가격 범위, 즉시 확정 여부로 필터링한다.
- 정렬은 추천순, 낮은 가격순, 높은 평점순, 가까운 날짜순을 제공한다.
- 검색 조건은 URL에 반영해 새로고침·뒤로가기·공유 후에도 유지한다.
- 결과 건수와 현재 적용 필터를 표시하고 필터를 개별·전체 해제할 수 있게 한다.

#### B2C-SRCH-02 검색 예외

- 결과가 없으면 조건 완화 방법과 인기 대안을 제공한다.
- 잘못된 쿼리는 무시하지 말고 유효한 값으로 정규화했음을 화면에 반영한다.
- 검색 API 실패 시 이전 결과를 최신 결과처럼 표시하지 않는다.

### 5.2 상품 상세

#### B2C-EXPR-01 상세 정보

- 제목, 이미지, 설명, 위치, 진행 시간, 포함·불포함 항목, 준비물, 연령 제한, 접근성 정보, 파트너 정보, 후기, 취소 정책을 표시한다.
- 가격은 1인 기준과 선택 인원 기준 예상 총액을 구분한다.
- 공개 중단 또는 삭제된 상품은 신규 예약을 막고 기존 예약 진입은 유지한다.
- 상세와 예약 진입은 같은 `{id}`를 사용한다. 상품명이 바뀌어도 공개 URL은 바뀌지 않는다.

#### B2C-EXPR-02 일정과 재고

- 날짜별 회차, 시작·종료 시각, 잔여 좌석, 매진 상태를 표시한다.
- 상세 페이지의 잔여 수량은 안내값이며 예약 시 서버가 다시 검증한다고 명시한다.
- 선택 회차가 품절되면 다른 회차를 선택하도록 안내한다.

#### B2C-EXPR-03 후기

- 이용 완료·정상 예약에 연결된 후기만 “이용 확인”으로 표시한다.
- 평점 분포와 최신순·평점순 정렬을 제공한다.
- 운영 정책 위반으로 숨김 처리된 후기는 집계 정책에 따라 제외한다.

### 5.3 인증

#### B2C-AUTH-01 로그인·가입

- 이메일과 비밀번호 방식만 MVP에 포함한다.
- 가입 시 필수 약관과 선택 수신 동의를 분리한다.
- 로그인 실패는 계정 존재 여부를 과도하게 노출하지 않는 메시지를 사용한다.
- 예약 중 로그인하더라도 선택한 상품·회차·인원은 보존한다. 단, 재고는 로그인 후 다시 확인한다.

#### B2C-AUTH-02 세션

- 인증 만료로 결제가 중단되면 재로그인 후 가능한 지점으로 복귀한다.
- 공용 기기에서 로그아웃하면 고객 데이터가 남은 화면·저장소를 정리한다.

### 5.4 예약·결제

#### B2C-RSV-01 일정·인원 선택

- 예약 인원은 1~6명이며 회차 잔여 수량을 넘을 수 없다.
- 선택 완료 시 서버가 10분짜리 임시 확보를 생성한다.
- 동일 사용자의 같은 회차에 활성 임시 확보가 있으면 새로 중복 생성하지 않고 복구한다.

#### B2C-RSV-02 주문 확인

- 상품·회차·장소·인원·단가·할인·총 결제액·취소 정책을 한 화면에서 확인한다.
- 쿠폰은 서버 검증 후 적용하며 유효하지 않으면 이유를 표시한다.
- 임시 확보 만료 시 결제 진행을 막고 회차 재선택으로 이동한다.

#### B2C-RSV-03 모의 결제

- 성공, 사용자 취소, 인증 실패, 시간 초과의 테스트 시나리오를 제공한다.
- 결제 버튼 연속 선택이나 네트워크 재시도로 중복 예약이 생기지 않아야 한다.
- 화면 전환만으로 결제 성공을 확정하지 않고 서버의 예약 상태를 조회한다.
- 처리 중 창을 닫았다가 다시 방문해도 결제 결과를 확인할 수 있어야 한다.

#### B2C-RSV-04 예약 완료·실패

- 성공 시 예약 번호, 상태, 회차, 인원, 결제액, 장소 안내, 취소 정책을 표시한다.
- 실패 시 실패 사유 범주와 재시도 가능 여부를 표시한다.
- 결과가 불명확하면 “확인 중” 상태를 제공하고 재결제를 유도하지 않는다.

### 5.5 예약 조회·취소·환불

#### B2C-BOOK-01 예약 목록

- 예정, 이용 완료, 취소로 구분한다.
- 각 항목에 상태, 체험명, 일시, 인원, 결제액을 표시한다.
- 페이지 이동 또는 더보기 후 뒤로 돌아왔을 때 목록 위치와 조건을 복구한다.

#### B2C-BOOK-02 예약 상세

- 예약·결제·환불·출석 상태를 섞지 않고 구분해 표시한다.
- 예약 당시 상품명, 장소, 회차, 가격, 취소 정책 스냅숏을 사용한다.
- 취소 가능 여부와 예상 환불액은 현재 서버 시각 기준으로 조회한다.
- 해당 예약의 문의 접수와 답변 스레드로 진입할 수 있다.

#### B2C-CAN-01 취소

- 접수 전 환불 예상액, 차감액, 적용 정책, 계산 기준 시각을 표시한다.
- 사용자가 명시적으로 동의한 뒤 취소 요청을 생성한다.
- 취소 요청 중복 전송은 같은 결과를 반환한다.
- 취소 완료와 환불 완료를 분리해 상태와 예상 처리 단계를 안내한다.

#### B2C-INQ-01 예약 문의

- 문의는 예약에 종속된다. 예약과 무관한 일반 문의 창구는 두지 않는다.
- 유형, 본문, 선택 이미지를 입력하고 접수 결과를 표시한다.
- 고객 문의와 운영자 답변을 시간순 스레드로 보여준다.
- 문의 접수 재전송은 같은 결과를 반환하고 중복 접수를 만들지 않는다.
- 취소·환불 처리 중인 예약에도 문의할 수 있으며 문의 상태와 예약·환불 상태를 섞어 표시하지 않는다.

### 5.6 찜·후기·계정

#### B2C-FAV-01 찜

- 비회원이 고른 찜은 로그인한 뒤에 이어서 반영한다.
- 판매 중단 상품은 찜 목록에서 상태를 표시하고 예약을 막는다.

#### B2C-REV-01 후기

- `COMPLETED` 예약의 대표 예약자만 예약당 후기 한 건을 작성한다.
- 평점 1~5, 본문, 선택 이미지로 구성한다.
- 금칙어·길이·이미지 형식 검사를 통과하지 못하면 항목별 오류를 표시한다.
- 수정 가능 기간과 운영자 숨김 상태를 표시한다.

#### B2C-MY-01 계정

- 이름, 연락처, 알림 동의, 비밀번호를 관리한다.
- 탈퇴 전 예정 예약과 처리 중 환불이 있으면 제한 사유를 표시한다.
- 법적 보관이 필요한 거래 데이터와 화면에서 제거되는 프로필 데이터를 구분해 안내한다.

## 6. 공통 화면설계 기준

### 6.1 레이아웃·반응형

- 기준 폭은 모바일 360px 이상, 태블릿 768px 이상, 데스크톱 1280px 이상으로 정의한다.
- 모바일을 기준으로 핵심 행동이 접히거나 가려지지 않게 한다.
- 결제·취소 화면의 최종 행동 버튼은 내용과 겹치지 않으며 화면이 짧을 때 고정 영역이 입력을 가리지 않는다.
- 이미지 비율이 달라도 카드 높이와 정보 순서가 무너지지 않아야 한다.

### 6.2 버튼·링크

- 한 화면의 주 행동은 원칙적으로 하나다.
- 처리 중인 버튼은 중복 선택을 막고 진행 상태를 표시한다.
- 삭제·취소처럼 되돌리기 어려운 행동은 대상과 영향을 다시 확인한다.
- 링크와 버튼은 시각뿐 아니라 의미와 키보드 동작도 구분한다.

### 6.3 폼·유효성 검사

- 필수 여부, 입력 예시, 제한 조건을 입력 전에 확인할 수 있게 한다.
- 오류는 상단 요약과 해당 항목 가까이에 함께 표시한다.
- 서버 오류가 발생해도 비밀번호·결제 보안값을 제외한 안전한 입력은 보존한다.
- 클라이언트 검사는 편의 기능이며 서버 검사를 대신하지 않는다.

### 6.4 로딩·빈 결과·오류

| 상태 | 표시 원칙 |
|---|---|
| 최초 로딩 | 화면 구조를 예측할 수 있는 자리 표시 또는 명확한 진행 표시 |
| 추가 로딩 | 기존 데이터를 유지하고 추가 영역에 진행 표시 |
| 빈 결과 | 오류와 구분하고 조건 완화·다음 행동 제공 |
| 재시도 가능 오류 | 원인 범주, 재시도 버튼, 입력 보존 여부 안내 |
| 권한 오류 | 로그인 필요와 접근 불가를 구분 |
| 처리 결과 불명 | 중복 실행을 막고 상태 조회 제공 |

### 6.5 팝업·알림

- 중요한 입력을 긴 팝업 안에 과도하게 넣지 않는다.
- 확인 팝업에는 대상, 결과, 되돌릴 수 있는지 여부를 적는다.
- 일시 알림만으로 결제·취소 결과를 전달하지 않고 결과 화면이나 상태 영역을 제공한다.

### 6.6 메시지 문체

- 내부 상태 코드나 기술 용어를 그대로 노출하지 않는다.
- “오류가 발생했습니다”에서 끝내지 않고 사용자가 할 수 있는 다음 행동을 안내한다.
- 가격, 환불, 재고 메시지는 서버가 확정한 값과 기준 시각을 사용한다.

## 7. 분석 이벤트

| 이벤트 | 발생 시점 | 필수 속성 |
|---|---|---|
| `view_home` | 홈 노출 | 구현 식별자, 세션 ID |
| `search_experience` | 검색 확정 | 조건, 결과 수 |

| `select_slot` | 회차 선택 | 상품·회차 ID, 인원 |
| `create_hold` | 임시 확보 결과 | 성공 여부, 실패 범주 |

## 8. API·데이터 요구사항

- 모든 쓰기 요청은 멱등 식별자를 사용한다.
- 가격과 재고는 서버 응답을 기준으로 최종 표시한다.
- 고객은 본인 예약·결제·환불·후기만 조회·변경할 수 있다.
- 예약 상세는 현재 상품이 아닌 예약 스냅숏을 우선 사용한다.
- 예약 문의 접수·조회는 본인 예약 범위에서만 허용하고 접수에 멱등 식별자를 사용한다.
- 목록 응답은 안정적인 정렬 기준과 페이지 정보를 제공한다.
- 오류 응답은 공통 코드, 사용자 메시지 키, 추적 ID, 재시도 가능 여부를 포함한다.

## 9. 성능·검색 노출 요구사항

- 홈, 지역, 카테고리, 공개 상품 상세는 검색 엔진이 핵심 내용을 읽을 수 있어야 한다.
- 제목, 설명, 대표 이미지, 표준 URL, 공유용 메타데이터를 페이지별로 제공한다.
- 품절·중단 상품의 색인 정책과 리디렉션 정책을 명시한다.
- 예약·계정·결제 화면은 검색 결과에서 제외한다.
- 주요 콘텐츠가 늦게 나타나거나 레이아웃이 크게 이동하지 않게 한다.
- 개인 데이터와 예약 가능 여부를 공용 캐시에 저장하지 않는다.

## 11. 대표 E2E 시나리오

1. 비회원 검색 → 상세 → 로그인 → 회차 선택 → 쿠폰 → 모의 결제 성공 → 예약 확인
2. 마지막 한 자리 동시 예약 → 한 사용자 확정 → 다른 사용자 품절 안내
3. 결제 처리 중 새로고침 → 서버 상태 조회 → 중복 없는 완료 화면
4. 임시 확보 만료 → 결제 차단 → 새 임시 확보 생성
5. 예약 상세 → 취소 예상액 조회 → 취소 접수 → 환불 처리 상태 확인
6. 이용 완료 → 후기 작성 → 상품 상세에 이용 확인 후기 노출
7. 판매 중단 상품의 기존 예약 조회는 가능하지만 신규 예약은 불가
8. 다른 고객 예약 ID 직접 접근 → 데이터 미노출

## 12. 출시 판단 기준

- P0·P1 인수조건이 두 구현에서 모두 통과해야 한다.
- 같은 테스트 계정과 시드 데이터로 결과를 비교해야 한다.
- B2C 한쪽에만 존재하는 기능·문구·업무 규칙이 없어야 한다.
- 결제·재고·취소의 최종 값이 클라이언트 계산에 의존하지 않아야 한다.
- 실제 PG와 법률 검토가 필요한 항목은 모의 구현임을 화면과 문서에 표시해야 한다.
