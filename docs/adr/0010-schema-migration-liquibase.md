# ADR-0010 스키마 마이그레이션은 Liquibase로 하고 changelog는 SQL 형식으로 쓴다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** |
| 결정일 | 2026-08-31 |
| 관련 문서 | `05 §4.2`, `06 §8.1`, `fixtures/README.md` |
| 관련 ADR | ADR-0009(이 결정을 예고했다), ADR-0004(명시적 SQL 우선), ADR-0006(MyBatis), ADR-0003(Java 21) |

## 맥락

ADR-0009는 "스키마 버전 관리 도구를 쓴다. 도구 택일은 M1 착수 시 확정"으로 미뤄뒀다. Core API 구현을 시작하기 전에 정해야 한다.

이 프로젝트에서 마이그레이션 도구가 할 일은 넷이다.

1. Core API가 쓸 테이블을 만든다 — `06 §4`의 엔터티 16종
2. **테넌트 스키마 넷에 같은 정의를 적용한다** — `t_next`·`t_nuxt`·`t_react`·`t_vue`. `05 §4.2`가 요구하는 구현별 격리다
3. 스키마 변경 이력을 남긴다
4. 테스트마다 초기화한다

두 번째가 이 프로젝트 특유의 요구다. 보통은 스키마 하나를 관리하는데 여기는 같은 정의를 네 벌 유지해야 하고, 네 벌이 어긋나면 `00 §9`의 동등성 비교가 무의미해진다.

## 결정

**Liquibase를 쓴다.**

**changelog는 SQL 형식으로 쓴다.** 파일 머리에 `--liquibase formatted sql`을 달고 그 아래는 순수 SQL이다. YAML·XML changelog를 쓰지 않는다.

**되돌리기는 `--rollback` 주석으로 직접 적는다.** SQL 형식은 자동 생성이 안 되므로 changeset마다 명시한다.

## 근거

**Liquibase를 고른 이유는 SI 현장에서 더 많이 보기 때문이다.** ADR-0003(Kotlin이 아닌 Java)과 ADR-0006(JPA가 아닌 MyBatis)이 같은 기준으로 결정됐다 — **학습 경량화보다 현장 전이 가치를 앞에 둔다**(`00 §2` 2순위 목적). 이 프로젝트의 백엔드는 제로 베이스이고, 제로 베이스 영역에서 배운 도구는 그대로 현장 읽기 능력이 된다.

**그런데 Liquibase의 기본 형식은 이 프로젝트의 다른 결정과 부딪힌다.** ADR-0004가 명시적 SQL을 앞세우고 ADR-0006이 MyBatis를 고른 이유가 둘 다 **SQL을 눈으로 보기 위해서**였다. `06 §8.1`은 "DB가 판정하게 하라"를 요구하며 `SELECT` 후 검사하고 `UPDATE` 하는 두 문장을 금지한다. 조건부 갱신·행 잠금·제약 조건 중 무엇을 쓰는지가 판단의 핵심인데, 스키마가 `createTable` 추상 태그 뒤에 있으면 그 판단이 흐려진다.

**SQL 형식 changelog가 이 충돌을 해소한다.** Liquibase는 형식을 고를 수 있고, SQL 형식이면 파일을 열었을 때 그냥 SQL이다. 도구는 Liquibase를 쓰되 보는 것은 SQL이다.

치르는 대가는 둘이다. 되돌리기 자동 생성을 잃어 `--rollback`을 직접 써야 하고, DB 이식성을 잃는다. 후자는 비용이 아니다 — ADR-0009가 PostgreSQL로 고정했고 이식할 계획이 없다. 전자는 실제 비용이지만, 되돌리기를 손으로 적는 것 자체가 "이 변경을 어떻게 되돌리나"를 생각하게 만드는 장치이기도 하다.

탈락한 대안이다.

| 대안 | 탈락 사유 |
|---|---|
| Flyway | 순수 SQL 파일이라 ADR-0004·0006과 결이 더 맞고 Spring 자료도 많다. 그러나 **현장 전이 가치**를 앞에 두는 기준(ADR-0003·0006)에서 Liquibase가 앞섰다. 무료판에 되돌리기가 없는 것도 테넌트 스키마를 반복 초기화하는 이 프로젝트에 불리하다 |
| Liquibase + YAML changelog | Liquibase 관례 형식이고 되돌리기가 자동 생성된다. 그러나 SQL이 한 꺼풀 안에 들어가 위 충돌이 그대로 남는다 |
| 도구 없이 `schema.sql` | Spring Boot가 기동 시 실행해 주므로 설정이 가장 적다. 그러나 **적용 이력이 남지 않아** 스키마가 바뀐 뒤 어느 테넌트가 따라왔는지 알 수 없다. `00 §9`가 요구하는 "네 구현이 같은 상태"를 보장할 수단이 사라진다 |
| JPA `ddl-auto` | ADR-0004가 이미 기각한 방향이다. 엔터티가 스키마를 정하면 `06 §8.1`이 요구하는 제약 조건과 인덱스를 통제할 수 없다 |

## 결과

- **테넌트 스키마 넷에 같은 changelog를 적용한다.** Liquibase를 스키마별로 한 번씩 돌리되 `databaseChangeLogTable`을 각 스키마에 두어 적용 이력이 섞이지 않게 한다. 초기화는 `DROP SCHEMA t_next CASCADE` 뒤 재적용이다.
- **changeset은 불변이다.** 이미 적용된 changeset을 고치면 checksum이 어긋나 Liquibase가 거부한다. 고칠 일이 생기면 새 changeset을 추가한다. ADR을 고치지 않고 새로 쓰는 것(ADR-0001)과 같은 규칙이다.
- **`--rollback`을 안 적으면 되돌릴 수 없다.** SQL 형식의 대가이므로 changeset을 추가할 때 함께 적는 것을 규칙으로 둔다.
- **시드는 changelog에 넣지 않는다.** `fixtures/*.json`이 시드의 유일한 원본이고 Core API의 로더가 넣는다. 마이그레이션은 구조만 다룬다. 둘을 섞으면 프론트가 보는 시드와 DB의 시드가 갈린다.
- **버전 숫자는 이 ADR에 적지 않는다.** ADR-0009의 원칙대로 잠금 파일이 권위다.
- **번복 조건**: ① SQL 형식으로 인한 `--rollback` 누락이 반복돼 실제 사고가 나면 YAML 형식으로 재검토한다 ② 테넌트 스키마 넷을 Liquibase로 관리하는 것이 M1에서 실제로 막히면 스키마 생성만 별도 스크립트로 빼고 Liquibase는 테이블 정의에 한정한다.
