# ADR-0022 테스트는 Testcontainers로 자기 데이터베이스를 띄운다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** |
| 결정일 | 2026-09-21 |
| 관련 문서 | `05 §4.1`, `05 §4.2`, `06 §12`, `06 §14.2` |
| 관련 ADR | ADR-0009(이 전환을 예고했다), ADR-0021(격리를 실행 단위로 옮긴다), ADR-0010(Liquibase), ADR-0007(동시성 근거) |

## 맥락

테스트가 개발용 데이터베이스(`docker compose`로 띄워 둔 `daylink-postgres`)에 그대로 붙어 있었다. `CreateHoldApiTest`가 실제 `slot` 테이블에 행을 넣었고, 실행이 끝나도 데이터가 남았다.

`06 §12`는 이 프로젝트의 구조적 취약점을 이렇게 적는다 — Core API에는 비교 대상이 없어 **잘못된 설계가 테스트를 통과하며 살아남을 수 있다.** 상시 기동 데이터베이스는 그 취약점을 키운다. 상태가 누적되므로, 준비가 빠진 코드도 "이미 있는 데이터" 덕에 통과한다.

실제로 그런 일이 있었다. 2026-09-18에 `TenantSchemaMigrator`를 지우자 기동 시 마이그레이션이 한 번도 돌지 않는다는 사실이 드러났는데(ADR-0021 결과 참조), 그때까지 가려져 있던 이유가 **개발용 데이터베이스에 테이블이 이미 있었기 때문**이다. 새 환경에 처음 배포했다면 바로 깨졌을 결함이다.

ADR-0021이 "격리는 스키마가 아니라 실행 단위에서 만든다"고 정했다. 이 ADR은 그 구현이다.

## 결정

**테스트가 PostgreSQL 컨테이너를 직접 띄운다.** 다섯 가지를 함께 정한다.

1. **컨테이너는 실행 전체에 하나다.** `TestDatabase`가 static 필드로 들고 있고 클래스 로딩 시 한 번 `start()` 한다. 테스트 클래스마다 띄우지 않는다. `stop()`은 부르지 않고 Testcontainers의 정리 컨테이너(Ryuk)에 맡긴다
2. **이미지 태그를 고정한다.** `postgres:18`이다
3. **Spring을 띄우는 테스트는 `@ServiceConnection`으로 접속 정보를 받는다.** `ContainerConfig`가 컨테이너를 빈으로 올리고, Boot의 `JdbcContainerConnectionDetailsFactory`가 JDBC URL·유저·패스워드를 `spring.datasource.*`에 채운다. `application.yml`의 URL은 테스트에서 쓰이지 않는다
4. **Spring 없이 도는 테스트도 같은 컨테이너를 쓴다.** `DatabaseFixture`가 환경변수 대신 `TestDatabase`에서 접속 정보를 가져온다
5. **실습용 `lab` 스키마는 테스트 코드가 만든다.** `LabSchemaFixture`가 `CREATE SCHEMA IF NOT EXISTS`와 테이블 셋을 실행하고, `LabHoldServiceTest`의 `@BeforeAll`이 부른다. changelog에는 넣지 않는다

**합격 기준을 명시한다.** 개발용 컨테이너를 내린 상태에서 전체 테스트가 통과해야 한다. 이것만이 "정말 격리됐는가"를 가린다.

## 근거

**컨테이너를 하나만 띄우는 이유는 시간이다.** PostgreSQL 컨테이너 기동은 1~2초가 걸리고, 지금 Spring을 띄우는 테스트 클래스만 넷이다. 클래스마다 띄우면 그만큼 곱해진다. 대신 클래스 간에 데이터가 이어지는데, 그건 각 테스트가 `@BeforeEach`로 자기 판을 되돌리는 기존 방식으로 이미 다루고 있다.

**태그를 고정하는 이유는 재현성이다.** `latest`로 두면 어느 날 이미지가 바뀌어 결과가 달라지고, 그 변화를 코드 이력에서 찾을 수 없다. ADR-0009가 잠금 파일로 의존성을 고정한 것과 같은 기준이다.

**`@ServiceConnection`을 쓰는 이유는 배선을 한 곳에 모으기 위해서다.** `@DynamicPropertySource`로 프로퍼티를 직접 채우는 방법도 있지만, 그러면 테스트 클래스마다 같은 코드가 반복되고 프로퍼티 이름을 손으로 맞춰야 한다. 실제로 이 작업 중에 `@ServiceConnection` 없이 `@SpringBootTest`를 붙인 클래스가 하나 있었고, 그것이 개발용 데이터베이스로 가서 컨텍스트가 뜨지 않았다. **배선이 빠지면 조용히 다른 곳에 붙는 게 아니라 요란하게 실패하는 편이 낫다.**

**`lab`을 changelog에 넣지 않는 이유는 경계다.** changelog는 `06 §4`가 정의한 제품 엔터티의 정의다. 학습 실습용 테이블이 거기 섞이면 운영 스키마 정의를 읽는 사람이 무엇이 제품이고 무엇이 연습인지 가릴 수 없다. ADR-0021에서 선택지를 셋 놓고 사용자가 이 방식을 골랐다.

**검토했으나 탈락한 대안**

| 대안 | 탈락 이유 |
|---|---|
| 개발용 컨테이너를 계속 쓴다 | 설정이 가장 적다. 그러나 상태가 누적돼 준비 누락이 가려진다 — 실제로 마이그레이션 결함을 두 달 가까이 가렸다 |
| 테스트 클래스마다 컨테이너 | 격리가 가장 강하다. 그러나 기동 시간이 클래스 수만큼 곱해지고, 지금 얻는 이득이 그 비용을 넘지 않는다 |
| 인메모리 H2 | 가장 빠르다. 그러나 `ADR-0007`의 근거가 PostgreSQL의 READ COMMITTED 동작과 `CHECK` 제약이다. H2로 바꾸면 **통과하는데 운영에서 깨지는** 상황이 되고, `06 §12`가 경고한 바로 그 구조가 된다 |
| `@DynamicPropertySource`로 수동 배선 | 어노테이션 하나를 덜 쓴다. 그러나 테스트마다 반복되고 프로퍼티 이름 오타가 조용한 실패를 만든다 |
| `lab`을 changelog에 넣는다 | 다른 기계에서도 돈다는 이점은 같다. 그러나 제품 스키마 정의에 실습용 테이블이 섞인다 |

## 결과

- **실습 파일을 git으로 추적하기 시작한다.** §6.3이 "`lab` 스키마가 이 노트북에만 있으니 추적하지 않는다"고 정했던 전제가 사라졌다. `LabSchemaFixture`가 어디서든 스키마를 만들기 때문이다
- **Docker가 없으면 테스트가 안 돈다.** 지금까지도 사실상 그랬지만(개발용 컨테이너가 필요했다), 이제는 명시적 전제다. CI를 붙일 때 Docker 사용 가능 여부를 먼저 확인해야 한다
- **첫 실행이 느릴 수 있다.** 이미지를 받아야 하는 환경에서는 그렇다. 현재 개발 기계에는 `postgres:18`이 이미 있다
- `DatabaseFixture`의 "연결 실패 시 `docker compose up -d`로 띄우라"는 안내는 더 이상 맞지 않아 지웠다
- **번복 조건**: 컨테이너 기동이 실제로 개발 흐름을 막을 만큼 느려지면, 자주 도는 테스트만 골라 컨테이너를 공유하는 방식을 재검토한다. 반대로 클래스 간 데이터 누적이 거짓 통과를 만들면 클래스마다 새 컨테이너로 좁힌다
