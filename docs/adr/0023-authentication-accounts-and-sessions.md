# ADR-0023 계정과 인증 수단을 분리하고, 세션은 짧은 액세스 토큰 + 서버 저장 refresh로 한다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** |
| 결정일 | 2026-09-22 |
| 관련 문서 | `06 §3.1`, `06 §7`, `06 §9.1`, `06 §9.3`, `02 §3.1`~`§3.3`, `01 §2`, `errors.md` |
| 관련 ADR | ADR-0003(Java 21), ADR-0006(MyBatis — 현장 전이 기준), ADR-0007(트랜잭션 경계), ADR-0010(Liquibase) |

## 맥락

인증은 처음부터 범위 안이었다. `06 §3.1`이 Core API 범위의 **첫 줄**에 "인증·인가와 역할·조직·장소 범위 판정"을 적어 뒀고, `06 §7`은 "B2C와 Admin의 토큰 대상(audience)을 분리. 한시 역할은 유효 기간을 매 요청에서 확인"을 규정한다. `02 §3.1`이 역할 8개와 데이터 범위를, `§3.3`이 행위별 권한표를 정의한다. `01 §2`는 비회원·고객·이용 정지 고객을 나눈다.

**명세도 이미 인증을 전제로 서 있다.** `openapi.yaml`에 `customerAuth`·`adminAuth`(Bearer)가 선언돼 있고 전역 `security: customerAuth`가 걸려 있으며, Admin 계열 오퍼레이션 다섯에는 개별 `security`가 붙어 있다.

**그런데 구현이 0이다.** 엔드포인트 12개 중 인증 관련은 하나도 없고, 서버는 요청자가 누구인지 모른다. 그 결과 `CORE-AC-10`(남의 예약 조회 거부)·`11`(범위 밖 데이터 미응답)·`12`(API가 권한 재검사)·`24`(철회·만료 시 세션 종료)·`29`(한시 역할 만료)가 전부 열리지 않는다. 인수조건 29개 중 다섯이 이 하나에 묶여 있다.

착수 직전에 한 번 방향이 갈렸다. Claude가 "인증은 학습 대상이 아니다"라며 `getHold`를 소유자 판정 없이 먼저 만들자고 제안했는데, 문서를 확인해 보니 **근거 없는 주장이었다.** `00 §12` 범위 밖에 있는 것은 "실명 인증"(본인 확인 절차)이지 인증 일반이 아니다. 사용자가 그 어긋남을 지적해 바로잡았다.

## 결정

### 1. 계정과 인증 수단을 분리한다

`account`(사람 하나)와 `auth_identity`(인증 수단 하나)를 나눈다. `auth_identity`는 `(provider, subject)`가 유일하고 `account_id`를 가리킨다. `provider`는 `LOCAL`로 시작하고 외부 IdP는 값이 늘어난다.

예약·확보 같은 업무 데이터는 `account`를 가리킨다. 인증 수단이 아니라 사람에 붙는다.

### 2. 세션은 짧은 액세스 토큰 + 서버에 저장한 refresh다

- **액세스 토큰** — JWT. 수명은 분 단위. 검증은 서명으로만 하고 **매 요청 저장소 조회를 하지 않는다**
- **refresh** — 서버에 저장한다(`refresh_session`). 갱신할 때 회전시키고 재사용을 감지한다
- **audience** — 액세스 토큰에 `b2c`·`admin`을 담아 가른다(`06 §7`)
- **만료 판정** — 토큰 발급 시각이 아니라 **요청 처리 시점의 서버 시각**으로 한다(`06 §7`, `CORE-AC-29`)

### 3. 비밀번호는 Argon2id로 저장한다

`Argon2PasswordEncoder`를 쓴다. 이 클래스는 BouncyCastle의 `Argon2BytesGenerator`를 직접 참조하는데 `spring-security-crypto`가 그것을 POM 의존으로 선언하지 않는다(optional이다). 그리고 Spring Boot BOM이 BouncyCastle 버전을 관리하지 않는다. 따라서 `org.bouncycastle:bcprov-jdk18on:1.86`을 **버전과 함께 직접 선언**하고 `gradle.lockfile`로 고정한다 — ADR-0006이 MyBatis에 쓴 방식과 같다.

### 4. Spring Security를 도입한다

`spring-boot-starter-security`(Spring Security 7.1.1, Boot BOM 관리)를 쓴다. 인증 필터를 직접 만들지 않는다.

### 5. 외부 IdP는 자리만 열어 둔다

명세에는 `LOCAL`만 넣는다. 소셜 로그인 흐름(콜백 경로·상태 검증)은 지금 명세에 적지 않는다.

## 근거

**계정과 수단을 나누는 이유는 나중에 붙이기 위해서다.** 한 사람이 이메일로 가입했다가 구글을 연결하면 같은 계정이어야 한다. `account`에 `provider`·`subject`를 직접 두면 그 순간 계정이 인증 수단에 종속되고, 두 번째 수단을 붙일 때 스키마가 바뀐다. 나눠 두면 **행 추가**로 끝난다.

**순수 무상태 JWT로는 명세를 못 지킨다.** `CORE-AC-24`가 "권한 철회 또는 한시 권한 만료 시 **활성 세션이 종료되고** 이후 요청이 거부된다"를 요구한다. 서명만으로 검증하는 토큰은 만료 전까지 회수할 수 없다. 그래서 refresh를 서버에 둔다. 이것은 옛 방식으로 돌아가는 것이 아니라 현재 표준이다 — OAuth 2.0 Security BCP(RFC 9700)가 refresh 토큰 **회전**과 **재사용 감지**를 권고하는데, 재사용을 감지하려면 서버가 발급 이력을 들고 있어야 한다.

**저장소 조회 부담은 갱신 시점에만 생긴다.** 액세스 토큰이 분 단위면 요청 수백 건에 조회 한 번이다. 무상태의 이점은 인스턴스가 여러 개일 때 커지는데, `06 §3.2`가 다중 인스턴스를 범위 밖으로 뒀다.

**Argon2id를 고른 기준은 OWASP의 현재 권고다.** bcrypt는 입력이 72바이트에서 잘린다 — UTF-8 한글은 글자당 3바이트라 24자에서 끊긴다. 그리고 메모리를 거의 쓰지 않아 GPU 병렬 공격에 상대적으로 약하다. Argon2id는 메모리 강도와 병렬도를 함께 조절한다. 파라미터를 직접 정하는 부담이 생기지만, 그 값이 무슨 뜻인지 재 보는 것 자체가 이 프로젝트에서는 학습이다.

**Spring Security를 고른 기준은 ADR-0003·0006과 같다.** 학습 경량화만 보면 필터를 직접 만드는 쪽이 배우는 것이 많다. 그러나 이 프로젝트의 2순위 목적은 SI 실무 적용이고, 현장에서 인증은 대부분 Spring Security 위에 있다. 여기서 익힌 필터 체인·`SecurityContext`·`PasswordEncoder` 구성이 그대로 전이된다.

**외부 IdP를 명세에 미리 적지 않는 이유는 간극이다.** `06 §9.1`이 "명세에 없는 것을 구현하지 않는다"를 요구하지만, 반대로 구현 계획이 없는 것을 명세에 먼저 적으면 "명세에 있는데 미구현"이 늘어난다. 지금도 11개 중 1개 구현이고 `SpecCoverageTest`가 그 간극을 매번 재고 있다.

**검토했으나 탈락한 대안**

| 대안 | 탈락 이유 |
|---|---|
| 순수 무상태 JWT만 | 저장소 조회가 없어 가장 가볍다. 그러나 **회수할 수 없어** `CORE-AC-24`를 만족하지 못한다. 짧은 만료로 완화해도 "즉시 종료"는 안 된다 |
| 서버 세션 쿠키만(액세스 토큰 없음) | 철회가 즉시 반영되고 단순하다. 그러나 **매 요청 저장소 조회**가 붙고, `06 §7`이 쓴 "토큰 audience 분리"라는 표현과 어긋난다. 프론트 네 벌이 각자 쿠키 정책을 다뤄야 한다 |
| bcrypt | 자료가 가장 많고 Spring Security 기본값이다. 그러나 72바이트 절단이 한글 비밀번호에서 실제 문제이고, 메모리 강도가 없다 |
| Spring Security 없이 직접 필터 | 배우는 것이 많고 의존이 늘지 않는다. 그러나 현장 전이가 약하다. ADR-0006이 JdbcClient 대신 MyBatis를 고른 것과 같은 교환이다 |
| 외부 IdP를 먼저 도입 | 실제 서비스에 가장 가깝다. 그러나 로컬 가입이 없으면 **계정 모델이 IdP에 종속**되고, 나중에 자체 가입을 붙일 때 스키마가 바뀐다. 순서를 뒤집는 편이 싸다 |

## 결과

- **명세를 먼저 고쳐야 한다**(`06 §9.1`). 인증 엔드포인트와 스키마를 `openapi.yaml`에 추가하고 `api-spec` 버전을 여섯 곳에서 맞춘다. 코드는 그다음이다
- **changelog 셋이 는다** — `account`, `auth_identity`, `refresh_session`. 그리고 `hold`에 소유자 컬럼이 붙는다
- **`CoreAcceptanceCriteriaTest`의 `@Disabled` 사유를 고친다.** `coreAc10`·`11`·`12`·`24`·`29`가 지금 "미구현"이라고만 적혀 있는데, 무엇이 선행 조건인지로 바꾼다
- **단계를 셋으로 나눈다.** ① B2C 고객 인증(가입·로그인·갱신·검증)과 `hold` 소유자 판정 → `CORE-AC-10` ② audience 분리와 Admin 역할·범위 → `CORE-AC-11`·`12` ③ 한시 역할과 세션 종료 → `CORE-AC-24`·`29`
- **외부 IdP를 붙일 때 바뀌는 곳은 좁다.** `auth_identity`에 행이 늘고, 콜백을 받아 `account`를 찾거나 만드는 경로가 하나 추가된다. 토큰 발급·검증·권한 판정은 그대로다. 바뀌지 않는다는 것이 이 구조를 고른 이유다
- **번복 조건**: 다중 인스턴스가 범위에 들어오면 refresh 저장소를 공유 캐시로 옮기는 것을 재검토한다. 반대로 Argon2id 파라미터가 단일 인스턴스에서 응답 시간을 실제로 해치면 파라미터를 낮추되 알고리즘은 바꾸지 않는다
