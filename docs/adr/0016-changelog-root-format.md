# ADR-0016 루트 changelog만 YAML로 두고 변경 정의는 전부 SQL 파일에 둔다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** |
| 결정일 | 2026-08-31 |
| 관련 문서 | `06 §4`, `daylink-core-api/src/main/resources/db/changelog/` |
| 관련 ADR | ADR-0010(파일 형식 결정을 이 ADR이 보완한다), ADR-0004(명시적 SQL 우선), ADR-0006(MyBatis), ADR-0009(도구) |

## 맥락

ADR-0010은 changelog를 SQL 형식으로 쓰기로 하면서 **"YAML·XML changelog를 쓰지 않는다"**고 적었다. 근거는 분명했다 — ADR-0004와 ADR-0006이 **SQL을 눈으로 보려고** 고른 결정인데, 스키마가 `createTable` 추상 태그 뒤에 있으면 그 판단이 흐려진다.

첫 changelog를 쓰면서 제약 하나가 드러났다.

**Liquibase 오픈소스에서는 SQL 형식 changelog가 다른 파일을 `include` 할 수 없다.** 이 기능은 상용판(Secure) 4.28.0부터다. 공식 문서는 오픈소스에서 파일을 나누려면 XML·YAML·JSON 루트가 SQL changelog들을 참조하게 하라고 안내한다.

ADR-0010을 문자 그대로 지키면 **모든 변경이 파일 하나에 쌓인다.** 그리고 그 파일은 줄어들지 않는다 — ADR-0010이 changeset을 불변으로 못 박았기 때문이다. `06 §4`의 엔터티 16종에 이후 변경이 계속 붙으면 수천 줄짜리 파일 하나가 된다. 어느 changeset이 어느 시점의 것인지 가릴 수 없고, 두 작업이 언제나 같은 파일에서 충돌한다.

## 결정

**루트 changelog 하나만 YAML로 둔다.** 파일 이름은 `db.changelog-master.yaml`이다.

**그 파일에는 `include` 목록 외에 아무것도 적지 않는다.** 변경 태그(`createTable`·`addColumn` 등)를 루트에 쓰지 않는다.

**모든 변경 정의는 SQL 형식 changelog 파일에 둔다.** ADR-0010의 `--liquibase formatted sql`과 `--rollback` 규칙이 그대로 적용된다.

**`includeAll`을 쓰지 않는다.** 적용 순서를 루트에 눈에 보이게 적는다.

## 근거

**ADR-0010이 YAML을 배제한 이유는 형식이 아니라 은닉이었다.** 그 ADR의 문장을 다시 읽으면 "SQL이 한 꺼풀 안에 들어가 위 충돌이 그대로 남는다"이고, 여기서 충돌은 `06 §8.1`이 요구한 "조건부 갱신·행 잠금·제약 조건 중 무엇을 쓰는지"가 안 보이게 되는 것을 말한다.

`include`만 있는 루트에는 숨는 SQL이 없다. 파일을 열면 목록이고, 목록을 따라가면 SQL이다. **테이블 정의를 추상 태그로 쓰지 않는 것**이 그 결정의 실질이며, 이 ADR은 그것을 그대로 지킨다.

**`includeAll`을 안 쓰는 이유는 순서 때문이다.** `includeAll`은 파일명 정렬에 적용 순서를 맡긴다. 나중에 파일 이름을 다듬으면 순서가 조용히 바뀌고, 그 사이 이미 적용된 환경과 새로 적용하는 환경이 갈린다. 스키마 넷을 같은 상태로 유지해야 하는 이 프로젝트(`00 §9`)에서 조용히 바뀌는 순서는 감당할 수 없다. 순서를 손으로 적는 대가는 줄 하나이고, 얻는 것은 그 줄이 곧 사실이라는 보장이다.

탈락한 대안이다.

| 대안 | 탈락 사유 |
|---|---|
| 단일 SQL 파일 | ADR-0010을 문자 그대로 지킨다. 그러나 changeset 불변 규칙 때문에 파일이 줄지 않고, 엔터티 16종과 이후 변경이 한 파일에 쌓인다. 되돌릴 수 없는 형태의 부채다 |
| 파일마다 Liquibase를 따로 실행하고 순서는 자바 코드에 | 루트 형식 문제를 피한다. 그러나 적용 순서가 changelog 밖으로 나가 `liquibase` CLI로 같은 결과를 재현할 수 없다. 도구를 쓰면서 도구의 표준을 벗어나면 현장 전이 가치(ADR-0003·0006의 기준)가 사라진다 |
| Liquibase 상용판 도입 | SQL 루트에서 `include`가 된다. 학습 프로젝트에 상용 라이선스는 과하고, `00 §2`의 목적 어디에도 맞지 않는다 |
| Flyway로 전환 | 순수 SQL 파일이고 루트 개념이 없어 이 문제가 아예 없다. 그러나 ADR-0010이 **현장 전이 가치**로 Liquibase를 고른 판단은 여전히 유효하고, 루트 파일 하나 때문에 도구를 바꾸는 것은 교환비가 맞지 않는다 |

## 결과

- **루트에 변경 태그가 등장하면 이 결정 위반이다.** 리뷰에서 본다. 루트가 커지기 시작하면 그 자체가 신호다.
- **`include` 목록의 순서가 적용 순서다.** 파일을 추가할 때 목록에도 적어야 하고, 빠뜨리면 그 changeset은 그냥 적용되지 않는다 — 조용한 실패다. 스키마 넷이 갈렸을 때 여기부터 본다.
- **ADR-0010의 나머지는 그대로 유효하다.** SQL 형식, `--rollback` 직접 작성, changeset 불변, 시드를 changelog에 넣지 않기, 테넌트 스키마 넷에 같은 changelog 적용이 전부 살아 있다. 이 ADR이 바꾸는 것은 루트 파일 하나의 형식뿐이다.
- **번복 조건**: Liquibase 오픈소스가 SQL 루트의 `include`를 지원하면 루트를 SQL로 옮기고 이 ADR을 대체한다. 그때 얻는 것은 형식의 일관성 하나뿐이므로 서두를 이유는 없다.
