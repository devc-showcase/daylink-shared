# ADR-0021 테넌트 격리를 스키마 분리에서 실행 단위로 옮긴다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** |
| 결정일 | 2026-09-18 |
| 관련 문서 | `05 §4.1`, `05 §4.2`, `00 §5`, `00 §9`, `fixtures/README.md` |
| 관련 ADR | ADR-0010(테넌트 스키마 넷을 정한 결정 — 이 부분만 대체), ADR-0009(Testcontainers 예고), ADR-0014(이름을 바꾸려면 지금이 가장 싸다는 선례) |

## 맥락

ADR-0010이 테넌트 스키마 넷(`t_next`·`t_nuxt`·`t_react`·`t_vue`)을 정했다. 근거는 `05 §4.2`의 "같은 테스트는 동일 시드의 별도 테넌트에서 실행한다"였다.

그런데 이름이 **프론트 프레임워크**에서 왔다. 스키마는 백엔드의 구조인데, 그 이름이 프론트 기술을 가리킨다. 기술을 바꾸면 이름이 거짓말이 되고, 더 근본적으로는 **어느 클라이언트가 호출했는지가 데이터 저장 구조에 나타난다.** 실제 제품이라면 클라이언트가 넷이어도 데이터베이스는 하나다.

실제 사용 현황도 확인했다(2026-09-18).

- 네 스키마 중 `t_next`만 쓰인다. 나머지 셋은 빈 채로 마이그레이션만 받고 있다
- `e2e/`에는 README만 있고 하네스가 없다. 프론트 구현은 아직 0벌이다
- `05 §4.1`의 CI 항목은 "구현별 **새 시드 데이터**"다. 새 스키마가 아니다

요구를 다시 읽으면 필요한 것은 **비교 실행이 서로를 오염시키지 않는 것**이고, 상시 스키마 분리는 그 수단 중 가장 무겁다. 게다가 다음 작업이 테스트 DB 분리(Testcontainers)라서, 실행마다 새 데이터베이스를 받으면 상시 스키마 넷의 근거는 더 줄어든다.

## 결정

**스키마를 하나로 줄인다.** 연결이 보고 있는 기본 스키마에 changelog를 올린다.

- `Tenant`·`TenantSchemaMigrator`·`MigrationRunner`·`SchemaMigrationException`을 지운다
- 마이그레이션은 Spring Boot의 Liquibase 자동 설정에 맡긴다. `search_path` 초기화와 `daylink.tenant.schema` 설정을 없앤다
- 구현별 격리는 실행 단위에서 만든다 — 테스트는 실행마다 시드를 되돌리고(이후 Testcontainers), 로컬 비교는 구현별 계정·시드 식별자로 가른다

## 근거

**이름이 문제의 표면이었고 구조가 문제의 본체였다.** 처음에는 이름만 역할 기반으로 바꾸려 했다. 그런데 역할 이름(기준선·학습 대상)은 **제품의 사실이 아니라 학습 운영상의 구분**이고, 그것을 스키마 이름에 넣는 것은 프레임워크 이름을 넣는 것과 같은 종류의 오류다. 제품 관점에서 B2C-Next와 B2C-Nuxt는 같은 제품의 두 구현일 뿐 역할이 다르지 않다.

**요구와 수단을 분리했다.** `05 §4.2`가 요구하는 것은 격리이고, 스키마는 그 수단 하나다. 수단을 요구로 착각해 ADR-0010에 굳혔다.

**지금이 가장 싸다.** ADR-0014가 `Session`을 `Slot`으로 바꿀 때 쓴 것과 같은 근거다. 붙은 프론트가 아직 없고, 스키마는 이 노트북에만 있으며, 의존 코드는 테스트 셋뿐이다.

**검토했으나 탈락한 대안**

| 대안 | 탈락 이유 |
|---|---|
| 이름만 제품+순번으로 바꾼다(`t_b2c_a` 등) | 프레임워크 이름은 사라지지만 **제품에 없는 구분이 백엔드 구조에 남는다.** 문제의 본체가 그대로다 |
| 제품 단위로 둘만 남긴다(`t_b2c`·`t_admin`) | 같은 제품의 두 구현을 동시에 띄우면 여전히 섞인다. 절반만 푸는 대신 개념은 그대로 남는다 |
| 현행 유지 | 네 스키마 중 셋이 빈 채로 유지 비용만 낸다. 마이그레이션·테스트·문서가 모두 넷을 전제로 복잡해진다 |
| `tenant_id` 컬럼 | ADR-0010이 이미 기각했다. 거르는 것을 한 번이라도 빠뜨리면 조용히 오염된다. 이 결정은 그 대안으로 돌아가는 것이 아니라 격리 자체를 실행 단위로 옮긴다 |

## 결과

- **`05 §4.1`의 "격리된 테스트 테넌트"를 스키마로는 더 이상 만족하지 않는다.** 실행 단위로 충족한다. PRD 문구와 구현 수단이 어긋나므로, 비교 실행을 실제로 시작할 때 이 문장을 다시 본다
- **다음 작업이 테스트 DB 분리다.** 지금은 테스트가 개발 데이터베이스에 그대로 붙는다. Testcontainers로 옮기면 실행마다 새 데이터베이스를 받아 이 결정의 격리 근거가 완성된다
- `fixtures/README.md`의 테넌트 절을 다시 썼다. `0001-catalog.sql`과 `daylink-core-api/README.md`의 관련 주석도 고쳤다
- **가려져 있던 결함이 드러났다.** `TenantSchemaMigrator`를 지우자 빈 스키마 첫 실행이 깨졌다. Spring Boot 4는 자동 설정을 기술별 모듈로 쪼갰고 `spring-boot-autoconfigure`에 Liquibase 항목이 없는데, 빌드가 `org.liquibase:liquibase-core`만 선언하고 있어 **기동 시 아무도 changelog를 돌리지 않았다.** 직접 돌리는 마이그레이터가 그 구멍을 가리고 있었던 것이다. `org.springframework.boot:spring-boot-starter-liquibase`를 넣어 고쳤고, 빈 `public`에서 전체 테스트가 통과하는 것을 확인했다
- **번복 조건**: 두 구현을 동시에 띄워 손으로 비교하는 일이 실제로 잦아지고 계정·시드 분리로 감당이 안 되면, 제품 단위 스키마 둘(`t_b2c`·`t_admin`)을 새 ADR로 다시 도입한다. 진짜 멀티테넌시(고객사별 분리)가 요구로 들어오면 그것은 이 결정과 무관한 별개 설계다
