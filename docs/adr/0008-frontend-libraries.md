# ADR-0008 프론트 라이브러리는 각 생태계 관용을 따르고, 비교는 층을 나눠 기록한다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** |
| 결정일 | 2026-09-04 |
| 관련 문서 | `04 §3`·`§10`·`§13`, `03 §12`, `00 §2.1`, `00 §9` |
| 관련 ADR | ADR-0003·0006(같은 판단 기준), ADR-0009(버전은 잠금 파일이 권위) |

## 맥락

`04 §3`이 영역별 기준선을 표로 정했지만 **구체 패키지는 비워 두고 "도구 선정은 구현 시작 전 ADR로 고정한다"고만 적었다.** ADR 번호 0008이 그 자리로 예약된 채 비어 있었다.

같은 절이 제약을 하나 걸었다.

> 도구 수를 같게 맞출 필요는 없지만 **한쪽에서만 어려운 문제를 외부 패키지로 완전히 숨기면 비교 근거가 약해지므로** 이유를 기록한다.

이 프로젝트는 같은 요구를 React와 Vue로 각각 구현해 차이를 재는 것이 목적이다(`00 §9`). 도구가 양쪽에서 다르면 관측된 차이가 프레임워크에서 온 것인지 도구에서 온 것인지 흐려진다.

`00 §2.1`이 정한 학습 비대칭도 걸린다 — React·Next는 기준선이고 Vue·Nuxt는 학습 대상이다.

## 결정

**각 생태계의 관용을 따른다.** 같은 도구를 양쪽에 억지로 맞추지 않는다.

React 쪽은 다음으로 고정한다.

| 영역 | 선택 |
|---|---|
| 라우팅 | **TanStack Router** |
| 서버 상태 | **TanStack Query** |
| 전역 UI 상태 | **경량 저장소**(Zustand 계열) |
| 폼 | **폼 라이브러리**(React Hook Form 계열) |

**Vue 쪽 구체 패키지는 M2 착수 시점에 고정한다.** 지금 정하지 않는 이유는 Vue 3 생태계에서 서버 상태 도구가 아직 하나로 굳지 않았다고 판단해서다 — `@tanstack/vue-query`, Pinia Colada, VueUse가 후보이고, 어느 것이 관용인지 확인 없이 단정하지 않는다(`04 §13`이 "구현 시작 시 공식 문서를 다시 확인한다"고 요구한다). 선정 기준만 여기서 못 박는다.

1. **Vue 팀·Pinia 팀 계보이거나 Vue 문서가 가리키는 것**을 우선한다
2. 같은 개념 층에 있어야 한다 — 서버 상태는 서버 상태 도구로, 전역 UI 상태는 Pinia로 푼다
3. 실무에서 실제로 쓰이는지를 본다. 새롭고 우아하지만 현장에서 안 보이는 것은 2순위 목적(SI 전이)에 기여하지 않는다

라우팅은 Vue Router, 전역 UI 상태는 Pinia, 테스트는 Vitest·Vue Test Utils로 이미 정해져 있다(`04 §3`).

**비교 기록은 층을 나눠 적는다.** `04 §10`의 각 항목에서 관측된 차이를 **프레임워크에서 온 것**과 **도구에서 온 것**으로 갈라 쓴다. 가르지 못하면 그 항목은 비교 결과로 쓰지 않는다.

## 근거

**각 생태계 관용을 따르는 이유는 목적의 2순위가 SI 실무 적용이기 때문이다.** ADR-0003이 Kotlin 대신 Java를, ADR-0006이 JPA 대신 MyBatis를 고른 것과 같은 기준이다 — 학습 경량화보다 현장 전이 가치를 앞에 둔다. Vue 프로젝트에 React 계열 도구를 얹으면 그 코드는 현장에서 다시 못 쓴다.

같은 도구를 양쪽에 쓰면 비교는 깨끗해지지만, 그때 재는 것은 **"같은 라이브러리를 두 프레임워크가 어떻게 받느냐"**이지 두 생태계의 차이가 아니다. `00 §9`가 요구한 동등성은 결과의 동등성이지 구현 수단의 동일성이 아니다.

**대신 `04 §3`이 경고한 위험이 실제로 남는다.** 그래서 층을 나눠 적는 규칙을 함께 정한다. 이것이 이 결정의 안전장치다 — 도구를 다르게 쓰는 대가를 기록 형식으로 치른다.

**폼을 라이브러리로 가는 이유도 같다.** 명시적 상태로 짜면 두 프레임워크의 반응성 차이가 더 직접 드러나지만, 실무에서 폼을 손으로 짜는 현장은 드물다. 다만 이 선택은 §3의 경고에 가장 가까이 가므로, **폼 항목은 비교 기록에서 층 구분을 특히 엄격히 적용한다.**

**TanStack Router를 고른 이유는 학습 계보가 이미 열려 있기 때문이다.** 별도 저장소에서 그 라우터를 따로 공부하고 있고, 타입 안전 라우팅은 Vue Router에 대응물이 약해 비교 항목이 하나 늘어난다. 그 항목을 `04 §10` "개발 경험"에서 다룬다. React Router가 실무 다수라는 점은 인정하되, 두 라우터의 개념이 겹치는 범위가 넓어 전이 손실이 크지 않다고 봤다.

**전역 UI 상태를 경량 저장소로 두는 이유는 Pinia와 개념 층을 맞추기 위해서다.** Context + reducer로 가면 한쪽은 "라이브러리", 다른 쪽은 "프레임워크 기본기"가 되어 비교가 도구 유무로 변한다.

### 탈락한 대안

| 대안 | 탈락 이유 |
|---|---|
| **양쪽에 TanStack Query** | 비교는 깨끗해지지만 Vue 생태계 관용을 배우지 못한다. 2순위 목적에 기여하지 않는 코드가 절반이 된다 |
| **폼을 양쪽 다 직접 짠다** | 반응성 차이가 가장 잘 드러나는 안이지만 분량이 크게 늘고 실무 관용과 멀어진다. M2가 밀린다 |
| **React도 Context + reducer** | 외부 의존이 줄지만 Pinia와 개념 층이 어긋난다. 비교가 "도구를 썼나 안 썼나"로 변질된다 |
| **React Router** | 실무 다수이고 Vue Router와 대응이 깔끔하다. 다만 이미 열려 있는 학습 계보를 버리게 되고, 타입 안전 라우팅이라는 비교 항목을 잃는다 |
| **지금 Vue 패키지까지 확정** | 확인 없이 정하면 근거 없는 수치를 만드는 것과 같은 일이 된다. `04 §13`이 착수 시 재확인을 요구한다 |

## 결과

- **`04 §10` 비교 기록의 양식이 바뀐다.** 항목마다 "프레임워크 차이 / 도구 차이"를 갈라 적는 칸이 필요하다. 가르지 못한 항목은 결과로 쓰지 않는다
- **각 도구가 무엇을 숨기는지 목록을 만들어야 한다.** M2 착수 시 도구별로 한 번 적고, 그 목록에 있는 것은 비교에서 제외하거나 별도 표기한다
- **Vue 서버 상태 도구 선정이 M2 착수 조건에 들어간다.** 위 세 기준으로 고르고 이 ADR을 대체하는 새 ADR에 남긴다
- **버전은 여기 적지 않는다.** 잠금 파일이 권위다(ADR-0009)
- Nuxt는 `useFetch`·`useAsyncData`가 내장이라 서버 상태 도구 선택이 Admin(Vue SPA)과 다를 수 있다. `03 §12`가 가리키는 문서를 착수 시 확인한다

**번복 조건**

1. 층을 나눠 적는 것이 실제로 안 되면 — 프레임워크 차이와 도구 차이가 계속 뒤섞이면 — 같은 도구로 통일하는 안을 다시 본다. 그때는 비교 정확도를 전이 가치보다 앞에 두는 것이다
2. TanStack Router의 학습 부담이 M2 분량을 실제로 밀면 React Router로 내린다
3. Vue 생태계에서 서버 상태 도구가 하나로 굳으면 위 세 기준 없이 그것을 쓴다
