# ADR-0002 Core API 스택을 Spring Boot(JVM)로 한다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** |
| 결정일 | 2026-08-23 |
| 관련 문서 | `00 §2`, `00 §8.1`, `06 §2`, `06 §2.1` |
| 관련 ADR | ADR-0003(언어), ADR-0004(영속성) |

## 맥락

Core API를 계약 기반 mock으로 대체하지 않고 **직접 구현하기로 했다**(`00 §8.1`). `00 §8`이 부여한 여덟 가지 책임 중 다섯 — 원자적 재고 확보, 중복 예약 방지, 상태 전이, 정산 원장, 멱등 처리 — 은 트랜잭션 경계와 동시성 제어 없이는 성립하지 않으므로, 응답만 흉내 내는 mock으로는 요구를 강제할 수 없다.

학습자의 백엔드 경험은 **프론트에서 API를 호출해 본 것이 전부**다. 서버 코드를 작성하거나 운영한 적이 없다.

프로젝트 목적은 학습이 1순위, **SI 실무 적용이 2순위**다.

## 결정

Core API를 **Spring Boot 기반 JVM 애플리케이션 한 벌**로 구현한다. 데이터 저장소는 관계형 데이터베이스를 쓰고 트랜잭션과 격리 수준을 실제로 사용한다. 프레임워크·라이브러리 버전은 착수 시점의 안정판으로 고정하고 잠금 파일에 기록한다.

프론트와 달리 **비교 구현을 만들지 않는다.**

## 근거

**Spring을 택한 이유는 학습 편의가 아니라 2순위 목적이다.** 국내 SI 현장에서 가장 널리 쓰이는 스택이므로, 여기서 익힌 트랜잭션 경계·계층 분리·감사 로그 패턴이 상주 현장에 그대로 옮겨진다. 학습만이 목적이었다면 다른 선택이 가능했다.

**단일 구현으로 두는 이유.** Core API는 네 프론트 구현이 공유하는 단일 권위자다. 두 벌로 만들면 프론트 구현 간 차이가 프레임워크 차이인지 백엔드 차이인지 판정할 수 없게 되고, `00 §9`의 동등성 비교와 `00 §11.5`("한 구현의 미완성 기능을 프레임워크 한계로 오판하지 않는다")가 무너진다. `00 §5`가 "구현마다 별도 백엔드를 만들어 결과가 달라지는 방식은 허용하지 않는다"고 못박은 것도 같은 이유다.

**검토했으나 탈락한 대안**

| 대안 | 탈락 이유 |
|---|---|
| Node.js + NestJS/Express | 프론트와 언어가 같아 OpenAPI 생성 타입을 공유할 수 있고 학습 축이 늘지 않는다. 그러나 2순위 목적인 SI 실무 전이 가치가 낮다. 국내 SI 백엔드에서 Node 비중이 Spring에 비해 작다 |
| 계약 기반 mock (MSW·Prism) | `00 §8`의 다섯 책임을 강제하지 못한다. 프론트가 규칙을 어겨도 테스트가 통과하므로 `00 §9`의 동등성 검증이 무의미해진다 |
| 백엔드도 2벌 비교 (예: Spring ↔ NestJS) | 분량이 두 배가 되고, 무엇보다 프론트 비교의 기준선이 흔들린다. 백엔드가 다르면 프론트 차이의 원인을 특정할 수 없다 |

## 결과

- **프론트와 언어가 분리된다.** 타입을 직접 공유할 수 없고 OpenAPI 생성기를 경유해야 한다(`06 §2.2`).
- **도메인 규칙이 두 언어로 표현될 위험이 생긴다.** 프론트가 금액·환불액·잔여 좌석·권한을 자체 계산하면 정의가 어긋난다. `06 §9.3`이 이를 금지하고, `06 §9.1`의 계약 우선 규칙이 방어선이다.
- **학습 축이 하나 늘어난다.** 언어·빌드 도구·테스트 도구가 프론트와 별개로 필요하다. Advisor 커리큘럼이 이 분량을 M1~M3에 배분했다.
- 후속 결정: 언어(ADR-0003), 영속성 계층(ADR-0004), 빌드 도구, 테스트 도구.
- **번복 조건**: 상주 예정 현장의 백엔드 스택이 Spring 계열이 아니고 그 코드를 직접 다룰 가능성이 확인되면 재검토한다. 다만 그 경우 2순위 목적의 대상 자체가 바뀐 것이므로 커리큘럼 전체를 다시 봐야 한다.
