# ADR-0005 저장소를 조직 아래 6개로 분리하고 공유 자산을 패키지로 배포한다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** — 공유 규격 폴더·패키지 이름만 ADR-0011로 대체됨 |
| 결정일 | 2026-08-24 |
| 관련 문서 | `00 §2.1`, `00 §9`, `03 §3.1`·`§3.2`, `04 §3`, `05 §4.1` |
| 관련 ADR | ADR-0001(문서 위치), ADR-0002(Core API 스택), ADR-0011(`contract/` → `api-spec/` 개명), ADR-0012→0013(문서 위치를 옮겼다 되돌림 — 이 ADR의 문서 위치가 유효) |

## 맥락

이 프로젝트는 코드베이스가 5개다 — Core API, B2C Next.js, B2C Nuxt, Admin React SPA, Admin Vue SPA. 여기에 `03 §3.1`이 "공유할 것"으로 지정한 자산이 별도로 있다.

| 공유 자산 | 소비자 |
|---|---|
| API 스키마와 생성 타입 | Core API가 만들고 프론트 4벌이 소비 |
| 시드 데이터·테스트 계정 | 5개 전부 |
| 디자인 토큰·아이콘 원본·이미지 비율 | 프론트 4벌 |
| 화면별 인수조건·E2E 시나리오 | 5개 전부 |
| 분석 이벤트 이름·속성 | 프론트 4벌 |
| 접근성 검사 기준 | 프론트 4벌 |
| 성능 측정 조건·기기·네트워크 프로필 | 프론트 4벌 |

**그런데 `00`~`06` 어느 문서에도 저장소 구조에 대한 언급이 없다.** `05 §4.1`이 환경 정책(구현별 별도 포트, 격리된 테스트 테넌트, `noindex`)을 규정했지만 그 환경이 어느 저장소에서 나오는지는 비어 있다.

이 프로젝트에는 일반 프로젝트에 없는 제약이 하나 더 있다. `00 §2.1` 규칙 1이다.

> 학습 대상 구현은 기준선 구현의 소스를 보고 시작하지 않는다. PRD와 화면 목록만 보고 다시 만든다.

Advisor 커리큘럼 `§0.5`가 이를 "에디터에서 기준선 소스를 닫고 착수한다"는 절차로 구체화했으나, **규율에 의존하는 장치는 혼자 하는 프로젝트에서 가장 먼저 무너진다.**

## 결정

**GitHub 조직을 신설하고 그 아래 저장소 6개를 둔다.** 조직명은 `daylink`를 가정한다(확정 시 치환).

| 저장소 | 내용 |
|---|---|
| `daylink-shared` | 계약·시드·토큰·E2E·**문서 전체** |
| `daylink-core-api` | Java 21 + Spring Boot 4 |
| `daylink-b2c-next` | B2C 기준선 구현 |
| `daylink-b2c-nuxt` | B2C 학습 대상 구현 |
| `daylink-admin-react` | Admin 기준선 구현 |
| `daylink-admin-vue` | Admin 학습 대상 구현 |

### 공유 자산 전달 — GitHub Packages

`daylink-shared`가 버전 태그를 달아 조직 레지스트리에 배포하고, 나머지 5개는 의존성으로 당겨 쓴다.

| 패키지 | 형식 | 소비자 |
|---|---|---|
| `@daylink/contract` | npm — OpenAPI에서 생성한 TypeScript 타입·오류 코드 | 프론트 4벌 |
| `@daylink/tokens` | npm — 디자인 토큰, 이미지 비율 | 프론트 4벌 |
| `@daylink/fixtures` | npm — 시드 데이터, 테스트 계정 | 프론트 4벌·E2E |
| `com.daylink:contract` | Maven — OpenAPI 스펙 원본과 서버 측 생성물 | Core API |

**버전 규약**: SemVer. 계약의 **호환 불가 변경은 major**, 필드·엔드포인트 추가는 minor, 문서·주석 수정은 배포하지 않는다.

## 근거

**저장소 분리를 택한 결정적 이유는 소스 봉인이다.** 모노레포에서는 `apps/b2c-next`와 `apps/b2c-nuxt`가 파일 트리에 나란히 보인다. Nuxt를 짜다 막히면 옆 폴더를 여는 데 1초가 걸리고, 그러면 `00 §2.1` 규칙 1이 무너진다. 저장소가 분리되면 기준선 코드를 보려면 **의도적으로 다른 저장소를 클론해 열어야 한다.** 규율이 아니라 마찰로 강제된다.

이 마찰이 학습에서 갖는 의미는 크다. `00 §11.5`가 완료 기준으로 지정한 "한 구현의 미완성 기능을 프레임워크 한계로 오판하지 않는다"는, 두 번째 구현을 **스스로 풀어봐야** 판정할 수 있다. 번역해서 옮긴 코드로는 어느 쪽이 어려웠는지 알 수 없다.

**GitHub Packages를 택한 이유는 계약 변경이 버전으로 추적되기 때문이다.** `06 §9.1`이 "OpenAPI 스키마와 오류 코드를 코드보다 먼저 확정한다"를 요구하고, 그 근거로 "네 프론트 구현이 서로 다른 시점에 개발되므로 계약이 흔들리면 구현마다 다른 가정이 굳는다"를 든다. 패키지 버전은 각 구현이 **어느 시점의 계약을 보고 있는지**를 파일에 남긴다. `package.json`의 버전만 비교하면 계약 드리프트를 즉시 발견할 수 있다.

**문서를 `daylink-shared`에 둔 이유.** PRD·IA·ADR은 다섯 코드베이스 모두의 상위 문서다. 어느 구현 저장소에 넣어도 그쪽에 종속된 것처럼 보인다. 별도 문서 저장소를 만드는 안도 검토했으나, 저장소가 7개가 되면서 얻는 것이 "커밋 로그가 깨끗해진다" 정도였다.

**검토했으나 탈락한 대안**

| 대안 | 탈락 이유 |
|---|---|
| 단일 모노레포 | 공유가 경로 참조로 끝나고 원자적 변경이 가능하다. 그러나 **소스 봉인이 규율에만 의존하게 된다.** 이 프로젝트의 핵심 학습 장치를 포기하는 대가가 편의보다 크다 |
| 하이브리드 3개 (공유+API / B2C 2벌 / Admin 2벌) | M1 작업이 가장 편하다. 그러나 비교할 두 구현이 같은 저장소에 나란히 있어 **소스 봉인이 가장 먼저 깨지는 배치**다 |
| git submodule | 배포 파이프라인이 필요 없고 커밋 해시로 버전이 고정된다. 그러나 submodule 업데이트를 깜빡하기 쉬워 **구현마다 다른 계약을 보고 있는 상황**이 생기고, 그것이 `00 §9` 동등성 비교를 오염시킨다 |
| 생성 스크립트 + 결과물 커밋 | 설정이 가장 단순하고 M1을 즉시 시작할 수 있다. 그러나 계약 버전이 커밋 해시 주석으로만 남아 자동 검증이 불가능하다 |
| 문서 저장소 분리 (7개) | 계약 저장소의 버전 태그가 깨끗해진다. 그러나 혼자 하는 프로젝트에서 저장소 전환 비용이 그 이점을 넘는다 |

## 결과

- **배포 파이프라인을 M1 초반에 만들어야 한다.** 이것이 이 결정의 가장 큰 비용이다. 계약을 쓰기 전에 GitHub Actions 워크플로와 레지스트리 인증(`GITHUB_TOKEN`, `.npmrc`, Gradle 자격 증명)을 먼저 세워야 한다. Advisor 커리큘럼 M1의 "계약·오류 코드·멱등 규약·DB 스키마·시드 45h" 안에 이 분량이 들어간다.
- **미배포 계약으로 개발할 방법이 필요하다.** 계약을 고치는 즉시 배포할 수는 없으므로, 로컬 개발용 우회로(npm `link`, Gradle `mavenLocal()`)를 저장소 README에 명시한다. 이 우회로를 쓴 채 커밋하지 않도록 CI에서 검사한다.
- **계약 변경 시 네 곳을 갱신해야 한다.** 모노레포였다면 한 커밋으로 끝났을 일이다. 대신 각 구현이 언제 따라왔는지가 기록된다. `00 §9`의 동등성 검증에서 **계약 버전 일치를 선행 조건**으로 둔다.
- **문서 수정 커밋이 계약 저장소에 쌓인다.** 버전 태그는 `contract/`·`tokens/`·`fixtures/` 변경에만 붙이고, `docs/` 변경은 배포를 트리거하지 않도록 워크플로에 경로 필터를 건다.
- **E2E가 네 구현을 모두 기동해야 한다.** `daylink-shared`의 E2E는 다섯 저장소를 클론한 상태를 전제하므로, 로컬 기동 절차와 포트 규약을 README에 고정한다. `05 §4.1`의 "구현별 테넌트 격리"도 여기서 구현한다.
- **번복 조건**: ① 패키지 배포 왕복이 M1 진도를 실제로 막으면 `daylink-shared`를 submodule 병행으로 완화한다 ② 소스 봉인이 저장소 분리로도 지켜지지 않는다면(예: 습관적으로 다섯 저장소를 한 창에 열어둠) 구조가 아닌 다른 장치가 필요하므로 재검토한다.

## 부록 — 저장소 초기화 순서

1. GitHub 조직 생성
2. `daylink-shared` 생성 → 현재 `portfolio` 폴더의 문서 전체를 `docs/prd`·`docs/adr`로 이관
3. `contract/`에 OpenAPI 스펙 뼈대, `fixtures/`에 시드 초안 배치
4. 패키지 배포 워크플로 작성 → `0.1.0` 최초 배포로 파이프라인 검증
5. `daylink-core-api` 생성 → Maven 의존성으로 계약 소비 확인
6. `daylink-b2c-next` 생성 → npm 의존성으로 계약 소비 확인
7. 나머지 3개는 해당 마일스톤 착수 시점에 생성 (미리 만들면 빈 저장소가 방치된다)
