# ADR-0009 빌드·테스트 도구를 고정하고 버전을 잠금 파일로 관리한다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** |
| 결정일 | 2026-08-24 |
| 관련 문서 | `03 §7`·`§12`, `04 §3`·`§8`·`§13`, `05 §4.1`, `06 §14` |
| 관련 ADR | ADR-0002·0003(Core API 스택·언어), ADR-0005(저장소 구조), ADR-0006(MyBatis) |

## 맥락

`03 §12`와 `04 §13`이 같은 요구를 남겼다.

> 구현 시작 시 공식 문서를 다시 확인하고, 선택한 라이브러리 버전과 브라우저 지원 범위를 **잠금 파일과 ADR에 기록한다.**

`04 §3`은 프론트 도구의 방향(Vite, Vitest, Testing Library / Vue Test Utils, 브라우저 테스트)을 이미 제시하면서 "도구 선정은 구현 시작 전 ADR로 고정한다"고 못박았다.

여기에 이 프로젝트만의 조건이 얹힌다. `06 §14.2`가 요구하는 동시성 테스트는 **실제 데이터베이스가 있어야 의미가 있다.**

> 마지막 1좌석 동시 요청 N=50 / **안전장치 제거 시 실패 확인(CORE-AC-02)**

락과 격리 수준의 동작이 운영과 다른 환경에서 이 테스트를 돌리면, `CORE-AC-02`가 거짓으로 통과할 수 있다. 그러면 `06 §12`가 경고한 구조 — 잘못된 설계가 테스트를 통과하며 살아남는 것 — 가 그대로 실현된다.

## 결정

### Core API (`daylink-core-api`)

| 항목 | 결정 |
|---|---|
| 빌드 | **Gradle** |
| JDK | **Java 21**. Gradle toolchain으로 고정해 로컬 JDK 설치에 의존하지 않는다 |
| 영속성 | MyBatis (ADR-0006) |
| 단위·통합 테스트 | JUnit 5 |
| 데이터베이스 | **PostgreSQL** |
| 마이그레이션 | 스키마 버전 관리 도구를 쓴다. 도구 택일은 M1 착수 시 확정 |

### 프론트 4벌

| 항목 | 결정 |
|---|---|
| 번들러·개발 서버 | Vite |
| 패키지 매니저 | **npm** |
| 단위·컴포넌트 테스트 | Vitest + Testing Library(React) / Vue Test Utils(Vue) |
| Node 버전 | `.nvmrc`로 저장소마다 고정 |

### 공통 (`daylink-shared`)

| 항목 | 결정 |
|---|---|
| E2E | Playwright. `daylink-shared/e2e/`에 두고 네 구현을 대상으로 실행 |
| 계약 타입 생성 | OpenAPI 생성기. npm·Maven 패키지로 배포 (ADR-0005) |

### 테스트 데이터베이스

**로컬 Docker를 상시 기동한다.** `daylink-core-api`에 `docker-compose.yml`을 두고 PostgreSQL을 띄운 상태에서 테스트를 돌린다. CI에서는 같은 이미지 태그를 GitHub Actions 서비스 컨테이너로 띄워 환경을 맞춘다.

### 버전 고정 원칙

- 모든 버전은 **착수 시점의 안정판**으로 정하고 잠금 파일(`gradle.lockfile`·`package-lock.json`)을 커밋한다.
- 이 ADR에 특정 버전 숫자를 적지 않는다. 숫자는 잠금 파일이 권위이고, ADR은 **어떤 도구를 왜 골랐는지**만 담는다.
- 메이저 버전 상향은 구현 도중에 하지 않는다. 필요하면 새 ADR로 기록하고 네 구현을 같은 변경 묶음으로 올린다(`00 §9`).

## 근거

**Gradle을 택한 이유.** Spring Initializr 기본값이고 최신 Spring Boot 자료가 Gradle 기준인 경우가 많다. 백엔드가 기준선 없는 신규 학습 영역이므로(`00 §2.1`) 검색했을 때 예제가 그대로 맞는 쪽이 유리하다. Maven이 SI 현장에서 더 흔하다는 점은 인정하지만, 빌드 도구는 ADR-0003(언어)·ADR-0006(MyBatis)과 달리 **현장 코드를 읽는 능력에 직접 기여하지 않는다.** `pom.xml`은 필요할 때 읽으면 되는 선언적 문서다.

**PostgreSQL을 택한 이유.** 이 프로젝트에서 가장 어려운 학습 대상은 동시성이고, ADR-0004가 "각 동시성 방어의 안전 근거를 격리 수준과 함께 ADR에 적는다"를 요구한다. **그 근거를 쓰려면 격리 수준과 락 동작이 문서로 명확해야 한다.** PostgreSQL은 이 부분의 공식 문서가 가장 명확하고, `FOR UPDATE`·`SKIP LOCKED` 같은 도구도 풍부하다. MySQL의 InnoDB 갭 락·넥스트 키 락은 실무에서 만나는 문제이지만, 백엔드 제로 베이스에서 학습 대상과 함께 다루기에는 변수가 하나 더 늘어난다.

**npm을 택한 이유.** ADR-0005로 저장소를 분리했으므로 워크스페이스 기능이 필요 없다. pnpm의 속도·디스크 이점은 저장소 6개 규모에서 체감이 작고, GitHub Packages 인증도 `.npmrc` 한 파일로 끝나 가장 단순하다. 학습 축을 늘리지 않는 쪽을 택했다.

**로컬 Docker 상시 기동을 택한 이유.** 실제 PostgreSQL이므로 락 동작이 운영과 같고, Testcontainers 대비 테스트가 빠르다. 반복 실행이 잦은 동시성 테스트에서 속도는 실질적 이점이다.

**검토했으나 탈락한 대안**

| 대안 | 탈락 이유 |
|---|---|
| Maven | SI 현장 사용률이 높고 선언적이라 예측 가능하다. 그러나 빌드 도구는 현장 코드 읽기 능력에 기여하지 않고, 최신 Spring 자료의 Gradle 편중이 신규 학습에서 더 큰 변수다 |
| 임베디드 DB (H2 등) | 가장 빠르고 설정이 없다. 그러나 **락과 격리 수준 동작이 실제 DB와 달라 `CORE-AC-02`가 거짓 통과할 수 있다.** 이 프로젝트에서 가장 위험한 선택이라 검토 즉시 기각했다 |
| Testcontainers | 테스트마다 실제 이미지를 띄워 격리와 CI 재현성이 가장 좋다. 그러나 기동 비용 때문에 동시성 테스트 반복이 느려지고, M1 초반에 설정 부담이 하나 더 생긴다 |
| pnpm | 속도·디스크 이점이 있으나 저장소가 분리돼 워크스페이스 이점이 없고, 학습 축만 늘어난다 |

## 결과

- **로컬 Docker 방식의 최대 위험은 테스트 격리다.** DB가 상시 살아 있으므로 앞선 테스트가 남긴 데이터가 다음 테스트에 흘러든다. 동시성 테스트에서 이런 오염은 **거짓 실패뿐 아니라 거짓 성공도** 만든다.
  - **완화 1**: 동시성·멱등 테스트는 전용 스키마에서 돌리고, 각 테스트 시작 시 관련 테이블을 초기화한다.
  - **완화 2**: `CORE-AC-02`(안전장치 제거 시 실패) 확인을 **매 실행마다** 수행한다. 이 검사가 통과하면 환경이 오염되지 않았다는 뜻이기도 하다.
  - **완화 3**: CI는 GitHub Actions 서비스 컨테이너로 매번 새 DB를 띄운다. 로컬에서 통과했지만 CI에서 실패하면 오염을 의심한다.
- **테스트 실행 전제가 생긴다.** "DB가 떠 있어야 테스트가 돈다"를 README에 명시하고, 기동 명령을 한 줄로 제공한다. 이 전제를 모른 채 실패를 보면 원인 추적에 시간을 버린다.
- **마이그레이션 도구가 미결로 남는다.** M1 착수 시 확정한다. 로컬 Docker를 상시 기동하는 구성에서는 스키마 초기화·재적용 절차가 곧 개발 편의를 좌우한다.
- **버전 숫자를 ADR에 적지 않았으므로 잠금 파일이 유일한 권위다.** 잠금 파일을 커밋하지 않으면 이 ADR은 아무것도 고정하지 못한다. 여섯 저장소 모두 첫 커밋에 잠금 파일을 포함한다.
- **번복 조건**: 동시성 테스트가 데이터 오염 때문에 거짓 통과하거나 원인 불명으로 흔들리는 일이 반복되면 **즉시 Testcontainers로 전환한다.** 속도보다 `CORE-AC-01`·`02`의 신뢰도가 우선이며, 이 전환은 재검토 대상이 아니라 예정된 대응이다.
