# ADR-0004 영속성은 명시적 SQL 우선, JPA는 M3 후반 낙관적 락에 한정한다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** |
| 결정일 | 2026-08-24 |
| 관련 문서 | `06 §8.1`, `06 §8.6`, `06 §12`, Advisor 커리큘럼 `§3.5` |
| 관련 ADR | ADR-0002(스택), ADR-0003(언어) |

## 맥락

PRD는 영속성 계층을 규정하지 않았다. 그런데 `06 §8.1`이 재고 확보에 대해 다음을 요구한다.

> `SELECT`로 잔여를 읽고 애플리케이션에서 비교한 뒤 `UPDATE` 하는 방식은 **금지**한다. 조건부 갱신, 행 잠금, 또는 제약 조건 중 하나로 **데이터베이스가 판정하게 한다.** 선택한 방식과 그 방식이 어떤 격리 수준에서 안전한지를 ADR에 기록한다.

학습자의 영속성 경험은 0이다. 관계형 스키마 설계, 인덱스, SQL, 트랜잭션 경계, 격리 수준, 락, 데드락 모두 신규 학습 대상이다.

Advisor 커리큘럼 `§2.7`이 이 구간에서 예상되는 오해로 **"ORM을 쓰면 트랜잭션은 알아서 된다"**, **"`SELECT` → 검사 → `UPDATE` 두 문장이면 원자적이다"** 를 지목했다. 특히 후자는 **동시 요청을 보내지 않으면 드러나지 않아, 모든 순차 테스트를 통과하면서 존재할 수 있다.**

`06 §12`가 이 프로젝트의 구조적 취약점으로 같은 문제를 적었다 — Core API에는 비교 대상이 없어 잘못된 설계가 테스트를 통과하며 살아남을 수 있다.

## 결정

두 단계로 나눈다.

| 단계 | 선택 |
|---|---|
| M1 ~ M3 전반 | **명시적 SQL** (Spring JDBC 또는 MyBatis). 도구 택일은 후속 ADR |
| M3 후반 | **JPA 도입, 낙관적 락(`@Version`)에 한정** |

M3 후반까지 JPA를 쓰지 않는다.

## 근거

**명시적 SQL을 먼저 쓰는 이유는 가시성이다.** `06 §8.1`이 "데이터베이스가 판정하게 하라"를 요구하는데, 명시적 SQL에서는 락과 조건이 코드에 그대로 보인다. 어떤 SQL이 언제 나가는지가 파일에 적혀 있으므로, 동시성 방어가 실재하는지 눈으로 확인할 수 있다.

**JPA를 처음부터 쓰지 않는 이유는 그 가시성을 가리기 때문이다.** dirty checking과 flush 타이밍은 "언제 어떤 SQL이 나가는지"를 감춘다. 위에 적은 오해를 가진 상태로 JPA를 쓰면 그 오해를 **관찰할 수 없는 형태로** 심게 된다. `06 §12`가 지적한 구조 — 잘못된 설계가 테스트를 통과하며 살아남는 것 — 가 여기서 가장 잘 작동한다.

**그럼에도 JPA를 M3 후반에 도입하는 이유.** `06 §8.6`의 버전 기반 충돌 감지는 JPA의 정석 사용처이고, SI 현장에서 JPA를 만나지 않기는 어렵다. 이 시점이면 SQL이 언제 나가는지를 추적할 기반이 생겨 있어, JPA의 추상화를 "편의"가 아니라 "무엇을 감추는 도구"로 이해할 수 있다.

**부수 효과 하나.** ADR-0003이 감수한 Kotlin 대비 손실 중 하나가 `kotlin-jpa`·`kotlin-allopen` 플러그인 마찰이었는데, Java를 택했으므로 그 문제는 애초에 없다. 반대로 이 결정은 JPA 도입 자체를 M3 후반까지 미루므로, 어느 언어였든 초기 마찰을 줄인다.

**검토했으나 탈락한 대안**

| 대안 | 탈락 이유 |
|---|---|
| 처음부터 JPA | 실무에서 가장 흔한 출발점이고 생산성이 높다. 그러나 영속성 경험 0인 상태에서 `06 §8.1`의 요구를 만족했는지 **스스로 검증할 수 없게 된다.** 학습 목적과 정면으로 충돌한다 |
| 끝까지 명시적 SQL만 | 가시성은 최대지만 JPA를 한 번도 다루지 않게 된다. SI 현장 전이 가치(2순위 목적)를 잃는다 |
| JOOQ 등 타입 안전 SQL 빌더 | 가시성과 타입 안전을 모두 갖지만 국내 SI 현장 사용률이 낮아 2순위 목적에 기여하지 않고, 학습 축만 하나 늘어난다 |

## 결과

- **Spring JDBC와 MyBatis 중 택일이 미결로 남는다.** M1 착수 전 후속 ADR로 확정한다. 판단 기준은 SQL 관리 방식(어노테이션 ↔ XML ↔ 문자열)과 SI 현장 사용률이다.
- **JPA 도입 시점의 판단 기준이 필요하다.** "M3 후반"은 분량 기준이므로, 실제 전환은 `06 §8.6`의 낙관적 동시성 요구를 구현할 때로 정한다.
- **한 프로젝트에 영속성 접근이 두 가지 공존하게 된다.** 어느 리포지토리가 어느 방식을 쓰는지 경계를 명시하지 않으면 혼란이 생긴다. 전환 시점에 경계를 ADR로 기록한다.
- **번복 조건**: M3 전반까지 명시적 SQL로 `06 §8.1`~`§8.5`를 구현했는데도 동시성 방어의 안전 근거를 격리 수준과 함께 설명하지 못한다면, 도구 문제가 아니므로 ADR을 바꾸지 말고 학습 방식을 다시 본다. 반대로 M1 중 명시적 SQL 작성 자체가 병목이 되어 진도가 멈추면 이 ADR을 재검토한다.
