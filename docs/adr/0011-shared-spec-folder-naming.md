# ADR-0011 공유 규격의 폴더·패키지 이름을 `api-spec`으로 한다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** |
| 결정일 | 2026-08-26 |
| 관련 문서 | `00 §11.3`, `06 §9.1`, `05 §11.1` |
| 관련 ADR | ADR-0005(저장소 구조 — 이 ADR이 명명 부분을 대체한다) |

## 맥락

ADR-0005는 공유 규격을 담는 폴더를 `contract/`로, 배포 패키지를 `@daylink/contract`·`com.daylink:contract`로 정했다. 영어권 관례를 그대로 옮긴 이름이다.

이 이름은 Bertrand Meyer가 1986년 Eiffel 언어와 함께 내놓은 Design by Contract에서 왔다. 호출자와 제공자가 각자 의무와 이익을 진다는 상거래 계약 비유였고, 여기서 precondition·postcondition·invariant가 나왔다. OpenAPI 진영의 "API contract"·"contract-first", Pact의 "consumer-driven contract testing"이 모두 같은 계보다. 비유의 출처가 법이라는 점에서 번역어 "계약"은 오역이 아니다.

문제는 한국어 쪽이다.

- **국내 SI에서 "계약"은 수주·도급 계약을 먼저 가리킨다.** 이 저장소 안에서도 `02 §2`의 "계약 전자서명", `00 §12`의 "실제 PG 계약"은 진짜 법률 계약을 뜻한다. 같은 단어가 두 뜻으로 쓰이고 있었다.
- **비유의 방점이 다르다.** 법률 계약의 핵심은 의사의 합치로 성립한다는 성립 요건이지만, 소프트웨어 계약의 핵심은 의무를 명시해 위반을 판정할 수 있게 만드는 쪽이다. 한국어 "계약"은 앞쪽을 강하게 연상시킨다.
- **당사자성이 약하다.** 이 프로젝트는 프론트도 백엔드도 한 사람이 만든다. 네 프론트 구현이 Core API 한 벌을 공유한다는 점에서 당사자가 여럿이긴 하나, 일상적으로는 잘 와닿지 않는다.

폴더명을 실제로 채우기 직전이고 패키지는 아직 배포하지 않았다. 바꾸려면 지금이 가장 싸다.

## 결정

**`contract/`를 `api-spec/`으로 개명한다.** 배포 패키지도 `@daylink/api-spec`(npm)·`com.daylink:api-spec`(Maven)으로 바꾼다.

**한국어 본문에서 은유로서의 "계약"은 "명세"로 쓴다.** 법률 계약을 뜻하는 자리(`02 §2` 계약 전자서명, `00 §12` PG 계약, `05 §10` PG 샌드박스 계약)는 그대로 둔다.

**영어 용어는 바꾸지 않는다.** contract testing·contract-first·Design by Contract는 검색 가능한 고유 용어이므로, 영어 자료를 찾을 때는 여전히 contract로 검색한다.

## 근거

`api-spec`을 고른 이유는 나머지 후보에 각각 걸리는 것이 있어서다.

| 후보 | 탈락 사유 |
|---|---|
| `interface/` | 국내 SI의 "IF 정의서"와 바로 통하지만, TypeScript와 Java 양쪽에 `interface` 키워드가 있다. npm·Maven으로 배포되는 저장소에서 `daylink-shared/interface`는 타입 정의로 읽힐 여지가 크다 |
| `openapi/` | 내용물이 OpenAPI 문서이므로 정직하나, `errors.md`·`design-checklist.md`처럼 OpenAPI 문서가 아닌 것도 함께 있어 이름이 내용보다 좁다. `openapi/openapi.yaml` 중복도 어색하다 |
| `spec/` | 짧지만 프론트 저장소에서 `spec`은 테스트 파일(`*.spec.ts`)을 연상시킨다. `e2e/`와 단위 테스트가 늘면 헷갈린다 |
| `contract/` (현행) | 위 맥락 참조 |

`api-spec`은 키워드와 충돌하지 않고, 무엇이 들어 있는지 이름만으로 분명하며, 한국어 "API 명세"와 1:1로 맞는다.

## 결과

- **ADR-0005의 명명 부분만 대체된다.** 저장소 6개 분리, GitHub Packages 배포, SemVer 규약, 로컬 포트 규약은 전부 그대로 유효하다. ADR-0005 본문은 ADR-0001 규칙에 따라 고치지 않고 상태 줄만 갱신했다.
- **배포 전에 바꿨으므로 소비자 갱신 비용이 없다.** ADR-0005 부록 4의 `0.1.0` 최초 배포가 아직이라 마이그레이션 대상이 존재하지 않는다. 배포 후였다면 다섯 저장소의 의존성을 동시에 갱신해야 했다.
- **`api-spec/`에는 이미 `openapi.yaml`·`errors.md`·`design-checklist.md`가 들어 있다.** ADR-0005 부록 3의 절반이 여기 있으므로 개명이 곧 그 작업의 이전이다.
- **혼란 지점이 하나 남는다.** 영어 자료는 contract, 한국어 문서는 명세로 갈린다. 이 ADR이 그 대응표 역할을 한다.
- **번복 조건**: 외부 협업자가 합류해 `contract/`를 관례로 기대하거나, contract testing 도구(Pact 등)를 도입해 도구 규약이 폴더명을 요구하면 재검토한다.
