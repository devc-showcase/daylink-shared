# ADR-0017 Swagger UI는 화면만 가져오고, 코드에서 명세를 생성하지 않는다

| 항목 | 내용 |
|---|---|
| 상태 | **유효** |
| 결정일 | 2026-09-01 |
| 관련 문서 | `06 §9.1`, `06 §9.2`, `api-spec/errors.md`, `daylink-core-api/src/main/resources/static/docs/` |
| 관련 ADR | ADR-0015(명세 패키지 배포), ADR-0005(저장소 구조) |

## 맥락

API를 만들면서 브라우저로 눌러 볼 화면이 필요해졌다. 배포본에도 붙여야 한다.

JVM 진영의 표준 답은 **springdoc-openapi**다. 의존성 한 줄이면 `/swagger-ui.html`이 생기고, 컨트롤러의 어노테이션을 읽어 OpenAPI 문서를 만들어 준다. SI 현장에서 압도적으로 많이 보이는 방식이고, ADR-0003·0006이 세운 현장 전이 기준으로는 이쪽이 유리해 보인다.

**그런데 이 프로젝트의 명세는 코드가 만드는 것이 아니다.**

`06 §9.1`이 명세 우선을 규정한다 — 스키마와 오류 코드를 코드보다 먼저 확정한다. ADR-0015는 그 명세를 `com.daylink:api-spec` 패키지로 배포하고, Core API는 그것을 **의존성으로 소비한다.** 프론트 네 벌도 같은 패키지에서 타입을 생성한다. 명세 한 벌이 다섯 저장소의 공통 기준점이다.

여기에 생성기를 붙이면 **명세가 두 벌이 된다.** 그리고 화면이 보여주는 것은 생성된 쪽이다 — 즉 화면이 계약이 아니라 구현을 비춘다.

## 결정

**springdoc을 쓰지 않는다.** 어떤 형태의 코드 → 명세 생성기도 넣지 않는다.

**Swagger UI는 화면만 가져온다.** `org.webjars:swagger-ui` 웹자를 의존성에 넣고, `static/docs/index.html`이 그것을 로드한다.

**화면이 읽는 것은 정본 명세다.** `ApiSpecCatalog`가 jar 안의 `daylink/openapi.yaml`을 `/api-spec/openapi.yaml`로 내보내고, 화면은 그 URL을 가리킨다.

**컨트롤러에 `@Operation`·`@Schema` 같은 문서용 어노테이션을 쓰지 않는다.** 설명은 명세에 적는다.

## 근거

**화면이 계약 쪽에 서 있으면 검증 도구가 된다.** 생성된 문서를 보면 "Try it out"은 항상 성공한다 — 문서가 코드에서 나왔으니 코드와 어긋날 수가 없다. 정본 명세를 보면 다르다. 실패하면 그것은 **구현이 계약을 지키지 않는다**는 뜻이고, 그 자리에서 드러난다. `00 §9`의 동등성 비교가 명세 한 벌 위에 서 있으므로 이 차이가 값을 한다.

**실제로 붙이자마자 결함을 찾았다.** 화면을 띄웠더니 `/favicon.ico` 요청이 500으로 나갔다. 확인해 보니 없는 경로·헤더 누락·깨진 JSON·잘못된 메서드가 **전부 500**이었다. `@ExceptionHandler(Exception.class)` 하나가 Spring이 이미 올바르게 정해 둔 상태 코드까지 삼키고 있었다.

그리고 그 과정에서 **명세의 구멍**도 드러났다. `errors.md`에 400·405·415에 해당하는 코드가 없었다. 업무 오류만 적고 프로토콜 오류를 빠뜨린 것이다. 네 프론트가 통합 중 반드시 만나는 응답인데 계약에 없었다 — 화면 하나가 오류 계층과 명세 양쪽의 결함을 드러낸 셈이다.

**생성기를 "끄고 쓰는" 선택지도 검토했다.** springdoc은 `springdoc.api-docs.enabled=false`로 생성을 끄고 `springdoc.swagger-ui.url`로 외부 명세를 가리킬 수 있다. 설정 두 줄이면 같은 결과다. 그러나 그 안전은 **설정에 달려 있다.** 생성기가 클래스패스에 있는 한 누군가 어노테이션을 붙이는 순간, 또는 설정 한 줄이 지워지는 순간 명세가 두 벌이 된다. 구조로 막을 수 있는 것을 규칙으로 막지 않는다 — ADR-0007이 `rollbackFor` 대신 예외 계층을 고른 것과 같은 판단이다.

탈락한 대안이다.

| 대안 | 탈락 사유 |
|---|---|
| springdoc (기본 설정, 코드에서 생성) | 화면이 계약이 아니라 구현을 비춘다. `06 §9.1`과 정면으로 부딪히고, 명세가 두 벌이 된다 |
| springdoc + 생성 비활성화 + 외부 URL | 결과는 같지만 안전이 설정에 달린다. 생성기가 클래스패스에 남아 있는 한 되살아날 수 있다 |
| Redoc | 읽기 전용이라 읽기에는 더 낫다. 그러나 "Try it out"이 없어 **계약과 구현을 대조하는** 이 결정의 핵심 가치가 사라진다. 정적 문서가 필요해지면 그때 함께 둔다 |
| 화면 없이 `curl`만 | 의존성이 안 늘지만 배포본에 붙일 것이 없다. 프론트 구현자가 계약을 눌러 볼 통로도 사라진다 |

## 결과

- **`/docs`가 배포본에 함께 나간다.** 웹자가 jar 안에 들어가므로 별도 배포물이 없다.
- **명세를 고치면 화면이 즉시 따라온다.** 화면이 파일을 읽으므로 재빌드 없이도 바뀐다. 반대로 **구현을 고쳐도 화면은 안 바뀐다** — 그게 이 결정의 요점이다.
- **`errors.md`에 프로토콜 절을 신설했다.** `MALFORMED_REQUEST`(400)·`METHOD_NOT_ALLOWED`(405)·`UNSUPPORTED_MEDIA_TYPE`(415)이다. `VALIDATION_FAILED`(422)와의 경계는 **읽을 수 있는데 값이 규칙을 어긴 것**과 **요청 자체를 읽지 못한 것**이다.
- **오류 핸들러가 `ResponseEntityExceptionHandler`를 상속한다.** Spring이 정한 상태 코드를 존중하고 본문만 우리 모양으로 바꾼다. 상태를 우리가 다시 정하면 프레임워크가 이미 아는 사실을 버리는 것이다.
- **컨트롤러에 문서 어노테이션을 쓰면 이 결정 위반이다.** 리뷰에서 본다. 설명이 필요하면 `openapi.yaml`에 적고 버전을 올린다.
- **`/v3/api-docs`가 404여야 한다.** 생성기가 들어온 것을 잡는 신호이므로 테스트로 고정했다.
- **번복 조건**: ① 명세를 손으로 유지하는 비용이 M3까지 실제로 진도를 막으면 재검토한다 ② 인증·보안 스키마가 복잡해져 화면에서 토큰을 다루기 어려워지면 springdoc의 UI 설정만 빌리는 방안을 다시 본다. 그때도 **생성은 켜지 않는다.**
