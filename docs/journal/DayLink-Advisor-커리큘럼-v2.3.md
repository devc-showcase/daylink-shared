## 0. v2.0에서 철회한 결정 2건

사용자 지시로 두 가지를 철회한다. 철회 사유를 먼저 기록한다 — 내 판단 오류였기 때문이다.

| 철회 항목 | v2.0 | v2.1 | 내 오류 |
|---|---|---|---|
| **M6 배치분(32 정의) 보류** | 32 정의를 범위 밖으로 두고 "학습 기여 0"이라 판정 | **전량 구현·학습 범위에 포함** | 실제 출발점은 분량 압박이었고, 학습 논리는 사후에 붙였다. 각 항목에 `(b) 잃는 것`을 적어놓고 "기여 0"이라 부른 것은 앞뒤가 맞지 않는다. **분량이 구속 조건이 아니면 제외 근거가 성립하지 않는다** |
| **UI 완성도 하향** | 완료 조건 충족 최소선으로 하향, 회수 120h | **복원** | 03 §7.2("픽셀보다 정보 계층·조작·결과·접근성의 동등성")는 **비교 기준**을 정한 문장이지 완성도를 낮추라는 허가가 아니다. 근거를 확대 해석했다 |

### 0.1 `Phase1 / Phase2` 라벨은 폐기한다

이 라벨은 원래 **"만들 것 / 안 만들 것"** 을 뜻했다. 그 결정이 철회됐는데 라벨만 남아 다른 뜻으로 쓰이고 있었다. **이름이 뜻을 배신한 상태**이므로 폐기한다.

대신 두 가지를 각각 별개의 열로 표기한다. 하나는 화면의 속성이고 하나는 순서다.

| 표기 | 내용 | 성격 |
|---|---|---|
| **완료 조건** | 그 화면에 걸린 AC ID 나열. 없으면 빈칸 | 화면의 **속성** — 끝났는지 객관적으로 판정할 수 있는가 |
| **마일스톤** | M1~M6 | **순서** |

**용어 정의.** 본 문서의 **완료 조건**은 PRD의 **인수조건**(01 §10, 02 §12, 06 §13)과 같은 것을 가리킨다. ID 체계(`B2C-AC` / `ADM-AC` / `CORE-AC`)는 PRD 표기를 그대로 쓴다. PRD 용어를 바꾼 이유는 `인수`가 발주처의 납품 수령을 뜻하는데 이 프로젝트에는 발주처가 없기 때문이다. **완료 조건은 화면의 시각적 완성도와 무관하다** — 판정 기준이 있는가를 뜻한다.

**순서 원칙:** 완료 조건이 걸린 화면을 먼저 만든다. 근거는 06 §12 보완책 2다 — M3(Core API 심화)가 "프론트가 돌아가는 상태에서 서버를 조인다"를 수행하려면 **판정 가능한 화면**이 먼저 있어야 한다. 그리고 각 마일스톤의 완료를 AC ID로 판정하는데, 판정 기준이 없는 화면이 섞이면 "이 마일스톤이 끝났는가"를 말할 수 없다.

### 0.2 철회의 부수효과 — 되돌아오는 것 3가지

| 항목 | v2.0 | v2.1 |
|---|---|---|
| 구현화면 | 94 (47 정의 × 2벌) | **158 (79 정의 × 2벌)** |
| 대표 E2E | 17개 실행 (Admin 1번 불가) | **18개 전부 실행** — PTN-002·OPS-002·003 복원 |
| IA 미해결 항목 | 3건 소멸·1건 부분 소멸 → 3건 남음 | **7건 전부 다시 열린다** (§4.4) |

**세 번째가 중요하다.** v1.0·v2.0에서 "범위 절단으로 자동 소멸"이라 보고한 IA 확인 항목 3·5·6·7번은 해당 화면을 만들지 않기로 했기 때문에 소멸한 것이었다. 화면이 돌아오면 질문도 돌아온다. **7번(B2C '서비스 소개' 화면 부재)은 특히 내 판정이 약했다** — 01 §4.1 하단 내비게이션에 '서비스 소개'가 있는데 §4.2 화면 목록에 없는 불일치이고, 배치 순서와 무관하게 원래 열려 있던 항목이다.

### 0.3 표기 전환 — 주·개월 제거

`h`는 분량 단위로만 쓴다. 달력 환산을 하지 않는 이유는 두 가지다.

1. 개인 학습자의 절대 소요는 편차가 2~3배까지 난다. 특히 §2.8의 **백엔드 학습 260h가 가장 불안정**하다 — Java·Spring·SQL 최초 학습 속도는 개인차가 가장 큰 영역이다.
2. 반면 **비중은 안정적이다.** 화면 분량(화면 수 × §2.8 배수)은 개인 속도와 무관한 상대값이므로, 배분 판단의 근거로 쓸 수 있다.

### 0.5 남은 긴장 1건 — 규칙으로 해소

00 §2.1("기준선으로 확정 후 학습 대상으로 재구현")과 03 §8·04 §9("기능 묶음별로 번갈아 완료")는 **기능 묶음 단위에서 양립한다.**

**판정: 묶음 단위 교차를 채택한다.** 00 §2.1이 금지한 것은 "기준선 코드를 옆에 두고 옮기는 것"이지 묶음 단위 교차가 아니다.

**절차를 강제한다.** 묶음 하나를 기준선으로 완성 → 커밋 → **에디터에서 기준선 소스를 닫고** PRD와 화면 목록만 열어둔 상태로 학습 대상 착수. 이 절차가 없으면 00 §2.1 규칙 1은 선언으로만 남는다.

## 2. 현재 수준 진단

(a) 가진 것 / (b) 없는 것 / (c) **잘못 알고 있을 가능성이 높은 것**. (c)는 **의미가 바뀐 API**와 **다른 실행 모델에서 오는 직관 오류**만 지목했다.

| (b) | JVM 실행 모델, Gradle/Maven, 표준 라이브러리 관용구, 예외 체계, 컬렉션 프레임워크, 스트림 API, 패키지 구조, JAR·클래스패스 |

TS `readonly`와 다르다 |

**Kotlin에서 Java로 바꾸면서 새로 생긴 위험 (2026-08-24).** Kotlin에는 체크 예외가 없어 §2.6 (c)③이 잘 드러나지 않았다. Java에서는 `throws`를 선언하는 것이 자연스럽고, **Spring의 `@Transactional`은 기본적으로 unchecked exception에서만 롤백한다.** 즉 체크 예외를 던지면 트랜잭션이 커밋된다. `06 §8`의 원자성 요구 전체가 이 한 가지로 조용히 무너질 수 있다. **D10의 3종 재현에 이 경로를 반드시 포함한다.**

**SI 현장 코드를 읽을 때의 간극.** 현장 레거시는 Java 8·11 + Spring Boot 2.x가 많다. Boot 2 → 3에서 `javax.*` → `jakarta.*` 네임스페이스가 바뀌었고 이것이 가장 먼저 마주치는 차이다. 최신으로 배우되 간극을 따로 인지한다.

Java 선택으로 발생 확률이 올라간 항목이다 ④ **`readOnly = true`는 최적화 힌트이지 쓰기 차단 보장이 아니다** ⑤ **"JS는 싱글 스레드라 경쟁 조건이 없다"는 직관이 통째로 무효.** JVM 웹 서버는 요청마다 스레드를 쓴다. 싱글턴 빈에 가변 필드를 두면 요청 간 상태가 오염된다. **이 프로젝트 전체에서 가장 위험한 negative transfer** ⑥ **커넥션 풀 크기가 실질적 동시성 상한**이다. 06 §14.2의 N=50 결과를 좌우한다 ⑦ **`isolation` 속성이 DB·드라이버에 따라 무시될 수 있다.** 06 §12 보완책 4가 "락을 걸었으니 안전하다"를 인정하지 않는 이유 |

### 3.4 언어 결정 — **Java 21 확정** (사용자 판단, 2026-08-24)

| 기준 | Java | Kotlin | 판정 |
|---|---|---|---|

| **SI 현장 코드 읽기**(2순위) | 레거시가 Java 8/11 + MyBatis + XML인 현장이 많다 | Kotlin으로 배운 Spring 지식은 Java Spring 코드를 읽는 데 **거의 그대로 전이된다** | **차이 작음** |
| JPA 마찰 | 없음 | `kotlin-jpa`·`kotlin-allopen` 플러그인이 필요하고 **초보에게 원인 불명 오류로 나타난다** | **Java 유리.** 이 항목이 Java 확정으로 해소됐다 (−5h) |

**결정: Java 21 + Spring Boot 4.** 위 표에서 나는 Kotlin을 권고했으나 **사용자가 Java로 확정했다.** 사유는 "국내에서 Kotlin이 백엔드로 많이 선호되지 않는다"이며, 이는 내가 적어둔 번복 조건 ①에 해당한다.

**내 권고를 철회한다.** 표의 판정 열은 학습 부담(1순위)만 본 것이고, SI 실무 적용(2순위)에서 Java가 갖는 이점을 "차이 작음"으로 과소평가했다. 채용 시장의 언어 선호는 코드 읽기 능력과 별개 변수인데 그것을 계산에 넣지 않았다.

**다만 당시 "우선순위 자체가 바뀐 것이므로 커리큘럼 전체를 다시 봐야 한다"고 쓴 것은 과장이었다.** 실제 영향은 국소적이다 — 언어 학습 +15h, 보일러플레이트로 인한 구현 +18h, JPA 플러그인 마찰 해소 −5h. 순증 **+28h(1.5%)** 이고 마일스톤 구조·완료 조건·순서는 그대로다.

**버전 결정 (Advisor 판단).** **Java 21 LTS.** Spring Boot 4의 최소 요구는 17, 권장은 21·25다. 25가 최신 LTS지만 Spring 실전 자료는 21 기준이 압도적이고, 백엔드는 이 프로젝트에서 유일하게 기준선이 없는 영역이므로 **자료 밀도가 결정 변수**다. 프레임워크는 Spring Boot 4로 시작한다 — 3→4 변경은 2→3만큼 파괴적이지 않아 기존 Boot 3 자료가 거의 그대로 통하고, 중간 메이저 마이그레이션을 피할 수 있다.

### 3.5 영속성 계층 — **명시적 SQL 우선, JPA는 M3 후반** (PRD 미규정)

| 단계 | 선택 | 근거 |
|---|---|---|
| M1~M3 전반 | **Spring JDBC 또는 MyBatis (명시적 SQL)** | 06 §8.1이 "**데이터베이스가 판정하게 하라**"를 요구한다. 명시적 SQL에서는 락과 조건이 코드에 그대로 보이므로 D9에 직접 도달한다 |
| M3 후반 | **JPA 도입, 낙관적 락(`@Version`)에 한정** | 06 §8.7의 버전 기반 충돌 감지는 JPA의 정석 사용처다. 이 시점이면 §2.7 (c)③④를 추적할 기반이 생긴다 |

**JPA를 처음부터 쓰지 않는 이유:** dirty checking과 flush 타이밍이 "언제 어떤 SQL이 나가는지"를 가린다. §2.7 (c)②의 오해를 가진 상태로 JPA를 쓰면 그 오해를 **관찰할 수 없는 형태로** 심게 된다. 06 §12가 지적한 "잘못된 설계가 테스트를 통과하며 살아남는" 구조가 여기서 가장 잘 작동한다.

### 4.2 UI 완성도 — 복원

v2.0의 하향 결정을 철회한다. 다만 **비교를 오염시키지 않는 제약 2가지**는 유지한다.

| 유지할 제약 | 근거 |
|---|---|
| 시각 완성도는 **네 구현에서 동일 수준**으로 올린다. 한쪽만 다듬지 않는다 | 00 §9 "한쪽 구현에만 편의 기능을 추가하면 비교 결과가 왜곡된다" |
| 04 §10의 성능 측정은 **같은 시각 완성도 상태에서** 수행한다. 측정 후 한쪽만 UI를 추가하면 이전 측정값을 폐기한다 | 04 §10 "같은 데이터량·기기에서 측정" |

**03 §7.2를 다시 읽는다.** "화면 픽셀을 완전히 같게 만들기보다 정보 계층·조작·결과·접근성의 동등성을 본다"는 **동등성 판정 기준**을 정한 문장이지 완성도 하향 허가가 아니다. v2.0에서 이를 확대 해석한 것을 정정한다.

### 4.3 Core API 비동기 작업 — 축소 유지

이 항목은 철회하지 않는다. **PRD 자신이 이미 잘랐기 때문이다.**

| 구현 | 보류 |
|---|---|
| `Job` 상태 전이, 파일 생성, 만료 시각, 권한·목적·시각·범위 기록 (**CORE-AC-22 전부**) | 전용 워커 프로세스, 재시도 정책, 우선순위 큐, 분산 잠금 |

**근거:** 00 §12와 06 §3.2가 "메시지 브로커를 전제로 한 이벤트 소싱·CQRS"를 명시적으로 범위 밖에 두었다. 이는 내 판단이 아니라 PRD 결정이다. CORE-AC-22가 요구하는 것은 큐 인프라가 아니라 **권한·목적·만료·감사**다.

## 6. 가장 비현실적인 가정 하나

v2.0에서 지목한 **"Core API는 1벌이므로 프론트 4벌보다 작다"는 착시**는 M6 배치분 복원으로 근거가 바뀌었다. 세 근거 중 하나가 무너졌으므로 먼저 정정한다.

| v2.0 근거 | v2.1 상태 |
|---|---|
| ① Core API 46% > 프론트 4벌 37% | **무너졌다.** 36% < 51%. Core API는 더 이상 최대 항목이 아니다 |
| ② CORE-AC 29개는 참조할 "먼저 푼 답"이 없다 (06 §1.3) | **그대로** |
| ③ 일정·진행 위험이 단일 블록에 몰려 있다 | **그대로, 오히려 선명해졌다** |

그래서 지목을 다시 한다.

> **"Core API가 늦거나 틀리면 무엇이 멈추는지"가 어느 문서에도 없다는 것.**

**1. 의존 방향이 완전히 일방적이다.**
00 §5 다이어그램에서 네 프론트가 모두 Core API를 가리킨다. 06 §1.1은 "가격·재고·권한·상태 전이·정산은 전부 이 서버가 결정한다"고 못박았다. 그 결과 **Core API가 막히면 M2~M6이 전부 막힌다.** 반대는 성립하지 않는다 — Nuxt 구현이 막혀도 Next·React·Vue·Core API는 진행된다. 프로젝트 전체 진행 위험의 대부분이 **35.8%짜리 하나**에 걸려 있다.

**2. 그런데 그 35.8%가 가장 못 배운 영역이다.**
§2.5·§2.6·§2.7의 (b)가 전부 비어 있다. 언어·프레임워크·영속성 세 가지가 동시에 신규다. **이 프로젝트에서 유일하게 "전제가 없는" 영역이 유일하게 "모두가 의존하는" 영역이다.**

**3. PRD는 이 위험의 절반만 다뤘다.**
06 §12는 "잘못된 설계가 테스트를 통과하며 살아남는다"는 **품질** 위험을 다루고 보완책 4개를 붙였다. 05 §10 잔여 위험 표에도 같은 항목이 들어갔다. 그러나 **"이 블록이 늦으면 나머지가 전부 멈춘다"는 진행 위험은 00·05·06 어디에도 없다.** 품질 게이트는 있고 진행 게이트는 없다.

**무엇을 바꾸라는 것이 아니다.** Spring 선택도, 직접 구현도, 1벌 결정도 각각 근거가 있다. 필요한 것은 **진행 위험을 문서에 올리는 것**이다. 두 가지를 권한다.

- **05 §10 잔여 위험 표에 한 행을 추가한다.** "Core API 지연 시 M2~M6 전체 정지 / 현재 완화: 없음 / 추가 검증: M1의 얇은 Core API가 M2를 실제로 굴릴 수 있는지 M1 종료 시 확인". 06 §12의 품질 보완책 4개와 나란히 놓여야 한다.
- **M1 종료 조건에 "M2를 시작할 수 있는가"를 명시적으로 넣는다.** 지금 M1의 완료 판정은 완료 조건과 ADR로 되어 있는데, 실질적인 질문은 **"이 얇은 Core API 위에서 Nuxt 구현을 시작할 수 있는가"**다. 이게 안 되면 M1은 끝난 것이 아니다.

이 프로젝트는 "프론트 4벌 비교 학습 + Core API"가 아니라 **"모두가 의존하는 35.8%짜리 신규 학습 + 그 위에 얹는 51%짜리 비교 학습"** 이다. 분량 순서는 프론트가 앞이지만 **의존 순서는 Core API가 앞이고, 위험은 의존 순서를 따른다.**
