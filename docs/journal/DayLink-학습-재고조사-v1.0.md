## 3. 뒤집힌 이해 — 2항목 (최우선)

모르는 게 아니라 **다르게 안다.** 커리큘럼 §2 머리말이 "(c) 잘못 알고 있을 가능성이 높은 것"을 따로 뽑은 이유가 이것이다.

### 3.1 좌석 확보 — SELECT 후 판정 본능

원문 답변:

> 먼저 좌석이 남아 있는지를 확인하고 요청이 들어온 순서대로 좌석 확보를 시도한다. 동시에 요청이 들어 왔다고 하더라도 분명 완전히 동일한 시간에 요청한것을 아닐 것이다.

두 겹으로 어긋난다.

1. **조회 후 판정.** 06 §8.1이 금지하고 `SlotMapper.xml`이 주석으로 경고하는 바로 그 형태다
2. **"완전히 동시는 아니다".** 도착 시각이 달라도 두 트랜잭션의 **읽기 구간이 겹치면** 둘 다 잔여 1석을 본다. 시각의 문제가 아니라 구간의 문제다

`CORE-AC-01`·`CORE-AC-02`가 정확히 이 지점을 요구한다. 커리큘럼 D4·D9의 합격선이 여기 걸려 있다.

### 3.2 멱등 키 — 방향이 반대

원문 답변:

> 달라야 한다. 서버는 작업이 같은지 다른지 보다 각각의 작업으로 볼것 같다.

실제는 반대다. 재전송은 **같은 키**를 실어야 서버가 하나의 작업으로 묶는다. 키가 매번 다르면 좌석이 두 번 잡힌다. 지금 `HoldController`가 `Idempotency-Key` 헤더를 받는 방식이 그것이고, `idempotency_record`의 기본 키가 중복 판정 수단이다.

`CORE-AC-03`·`04`·`05`, 커리큘럼 D5가 여기 걸려 있다.

### 3.3 부수 발견 — 동시성과 멱등성을 한 덩어리로 본다

"좌석 로직이 안전함을 어떻게 증명하겠나"에 대한 답이 "멱등 키, 요청시간 등을 겹겹이 판단하면"이었다. 질문은 **검증 방법**을 물었는데 답은 **구현 수단**으로 왔고, 그 수단도 다른 문제의 것이다.

- 동시성 — 같은 자원에 서로 다른 요청 여럿
- 멱등성 — 같은 요청이 여러 번

둘은 다른 문제이고 방어 수단도 다르다. 이 구분이 서기 전에는 D4도 D5도 안 선다.

## 5. 재설계 방향

### 5.1 프레임워크를 먼저 얹지 않는다

`@Transactional`·MyBatis·Liquibase를 먼저 가르치면, 3.1이 왜 깨지는지가 프레임워크 뒤에 숨는다. **DB 하나만 놓고 손으로 깨뜨려 보는 회차를 앞에 둔다.**

터미널 창 두 개로 `psql`에 붙어 `BEGIN`을 직접 치는 형태다. 자바는 그다음이다.

### 5.2 회차 순서 초안 (백엔드)

각 회차는 개념 하나 + 손으로 하나 + 확인 질문 셋이다.

1. **BEGIN과 ROLLBACK** — 창 하나에서 쓰고 되돌린다. 2절의 트랜잭션 빈칸을 채운다
2. **창 두 개** — 한쪽이 커밋하기 전에 다른 쪽이 무엇을 보는가. 3.1의 "완전히 동시는 아니다"를 손으로 깬다
3. **SELECT 후 UPDATE를 직접 짜서 깨뜨린다** — 잔여 1석에 두 창이 모두 성공하는 것을 자기 눈으로 본다
4. **조건부 UPDATE와 영향 행 수** — 같은 상황에서 한 건만 통과하는 것을 확인한다. 여기까지가 D4·D9의 바닥이다
5. **같은 요청을 두 번** — 3.2를 같은 방식으로 깬다. 같은 키·다른 키를 직접 쏜다
6. **Spring `@Transactional`** — 1~4를 프레임워크로 옮긴다. 자기 호출 함정은 여기서
7. **MyBatis 배선** — 2절 빈칸
8. **Liquibase** — 2절 빈칸. 적용된 changeset을 고쳐서 체크섬 위반을 직접 낸다

1~5는 자바 없이 SQL만 쓴다.

### 5.3 코드 재작성 제안 — 끝났다 (2026-09-21~22, 회차 13)

셋 다 사용자가 다시 썼다. 진행과 결과는 §6.2 회차 13에 있다.

지우고 다시 쓴 후보 셋이었다.

- `CreateHoldTransaction.java` — 트랜잭션 경계. 회차 6의 산출물
- `SlotMapper.xml`의 `tryHoldSeats` — 조건부 UPDATE. 회차 4의 산출물
- `CreateHoldService.java` — 멱등 처리. 회차 5의 산출물

CLAUDE.md 담당표 기준으로 셋 다 원래 사용자 담당인 도메인 로직이다. 남기는 것 — 예외 매핑, 명세 검사, 컨트롤러, 테스트 배선(`TestDatabase`·`ContainerConfig`). 마이그레이션 러너는 이 목록에 있었으나 ADR-0021로 클래스가 사라졌다.

### 3.3 재질문 — 회차 5 직후

## 6.2 진행 기록

회차마다 확인 질문 셋을 통과해야 다음으로 넘어간다. 못 맞히면 같은 자리에서 다른 각도로 다시 묻는다.

**회차 1 — 되돌리기 (2026-09-07, 통과)**
DBeaver 수동 커밋으로 트랜잭션 경계를 손에 넣었다. 예측 실패 지점은 "커밋 전 값을 다른 연결이 볼까"였다 — 1로 예측했고 실제는 0이었다. 여기서 READ COMMITTED와 행의 다중 버전이 나왔다. 확인 질문 3/3.

**회차 2 — 쓰기끼리 부딪히면 (2026-09-07, 통과)**
예측 실패 지점은 "경쟁 UPDATE가 바로 성공한다"였다 — 실제로는 20초 넘게 멈췄다. 회차 1의 "읽기는 안 기다린다"를 쓰기에 그대로 확장한 오류다. 행 잠금이 나왔다.

**회차 3 — 확인 후 갱신 (2026-09-07, 통과)**
2절 3.1의 제안을 사용자가 직접 짜서 깨뜨렸다. 정원 10에 taken 11. 두 창 모두 SELECT로 확인했고 두 창 모두 정상 판단했는데 초과했다. **손으로 친 두 문장이 20초 이상 벌어졌는데도 깨졌다** — "완전히 동일한 시간이 아니다"라는 오해가 여기서 무너졌다. 확인 질문 3/3.

**회차 4 — 판단과 실행을 붙인다 (2026-09-07, 통과)**
조건부 UPDATE와 영향 행 수. WHERE 재평가가 나왔다. 확인 질문 2/3 — "멈춘 원인과 0건이 된 원인이 같은가"를 같은 원인이라고 답했다. 롤백 시나리오를 직접 실행해 1건이 나오는 것을 보고 교정했다. 같은 대기, 다른 결과이므로 원인이 둘이다.

여기까지 자바 없이 SQL만 썼다. 실습 테이블은 `lab.seat`이고 안전장치를 일부러 뺐다.

**회차 5 — 같은 요청이 두 번 (2026-09-07, 통과)**
멱등. 조건부 UPDATE가 멀쩡한데도 버튼 두 번에 예약 두 건이 생기는 것을 직접 만들었다. 이어서 조회 후 삽입이 회차 3과 같은 모양으로 깨지는 것을 확인하고, 기본 키로 판정을 문장 안에 넣어 유니크 위반을 받았다.

확인 질문 1/3에서 멈췄다. 2번(왜 하나는 0건이고 하나는 에러인가)은 `ON CONFLICT DO NOTHING`으로 같은 중복 상황에서 0건이 나오는 것을 보여 교정했다 — 에러를 만든 것은 중복이 아니라 문장에 조건이 없다는 사실이다. 3번(왜 층이 둘인가)은 한 층짜리 흐름을 단계로 적어 ③에서 막히는 지점을 짚었다.

**도구가 동작을 가린 사례.** DBeaver는 문장마다 저장 지점을 깔아서 제약 위반 뒤에도 트랜잭션을 살려둔다. `psql`로 직접 실행해 `current transaction is aborted`를 확인했다. 학습 환경이 실제 동작과 다를 수 있다 — 이상하면 도구를 의심하고 DB에 직접 묻는다.

**중간에 상태가 어긋난 사건.** 사용자가 문장을 두 번 실행하고 한 문장을 건너뛰어 `hold` 3행·`idem` 1행이 됐다. 추측하지 않고 `pg_stat_activity`와 실제 행을 열어 확인한 뒤 판을 다시 깔았다. 그 뒤로는 지시를 문장 단위로 쪼개고 실습 범위에서 좌석 갱신을 뺐다.

**연결이 하나면 창이 둘이어도 창 하나다.** 편집기를 새로 열어도 같은 연결이면 같은 트랜잭션 안이다. 별도 연결(`daylink 1`)을 복사해서 쓴다.

**회차 6 — 버튼을 코드에 넘긴다 (2026-09-08, 통과)**
`@Transactional`. 사용자가 자바 파일을 처음 직접 썼다 — `src/test/java/com/daylink/coreapi/lab/LabHoldService.java`. 실습 파일이므로 본문 44개에는 안 들어간다. 테스트 뼈대는 이번 한 번만 Claude가 줬고, 다음 회차부터는 사용자가 쓴다.

규칙은 하나다 — 메서드가 정상 종료하면 커밋, 예외로 끝나면 롤백. "왜 반환값이 아니라 예외인가"에서 한 번 막혔고, `void`를 돌려주는 메서드와 `0`을 돌려주는 메서드를 예로 들어 교정했다. **Spring은 값의 뜻을 모른다.**

**음성 대조를 실행했다.** `@Transactional`을 지우면 롤백 테스트만 깨지고 커밋 테스트는 통과한다. 커밋 테스트는 이 어노테이션을 검증하지 못한다는 사실을 사용자가 직접 확인했다.

**확인 질문 3번에서 회차 5의 abort가 되살아났다.** "@Transactional 안에서는 예외 발생 여부를 알 수 없다", "catch 안에서 조회가 될 것이다"로 답했다. 설명으로 다투지 않고 `잡고_조회한다` 메서드를 사용자가 직접 써서 돌렸고, `SQL state [25P02] current transaction is aborted`를 자바 스택 트레이스에서 확인했다. 그 뒤 3번을 자력으로 재구성했다.

정정된 문장 — 문제는 "예외를 알 수 없다"가 아니라 **"알아도 그 자리에서는 아무것도 못 한다"** 다.

**회차 7 — 중간에 낀 것 (2026-09-08, 통과)**
프록시와 자기 호출. 회차 6의 스택 트레이스에 남은 `ReflectiveMethodInvocation.proceed`에서 시작했다. `withTransaction(fn)`으로 원본 함수를 감싸 바꿔치기하는 JS 비유가 통했고, 사용자가 "`this`는 원본 객체라서 `@Transactional`이 안 걸린다"를 자력으로 말했다.

**사용자가 처음으로 테스트를 직접 썼다.** 첫 번째는 Claude가 쓰고 두 번째를 사용자가 썼다. 단언을 `isZero()`로 적어 실패했고, 그 실패 메시지(`expected: 0L but was: 1L`)가 그대로 증명이 됐다 — 예측은 1행으로 맞췄고 단언만 어긋났다.

같은 메서드·같은 어노테이션인데 부른 쪽에 따라 결과가 갈린다. 직접 호출은 0행(롤백), 자기 호출은 1행(자동 커밋). 확인 질문 3/3.

**회차 8 — 규칙에 예외가 있다 (2026-09-09, 통과. 최다 재시도)**
체크 예외는 롤백되지 않고 커밋된다. 사용자가 `체크예외로_끝난다`를 직접 쓰고 돌려 `expected: 0L but was: 1L`을 확인했다.

**단언 없는 테스트를 처음 만났다.** 사용자가 쓴 첫 판에는 `count` 단언이 없어 통과했다. 예외가 났는지만 보고 롤백 여부를 묻지 않는 테스트였다 — 회차 6의 음성 대조와 같은 교훈.

**방향을 여러 번 뒤집었다.** "체크가 롤백"으로 계속 돌아갔다. (2026-09-09 정정 — 대화창에 사용자가 쓰지 않은 답변이 끼어드는 일이 있었다. 같은 질문에 상반된 답이 연달아 온 경우가 여러 번이고, 그중 어느 쪽이 사용자의 답인지 확정할 수 없다. **"네 번"이라는 횟수는 근거가 약하므로 취소한다.** 확실한 것은 세 가지 방법으로 해소됐다는 사실뿐이다.) 원인 진단 — **용어가 오해를 만든다.** 한국어로 "체크 예외"를 읽으면 "확인되는 예외 → 시스템이 처리 → 롤백"으로 읽힌다. 실제로 체크는 컴파일러가 확인한다는 뜻이고, Spring은 그것을 "예상된 상황"으로 보아 되돌리지 않는다.

해소한 방법 셋. ① 자기가 돌린 두 테스트 결과(0행 vs 1행)를 롤백·커밋에 직접 대응시켰다 ② `RuntimeException`도 `Exception`을 상속하지만 언체크라는 예외 가지를 상속 트리로 그렸다 — 사용자가 "Exception을 상속받으니 체크"라고 본 지점이다 ③ **"예상된 것은 커밋, 사고는 롤백"** 을 한 줄로 주고 사용자 파일에 주석으로 직접 써넣게 했다.

부수 정리 — 체크/언체크 구분이 컴파일러(throws 강제)와 Spring 롤백 판정 두 곳에서 각각 작동하며 서로 별개라는 것을 갈라줬다.

**D10 3종 중 2종 완료.** 자기 호출과 체크 예외를 재현했다. 남은 것은 전파 속성이다.

**회차 9 — 몸통 없는 인터페이스 (2026-09-09, 통과)**
MyBatis 배선. 2절 빈칸 하나를 채웠다. 사용자가 `LabMapper` 인터페이스와 `labmapper/LabMapper.xml`을 직접 쓰고 테스트까지 붙였다. 회차 7의 프록시를 그대로 옮겨 붙여 "labMapper는 프록시고 호출을 받으면 SQL을 찾아 실행한다"를 자력으로 말했다.

**착수 전에 Claude가 배선 위험을 먼저 확인했다.** `application.yml`의 `mybatis.mapper-locations`가 `classpath:mapper/*.xml`이라 별표가 없다 — 클래스패스에서 먼저 찾은 `mapper/` 폴더 하나만 본다. `src/test/resources/mapper/`에 파일을 하나 놓자 `CreateHoldApiTest` 6개가 전부 깨졌다. 그래서 실습 XML은 `labmapper/`로 폴더를 갈랐다. **이 제약은 앞으로도 유효하다.**

**파일 위치 실수가 그대로 교재가 됐다.** 사용자가 두 파일을 `src/main`에 두어 `Invalid bound statement (not found)`가 났다. 컴파일은 통과했고 그 메서드를 부르는 순간 터졌다 — 이번 회차의 논점이 사고로 먼저 나타났다.

**두 실수를 대조했다.** ① `id` 오타 → 스프링은 정상 기동, 해당 경로만 실패 ② XML 문법 오류 → `Failed to load ApplicationContext`, 그 클래스 테스트 전멸. 요란한 ②가 더 안전하고, 조용한 ①이 위험하다. **더 일찍 터지는 실수가 더 안전한 실수다.**

확인 질문 1/3에서 시작해 두 번 좁혀 3/3. 3번의 답은 "규칙"이 아니라 **그 메서드를 실제로 부르는 테스트**다. 같은 발상의 기존 예로 `SpecCoverageTest`를 연결했다.

**회차 10 — 한 번만 실행된다 (2026-09-09, 통과)**
Liquibase. 2절의 마지막 빈칸을 채웠다. `t_next.databasechangelog`를 직접 조회해 이력 표를 보고, 적용이 끝난 `0004-slot`에 주석 한 줄을 넣어 검증 실패를 냈다.

```
Validation Failed:
     1 changesets check sum
          db/changelog/0002-slot.sql::0004-slot::daylink
          was: 9:cac8766b358fb65ee30d699efcbe8a96 but is now: 9:a8803a9c...
```

`was:` 값이 조회해 둔 이력 표의 `md5sum`과 같다는 것을 대조로 확인시켰다.

**어제 것과 같은 도구임을 연결했다.** `idempotency_record.request_fingerprint`(같은 키에 다른 본문)와 `databasechangelog.md5sum`(같은 changeset에 다른 내용)은 형태가 같다 — 식별자 하나, 내용 해시 따로, 다음에 대조.

확인 질문 2번에서 "불변이기 때문이다"라고 결론을 이유로 답했다. 세 환경(내 노트북·동료·운영) 시나리오로 되물어 **"서로 다르다"** 를 사용자가 말하게 했다. 이유가 먼저고 규칙이 나중이다. 3번(컬럼 추가)은 2번이 서자 자력으로 나왔다.

**2절 빈칸 3건이 모두 해소됐다.** 트랜잭션(회차 1·6), MyBatis(회차 9), Liquibase(회차 10).

**회차 11 — 전파(propagation) (2026-09-18, 통과)**
`D10` 3종의 마지막이다. 자기 호출(회차 7)과 체크 예외(회차 8)에 이어 전파를 재현했다.

전파는 이미 트랜잭션이 열려 있을 때 안쪽 `@Transactional`이 어떻게 할지를 정한다. 기본값 `REQUIRED`는 합류하고 `REQUIRES_NEW`는 따로 연다. 회차 7의 조건이 그대로 붙는다. 프록시를 거칠 때만 의미가 있어서 실습도 빈을 둘로 나눴다(`LabOuterService`·`LabInnerService`).

예측 둘을 모두 맞혔다. `REQUIRED`는 "사라진다. 합류했으니 같은 트랜잭션이다", `REQUIRES_NEW`는 "남는다"였고 테스트로 확인했다. 확인 질문 셋도 통과했다. ① 멱등 기록만 `REQUIRES_NEW`로 빼면 본 작업이 롤백돼도 키가 남아 재전송이 중복으로 판정된다 ② `markCompleted`의 `@Transactional`은 바깥에 열린 것이 없으므로 새 트랜잭션을 연다 ③ 자기 호출로 부르면 `create`의 트랜잭션에 묶여 함께 롤백된다.

**시작할 때 옵션 문법을 몰랐다.** `REQUIRED`·`REQUIRES_NEW`가 어디에 적는 값인지 모르겠다고 해서 `@Transactional(propagation = Propagation.REQUIRES_NEW)` 모양을 먼저 보여 준 뒤 예측을 받았다. C 이후의 방식 그대로다.

**실제 코드에는 전파 속성이 하나도 없다.** 대신 빈을 나눠 경계를 갈랐다. `CreateHoldService`는 트랜잭션이 없고, `CreateHoldTransaction.create`가 유일한 경계이며, 멱등 기록과 좌석 확보가 한 트랜잭션에 묶여 있다(ADR-0007 결정 7).

**문서-코드 어긋남 1건을 고쳤다.** `IdempotencyMapper.xml`의 주석이 저장소에 없는 `IdempotencyGuard`를 가리켰고, 호출 경계도 "CreateHoldService#create 의 @Transactional 안"으로 잘못 적혀 있었다. 실제 담당은 트랜잭션이 없는 `CreateHoldService`이고 경계는 `CreateHoldTransaction#create`다. 둘 다 정정했다.

**가짜 답변이 또 끼어들었다(2026-09-18, 이날 세 번째).** 확인 질문 3의 답이 사용자 턴에 채워졌고 사용자가 지적했다. 답이 화면에 드러났으므로 같은 질문 대신 한 걸음 뒤의 결과를 물어 통과했다. 채점한 다섯 답은 기록 전에 작성자를 확인했다.

정리 상태 — 실습 파일 `LabInnerService.java`와 `LabOuterService.java`가 늘었다. 전체 테스트 44개가 통과한다(2026-09-18, Claude가 실행해 확인).

**숫자를 진도 지연으로 읽으면 틀린다.** 커리큘럼은 M1 275h 중 **115h(42%)를 화면 0개인 Java·Spring 기초**에 배정했고, 회차 1~13이 정확히 그 구간이다. `00 §11` 완료 기준 6번("실제 데이터베이스와 동시 요청 조건에서 통과")은 임시 확보 하나에 대해 이미 만족한다.

**실제 격차는 셋이다.** API 표면이 1/11, 인수 테스트가 59개 중 2개, 프론트 0벌. 마지막 것은 `05 §10`이 최대 위험으로 지목한 "Core API 지연이 전체를 멈춘다"가 현실화된 상태다.

**그중 하나를 바로 메웠다 — CORE-AC 29개 골격**(`097e100`). `06 §13`의 인수조건을 메서드 하나씩으로 세우고 전부 `@Disabled`로 뒀다. 사유를 둘로 갈랐다. **덮임 4개**(01·02·03·05)는 어느 테스트가 검증하는지 적고 여기서 다시 단언하지 않는다 — 같은 것을 두 곳에서 재면 한쪽이 낡는다. **미구현 25개**는 검증하려면 무엇이 먼저 있어야 하는지 적었다. 단언은 기능을 붙일 때 사용자가 채운다. 골격만 Claude가 만드는 분담을 이날 합의했다.

B2C·ADM 30개는 만들지 않았다. 프론트가 0벌이라 실행할 대상이 없어서, 만들면 "실패"가 아니라 "실행 불가"로 남는다. 그건 M1이 말한 실패와 다르다.

**회차 13 — §5.3 재작성 셋 (2026-09-21~22, 통과)**
원본을 치우고 요구사항만 보고 다시 쓰는 방식이다. 조각마다 커밋했다 — `ba2b696`(tryHoldSeats), `073ddf5`(CreateHoldTransaction), `6e63b39`(CreateHoldService).

**`tryHoldSeats`.** `06 §8.1`과 `CORE-AC-01`·`02`만 보고 썼고 결과 문장이 원본과 같다. 중간에 `WHERE`에서 `held_seats`가 빠진 판이 나왔는데, 그때 동시 50건 중 49건이 `WHERE`를 통과해 `slot_overbook_ck`에 걸렸다. **좌석은 초과되지 않았으므로 좌석 수만 세는 SQL 테스트는 통과했고, `CreateHoldApiTest`가 잡았다**(409 대신 500). 두 번째 겹이 일하고 있으면 첫 번째가 새는 중이라는 실측이라 매퍼 주석에 남겼다.

**`CreateHoldTransaction`.** 순서와 경계를 사용자가 정했고 원본과 같았다. 멱등 기록이 먼저, 좌석 확보가 판정, 스냅숏 조회는 금액용이다. `@Transactional`을 어디에 붙일지도 직접 정했다.

**`CreateHoldService`.** 이 층에 트랜잭션이 없는 이유(abort된 트랜잭션에서는 저장된 응답을 못 읽는다)와 `replay`의 검사 순서가 논점이었다. 순서 질문에는 "모르겠다"가 나와 설명으로 메웠다 — §0에 다시 물을 것으로 적어 뒀다.

**방식.** 자바 문법이 아직 미숙하다고 해서 한 줄씩 붙여 나가는 방식으로 바꿨다. 맨 아래 `throw`를 남겨 두고 그 위에 한 단계씩 추가하면 중간에도 컴파일이 된다. 사용자가 물은 것 — `explainFailure`를 `this` 없이 부르는 이유(자바는 이름이 클래스에 선언돼 있어 컴파일러가 찾는다. JS는 메서드가 객체의 속성이라 `this.`가 필요하다. 그래서 회차 7의 자기 호출 함정도 `this.` 유무와 무관했다).

**부수 발견.** 사용자가 `HttpStatus.UNPROCESSABLE_ENTITY`가 deprecated인 것을 찾아냈다. Spring 7이 RFC 9110을 따라 `UNPROCESSABLE_CONTENT`로 바꿨다. 세 곳을 교체하고 `-Xlint:deprecation`을 빌드에 상시로 켰다(`2065548`). 켠 뒤 경고가 0건이라 그 상수가 유일한 deprecated 사용이었음이 확인됐다.

**편의 설정.** Cursor에서 매번 명령을 치기 번거롭다고 해서 `.vscode/tasks.json`에 태스크 다섯을 넣었다(컴파일, 확보 API, 동시성, 전체, 전체 개발 DB 끄고). `.gitignore` 대상이라 커밋되지 않는다. `java.configuration.updateBuildConfiguration`을 `automatic`으로 바꿨다 — `build.gradle.kts`를 고쳐도 언어 서버가 안 읽던 문제의 원인이었다.

정리 상태 — 개발용 컨테이너를 내린 채 전체 테스트 46개가 통과한다(2026-09-22, Claude가 `--rerun-tasks`로 실행해 확인).

**회차 12 — 테스트가 자기 데이터베이스를 갖는다 (2026-09-19~21, 통과)**
`ADR-0009`가 예고한 Testcontainers 전환이다. 합격 기준을 먼저 정했다 — **개발용 컨테이너를 내린 채 전체 테스트가 통과할 것.**

**방식을 두 가지 바꿨다.** 사용자가 "배경지식이 없으니 예측이 전혀 안 된다"고 해서 예측을 접고 설명부터 했다. 그리고 용어 지적을 받았다 — 원문은 "억지로 한글로 번역하는 것 같다. 개발자들이 쓰는 용어는 어느 정도 이해할 수 있다". 테이블을 "표", 래퍼를 "상자"로 옮겨 쓰던 것을 그만뒀다. `CLAUDE.md` §1이 이미 정한 규칙인데 내가 어기고 있었다. 메모리 `daylink-writing-style`에 적었다.

만든 것 넷이다. `TestDatabase`(컨테이너 하나를 static으로 띄운다. 이미지는 `postgres:18` 고정, `stop()`은 Ryuk에 맡긴다), `ContainerConfig`(`@TestConfiguration` + `@Bean @ServiceConnection`), `DatabaseFixture`를 컨테이너 기반으로 전환(Spring 없는 테스트 둘도 같은 컨테이너를 본다), `LabSchemaFixture`(`lab` 스키마와 테이블 셋을 만든다. `ADR-0021`이 고른 "테스트 코드가 만든다" 방식이다). Spring 테스트 네 곳에 `@Import(ContainerConfig.class)`를 붙였다.

의존성에서 한 번 막혔다. Boot BOM은 `org.testcontainers:testcontainers` 버전만 관리하고 기술별 모듈은 관리하지 않아서, Testcontainers BOM을 따로 들여왔다. 게다가 2.x에서 모듈 이름이 바뀌었다 — 1.x의 `org.testcontainers:postgresql`이 `testcontainers-postgresql`이다. 옛 이름으로 적으면 "Could not find ... :."로 버전을 못 찾는다.

**틀린 배선이 교재가 됐다.** 확인용으로 만든 `TestDatabaseTest`에 `@SpringBootTest`와 `@Import({TestDatabase.class})`를 붙였더니 컨텍스트가 안 떴다. 원인은 `localhost:5432` 연결 거부였다 — `@ServiceConnection`이 없으니 Spring이 `application.yml`을 그대로 본 것이다. 컨테이너를 쓰지 않으면 어떻게 되는지가 그대로 드러났다. 그리고 세션 첫머리 자기 호출 실험에서 만든 단언이 예측값(1) 그대로 남아 있어 `isZero()`로 고쳤다.

정리 상태 — 개발용 컨테이너를 내린 채 전체 테스트 46개가 통과한다(2026-09-21, Claude가 `--rerun-tasks`로 실행해 확인).

**처리 방침 — 그대로 둔다(선택지 C, 2026-09-09 사용자 결정).** 재작성 회차에서 정리한다. changeset으로 넣거나(A) 테스트가 스스로 만들게 하는(B) 데 시간을 쓰지 않는다.

### 테스트 DB 분리 — 해소됨 (회차 12, 2026-09-21)

사용자가 C를 고르며 든 이유가 실제로는 다른 것을 가리켰다. **"테스트 DB를 실제 DB와 별개로 둔다."** 오랫동안 성립하지 않았다 — `src/test`에 설정 파일이 없어 테스트가 `application.yml`을 그대로 쓰고 `localhost:5432/daylink`에 직접 붙었다. `CreateHoldApiTest`가 개발용 데이터베이스의 `slot`에 행을 넣었다.

`ADR-0009`가 Testcontainers 전환을 예고했고, `daylink-jvm-transfer` 메모도 **상시 기동 DB는 격리가 약해 동시성 테스트가 거짓 통과할 수 있다**고 적어뒀다. 회차 12에서 그 전환을 끝냈다. 이제 테스트가 컨테이너를 직접 띄우고, 개발용 컨테이너를 내린 상태에서도 전체가 돈다.

### 테넌트 스키마 넷을 걷어냈다 (2026-09-18, ADR-0021)

발단은 사용자의 질문이었다. `Tenant` enum의 `NEXT`·`NUXT`·`REACT`·`VUE`를 왜 나눠 놨느냐고 물었고, 이어서 **프레임워크 이름으로 짓지 말고 용도와 역할로 지어야 한다**고 지적했다. 그다음 질문이 더 멀리 갔다. "왜 계속 넷으로 나누려고 하는가."

그 지적이 맞았다. 넷으로 가른 것은 제품의 사실이 아니라 비교 실험의 사정이었다. 실제 제품이라면 클라이언트가 넷이어도 데이터베이스는 하나다. Claude가 `05 §4.2`의 "별도 테넌트"를 문자 그대로 받아 상시 스키마 넷으로 굳혔고, 그 순간 학습 사정이 제품 구조로 새어 들어갔다.

중간에 Claude가 한 번 더 같은 오류를 냈다. 역할 기반 이름으로 `B2C_LEARNING` 같은 후보를 냈는데, 기준선·학습 대상은 **제품의 역할이 아니라 학습 운영상의 구분**이다. 사용자가 그 자리에서 잡았다.

바꾼 것 — 스키마는 하나(`public`)다. `Tenant`·`TenantSchemaMigrator`·`MigrationRunner`·`SchemaMigrationException`을 지우고 Spring Boot의 Liquibase 자동 설정에 맡겼다. `search_path` 초기화와 `daylink.tenant.schema` 설정도 없앴다. 테스트 픽스처 둘에서 스키마 인자를 걷어냈고, `TenantSchemaMigrationTest`는 `SchemaMigrationTest`로 다시 썼다. 로컬 DB에서 `t_next`·`t_nuxt`·`t_react`·`t_vue`를 지웠다.

**실패 6건의 원인을 찾았다. 그리고 그 과정에서 내 검증이 헛것이었다는 것도 드러났다.**

작업 중 `CreateHoldApiTest` 6건이 `relation "hold" does not exist`로 실패했다. 나는 "재현되지 않는다, 원인 미상"이라고 두 번 보고했는데 **그 재실행들은 애초에 실행되지 않았다.** Gradle이 `> Task :test UP-TO-DATE`로 건너뛰었고, 나는 옛 결과 XML을 읽어 "44개 통과"라고 적었다. 코드가 안 바뀌면 Gradle은 DB를 비운 사실을 모른다.

`--rerun-tasks`로 강제 실행하자 빈 스키마에서 6건이 그대로 재현됐다. 원인은 이것이다. **Spring Boot 4는 자동 설정을 기술별 모듈로 쪼갰고, `spring-boot-autoconfigure`에 Liquibase 항목이 없다.** 빌드는 `org.liquibase:liquibase-core`만 선언하고 있어서 기동 시 아무도 changelog를 돌리지 않았다. 예전에는 `TenantSchemaMigrator`가 직접 돌려 이 구멍을 가리고 있었고, 그것을 지우자 드러났다.

고친 방법은 `org.springframework.boot:spring-boot-starter-liquibase`를 넣고 잠금 파일을 다시 쓴 것이다. 검증도 다시 했다 — 빈 `public`에서 `CreateHoldApiTest`만 강제 실행해 6개 통과와 표 8개 생성을 확인하고(다른 테스트가 안 돌았으니 표를 만든 것은 앱 컨텍스트뿐이다), 이어서 전체 44개를 빈 스키마에서 통과시켰다.

**교훈 둘.** 하나, 지운 코드가 가리고 있던 결함은 지워야 보인다. 둘, `UP-TO-DATE`로 건너뛴 실행을 통과로 읽으면 검증이 통째로 거짓이 된다. 오늘 B-3에서 다룬 "조용한 실수"를 Claude가 그대로 밟았다.

부수 정정 — `05 §10`의 "위험 6번"을 잘못 인용한 자리가 둘 있었다(`Tenant.java`, `fixtures/README.md`). §10의 여섯 번째는 "Core API 지연이 전체를 멈춤"이고 `tenant_id` 오염 항목은 §10에 없다. 인용을 걷어냈다.

## 6.4 기초 레인 — 2026-09-09 신설

**발단.** 사용자가 학습 자체에 대해 말했다. 자바 언어가 거의 백지고(변수 선언·함수·클래스를 자바 레벨에서 읽기 어렵다), DB 지식은 더 없고, "왜 SQL을 XML로 쓰는지"를 모른다. 반면 JS/TS는 깊다. **"레벨을 낮출지, 계속할지, 기초를 배우고 돌아올지"** 를 물었다.

**판단 — 떠나서 배우고 오지 않는다.** 일반 자바 강의는 이 프로젝트가 쓰지 않는 것을 가르치고 붙을 데가 없다. 필요한 범위는 좁다 — 클래스와 객체, 필드와 생성자, 인터페이스, 타입, 애노테이션, 예외. 그리고 예측→확인 순환이 실제로 작동 중이라 그것을 버릴 이유가 없다. **레벨도 낮추지 않는다.**

**대신 기초를 옆 레인으로 깐다.** 재료는 사용자가 이미 쓴 파일이다. 새로 배우는 게 아니라 **이미 손에 있는 것에 이름을 붙이는** 작업이라 발밑이 있다.

**회차 A-1 — 파일의 뼈대 (통과)**
`LabHoldService.java` 1~13줄. `package`(폴더와 일치해야 한다), `import`(이름이 곧 주소), `public class`(= export, 파일명과 일치), `private final JdbcClient jdbc;` 네 부분, 생성자(클래스 이름과 같으면 생성자). JS와 1:1로 대봤다.

손으로 — `this.jdbc = null;`을 넣어 `cannot assign a value to final variable jdbc`를 냈다. **컴파일러가 볼 수 있는 것은 컴파일러가 잡고, 못 보는 것은 테스트가 잡는다** — 회차 9의 매퍼 `id` 오타와 대조시켰다.

**회차 A-2 — 메서드 (통과)**
`@Transactional public void createHold(String key, boolean explode)`를 조각냈다. 반환 타입·파라미터 타입이 JS와의 최대 차이이고 TS 경험이 다리가 된다. 애노테이션은 **표시일 뿐 실행되는 코드가 아니다** — 누군가 읽어야 의미가 생긴다.

핵심 구분 — **필드는 객체에 딸리고 지역 변수는 호출에 딸린다.** 그리고 **공유 자체가 아니라 바뀌는 공유가 문제다.** `jdbc`는 `final`이고 요청별 상태를 안 쌓아서 공유해도 안전하고, 어제 `lab.seat.taken`은 계속 바뀌어서 다툼이 났다.

**회차 A-3 (앞부분) — 예외 문법 (2026-09-11, 통과)**
`try/catch`와 `throw`/`throws`. JS와의 차이는 **`catch`에 종류를 적는다**는 것이다.

`잡고_조회한다`의 `catch` 타입을 `IllegalStateException`으로 바꿔 A/B를 했다. 밖으로 나오는 예외의 종류가 갈린다 — 안 잡으면 `DuplicateKeyException`, 잡으면 그다음 `SELECT`가 터져 `UncategorizedSQLException`(abort). `catch` 한 단어가 결과를 바꾼다.

**느슨한 단언을 또 만났다.** `잡은_뒤_조회`가 `.isInstanceOf(...)` 없이 `assertThatThrownBy`만 써서 양쪽 다 통과했다. 회차 8과 같은 함정이다. `UncategorizedSQLException` + `hasMessageContaining("current transaction is aborted")`로 조여서 **실제로 재는 테스트**로 바꿨다.

`throws`는 실행되지 않는 선언이고 `throw`는 문장이다. `throws`를 지우고 `Exception`을 던지면 `must be caught or declared to be thrown`으로 컴파일이 막히고, `IllegalStateException`으로 바꾸면 통과한다. **컴파일러가 강제하는 쪽이 체크다** — 사용자가 "언체크"라고 답했던 것을 이 A/B로 뒤집었다.

**회차 A-3 뒷부분 — `long`과 `Long` (2026-09-11~12, 통과)**
TS의 `number`와 `number | null`에 먼저 붙이고, 그 위에 원시 타입과 래퍼 타입 두 용어를 얹었다. 재료는 사용자가 `LabMapper`에 추가한 `maxPartySize()`(`SELECT max(party_size) FROM lab.hold`)다. 빈 테이블에 걸었으니 NULL이 돌아온다.

매퍼 반환 타입과 받는 변수 타입을 바꿔 가며 세 번 돌렸다.

- 매퍼 `long` → `BindingException`. MyBatis(`MapperMethod`)가 값을 넘기기 전에 멈췄다. 예측은 "null이 나온다"였다. `long`에는 null이 들어갈 자리가 없다
- 매퍼 `Long`, 받는 변수 `long` → NPE(`Cannot invoke "java.lang.Long.longValue()"`). 스택에 MyBatis가 없다. 자바가 몰래 끼운 `.longValue()`에서 터졌다. 사용자가 터지는 줄은 맞혔지만 "MyBatis가 터뜨린다"는 이유는 틀렸다
- 둘 다 `Long` → null이 그대로 담긴다

**null은 가만히 있고 터지는 자리만 옮겨 간다.** null이 `long`을 만나는 곳에서 터지고, 만난 자리가 에러 이름을 정한다. TS 직관과 갈리는 곳은 `Long`을 `long`에 넣는 줄을 컴파일러가 막지 않는다는 점이다.

확인 질문 1 — `잡고_조회한다`의 `count(*)`가 NULL을 돌려줄 수 있나. "그럴 것 같다"로 틀렸다. DBeaver에서 빈 테이블에 `count(*)`(0)와 `max`(NULL)를 나란히 돌려 교정했다. **`count`만 행을 세고, 나머지 집계는 값이 없으면 NULL이다.** 증거는 사용자 테스트의 `count()` 도우미에 이미 있었다. `sum`으로 다시 묻자 NULL은 맞혔고, 에러 이름을 NPE라고 적은 것은 `BindingException`으로 바로잡았다.

확인 질문 2 — 에러를 보고 코드를 거꾸로 맞힌다. **이번 회차에서 가장 오래 걸렸다.** NPE 쪽은 매퍼와 변수를 거꾸로 적었다가 손으로 재현한 뒤 맞췄다. `BindingException` 쪽은 "메시지에 받는 쪽 타입이 나와 있다"고 답했다. 받는 변수를 `long`·`Long`으로 바꿔도 메시지가 한 글자도 안 바뀐 두 실행을 대조해서 교정했다. 메시지의 `return type (long)`은 **선언**(`LabMapper.java`)의 타입이다. 사용자가 이 선언을 "호출하는 부분"이라고 불렀다. 선언과 호출이 아직 섞여 있다.

확인 질문 3 — 빈 슬롯의 `sum`이 NULL일 때 어디서 처리하나. 사용자는 SQL에서 0으로 바꾸는 쪽을 골랐고, 잃는 것은 "모르겠다"였다. "0만 보고 '예약 없음'과 '합계 0'을 구별할 수 있나"로 좁히자 자력으로 답했다. SQL에서 0으로 바꾸는 방법은 **NULL의 뜻이 0과 같을 때만 쓴다.**

**마무리에서 지시가 모호했다.** 관찰용 `println` 테스트를 단언으로 바꾸라고만 해서 사용자가 무엇을 쓰라는 건지 되물었다. Jest의 `expect(x).toBeNull()`과 `assertThat(x).isNull()`을 나란히 보여 주자 바로 썼다. 지금 상태는 매퍼 `Long`, 단언 `isNull()`이고 전체 테스트 35개가 통과한다(2026-09-12, Claude가 실행해 확인).

**회차 A-4 — `Long.class` (2026-09-13, 통과)**
세션은 A-3의 약한 자리로 열었다. BindingException 메시지의 `(long)`이 어느 파일의 것인지 묻자 선언이라는 건 맞혔지만 파일은 "XML"이라고 답했다. `resultType="long"` 때문이었다. XML에 `long`이 그대로 있는데 테스트는 초록이라는 지금 상태를 보여 교정했다.

`count(*)`를 `query(String.class)`로 받자 문자열 `"0"`이 돌아왔다. 예측이 맞았다. `fetch`의 `res.json()`과 `res.text()`에 대봤다. `String.class`로 받은 값을 `long`에 넣으면 컴파일이 막힌다는 것도 맞혔지만, 이유는 몰랐다.

**첫 설명이 너무 빽빽했다.** 제네릭 시그니처, `Class<T>`, 런타임 정정, zod를 한꺼번에 얹었다. 확인 질문 1("`String.class`가 쓰인 두 곳")에 "설명을 못하겠다"가 돌아왔다. 사용자가 겪은 두 장면으로 쪼개서 다시 쌓았다. 밑줄은 돌리기 전에, `"0"`은 돌린 뒤에 봤다는 장면이다. 그래도 한 번 더 빗나가서, `SELECT 'hello'`를 `query(Long.class)`로 받는 예측으로 각도를 바꿨다. 밑줄은 없고 실행 중에 에러가 난다는 것을 이유와 함께 맞혔다. 스택 트레이스에서 두 가지를 짚었다. 실행은 `.single()`에서 시작하고, `getLong`이 `Long.class`의 실행 중 쓰임이다.

확인 질문 2 — `Long.class` 없이 받는 변수만 보고 정할 수 있나. 사용자가 자력으로 답했다. "메서드가 다 실행된 후에 변수에 저장되기 때문에, 실행 중인 메서드는 결과가 저장될 변수의 타입을 알 수 없다."

**Claude의 부정확한 설명이 오해를 만들었다.** "자바도 TS와 사정이 비슷하다"(타입이 런타임에 사라진다)고 범위를 넓게 말했다. 실제로 사라지는 건 `<T>` 자리와 받는 쪽 변수이고, 메서드 선언은 남는다. 이 전제 탓에 확인 질문 3("MyBatis는 `long`을 어디서 읽었나")에 다시 "XML의 resultType"이 나왔다. `LabMapper.class.getMethod("maxPartySize").getReturnType()`을 단언하는 실험으로 갈랐다. 첫 판은 두 설명이 모두 초록을 예측해서 가르지 못했다. 매퍼 선언만 `long`으로 바꾼 두 번째 판에서 `expected: java.lang.Long but was: long`이 나왔다. 그 뒤 "`LabMapper.java`에서 읽었다"를 자력으로 답했다. `resultType`은 JdbcClient의 `Long.class`처럼 실행 중에 꺼낼 타입을 지시하는 자리라고 연결했다.

**사용자 첨언 (2026-09-13).** "나는 XML작성에 대한 문법이나 원리를 잘 모른다. 모르는 내용을 계속 나보고 유추하라고 하니 어렵다." `resultType`을 가르친 적 없이 두 번 추론하게 했다. 교습 방식의 결함이다. 앞으로 발밑이 없는 것은 먼저 알려 주고, 그 위에서 묻는다(메모리 `daylink-teaching-protocol`).

정리 상태 — 매퍼는 `Long`이고, `dbValueCheck`는 선언을 읽는 단언(`isEqualTo(Long.class)`)이다. 앞선 실험 줄들은 주석으로 남아 있다. 전체 테스트 36개가 통과한다(2026-09-13, Claude가 실행해 확인).

**회차 C-1 — XML 파일의 뼈대 (2026-09-13, 통과)**
A-4에서 받은 지적대로 방식을 바꿨다. 먼저 설명하고, 그 위에서 물었다. 세션은 A-4의 `Long.class` 두 쓰임으로 열었고 통과했다. 런타임에 읽는 쪽이 JdbcClient라는 이름만 채웠다.

출발점은 XML이 HTML과 문법이 같다는 것이다. 다른 것은 태그를 정하는 쪽뿐이다. HTML은 브라우저가, 매퍼 파일은 MyBatis가 정한다. `LabMapper.xml`을 줄마다 풀었다 — XML 선언, `DOCTYPE`(규칙집), `namespace`(인터페이스 전체 이름), 태그 이름(SQL 종류), `id`(메서드 이름), `#{key}`(`@Param`), `resultType`(`Long.class`와 같은 역할). `insert`·`update`·`delete`는 결과 표 대신 영향 행 수를 돌려준다. 그래서 `resultType`이 없고 반환 타입이 `int`다. MyBatis가 SQL을 `namespace.id` 이름으로 보관한다는 것을 A-3 에러 메시지의 문자열과 회차 9의 `Invalid bound statement`에 이었다.

손으로 — 사용자가 `deleteAllIdem` 짝(선언, `<delete>` 태그, 테스트)을 처음부터 썼다. 선언 `int`, `resultType` 없음, `isEqualTo(2)` 단언까지 맞았다. XML `id`만 `deleteAllItem`으로 오타가 나서 `Invalid bound statement (not found)`를 받았고, 고친 뒤 통과했다.

**설명이 길다는 지적을 받았다.** 오타 하나를 짚는데 맞은 것, 에러, 나란히 놓기까지 길게 풀었다. 사용자 원문 — "오타가 났다는 말을 설명하려다 보니 길게 한 것 같다." 단순한 것은 한 줄로 짚는다(메모리 `daylink-teaching-protocol`).

확인 질문 3/3. 에러 메시지의 이름은 `namespace`와 `id`를 이은 것이다. 빈 테이블에서 `deleteAllIdem()`은 0을 돌려준다. `namespace`를 틀리면 네 메서드 전부 짝을 못 찾는다.

정리 상태 — 전체 테스트 37개가 통과한다(2026-09-13, Claude가 실행해 확인).

**회차 C-2 — `#{key}` (2026-09-13~14, 통과)**
세션은 C-1의 `namespace`·`id` 짝으로 열었다. `id`는 맞았다. `namespace`를 "경로"라고 답해서 인터페이스 전체 이름으로 바로잡았다. XML 파일은 `labmapper/`에 있는데 `namespace`는 `com.daylink.coreapi.lab.LabMapper`라는 것이 근거다.

출발점은 JS 템플릿 리터럴로 SQL을 만들면 뚫린다는 것이다. `${}`는 템플릿 리터럴처럼 글자를 이어 붙인다(`innerHTML`). `#{}`는 `?` 자리와 값을 따로 보낸다(`textContent`). 새 용어는 SQL 인젝션 하나다.

손으로 — `countByKeySafe`(`#{key}`)와 `countByKeyUnsafe`(`'${key}'`)를 나란히 만들었다. 세 행을 넣고 `' OR '1' = '1`을 넘겼다. 예측은 둘 다 3이었고, 실제는 `#{}` 0, `${}` 3이었다. 사용자가 테스트 쓰는 법을 물어서 뼈대를 줬다. 입력 끝에 붙은 따옴표 하나와 빠진 `@Param`은 한 줄씩 짚었다.

확인 질문 2에서 한 번 갈렸다. DB가 따로 받은 두 가지를 묻자 입력을 `'`와 `'1' = '1`로 쪼개 답했다. Node DB 라이브러리의 `db.query(문장, [값])` 모양을 보여 주자, 문장(`... WHERE key = ?`)과 값(입력 전체 한 덩어리)을 맞게 적었다. 확인 질문 3 — 클라이언트가 보내는 멱등 키는 `#{}`로 넣는다. 이유를 "들어온 값을 그대로 넣는다"고 적었는데, 이 말은 `${}`에도 맞는다. 차이는 값으로 넣느냐, 문장 속 글자로 넣느냐다. `src/main/resources/mapper/`에는 `${`가 하나도 없다(2026-09-14 검색으로 확인).

정리 상태 — 전체 테스트 38개가 통과한다(2026-09-14, Claude가 실행해 확인).

**회차 C-3 — SQL을 어디에 두나 (2026-09-15, 통과)**
세션은 C-2의 "DB가 따로 받는 두 가지"로 열었고, "문장과 값"으로 통과했다.

`ADR-0004`와 `ADR-0006`을 먼저 설명하고 물었다. JPA는 Vue 반응성에 대봤다. 필드를 바꾸면 언제 무엇이 나가는지를 프레임워크가 정한다는 점이 같다. JdbcClient와 XML은 CSS-in-JS와 별도 `.css` 파일에 대봤다. XML을 고른 결정적 이유는 SI 현장 사용률(2순위 목적)이다. 대가는 SQL과 트랜잭션 경계가 두 파일로 갈린다는 것이고, `SlotMapper.xml` 7~30줄의 주석이 그 대가를 메우는 규칙이다.

손으로 — XML의 비용을 봤다. `countSmallParty`에 `<`를 그대로 쓰면 스프링 기동이 실패한다고 예측했고, 맞혔다. 실습 테스트 11개가 전부 실패했고, 맨 안쪽 원인은 `SAXParseException; lineNumber: 32; columnNumber: 57`이었다. `&lt;`로 고쳐 통과했다. `Caused by` 사슬을 바깥에서 안쪽으로 읽는 법을 짚었다.

확인 질문 3/3. 1 — JPA를 쓰면 언제 어떤 SQL이 나가는지 안 보인다. 2 — 처음에는 "주석을 상세히 남겨야 한다"고 답했다. 그건 잃은 것을 메우는 비용이라고 좁히자, 잃은 것(트랜잭션 경계와 락을 두 파일에서 따라가야 한다)을 맞게 적었다. 3 — `<` 실수가 `id` 오타보다 안전하다. 호출할 때 터지는 에러는 언제 드러날지 모르고, 눈에 보이게 먼저 실패해야 고칠 기회가 먼저 온다는 이유를 자력으로 적었다.

**기초 C를 마쳤다.** A-4 끝에 방식을 "먼저 알려 주고 묻는다"로 바꿨다. 그 뒤 C-1~C-3 확인 질문 9개 가운데 7개를 첫 시도에 통과했다. 비교하자면 A-4는 세 질문 중 둘(1·3)을 각도를 바꿔 다시 물어야 했다.

정리 상태 — 전체 테스트 38개가 통과한다(2026-09-15, Claude가 실행해 확인). `countSmallParty`를 부르는 테스트는 없다.

**회차 B-1 — 인터페이스 (2026-09-15~17, 통과)**
세션은 C-3의 "잃은 것과 그걸 메우는 규칙"으로 열었고 통과했다.

TS라는 발밑이 있어서 예측부터 받았다. 모양이 같은 `Korean`을 `Greeter` 자리에 대입하면 TS는 통과하고 자바는 컴파일이 막힌다. 예측이 맞았다. 그 위에 용어 둘을 얹었다. **TS는 구조적 타이핑, 자바는 명목적 타이핑이다.** `implements`는 약속이고, 약속을 적으면 컴파일러가 클래스에서 검사한다. 메서드 이름을 `hello`로 바꾸자 에러가 쓰는 곳이 아니라 클래스 줄로 옮겨 갔다. 이것도 예측이 맞았다.

확인 질문 1에서 TS식 사고가 한 번 되살아났다. 프록시가 "XML의 `id`와 같은 이름의 메서드를 갖고 있어야 한다"고 답했다. 방금 본 `Korean`과 같은 함정이다. 필요한 것은 `implements LabMapper` 선언이고, 만든 쪽은 스프링이 아니라 MyBatis다. `labMapper.getClass().getInterfaces()`가 `LabMapper`를 담고 있다는 테스트로 확인했다.

확인 질문 2 — `@Override`와 기본 몸통. 메서드 이름에 오타가 나면 `@Override`가 있을 때는 컴파일이 막히고, 없으면 아무도 안 부르는 메서드가 조용히 생긴다. 뒤쪽은 한 번 좁혀서 맞혔다. 확인 질문 3 — 가짜 매퍼를 만들려면 `implements SlotMapper`를 선언한 클래스가 필요하다. 자력으로 답했다.

실습 파일이 하나 늘었다. `src/test/java/com/daylink/coreapi/lab/InterfaceLab.java`다. 처음 만들 때 파일 이름이 `IntefaceLab`으로 오타가 났고, B-2에서 사용자가 고쳤다. B-2에서 람다 재료로 다시 쓴다.

정리 상태 — 전체 테스트 39개가 통과한다(2026-09-17, Claude가 실행해 확인).

**회차 B-2 — 람다 (2026-09-17~18, 통과)**
세션을 열 때 "어떤 객체가 인터페이스 자리에 들어가려면 무엇이 필요한가"라고 물었더니 질문 자체를 이해하지 못했다. `Greeter g = new Korean();`을 보여 주고 "`Korean` 쪽에 무엇이 적혀 있어야 하나"로 바꾸자 바로 답했다. **질문도 코드로 한다.**

설명은 JS에서 출발했다. JS에서 함수는 그 자체로 값이지만, 자바에는 함수 타입이 없다. 람다는 대입되는 자리의 인터페이스를 구현한 객체가 되고, 그 인터페이스는 채워야 할 메서드가 하나여야 한다. 새 용어는 함수형 인터페이스와 익명 클래스 둘이다.

예측 셋 중 둘을 맞혔다. `Greeter g = name -> ...`를 TS처럼 "컴파일 안 된다"로 예측해 틀렸다. 이유가 "람다식 자체가 인터페이스가 될 수 없다"였는데, 람다는 인터페이스가 되는 게 아니라 그 인터페이스를 구현한 객체가 된다. **자리가 타입을 정한다.** 파라미터 개수가 안 맞으면 컴파일이 막힌다는 예측은 맞혔다. `this`도 맞혔다. 람다는 바깥 `this`(화살표 함수 쪽), 익명 클래스는 자기 `this`(`function(){}` 쪽)다. 실제로 `com.daylink.coreapi.lab.InterfaceLab`과 `...InterfaceLab$1`이 나왔다. `$1`은 그 클래스 안의 첫 번째 이름 없는 클래스라는 뜻이다.

확인 질문 1은 틀렸다. `var g = name -> ...`의 타입이 "반환값으로 정해질 것"이라고 답했다. 실제로는 컴파일이 막힌다 — `cannot infer type for local variable g (lambda expression needs an explicit target-type)`. Claude가 같은 코드를 따로 컴파일해 확인했다. 확인 질문 2는 `default` 메서드를 더해도 람다를 쓸 수 있느냐였고, 채워야 할 메서드가 여전히 하나라는 이유와 함께 맞혔다. 확인 질문 3은 `Greeter` 자리에 올 수 있는 셋(implements한 클래스, 익명 클래스, 람다)이다.

**가짜 답변이 두 번 끼어들었다(2026-09-18).** `var` 줄의 컴파일 에러 메시지 하나와 확인 질문 2의 답변 하나다. 사용자가 둘 다 지적했고 데이터에서 버렸다. 확인 질문 2는 답과 근거를 이미 화면에 적은 뒤라 같은 질문을 다시 낼 수 없어서, 같은 개념을 `default` 메서드로 각도를 바꿔 새로 냈다. 기록 전에 세 답의 작성자를 사용자에게 확인했다. 메모리 `daylink-teaching-protocol`에 대응을 적었다.

정리 상태 — `InterfaceLab.java`에 `lambda()`와 `AnnonymousClass()`가 늘었고, 테스트 `whoIsThis`가 붙었다. 전체 테스트 40개가 통과한다(2026-09-18, Claude가 실행해 확인).

**회차 B-3 — `==`와 `equals` (2026-09-18, 통과)**
세션은 "이 람다의 타입은 무엇이 정하나"를 코드와 함께 물어 열었고, "대입되는 자리"로 통과했다.

설명은 갈림길 하나다. `==`는 원시 타입끼리면 값을 비교하고, 객체끼리면 같은 상자인지를 비교한다. 내용물을 묻는 건 `.equals()`다. JS의 `===`에는 이 구분이 없다.

예측 둘이 갈렸다. `Long` 127과 128을 둘 다 `true`로 예측했는데, 실제로는 127만 `true`다. 자바가 `-128`부터 `127`까지의 상자를 미리 만들어 재사용하기 때문이다. 얻을 것은 캐시 범위가 아니라 **`==`가 작은 값에서 우연히 맞는다**는 사실이다. 문자열에서도 같은 일이 났다. `s1 == s2`를 `false`로 예측했지만 리터럴은 재사용되므로 `true`였다. `new String("a")`만 새 상자다.

확인 질문 2 — 멱등 키를 `==`로 비교하면 리터럴을 쓰는 테스트는 통과하고 헤더에서 읽은 실제 요청에서 틀린다. 맞혔다. 확인 질문 3은 "모르겠다"로 시작했다. `long y == z`로 좁히자 원시 타입은 값을 비교하니 안전하다고 답했다. `y.equals(z)`는 `cannot invoke equals(long) on the primitive type long`으로 막히는 것을 직접 확인했다. A-3의 "원시 타입에는 메서드가 없다"와 같은 자리다.

정리 상태 — 테스트 `compareBox`와 `compareString`이 늘었다. 전체 테스트 42개가 통과한다(2026-09-18, Claude가 실행해 확인).

**기초 레인을 마쳤다.** 2026-09-09에 신설해 2026-09-18에 끝냈다. 재료는 처음부터 끝까지 사용자가 이미 쓴 파일이었고, 새로 배우는 대신 손에 있는 것에 이름을 붙이는 방식을 유지했다.

**답해준 것** — 자바 람다도 화살표 함수처럼 자기 `this`를 만들지 않는다. XML은 법이 아니라 선택이다(`@Select` 애노테이션도 된다). 더 큰 갈림길은 JPA·Hibernate를 쓸지인데 `ADR-0004`가 명시적 SQL을 골랐고, 이유는 동시성 방어를 손으로 짜야 해서다.
