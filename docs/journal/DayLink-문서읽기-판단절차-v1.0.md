# DayLink 문서 읽기·판단 절차 v1.0

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-08-25 |
| 목적 | 설계 질문 하나를 문서에서 답으로 바꾸는 **반복 가능한 절차**를 고정한다 |
| 범위 | 명세 작성 단계에서 도출했으나 M1~M6 전 구간에 적용된다 |

---

## 0. 이 문서가 채우는 빈칸

기존 문서는 **무엇을 언제 하는가**까지만 정해져 있다.

| 문서 | 정한 것 | 정하지 않은 것 |
|---|---|---|
| 커리큘럼 v2.3 §3·§5 | 기술 학습 순서, 마일스톤 6개 | 문서를 어떻게 읽는가 |
| ALTER 운영가이드 §1·§2 | 역할 투입 시점, 보호 장치 3개 | 판단을 어떻게 만드는가 |
| `design-checklist.md` 작업 절차 | 4단계(질문 → 한국어 답 → 스펙 → 검수) | **2단계의 답을 어디서 끌어오는가** |

빠진 것은 **2단계의 내부**다. "한국어로 답을 적는다"까지는 있는데, 그 답의 재료를 어느 문서 어느 절에서 가져오는지가 없다. 이 문서가 그 자리를 채운다.

---

## 1. 기반 읽기 — 딱 한 번, 통독

**전체 PRD를 읽지 않는다.** 통독할 가치가 있는 것은 다음 두 절뿐이다.

| 대상 | 크기 | 이유 |
|---|---:|---|
| `00 §6` 공통 업무 규칙 | 약 3.4 KB | 예약 단위, 금액 공식, 취소 정책 템플릿. 나머지 문서가 전부 여기를 참조한다 |
| `00 §7` 상태 모델 | (위에 포함) | 상품·재고확보·예약·환불·출석 다섯 개 상태도. **설계 질문의 절반이 여기서 답이 나온다** |
| `00 §8` Core API 책임 | 약 0.6 KB | 여덟 책임. "이건 서버 일인가 클라이언트 일인가"의 판정 기준 |

합쳐서 **4 KB, 20분 남짓**이다. PRD 5종 전체는 124 KB이고, 나머지 120 KB는 **통독 대상이 아니라 조회 대상**이다.

기반 읽기의 목표는 암기가 아니다. "아, 그 얘기는 00 §7 어딘가에 있었다"는 감각 하나만 남으면 된다.

## 2. 라우팅 — 어느 문서를 여는가

질문을 받으면 먼저 좌표를 찍는다.

| 질문의 성격 | 여는 곳 |
|---|---|
| 이 개념의 정의·상태·공식은? | `00 §6`·`§7` |
| 이 서버 책임이 누구 것인가? | `00 §8` |
| 화면이 무엇을 요구하는가? (고객) | `01` |
| 화면이 무엇을 요구하는가? (파트너·현장·플랫폼) | `02` |
| 여러 화면을 가로지르는 흐름이 끊기는가? | `05` |
| 서버가 무엇을 강제해야 하는가? | `06 §7`(공통 규약) `§8`(동시성) `§11`(오프라인) |
| 무엇을 통과해야 완료인가? | `01 §10` / `02 §12` / `06 §13` |
| 이미 결정된 사항인가? | `docs/adr/` |
| 기계가 읽는 형태는? | `api-spec/openapi.yaml` · `errors.md` |

**ID 접두사가 곧 주소다.**

```
B2C-AC-nn   → 01 §10
ADM-AC-nn   → 02 §12
CORE-AC-nn  → 06 §13
```

체크리스트는 항목마다 `(06 §8.3)` 같은 조항을 이미 달아 놓았다. 달려 있으면 그걸 그대로 열면 된다. 라우팅 표는 조항이 안 달린 항목용이다.

### 분량 감각

한 항목이 요구하는 분량은 보통 **1~2곳, 3 KB 미만**이다. 실측 예: `GET /holds/{holdId}` 6항목 전체가 `00 §7.2`(290 B) + `06 §7`(1,009 B) + `Hold`·`Quote` 스키마(1,761 B) = **3.1 KB**.

**세 곳을 넘겨 열고 있다면 질문을 잘못 해석한 것이다.** 그때는 더 읽지 말고 멈춘다.

## 3. 질문 분류 — 이게 가장 중요하다

문서를 열기 **전에** 질문이 둘 중 무엇인지 판정한다. 이걸 틀리면 시간이 통째로 날아간다.

### 조회형 — 답이 문서에 문장으로 있다

찾으면 끝이다. 고민할 것이 없다.

- 신호: 체크리스트가 조항 번호를 괄호로 달아 놓았다
- 예: "정원 축소 한계를 어떻게 계산하나 (06 §8.3)" → `06 §8.3`에 "확정 예약 인원 + 활성 임시 확보 인원"이라고 그대로 쓰여 있다
- **실패 양상**: 조회형인데 머리로 풀려고 한다. 답이 안 나오는 게 당연하다 — 안 열어봤으니까

### 판단형 — 문서는 제약만 주고 답은 없다

내가 정하고 근거를 남긴다. 찾으면 안 된다. 없으니까.

- 신호: "왜?", "의미가 있는가", "무엇을 고르든", "정답이 하나는 아니다"
- 예: "`DELETE`가 맞는가, `POST /holds/{id}/release`가 맞는가" — 체크리스트가 직접 *"정답이 하나는 아니다. 무엇을 고르든 이유를 적는 것이 이 항목의 목적"*이라고 명시한다
- **실패 양상**: 판단형인데 정답을 찾아 문서를 헤맨다. 영원히 안 나온다

### 혼합형 — 제약은 조회, 결론은 판단

대부분이 여기다. 제약을 먼저 조회로 확정한 뒤, 남은 자유도 안에서 판단한다.

예: "만료된 hold에 무엇을 주는가"
→ 조회 부분: `00 §7.2`가 `EXPIRED`를 **상태 전이**로 정의했다(삭제가 아니다)
→ 판단 부분: 그렇다면 404인가 200인가. 문서는 여기까지 안 정했다

## 4. 판단 루프 5단계

항목 하나마다 이 다섯을 돈다. 순서를 바꾸지 않는다.

### ① 분류
조회형 / 판단형 / 혼합형 중 무엇인지 한 단어로 적는다.

### ② 사실 수집 — 해석 금지
해당 조항을 열어 **인용과 조항 번호만** 적는다. 이 단계에서 결론을 내지 않는다.

```
사실: 00 §7.2 — "ACTIVE → PAYMENT_PENDING → CONSUMED / ├─ EXPIRED / └─ RELEASED"
사실: 00 §7.2 — "고객 화면의 타이머는 안내 수단이며 최종 권위가 아니다"
사실: openapi.yaml 263행 — status enum에 EXPIRED 포함
```

사실과 해석을 섞는 것이 가장 흔한 오염이다. 나중에 판단이 틀렸을 때 **어디서 틀렸는지 되짚을 수 있는 유일한 장치**가 이 분리다.

### ③ 판단 — 결론 · 근거 · 버린 대안

```
결론: 200 + status: EXPIRED
근거: 00 §7.2가 만료를 삭제가 아니라 상태 전이로 정의했다
버린 대안: 404. 버린 이유 — 만료와 "애초에 없음"이 구분되지 않아
          네 프론트가 각자 다르게 처리하게 된다
```

**버린 대안을 적는 것이 핵심이다.** 이유는 셋이다. 판단형 항목은 이걸 안 적으면 근거가 없는 것과 같고, 나중에 뒤집을 때 무엇을 재검토할지 알 수 있으며, 이 형식 그대로 ADR로 승격된다(`docs/adr/_template.md`).

### ④ 반례 한 줄 — "틀렸다면 무엇이 깨지는가"

`06 §12`가 보완책으로 규정한 기법을 항목 단위로 당겨 쓰는 것이다. 원문은 이렇다.

> **책임별 반례 작성** — "클라이언트가 판단하면 깨지는 시나리오"를 문장으로 쓴다. **쓰지 못하면 그 책임을 이해하지 못한 것이다.**

반례가 안 써지면 ③으로 돌아간다. 이것이 자가 채점 장치다.

### ⑤ 파급 확인 — 한 곳만 본다

이 판단이 다른 문서와 충돌하는가. 시간을 많이 쓰지 않는다. **딱 한 곳**만 대조한다.

- 서버 판단이면 → 그 요구를 낸 화면 문서(`01` 또는 `02`)
- 화면 판단이면 → `06`

실제 사례: `06 §8.3`은 정원 축소 하한을 "확정 예약 + 활성 hold"로, `02 §6 ADM-PTN-03`은 "확정 예약 수"로 쓴다. **한 문서만 봤으면 못 잡는다.**

## 5. 막혔을 때 — 물어봐도 되는 것과 아닌 것

막힘을 세 종류로 나눈다. 대응이 완전히 다르다.

| 막힘 | 예 | 물어봐도 되는가 |
|---|---|:---:|
| **용어를 모른다** | "`quote`가 뭔가" | ✅ 된다 |
| **문법·도구를 모른다** | "OpenAPI에서 응답을 어떻게 쓰나" | ✅ 된다 |
| **판단이 안 선다** | "404가 맞나 200이 맞나" | ❌ 안 된다 |

앞의 둘은 **조회 비용**이다. 혼자 헤매도 배우는 게 없다. `design-checklist.md`가 직접 *"문법이 맞는 것과 설계가 맞는 것은 다르다"*고 구분해 두었다.

세 번째만 학습 대상이다. 이때 하는 것:

1. 대안 **두 개**를 나열한다
2. 각 대안을 골랐을 때 **무엇을 잃는지** 한 줄씩 적는다
3. 그래도 못 고르겠으면 **그 두 줄을 들고** 온다

"모르겠다"로 오면 채점할 것이 없다. "A와 B 중 A로 기울었는데 B의 손해를 모르겠다"로 오면 그 지점만 짚어줄 수 있다. ALTER 보호 장치 1번(**먼저 답하고 나서 묻기**)이 요구하는 것이 이것이다.

## 6. 기록 형식

`design-checklist.md`의 각 체크박스 아래에 그대로 적는다. 별도 파일을 만들지 않는다.

```markdown
- [x] 만료된 hold를 조회하면 무엇을 주는가
  - 분류: 혼합형
  - 사실: 00 §7.2 — EXPIRED는 상태 전이다(삭제 아님)
  - 사실: openapi.yaml 263행 — status enum에 EXPIRED 존재
  - 결론: 200 + status: EXPIRED
  - 버린 대안: 404 — 만료와 부존재가 구분되지 않는다
  - 반례: 404를 주면 프론트가 "만료"와 "잘못된 링크"를 같은 화면으로 처리한다
```

여섯 줄이면 충분하다. 길게 쓰는 것이 목적이 아니다.

## 7. 지금 적용 — `GET /holds/{holdId}`

| 단계 | 할 일 |
|---|---|
| 기반 읽기 | `00 §7.2` (290 B). §6·§8은 이 엔드포인트에 필요 없다 |
| 라우팅 | `00 §7.2`, `06 §7`, `openapi.yaml` `Hold`·`Quote` 스키마 |
| 분류 | 6항목 중 ③은 완료됨(체크리스트 20행 예시). ⑤가 혼합형 핵심 |
| 루프 | ⑤ → ⑥ 순으로. ⑥은 ⑤에 종속되므로 순서를 바꾸지 않는다 |
| 검수 | ⑤·⑥ 두 개만 먼저 가져와도 된다 |

## 8. 이 절차를 언제 고치는가

- 조회형/판단형 분류가 자주 틀리면 → §3의 신호 목록을 보강한다
- 라우팅에서 문서를 세 곳 넘게 열게 되는 항목이 반복되면 → §2 표에 행을 추가한다
- ⑤ 파급 확인에서 문서 불일치가 또 나오면 → 발견 즉시 PRD를 고치고 ADR에 남긴다

> **미해결**: `ALTER 운영가이드 v1.0`은 커리큘럼 v1.0 시점 문서라 현재 수치(화면 168 구현벌, 완료 조건 59개, Core API 37%)를 반영하지 못한다. 갱신 시 이 문서를 §2 단계별 적용 지도에 연결할 것.
