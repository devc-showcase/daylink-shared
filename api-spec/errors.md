# 오류 코드

모든 오류 응답은 `code` · `messageKey` · `traceId` · `retryable` 넷을 포함한다(06 §7).

`code`는 **클라이언트가 분기하는 근거**이므로 한 번 정하면 바꾸지 않는다. 바꿔야 하면 새 코드를 추가하고 옛 코드를 한동안 함께 내려준다.

## 왜 서버가 완성된 문장을 주지 않나

`messageKey`만 주고 문구는 클라이언트가 만든다. 네 프론트 구현이 각자의 문구 체계를 갖고, 같은 오류라도 화면 맥락에 따라 다르게 표현해야 하기 때문이다. 예를 들어 `SEAT_UNAVAILABLE`은 검색 목록에서는 "매진", 결제 직전에는 "방금 마감되었습니다. 다른 회차를 선택해 주세요"가 된다.

## `retryable` 판단 기준

같은 요청을 **그대로** 다시 보내도 되는가를 뜻한다.

- `true` — 일시적 경합·타임아웃. 클라이언트가 재시도해도 안전하다
- `false` — 입력을 바꾸거나 다른 흐름으로 가야 한다

멱등 키가 있으므로 `retryable: true`인 쓰기 요청을 재전송해도 중복이 생기지 않는다.

## 직접 채울 코드

아래는 요구사항이 존재하지만 코드 이름과 HTTP 상태가 아직 정해지지 않았다.

### 결제·예약

- 결제 실패 (거절·인증 실패·시간 초과) — `06 §5`의 `PAYMENT_FAILED` 전이와 어떻게 연결할 것인가
- **결과 불명** — `B2C-AC-06`이 "재결제 대신 서버 상태를 조회한다"를 요구한다. 이건 오류인가 정상 응답인가?

### 환불

- 누적 환불액이 실결제액 초과 (`CORE-AC-19`)
- 외부 처리 상태 확인 전 재시도 차단 (`ADM-AC-12`)

### 회차·정원

- 확정 예약보다 작게 정원 축소 (`CORE-AC-13`)

| 권한 회수된 행위자 | ? | ? |

**첫 번째 행이 함정이다.** 재전송은 오류인가 성공인가? `06 §11.2`는 "저장된 결과 반환"이라고 했다. 그렇다면 오류 코드가 아니라 200이어야 한다. 나머지 다섯 개도 같은 질문을 던져야 한다 — **어떤 것이 오류이고 어떤 것이 정상 결과인가.**
