# API 명세 설계 체크리스트

`openapi.yaml`의 나머지를 채울 때 각 엔드포인트가 답해야 하는 질문들이다.

---

## 작업 절차

엔드포인트 하나마다 이 네 단계를 돈다.

### 1단계 — 질문 읽기

아래 "엔드포인트별 판단 항목"에서 해당 절을 읽는다. 아직 스펙을 쓰지 않는다.

### 2단계 — 답을 한국어 문장으로 먼저 적는다

각 체크박스 아래에 답을 **문장으로** 적는다. YAML이 아니라 한국어다. 항목당 2~4줄이면 충분하다.

```markdown
- [x] 권한 밖 리소스에 403을 주는가 404를 주는가
  → 404를 준다. 403을 주면 "그 예약이 존재하긴 한다"는 사실이 새어 나간다.
    CORE-AC-10이 "존재 여부를 노출하지 않고 거부한다"고 했으므로 404가 맞다.
```

**이 단계를 건너뛰면 안 된다.** 답이 안 나오는 항목이 곧 아직 이해하지 못한 지점이고, 그걸 발견하는 것이 이 작업의 목적이다. 스펙부터 쓰면 문법은 맞는데 왜 그런지 모르는 상태가 된다.

### 3단계 — 스펙 작성

2단계의 답을 근거로 `openapi.yaml`에 쓴다. `POST /holds`를 옆에 두고 구조를 참고하되 **판단은 베끼지 않는다.** 엔드포인트마다 상황이 다르다.

새 오류 코드가 필요하면 `errors.md`의 "직접 채울 코드"에 추가한다.

### 4단계 — 검수 요청

`design-checklist.md`(2단계 답)와 `openapi.yaml`(3단계 스펙)을 **함께** 가져간다. 스펙만 보여주면 판단 근거를 검수할 수 없다.

---

## 작업 순서

쉬운 것부터 간다. 앞의 둘은 OpenAPI 문법에 손을 익히는 구간이고, 뒤로 갈수록 판단이 어려워진다.


| 순서 | 엔드포인트                         | 난이도      | 핵심                             |
| ---- | ---------------------------------- | ----------- | -------------------------------- |
| 1    | `GET /holds/{holdId}`              | 쉬움        | 조회 기본형.`Hold` 스키마 재사용 |
| 2    | `DELETE /holds/{holdId}`           | 쉬움        | 상태 전이 하나(`RELEASED`)       |
| 3    | `GET /bookings/{bookingId}`        | 보통        | **상태 4개 분리**, 스냅숏 반환   |
| 4    | `GET /bookings/{id}/cancel-quote`  | 보통        | 기준 시각을 왜 응답에 넣나       |
| 5    | `POST /bookings`                   | 어려움      | 결제.**결과 불명 상태**          |
| 6    | `POST /bookings/{id}/cancellation` | 어려움      | 취소와 환불의 분리               |
| 7    | `PATCH /sessions/{id}`             | 어려움      | 정원 축소 한계                   |
| 8    | `POST /check-ins`                  | 가장 어려움 | 여섯 분기의 오류/정상 구분       |

**1번을 끝내면 바로 가져온다.** 8개를 다 쓰고 오면 같은 실수가 여덟 번 굳어 있다. 첫 개를 검수받고 방향을 잡은 뒤 2~3번을 묶어서, 그다음부터는 하나씩 가져오는 편이 낫다.

### 문법 검증

스펙이 문법적으로 맞는지는 이것으로 확인할 수 있다.

```bash
npx @redocly/cli@latest lint api-spec/openapi.yaml
```

문법이 맞는 것과 설계가 맞는 것은 다르다. 검증기는 전자만 본다.

## 엔드포인트별 판단 항목

각 엔드포인트는 **"공통" 항목 + 아래 해당 절** 둘 다에 답한다.

### `GET /holds/{holdId}` — 확보 상태 조회 ← 여기부터

- [ ]  **이 엔드포인트가 왜 필요한가.** 클라이언트가 확보 생성 응답의 `expiresAt`으로 카운트다운만 하면 안 되는 이유는?
  - 힌트: `00 §7.2`가 "클라이언트 화면의 타이머는 안내 수단이며 최종 권위가 아니다"라고 한 이유를 뒤집어 생각한다
  - **답변**: 이미 누군가 확보 했는지를 체크할 필요가 있다. expiresAt은 확보상태를 언제 파기한 했는지에 대한 결과일뿐이지 지금 확보할 수 있다는 뜻이 아니다.
- [ ]  **남의 hold를 조회하면 403인가 404인가.** `CORE-AC-10`을 근거로 답한다
  - **답변**:  이미 확보된 남의 상태 이기 때문에 403입니다.
- [ ]  **만료된 hold를 조회하면 무엇을 주는가.** 404인가, 200에 `status: EXPIRED`인가
  - 이게 이 엔드포인트의 진짜 판단이다. `00 §7.2`가 만료를 *삭제*가 아니라 *상태 전이*로 정의했다는 점이 단서다
  - 둘 중 하나를 고르면 네 프론트가 만료를 같은 방식으로 다루게 된다. 다른 하나를 고르면 각자 추측하게 된다
  - **답변**: 200에 `status: EXPIRED`입니다. 만료되어 상태가 변경된 것이기 때문에 찾을수 없는 것이 아닌 만료 된것으로 봐야하기 때문입니다.
- [ ]  **만료된 hold에도** `quote`**를 함께 주는가.** 이미 무효가 된 가격을 보여주는 것이 의미가 있는가
  - 만료된 당시의 가격을 보여주는 것은 의미가 있습니다. 가격이 변동여부 정보를 함께 준다는 측면이 있습니다.

### `DELETE /holds/{holdId}` — 확보 해제

- [ ]  `DELETE`**가 맞는가,** `POST /holds/{id}/release`**가 맞는가.**
  - `00 §7.2`는 `RELEASED`를 상태 전이로 정의한다. 리소스가 사라지는 것이 아니다. 그렇다면 `DELETE`라는 동사가 정확한가?
  - 정답이 하나는 아니다. 무엇을 고르든 **이유를 적는 것**이 이 항목의 목적이다
  - **답변**: 이 경우 POST가 맞다고 생각함.
- [ ]  **이미 해제된 hold를 다시 해제하면?** 오류인가 성공인가
  - 멱등의 정의를 여기에 적용해 본다
  - **답변**: 성공
- [ ]  **이미** `CONSUMED`**된(결제까지 끝난) hold를 해제 요청하면?** 위 항목과 답이 같은가 다른가
  - **답변**: 답이 같다.
- [ ]  **응답 본문이 있는가, 204인가.** 있다면 무엇을 담는가
  - **답변**: 해제 성공이 어떻게 이뤄졌는지 본문을 담을 필요가 있다고 본다. 성공했지만 이미 해제된 hold를 다시 해제하는 요청 케이스가 있다.

### `POST /bookings` — 결제 제출

- [ ]  결제 성공과 예약 확정을 **한 응답으로** 줄 것인가, 나눌 것인가?
  - 05 §5.4가 "클라이언트 성공 화면만으로 예약을 확정하지 않는다"고 했다. 그렇다면 응답에 무엇이 담겨야 하나?
  - **답변**: 응답에는 확보 중이라는 내용이 담겨야 할듯
- [ ]  `B2C-AC-06`의 "결과 불명" 상태를 어떻게 표현하나. 202? 200에 상태 필드?
  - **답변**: 200에 상태필드
- [ ]  hold가 만료된 상태로 결제를 시도하면 어떤 코드인가?
  - **답변**: HOLD_EXPIREDHOLD

### `GET /bookings/{id}` — 예약 상세

- [ ]  예약·결제·환불·출석 **네 상태를 각각 별도 필드로** 낸다(CORE-AC-09). 하나로 합치고 싶은 유혹이 왜 위험한가?
  - **답변**: 잘 모르겠음.
- [ ]  예약 스냅숏(가격·정책·상품명)과 현재 상품 정보 중 무엇을 반환하나 (CORE-AC-25)
  **답변**: 예약 스냅숏

### `GET /bookings/{id}/cancel-quote` — 취소 예상액

- [ ]  계산 **기준 시각**을 응답에 넣는가. 왜 필요한가? (01 §5.5)

- [ ]  이 응답을 받고 실제 취소하기까지 시간이 지나 정책 구간이 바뀌면?
  - **답변**: 잘 모르겠음

### `POST /bookings/{id}/cancellation` — 취소 실행

- [ ]  취소와 환불은 다른 상태다(00 §7.3·7.4). 응답에 둘을 어떻게 담나?
  - **답변**: 잘 모르겠음.
- [ ]  재전송이 중복 취소를 만들지 않으려면 (CORE-AC-08)
  - **답변**: 잘 모르겠음.

## 명세 전체에 대한 판단

- [ ]  **OpenAPI 3.1을 쓸 것인가 3.0으로 낮출 것인가.** 3.1은 JSON Schema와 정렬되지만 생성기 지원을 확인해야 한다. 착수 시 npm·Maven 생성기로 실제 생성해 보고 정한다
- [ ]  목록 페이지네이션을 커서로 할 것인가 오프셋으로 할 것인가. 하나로 통일한다(06 §7)
- [ ]  시간 필드는 전부 UTC ISO 8601인가 (06 §7)
- [ ]  B2C와 Admin 경로를 한 파일에 둘 것인가 나눌 것인가
- [ ]  생성된 타입을 npm과 Maven 양쪽에 어떻게 배포할 것인가 (ADR-0005)
