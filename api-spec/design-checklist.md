# API 명세 설계 체크리스트

`openapi.yaml`의 나머지를 채울 때 각 엔드포인트가 답해야 하는 질문들이다.

---

## 작업 절차

엔드포인트 하나마다 이 네 단계를 돈다.

### 1단계 — 질문 읽기

아래 "엔드포인트별 판단 항목"에서 해당 절을 읽는다. 아직 스펙을 쓰지 않는다.

### 2단계 — 답을 한국어 문장으로 먼저 적는다

각 체크박스 아래에 답을 **문장으로** 적는다. YAML이 아니라 한국어다. 항목당 2~4줄이면 충분하다.

```markdown
- [x] 권한 밖 리소스에 403을 주는가 404를 주는가
  → 404를 준다. 403을 주면 "그 예약이 존재하긴 한다"는 사실이 새어 나간다.
    CORE-AC-10이 "존재 여부를 노출하지 않고 거부한다"고 했으므로 404가 맞다.
```

**이 단계를 건너뛰면 안 된다.** 답이 안 나오는 항목이 곧 아직 이해하지 못한 지점이고, 그걸 발견하는 것이 이 작업의 목적이다. 스펙부터 쓰면 문법은 맞는데 왜 그런지 모르는 상태가 된다.

### 3단계 — 스펙 작성

2단계의 답을 근거로 `openapi.yaml`에 쓴다. `POST /holds`를 옆에 두고 구조를 참고하되 **판단은 베끼지 않는다.** 엔드포인트마다 상황이 다르다.

새 오류 코드가 필요하면 `errors.md`의 "직접 채울 코드"에 추가한다.

### 4단계 — 검수 요청

`design-checklist.md`(2단계 답)와 `openapi.yaml`(3단계 스펙)을 **함께** 가져간다. 스펙만 보여주면 판단 근거를 검수할 수 없다.

---

## 작업 순서

쉬운 것부터 간다. 앞의 둘은 OpenAPI 문법에 손을 익히는 구간이고, 뒤로 갈수록 판단이 어려워진다.


| 순서 | 엔드포인트                         | 난이도      | 핵심                             |
| ---- | ---------------------------------- | ----------- | -------------------------------- |
| 1    | `GET /holds/{holdId}`              | 쉬움        | 조회 기본형.`Hold` 스키마 재사용 |
| 2    | `POST /holds/{id}/release`         | 쉬움        | 상태 전이 하나(`RELEASED`)       |
| 3    | `GET /bookings/{bookingId}`        | 보통        | **상태 4개 분리**, 스냅숏 반환   |
| 4    | `GET /bookings/{id}/cancel-quote`  | 보통        | 기준 시각을 왜 응답에 넣나       |
| 5    | `POST /bookings`                   | 어려움      | 결제.**결과 불명 상태**          |
| 6    | `POST /bookings/{id}/cancellation` | 어려움      | 취소와 환불의 분리               |
| 7    | `PATCH /slots/{id}`             | 어려움      | 정원 축소 한계                   |
| 8    | `POST /check-ins`                  | 가장 어려움 | 일곱 분기의 오류/정상 구분       |
| 9    | `POST /slots/{id}/reschedule` 2단계 | 어려움      | 확인 절차를 계약에 드러내기      |

**1번을 끝내면 바로 가져온다.** 8개를 다 쓰고 오면 같은 실수가 여덟 번 굳어 있다. 첫 개를 검수받고 방향을 잡은 뒤 2~3번을 묶어서, 그다음부터는 하나씩 가져오는 편이 낫다.

### 문법 검증

스펙이 문법적으로 맞는지는 이것으로 확인할 수 있다.

```bash
npx @redocly/cli@latest lint api-spec/openapi.yaml
```

문법이 맞는 것과 설계가 맞는 것은 다르다. 검증기는 전자만 본다.

## 모든 쓰기 엔드포인트에 공통

- [x] 멱등 키를 어디서 받는가 — 헤더인가 본문인가. 왜?
  → **체크인만 본문(`clientEventId`), 나머지는 전부 `Idempotency-Key` 헤더**다(06 §7·§8.2).
    두 키의 생명주기가 다르다. 헤더 키는 *요청*을 보내는 순간 만들어져 그 요청에 붙고,
    `clientEventId`는 *사건*이 벌어진 순간 만들어져 사건에 붙는다. 오프라인 체크인은
    기기에 저장됐다가 나중에 전송되므로(02 §7 ADM-DSK-03) 그 사이 앱이 재시작되면
    헤더 키는 새로 생긴다. 사건 단위 키라야 CORE-AC-15가 성립한다.

- [x] 같은 키로 재전송하면 **몇 번 코드**를 주는가. 201인가 200인가. 근거는?
  → **최초와 같은 코드를 준다.** 생성 계열은 201, 해제·체크인 재전송은 200이다.
    낮추지 않는 이유는 클라이언트가 최초와 재전송을 구분해서 할 일이 없기 때문이다.
    구분해 주면 분기가 하나 늘고, 그 분기를 빠뜨린 구현에서 화면이 갈린다(06 §8.2).
  → 버린 대안: 재전송에 200을 주고 최초에 201. 클라이언트가 "이미 처리됨"을 알 수 있지만,
    그 정보로 무엇을 할지 말할 수 없어서 버렸다.

- [x] 이 요청이 실패했을 때 클라이언트가 **재시도해도 되는가**. `retryable` 값의 근거는?
  → `errors.md` 기준 그대로다. **일시적 경합·타임아웃이면 true, 입력을 바꿔야 하면 false.**
    지금 true인 것은 `IDEMPOTENCY_IN_PROGRESS`와 `REFUND_IN_PROGRESS` 둘뿐이다.
    둘 다 시간이 지나면 해소되고 클라이언트가 바꿀 입력이 없다.
    `HOLD_EXPIRED`가 false인 이유는 같은 요청을 다시 보내도 영원히 같은 결과이기 때문이다.
    새 확보를 만들어야 하므로 흐름을 바꿔야 한다.

- [x] 응답이 유실됐을 때 클라이언트가 결과를 확인할 **조회 경로**가 있는가?
  → 쓰기마다 짝이 되는 GET을 뒀다.
    `POST /holds` → `GET /holds/{holdId}` /
    `POST /bookings` → `GET /bookings/{bookingId}` /
    `POST /holds/{id}/release` → `GET /holds/{holdId}` /
    `POST /bookings/{id}/cancellation` → `GET /bookings/{bookingId}` /
    `PATCH /slots/{id}` → 응답이 최신 `Slot`이므로 재조회로 확인.
  → 체크인만 전용 조회가 없다. 대신 같은 `clientEventId` 재전송이 저장된 결과를
    돌려주므로(06 §11.2 첫 행) 재전송 자체가 조회 역할을 한다.
  → 이 짝이 없으면 클라이언트는 재전송밖에 못 하고, 멱등 키가 없는 경로에서는
    중복이 생긴다. B2C-AC-06이 요구하는 "재결제 대신 서버 상태를 조회한다"가 이것이다.

## 모든 조회 엔드포인트에 공통

- [x] 권한 밖 리소스에 403을 주는가 404를 주는가. **존재 여부가 노출되는가?** (CORE-AC-10)
  → **B2C 리소스는 404, Admin 리소스는 403**으로 갈랐다.
    B2C에서 403은 "그건 있는데 네 것이 아니다"를 말해 준다. 식별자를 바꿔가며 찔러보면
    어떤 예약이 살아 있는지 알아낼 수 있다. CORE-AC-10이 이를 막는다.
    Admin에서는 행위자가 이미 시스템 안에 있고 회차·예약의 존재 자체는 비밀이 아니다.
    범위 밖이라는 사실을 알려 주는 편이 운영에 낫다(CORE-AC-11, `FORBIDDEN_SCOPE`).
  → 404를 줄 때는 **응답 본문도 같아야 한다.** 오류 코드나 응답 시간으로 둘을 가를 수
    있으면 감춘 의미가 없다.

- [x] 목록이면 정렬 기준이 안정적인가. 같은 조건으로 두 번 부르면 순서가 같은가?
  → **지금 작성한 여덟 개에는 목록이 없다. 해당 없음.**
    다만 `/ops/inquiries`·`/ops/refunds` 같은 Admin 대기열을 쓸 때 다시 온다.
    그때 정렬 키가 중복되면(생성 시각만으로 정렬 등) 페이지 경계에서 같은 행이 두 번
    나오거나 빠진다. 06 §7이 "안정적인 정렬 기준"을 요구하는 이유다.

- [x] 개인정보 필드가 기본 마스킹되는가 (06 §7)
  → **지금 작성한 응답에는 개인정보 필드가 없다.** `Hold`·`Booking`·`Slot` 모두
    식별자·금액·상태·시각뿐이고 이름·연락처가 없다.
  → 06 §7은 "**목록** 응답은 기본 마스킹"만 규정한다. 단건은 규칙이 침묵한다.
    본인 예약을 본인이 조회하는 B2C 단건에는 마스킹이 필요 없다고 판단했다.
    현장 스냅숏의 "표시용 최소 이름"(06 §11.1)처럼 이름이 필요한 자리는
    Admin 엔드포인트를 쓸 때 다시 판단한다.

## 엔드포인트별 판단 항목

각 엔드포인트는 **"공통" 항목 + 아래 해당 절** 둘 다에 답한다.

### `GET /holds/{holdId}` — 확보 상태 조회

- [x] **이 엔드포인트가 왜 필요한가.**
  → 클라이언트 타이머는 브라우저 시계로 도는 추정치다. 00 §7.2가 "10분 만료는 서버
    시간을 기준으로 판단한다. 고객 화면의 타이머는 안내 수단이며 최종 권위가 아니다"라고
    못박았다. 탭을 절전에 두거나 기기 시계가 틀리면 화면과 서버 판정이 어긋난다.
  → 타이머가 못 잡는 것이 하나 더 있다. 확보가 `ACTIVE`를 벗어나는 길은 만료 말고도
    있다 — 다른 탭에서 해제(`RELEASED`)했거나 결제로 넘어갔을(`PAYMENT_PENDING` →
    `CONSUMED`) 수 있다. 타이머는 이 전이를 전혀 모른다.
  → 결제 응답이 유실됐을 때의 복구 경로이기도 하다.
  ※ 처음 적은 답의 "이미 누군가 확보했는지 체크"는 이 엔드포인트가 하는 일이 아니다.
     여기는 `holdId`로 **내 확보 하나**를 본다. 좌석이 남았는지는 회차 조회다.

- [x] **남의 hold를 조회하면 403인가 404인가.**
  → **404.** 403은 "그건 있는데 네 것이 아니다"라고 말해 존재를 확인해 준다.
    CORE-AC-10이 "존재 여부를 노출하지 않고 거부한다"를 요구하므로 없는 것과 같게 답한다.
    `errors.md`도 `NOT_FOUND`에 "존재 여부를 감춰야 할 때도 이 코드를 쓴다"고 적어 두었다.
  → 그래서 이 엔드포인트의 응답 목록에 403이 아예 없다. 누락이 아니라 결정이다.
  ※ 처음 적은 답은 403이었다. 스펙을 쓰는 동안 스스로 404로 고쳤다.

- [x] **만료된 hold를 조회하면 무엇을 주는가.**
  → **200 + `status: EXPIRED`.** 00 §7.2가 만료를 삭제가 아니라 `ACTIVE → EXPIRED`
    상태 전이로 정의했다. 리소스는 그대로 있다.
  → 404를 주면 클라이언트가 "만료됐다"와 "잘못된 링크다"를 구분하지 못한다.
    B2C-AC-07이 "만료되면 결제를 막고 회차 재선택을 안내한다"를 요구하는데,
    만료인지 모르면 어디로 보낼지 정할 수 없다.

- [x] **만료된 hold에도 `quote`를 함께 주는가.**
  → **준다.** 스냅숏은 "그때 이 금액으로 잡았다"는 지난 사실이고, 만료가 그 사실을
    지우지 않는다. 화면이 "이 가격으로 잡아둔 자리가 만료됐습니다"라고 말하려면 금액이
    필요하다.
  → 버린 대안: 만료 시 `quote`를 빼기. 결제 가능한 금액처럼 보일 위험은 줄지만
    `Hold` 스키마의 required가 조건부가 되어 네 구현이 전부 null 분기를 진다.
    결제 가능 여부는 `quote`의 유무가 아니라 `status`가 정한다. **필드 유무로 상태를
    암시하는 설계는 계약을 읽기 어렵게 만든다.**
  ※ 처음 적은 "가격 변동 여부를 알려준다"는 성립하지 않는다. 이 응답에 현재 가격이
     없어 비교할 대상이 없다.

### `POST /holds/{holdId}/release` — 확보 해제

- [x] `DELETE`가 맞는가, `POST /holds/{id}/release`가 맞는가.
  → **POST를 골랐다.** 00 §7.2·06 §5가 `RELEASED`를 상태 전이로 정의하고, 해제 뒤에도
    `GET /holds/{holdId}`가 200을 준다. `DELETE`는 "지웠다"고 말하는데 지우지 않으므로
    계약이 거짓말을 한다. 생성기가 만드는 이름도 `deleteHold()`가 되어 오해를 옮긴다.
  → 버린 대안: `DELETE`. REST 관례이고 경로가 짧다. 그럼에도 버린 이유는 이 계약을
    네 구현이 각자 읽기 때문이다. 동사가 상태 모델과 어긋나면 구현마다 다르게 읽는다(06 §9.1).
  ※ 처음 적은 "POST가 맞다고 생각함"에 이유가 없었다. 이 항목은 이유가 답이다.

- [x] **이미 해제된 hold를 다시 해제하면?**
  → **200. 성공이다.** 요청의 목적은 "이 확보를 해제 상태로 만들어라"인데 이미 그
    상태이므로 목적이 이미 이뤄져 있다. 06 §8.2의 멱등 규칙을 상태 전이에 적용한 결과다.
    오류를 주면 클라이언트가 재시도 실패로 오해한다.

- [x] **이미 `CONSUMED`된 hold를 해제 요청하면?** 위 항목과 답이 같은가 다른가
  → **다르다. 409 `INVALID_STATE_TRANSITION`이다.**
  → 두 경우의 차이는 **출발 상태**다. 앞은 이미 목적지에 있고, 뒤는 다른 곳에 있으면서
    그리로 가는 길이 없다. 06 §5 전이 표에 `CONSUMED → RELEASED`가 없다.
  → 결제까지 끝난 확보의 좌석을 되돌리면 예약이 좌석 없이 남는다. 그 좌석을 다른 고객이
    가져가면 06 §10의 "확정 인원 > 회차 정원 불가"가 결제 완료 시점에 깨진다.
  → `EXPIRED`도 같다. 이미 좌석이 반환됐고 `EXPIRED → RELEASED` 전이도 없다.
  ※ 처음 적은 "답이 같다"를 뒤집었다. 체크리스트가 "같은가 다른가"라고 물은 것 자체가
     신호였다. 같다면 따로 물을 이유가 없다.

- [x] **응답 본문이 있는가, 204인가.**
  → **200 + `Hold` 전체.** 클라이언트가 `status`와 `releasedAt`을 곧바로 확인해야
    화면을 그린다. 204를 주면 GET을 한 번 더 불러야 하므로 왕복 하나를 아끼는 쪽을 골랐다.
  → 버린 대안: 204. 서버가 할 말이 없다는 뜻이라 간결하지만, 여기서는 상태가 바뀌었고
    그 상태가 클라이언트에 필요하다.

### `POST /bookings` — 결제 제출

- [x] 결제 성공과 예약 확정을 **한 응답으로** 줄 것인가, 나눌 것인가?
  → **한 응답에 담되, 결제 결과를 예약 상태로 표현한다.** 응답은 언제나 201 +
    `Booking`이고 `bookingStatus`가 `CONFIRMED`·`PAYMENT_FAILED`·`PAYMENT_PENDING`
    중 하나다.
  → **결제 실패를 4xx로 주지 않는다.** 00 §7.3이 `PAYMENT_PENDING → PAYMENT_FAILED`를
    예약 상태 전이로 정의했다. 결제가 거절돼도 예약 리소스는 만들어진다. 4xx로 잘라내면
    예약이 생기지 않아 B2C-RSV-04의 "실패 사유 범주와 재시도 가능 여부를 표시한다"를
    담을 곳이 없어진다. 사유는 `paymentFailureReason`에 담는다.
  → 05 §5.4의 "클라이언트 성공 화면만으로 예약을 확정하지 않는다"는 이 구조로 지켜진다.
    화면은 서버가 준 `bookingStatus`만 믿는다.
  ※ 처음 적은 "확보 중이라는 내용"이 hold·결제·예약 중 무엇인지 불분명했다.
     셋은 각각 다른 상태 기계다(00 §7.2·7.3).

- [x] `B2C-AC-06`의 "결과 불명" 상태를 어떻게 표현하나. 202? 200에 상태 필드?
  → **201 + `bookingStatus: PAYMENT_PENDING`.** 클라이언트는 재결제하지 않고
    `GET /bookings/{bookingId}`로 확인한다.
  → 버린 대안: 202. "받았고 아직 처리 중"을 HTTP 층에 드러내지만, 이 응답은
    "아직 안 만들었다"가 아니라 "만들었고 결제 결과가 아직이다"이다. 리소스는 이미 있고
    조회 경로도 있다. 상태를 본문 필드에 두면 세 결과를 클라이언트가 한 자리에서 분기한다.
    코드와 필드 두 곳에 나눠 두면 네 구현이 각자 다른 곳을 본다.

- [x] hold가 만료된 상태로 결제를 시도하면 어떤 코드인가?
  → **409 + `HOLD_EXPIRED`, `retryable: false`**(`errors.md` 확정 코드).
  → false인 이유는 같은 요청을 다시 보내도 영원히 같은 결과이기 때문이다. 새 확보를
    만들어야 하므로 흐름을 바꿔야 한다. B2C-AC-07의 "회차 재선택 안내"가 여기서 일어난다.
  → 이건 예약을 만들지 않는다. 확보가 없으면 좌석을 소진할 근거가 없으므로
    위의 "실패도 예약이다"와 다른 경우다.

### `GET /bookings/{bookingId}` — 예약 상세

- [x] 예약·결제·환불·출석 **네 상태를 각각 별도 필드로** 낸다(CORE-AC-09).
      하나로 합치고 싶은 유혹이 왜 위험한가?
  → 합치면 이름을 붙일 수 없는 조합이 실제로 생긴다.
    · 예약 `CANCELLED` + 환불 `FAILED` — 06 §10이 명시적으로 허용한다
    · 예약 `CANCELLED` + 출석 `COMPLETE` — 06 §10이 충돌 대기열로 보낸다
    · 예약 `CONFIRMED` + 출석 `PARTIAL` — 일부 인원만 입장했다
  → 배지 하나로 만들면 네 프론트가 각자 다른 우선순위로 하나를 골라 보여준다.
    06 §5.1이 "예약이 CANCELLED인데 환불이 FAILED일 수 있다"고 못박은 이유다.
  → 환불이 없을 때 필드를 빼거나 null로 두는 대신 `NONE` 값을 준다. 필드 유무로 상태를
    암시하면 null 분기를 빠뜨린 구현에서 화면이 깨진다.

- [x] 예약 스냅숏과 현재 상품 정보 중 무엇을 반환하나 (CORE-AC-25)
  → **스냅숏.** 00 §6.2가 "가격, 상품 핵심 정보, 회차, 취소 정책은 예약 시점 스냅숏으로
    저장한다"고 정했고, 06 §4.2가 스냅숏 원칙을 데이터 계층에서 강제한다.
  → 상품명·가격·정책이 나중에 바뀌어도 지난 예약의 표시와 환불 계산은 흔들리면 안 된다.
    현재 상품을 보려면 스냅숏 안의 `experienceId`로 따로 조회한다.
    **한 응답에 두 시점을 섞지 않는다.**

### `GET /bookings/{bookingId}/cancel-quote` — 취소 예상액

- [x] 계산 **기준 시각**을 응답에 넣는가. 왜 필요한가? (01 §5.5)
  → **넣는다(`calculatedAt`).** 환불액을 바꾸는 것은 상품 가격이 아니라 **경과 시간**이다.
    00 §6.4의 정책 표는 체험 시작까지 남은 시간으로 환불률을 나눈다 — STANDARD면
    72시간 전 100%, 24시간 전 50%, 그 뒤 0%. 같은 예약도 언제 묻느냐에 따라 답이 달라지므로
    금액만 주면 그 값이 언제 것인지 알 수 없다.
  → 판정은 클라이언트 시각이 아니라 **서버 시각**으로, 정책은 현재 상품 정책이 아니라
    **예약에 저장된 스냅숏**으로 한다(06 §6.2). B2C-CAN-01이 "계산 기준 시각"을 화면에
    표시하라고 요구한다.
  ※ 처음 적은 "가격 변동" 근거는 어긋난다. 상품 가격이 바뀌어도 이 예약은 스냅숏을 쓴다.

- [x] 이 응답을 받고 실제 취소하기까지 시간이 지나 정책 구간이 바뀌면?
  → **두 겹으로 막는다.**
    ① 응답에 `boundaryAt`(이 금액이 유지되는 마지막 시각)을 넣어 클라이언트가 남은 시간을
       보여주고 만료 시 다시 조회하게 한다.
    ② 취소 실행 요청에 `expectedRefundAmount`를 **필수로** 실어 보내게 하고, 서버가
       다시 계산해 다르면 409 `REFUND_QUOTE_STALE`로 막고 새 금액을 `details.currentQuote`에
       담아 준다.
  → 두 겹인 이유는 06 §9.3이다. ①만 두면 클라이언트 판정을 믿는 것이 된다.
  → 근거는 B2C-CAN-01의 "사용자가 명시적으로 동의한 뒤 취소 요청을 생성한다"이다.
    동의한 금액과 실제가 달라지면 동의를 다시 받아야 한다.
  → 이 문제의 꼴은 `POST /holds`가 "왜 견적과 확보가 한 요청인가"에서 다룬 것과 같다.
    조회와 실행 사이의 시간 간극을 누가 책임지는가.
  → 버린 대안: 실행 시 조용히 재계산해 실제 금액으로 진행. 고객이 본 금액과 다른 돈이
    들어오므로 동의가 무의미해진다.

### `POST /bookings/{bookingId}/cancellation` — 취소 실행

- [x] 취소와 환불은 다른 상태다(00 §7.3·7.4). 응답에 둘을 어떻게 담나?
  → **`bookingStatus`와 `refundStatus`를 나란한 별도 필드로 담는다.**
    취소는 서버가 즉시 확정하지만 환불은 외부 처리라 응답 시점에 끝나 있지 않다.
    정상적인 최초 응답은 `bookingStatus: CANCEL_PENDING`(또는 `CANCELLED`) +
    `refundStatus: REQUESTED`다.
  → 이 자리에 `SUCCEEDED`가 바로 온다고 전제하고 화면을 짜면 안 된다.
    06 §5.1이 "예약이 CANCELLED인데 환불이 FAILED일 수 있다"고 했고, 06 §10이 그 조합을
    허용으로 분류했다.
  ※ 처음 적은 답은 상태 **이름**을 찾은 것이었다. 질문은 그 둘을 응답에 **어떻게 담을지**였다.

- [x] 재전송이 중복 취소를 만들지 않으려면 (CORE-AC-08)
  → **멱등 키다.** 같은 `Idempotency-Key` + 같은 본문이면 저장된 응답을 그대로 돌려주고
    새 환불을 만들지 않는다(06 §8.2).
  → **다른 키로 이미 취소된 예약에 다시 요청하는 것은 재전송이 아니라 새 요청**이므로
    409 `INVALID_STATE_TRANSITION`이다. 06 §5에 `CANCELLED → CANCEL_PENDING` 전이가 없다.
    이 둘을 구분하지 않으면 환불이 두 번 나간다.
  → 같은 키에 다른 본문이면 422 `IDEMPOTENCY_KEY_REUSED`다(CORE-AC-05).
  ※ 처음 적은 "동일 사용자의 같은 회차에 활성 임시 확보가 있으면..."은 01 §5.4 B2C-RSV-01의
     **hold 중복 생성** 규칙이다. 취소와 무관한 다른 문제의 답이다.

### `POST /check-ins` — 체크인

- [x] 멱등 키가 `Idempotency-Key` 헤더가 아니라 `clientEventId`인 이유는?
  → **두 키가 붙는 대상이 다르다.** 헤더 키는 *요청*에, `clientEventId`는 *사건*에 붙는다.
  → 헤더 키는 요청을 보내려는 순간 만들어지고 요청이 끝나면 역할이 끝난다.
    `clientEventId`는 현장에서 체크인이 벌어진 순간 만들어져 기기에 저장됐다가 몇 분에서
    몇 시간 뒤 전송된다(02 §7 ADM-DSK-03).
  → 차이가 드러나는 자리 — 오프라인에서 체크인을 하나 찍었는데 전송이 두 번 시도됐고
    그 사이 앱이 재시작됐다고 하자. 헤더 키는 새로 만들어지므로 서버가 두 요청을 다른
    요청으로 보고 출석을 두 번 기록한다. `clientEventId`는 사건에 붙어 있으므로 앱이 몇 번
    재시작하든 같다.
  → CORE-AC-15의 "반복 전송해도 출석이 중복되지 않는다"는 사건 단위 키로만 성립한다.

- [x] `06 §11.2`의 **일곱** 분기 중 무엇이 오류이고 무엇이 정상 결과인가
  → 먼저 개수를 바로잡았다. 이전 판본이 "여섯"이라고 쓰면서 **2시간 초과 스냅숏** 행을
    빠뜨렸다. 06 §11.2 표는 7행이다.
  → **넷은 오류가 아니다.** 오프라인 이벤트는 이미 벌어진 사실이므로 4xx로 잘라내면
    06 §11.3의 "원본 이벤트를 삭제하지 않는다"가 깨진다. 자동 반영할 수 없는 것은
    거부 대신 대기열로 접수한다.

    | 상황 | 판정 | HTTP | outcome / code |
    |---|---|:---:|---|
    | 같은 `clientEventId` 재전송 | 정상 | 200 | `REPLAYED` |
    | 다른 기기가 같은 인원 이미 처리 | 정상 | 200 | `RECONCILED` |
    | 누적 인원 초과 | 오류 | 409 | `CHECKIN_EXCEEDS_PARTY` |
    | 취소된 예약의 늦은 이벤트 | 정상(보류) | 202 | `QUEUED_CONFLICT` |
    | 다른 회차의 토큰 | 오류 | 409 | `CHECKIN_SLOT_MISMATCH` |
    | 권한 회수된 행위자 | 정상(보류) | 202 | `QUEUED_QUARANTINE` |
    | 2시간 초과 스냅숏 | 오류 | 409 | `SNAPSHOT_STALE` |

  → 재전송·교정을 409로 주면 담당자 화면에 붉은 실패가 뜨는데 출석은 정상 기록된
    상태가 된다. 06 §11.2 첫 행이 "저장된 결과 반환"이라고 정했다.
  → 권한 회수 건을 403으로 거부하면 그 이벤트가 어디에도 남지 않는다. 06 §11.2가
    격리 대기열로 보내라고 했으므로 접수는 하되 자동 반영을 막는다. 행위자의 권한 상실은
    **판정 대상**이지 요청 형식의 문제가 아니다.

- [x] 오프라인에서 만든 이벤트의 `clientRecordedAt`을 서버가 신뢰하는가?
  → **저장하되 판정에 쓰지 않는다.** 기기 시계는 틀릴 수 있고 조작될 수도 있다.
    00 §7.2가 hold 만료에서 클라이언트 시각을 거부한 것과 같은 논리다.
  → 다만 오프라인 이벤트는 정의상 서버가 그 순간을 보지 못했으므로 값 자체는 감사
    기록으로 남긴다. 06 §11.3의 원본 보존과 같은 방향이다.
  → **판정에 쓰는 시각은 둘이다** — 서버 수신 시각, 그리고 스냅숏의
    `snapshotSyncedAt`. 후자로 2시간 규칙을 판정한다(06 §11.1, CORE-AC-16).
  → 버린 대안: 기기 시각을 그대로 신뢰. 시계를 되돌리면 2시간 규칙을 우회할 수 있다.

### `PATCH /slots/{slotId}` — 회차 수정

- [x] 정원 축소 한계를 어떻게 계산하나 — 확정 예약만인가, 활성 hold도 포함인가? (06 §8.3)
  → **확정 예약 인원 + 활성 임시 확보 인원.** 06 §8.3에 문장 그대로 있다.
  → 활성 확보를 빼면 결제 직전인 고객의 좌석이 사라진다. 그 고객은 10분 안에 결제할
    권리를 이미 받았으므로(00 §6.2), 확보를 무시하고 줄이면 06 §10의
    "확정 인원 > 회차 정원 불가"가 결제 완료 시점에 깨진다.
  → 판정은 축소 요청 시점의 값을 잠그고 한다. 세는 동안 새 확보가 생기면 06 §8.1과
    같은 경쟁 조건이 된다.
  → **문서 불일치는 해소했다**(2026-08-31). 02 §6 ADM-PTN-03과 ADM-AC-05가 하한을
    "확정 예약 수"로만 쓰고 있었다. 06 §8.3에 맞춰 02를 v2.2로, 05 §5.2를 함께 정정했다.
    06을 기준으로 삼은 이유는 이 규칙이 서버 판정이고, 06이 그 판정을 정의하는 문서이기
    때문이다. 02는 화면 요구를 적는 문서라 서버 규칙을 요약해 옮기다 한쪽을 빠뜨렸다.

- [x] 날짜·장소 변경은 이 엔드포인트로 처리하나, 별도 흐름인가? (02 §6)
  → **별도 흐름으로 뺐다.** `POST /slots/{slotId}/reschedule`(아직 미작성).
  → 02 §6 ADM-PTN-03이 "이미 예약된 회차의 시간·장소 변경은 **영향받는 예약 수와 알림
    필요성을 확인한다**"를 요구한다. 확인과 동의가 끼는 절차인데, 필드 하나를 바꾸는
    `PATCH`와 같은 요청으로 묶으면 그 절차가 계약에 드러나지 않는다. 네 구현이 각자
    확인 화면을 붙이거나 빠뜨린다.
  → 영향 범위를 먼저 돌려주고 사용자가 동의한 뒤 실행하는 2단계로 둔다.
  → 버린 대안: `PATCH` 하나로 처리. 경로가 줄지만 "정원 1명 축소"와 "날짜를 옮겨 예약
    40건에 알림 발송"이 같은 요청 형태가 된다. 위험도가 다른 조작을 같은 문으로 보내면
    권한과 감사 로그도 같이 뭉개진다.
  ※ 처음 적은 "이 엔드포인트에서 처리된다"를 뒤집었다. PRD가 답을 정하지 않은 판단형이라
     반대 결론도 성립하지만, 그렇다면 확인 절차를 어떻게 담을지 함께 적어야 한다.

### `POST /slots/{slotId}/reschedule-preview` · `.../reschedule` — 일정·장소 변경

7번 `PATCH /slots/{slotId}`에서 갈라져 나온 흐름이다. 판단 셋을 더 정했다.

- [x] **조회인데 왜 POST인가.**
  → `GET .../reschedule-impact?startAt=...&venueId=...`도 가능하고 REST로는 그쪽이 곧다.
    그럼에도 POST를 고른 이유는 **이 요청이 `impactToken`을 발급하기 때문**이다.
    서버가 영향 범위 스냅숏과 토큰을 저장하므로 순수한 읽기가 아니다.
  → 버린 대안: GET. 부작용이 있는 것을 GET에 두면 캐시·프리페치·재시도가 조용히
    토큰을 찍어낸다.

- [x] **왜 2단계로 나눴나. 왜 토큰을 쓰나.**
  → 02 §6 ADM-PTN-03이 "영향받는 예약 수와 알림 필요성을 확인한다"를 요구한다.
    확인이 끼는 절차를 한 요청으로 묶으면 그 절차가 계약에 드러나지 않는다.
  → 토큰이 필요한 이유는 운영자가 화면을 보는 동안 예약이 더 들어올 수 있어서다.
    "예약 3건에 영향"을 보고 승인했는데 실행 시점에 11건이면 승인의 근거가 사라진다.
    다르면 409 `RESCHEDULE_IMPACT_STALE`로 막고 새 계산을 준다.
  → `cancel-quote` → `cancellation`이 `expectedRefundAmount`를 대조하는 것과 같은 꼴이다.
    **보여주고 동의받은 값이 실행 시점에도 같은지 서버가 판정한다.**

- [x] **`notifyCustomers`에 기본값을 둘 것인가.**
  → **두지 않는다. 필수 필드다.** 기본값이 있으면 "확인한다"가 확인이 아니라 통과가 된다.
    운영자가 매번 고르고, 고른 값은 06 §4의 `AuditLog`에 사유와 함께 남는다.
  → 영향받는 예약이 있는데 `false`를 골라도 막지 않는다. 알리지 않기로 한 판단도
    판단이고, PRD는 확인만 요구했다. 서버가 정책을 대신 정하지 않는다.
  → 알림 자체는 백그라운드다(02 §5 ADM-COM-04). 응답의 `notificationJobId`는
    "보내기 시작했다"이지 "도착했다"가 아니다.

## 명세 전체에 대한 판단

- [x] **OpenAPI 3.1을 쓸 것인가 3.0으로 낮출 것인가.**
  → **3.1을 쓰되, `$ref` 옆에 다른 키를 두는 문법은 피한다.**
    설명을 붙여야 하는 자리는 `allOf: [{ $ref: ... }]`로 감싼다. 3.0에서는 `$ref`의
    형제 키가 무시됐고 그 우회가 관행이 됐는데, 3.1은 제약이 없어졌지만 생성기 지원이
    아직 갈린다. 착수 시 npm·Maven 생성기로 실제 생성해 확인한다.

- [x] 목록 페이지네이션을 커서로 할 것인가 오프셋으로 할 것인가.
  → **커서.** 06 §7이 "하나로 통일"만 요구하고 선택은 열어 뒀다.
    Admin 대기열(`/ops/inquiries`·`/ops/refunds`)은 처리하는 동안 행이 계속 사라지므로,
    오프셋을 쓰면 페이지를 넘길 때 항목이 건너뛰어진다.
  → 아직 목록 엔드포인트를 쓰지 않았으므로 첫 목록에서 이 결정을 실제로 적용한다.

- [x] 시간 필드는 전부 UTC ISO 8601인가 (06 §7)
  → **그렇다.** 모든 시각 필드에 `format: date-time`을 붙였다.
    화면 변환은 클라이언트 책임이다(06 §7). 지역 시간대는 00 §6.1이 정한다.

- [x] B2C와 Admin 경로를 한 파일에 둘 것인가 나눌 것인가
  → **한 파일에 둔다.** `Money`·`Error`·`Quote`처럼 양쪽이 공유하는 스키마가 많고,
    나누면 같은 정의가 두 벌이 되어 어긋난다. 06 §9.3의 이중 정의 방지와 같은 이유다.
  → 대신 **인증을 operation 단위로 갈랐다.** 파일 전역 기본값은 `customerAuth`이고,
    `POST /check-ins`와 `PATCH /slots/{id}`는 `security: [{ adminAuth: [] }]`로
    덮어썼다. 06 §7이 "B2C와 Admin의 토큰 대상을 분리"하라고 요구한다.
  → 파일이 커지면 `tags`로 나누거나 나중에 분할한다. 지금 나누면 얻는 것보다 잃는 것이 크다.

- [x] 생성된 타입을 npm과 Maven 양쪽에 어떻게 배포할 것인가 (ADR-0005)
  → ADR-0011이 패키지명을 `@daylink/api-spec`·`com.daylink:api-spec`으로 확정했다.
    생성물은 커밋하지 않고 빌드 시점에 만든다(`api-spec/README.md`).
    실제 배포 구성은 M1 후반 과제로 남는다.

## 다 채운 뒤 확인

- [x] `06 §13`의 CORE-AC 29개 중 명세로 표현되는 것이 전부 반영됐는가
  → 계약으로 표현되는 것은 반영했다.
    01·03·04·05·06·07·08·09·10·13·15·16·17·18·19·25·26·27이 이 파일에 드러난다.
  → 계약이 아니라 **구현과 테스트로만 증명되는 것**은 여기 담기지 않는다 —
    02(안전장치 제거 시 실패), 20·21(불변 원장), 22(비동기 작업), 23(감사 로그),
    24(권한 철회), 28(접근성), 29(권한 재검사). 이건 누락이 아니라 계약의 범위 밖이다.

- [x] 프론트가 자체 계산해야만 하는 값이 남아 있지 않은가 (06 §9.3)
  → 남기지 않았다. 확인한 자리는 넷이다.
    · 잔여 좌석 → `Slot.remainingSeats`를 서버가 계산해 준다
    · 환불액·환불률·차감액 → `CancelQuote`가 전부 담는다
    · 누적 체크인 인원 → `CheckInResult.officialCheckedIn`이 서버 판정값이다
    · 만료 여부 → `Hold.status`와 `expiresAt`을 서버가 준다
  → `CreateBookingRequest`가 `holdId`만 받는 것도 같은 이유다. 금액을 클라이언트가
    실어 보내면 그 값을 신뢰할지 정해야 하는데, 신뢰하지 않을 것이면 받을 이유가 없다.

- [x] 같은 개념에 다른 이름을 쓴 곳이 없는가
  → `partySize`를 예약 인원에 일관되게 썼다. 체크인의 증분 인원만 `headcount`로 구분했다.
    누적이 아니라 이번 요청의 인원이라는 뜻이므로 다른 개념이고, 이름을 달리하는 편이 맞다.
  → **한 번 걸렸고 고쳤다.** 회차 엔터티가 원래 `Session`이었는데, 06 §8.6이 같은 절
    안에서 "이미 발급된 **세션**"으로 인증 세션을 가리켰다. Java에서 `Session`과
    `HttpSession`이 한 파일에 들어오면 구분이 어렵다. ADR-0014로 `Slot`으로 개명했다.
  → **`Slot`에도 겹치는 자리가 하나 남아 있다.** Vue의 `<slot>`이다. 04 §Vue가 다루는
    컴포넌트 슬롯과 도메인 타입 `Slot`이 같은 `.vue` 파일에 들어온다. 사용자 판단으로
    이름은 유지하고, 00 §5.1에 구분 규약을 적었다 — `.vue` 안에서 도메인 값을 담는
    변수·prop 이름으로 `slot`을 쓰지 않고 `timeSlot` 같은 이름을 쓴다.
